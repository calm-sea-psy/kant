1. backward
loss.backward()를 호출하면 autograd 엔진이 계산 그래프(computation graph)를 출력(loss)에서부터 역방향으로 순회하면서 각 텐서에 대한 그래디언트(미분값)를 계산 — 이게 바로 역전파(backpropagation)다.

동작 흐름:
    - 순전파(forward): 연산을 수행하면서 PyTorch가 자동으로 계산 그래프를 기록함 (requires_grad=True인 텐서 기준)
    - backward(): 체인 룰(chain rule)을 이용해 그래프를 거꾸로 타고 가며 각 leaf 텐서(예: 가중치, 편향)에 대한 그래디언트를 계산
    - 계산된 그래디언트는 각 텐서의 .grad 속성에 누적됨 (그래서 보통 다음 스텝 전에 optimizer.zero_grad()로 초기화)

즉 backward() 자체가 "역전파 알고리즘"을 실행하는 함수이고, 그 결과로 얻은 .grad 값을 optimizer.step()이 이용해 파라미터를 업데이트하는 구조다.

2. 계산 그래프(computation graph)
텐서 연산들의 흐름을 노드와 엣지로 표현한 방향성 그래프(DAG, Directed Acyclic Graph)다. backward()가 미분을 계산할 때 이 그래프를 거꾸로 타고 올라간다.

ㄱ) 구조
    - 노드(node): 텐서 또는 연산(함수)
    - 엣지(edge): 데이터가 흐르는 방향 (입력 → 연산 → 출력)
    - leaf 텐서: 사용자가 직접 만든 텐서 (예: 가중치 w, 편향 b). requires_grad=True면 그래디언트가 쌓이는 대상
    - grad_fn: 중간 결과 텐서가 "내가 어떤 연산으로 만들어졌는지" 기억하는 포인터

ㄴ) 예시

    x = torch.tensor(2.0, requires_grad=True)
    w = torch.tensor(3.0, requires_grad=True)
    b = torch.tensor(1.0, requires_grad=True)

    y = w * x + b   # y = 7.0

이 순간 PyTorch는 내부적으로 그래프를 만든다.

    x ─┐
       ├─(mul)─► w*x ─┐
    w ─┘              ├─(add)─► y
                  b ───┘

y.grad_fn을 출력해보면 <AddBackward0> 같은 게 찍히는데, 이게 "y는 덧셈으로 만들어졌다"는 기록이다. 그 안에 다시 곱셈(MulBackward0)에 대한 참조가 연결되어 있다.

ㄷ) 동적 그래프 (Define-by-Run)
PyTorch의 특징은 순전파를 실행하는 시점에 그래프가 즉석에서 만들어진다는 것이다 (TensorFlow 1.x의 정적 그래프와 대비)
    - 매 반복(iteration)마다 그래프가 새로 생성됨
    - 조건문/반복문 등 파이썬 제어 흐름을 그대로 써도 그래프에 반영됨 (유연함)

y.backward()를 호출하면 y부터 시작해 grad_fn을 따라 거꾸로 이동하며 체인 룰로 미분을 계산하고, leaf 텐서(x.grad, w.grad, b.grad)에 결과를 누적한다.

backward()를 호출하고 나면 메모리 절약을 위해 그래프가 해제된다. 같은 그래프로 다시 backward()를 호출하려면 retain_graph=True를 줘야 한다.

또는 .detach()를 쓰면 해당 연산은 그래프에 기록되지 않는다 — 추론(inference)이나 그래디언트가 필요 없는 구간에서 메모리/속도를 아끼기 위해 사용한다.

3. Chain Rule
체인 룰(연쇄 법칙)은 합성함수의 미분을 구하는 규칙으로, 역전파가 그래디언트를 계산하는 핵심 수학적 도구다.
함수가 중첩되어 있을 때 즉, "바깥 함수의 미분 × 안쪽 함수의 미분"을 곱해서 전체 미분을 구한다.

y를 x에 대해 미분하고 싶다면, 직접 미분하기보다 체인 룰로 중간 변수를 거쳐 간다. 계산 그래프에서 보면:

    x ──(mul)──► u ──(add)──► y
    w ──┘              b ──┘

backward()는 이 그래프를 출력에서 입력 방향으로 거슬러 올라가며, 각 노드를 지날 때마다 "그 노드의 로컬 미분"을 이전 단계에서 넘어온 그래디언트에 곱해서 전달한다. 이게 바로 체인 룰을 반복 적용하는 것이다.

ㄱ) 딥러닝에서 Chain Rule을 사용하는 이유
신경망은 층(layer)이 여러 개 쌓인 합성함수 그 자체다.
가중치 w_1(첫 번째 층)에 대한 그래디언트를 구하려면, loss부터 시작해 f_3, f_2, f_1 을 차례로 거슬러 올라가며 각 층의 로컬 미분을 곱해야 한다.
이걸 한 번에 직접 계산하려면 매우 복잡하지만, 체인 룰 덕분에 각 층에서 "국소적인 미분 하나씩만" 계산하고 곱해나가면 된다. backward()가 그래프의 각 grad_fn 노드마다 이 로컬 미분(vector-Jacobian product)을 계산해서 뒤로 전달하는 방식으로 전체 과정을 자동화한 것이 바로 역전파(backpropagation)다.

ㄴ) 여러 경로가 있을 때 (분기 → 합류)
한 변수가 여러 경로를 거쳐 출력에 영향을 준다면, 그래디언트는 각 경로의 기여를 모두 더한다 (다변수 체인 룰).

    x = torch.tensor(2.0, requires_grad=True)
    a = x * 2
    b = x * 3
    y = a + b        # y = 2x + 3x = 5x

    y.backward()
    print(x.grad)    # 5.0  (2 + 3, 두 경로의 기여가 합산됨)

이 "분기 시 그래디언트 합산" 규칙이 실제 신경망에서 파라미터 하나가 여러 출력 경로(예: skip connection, 여러 뉴런)에 관여할 때 정확한 그래디언트를 보장해 준다.

ㄷ) 실전 감각
    - 그래디언트 = 민감도: w.grad가 크면 그 파라미터를 조금만 바꿔도 loss가 크게 움직인다는 뜻 → 학습이 잘 안 될 때(loss가 안 줄거나 NaN 나올 때) .grad 값을 찍어보면 원인 파악에 도움됨
    - 그래프가 끊기면 grad가 None: requires_grad=False거나 .detach()한 텐서, 혹은 with torch.no_grad() 안에서 만든 텐서는 grad가 안 쌓임 → "왜 w.grad가 None이지?" 디버깅할 때 이 사실만 알아도 반은 해결
    - grad는 누적된다: 그래서 매 스텝마다 optimizer.zero_grad() 안 하면 이전 값이 계속 더해져서 이상해짐 → 이거 까먹어서 나는 버그가 실제로 흔함

4. requires_grad
텐서에 대한 그래디언트를 계산해서 추적할지 말지를 정하는 스위치다.

ㄱ) 기본 동작

    w = torch.tensor(3.0, requires_grad=True)   # 그래디언트 추적 O
    x = torch.tensor(2.0)                        # requires_grad=False (기본값)
    b = torch.tensor(1.0)                        # requires_grad=False (기본값)

requires_grad=True인 텐서가 연산에 관여하면, PyTorch는 그 텐서를 계산 그래프에 등록하고 역전파 시 grad를 계산해서 .grad에 저장한다. False면 그 텐서는 그래프에서 "그냥 상수"처럼 취급되어 grad가 계산되지 않는다.

x와 b는 requires_grad=False라서 x.grad, b.grad는 계속 None

ㄴ) 필요성

    z = x * w + b   # x는 False, w는 True → z는 자동으로 True가 됨
    print(z.requires_grad)  # True

requires_grad=True인 텐서가 연산에 하나라도 섞이면, 결과 텐서도 자동으로 requires_grad=True가 된다. "전염성"이 있다고 보면 된다.

ㄷ) 사용처

a. 학습 대상(파라미터)만 True로 둔다
    - 신경망의 가중치(nn.Parameter)는 기본적으로 requires_grad=True다. 입력 데이터(x)는 보통 학습 대상이 아니므로 False로 둔다 — 안 그러면 불필요한 그래프/메모리가 쌓임.

b. 추론(inference)할 때는 꺼서 메모리/속도 절약

    with torch.no_grad():
        pred = model(x)   # 그래프를 안 만드니까 빠르고 메모리도 적게 씀

학습이 끝난 모델로 예측만 할 때는 그래디언트가 필요 없으니 이렇게 꺼준다.

c. 특정 레이어만 얼리고(freeze) 싶을 때

    for param in model.backbone.parameters():
        param.requires_grad = False   # 이 부분은 학습 안 시킴 (fine-tuning 등에서 자주 씀)

| 상황 | requires_grad |
|---|---|
| 학습시킬 파라미터 (w, b) | True |
| 입력 데이터, 정답 라벨 | False |
| 추론만 할 때 전체 | False (torch.no_grad()로 일괄 처리) |
| 특정 층 freeze | False로 수동 변경 |

backward() 때 grad 계산해줘? 를 묻는 플래그이고, 학습 대상이 아니면 꺼두는 게 기본 원칙이다.

5. Leaf tensor 와 Non-leaf tensor

ㄱ) Leaf tensor (리프 텐서)
사용자가 직접 만든 텐서, 즉 계산 그래프에서 다른 연산으로부터 만들어지지 않고 "시작점"에 있는 텐서다.

    w = torch.tensor(3.0, requires_grad=True)   # leaf
    x = torch.tensor(2.0)                        # leaf (requires_grad=False여도 leaf)
    b = torch.tensor(1.0)                        # leaf

ㄴ) Non-leaf tensor (논리프 텐서)
연산의 결과로 만들어진 텐서, 즉 그래프 중간에 있는 텐서다.

    u = x * w        # non-leaf (mul 연산의 결과)
    z = u + b         # non-leaf (add 연산의 결과)
    loss = z ** 2      # non-leaf (pow 연산의 결과)

    x ──┐
        ├─(mul)─► u [non-leaf] ──┐
    w ──┘                        ├─(add)─► z [non-leaf] ──(pow2)──► loss [non-leaf]
                        b ──────┘

w, x, b만 leaf고, u, z, loss는 전부 non-leaf다.

ㄷ) Leaf tensor 와 Non-leaf tensor의 차이점 — .grad가 채워지는 대상이 다름
기본적으로 .grad는 leaf 텐서에만 저장된다.

    loss.backward()

    print(w.grad)   # tensor(28.) — leaf라서 채워짐
    print(u.grad)   # None (경고까지 뜸) — non-leaf라서 기본적으로 안 채워짐

이유는 메모리 절약이다. 학습에 실제로 필요한 건 w, b같은 파라미터의 grad뿐이고, 중간 계산값(u, z)의 grad는 대부분 쓸 일이 없기 때문에 PyTorch가 기본적으로 버린다.

non-leaf의 grad가 보고 싶다면:

    u = x * w
    u.retain_grad()   # "이 non-leaf도 grad 유지해줘" 라고 명시적으로 요청
    z = u + b
    loss = z ** 2
    loss.backward()

    print(u.grad)   # 이제 값이 나옴

디버깅할 때(중간 레이어의 grad를 확인하고 싶을 때) 종종 쓴다.

| 구분 | Leaf | Non-leaf |
|---|---|---|
| 생성 방식 | 사용자가 직접 생성 | 연산의 결과로 생성 |
| 예시 | w, x, b, nn.Parameter | u, z, loss, 레이어 중간 출력 |
| .grad 저장 | 기본적으로 저장됨 | 기본적으로 저장 안 됨 (retain_grad() 필요) |
| 실전 의미 | 학습 대상 파라미터가 보통 여기 속함 | 순전파 중 잠깐 쓰고 버려지는 중간값 |

grad를 실제로 업데이트에 쓸 대상(파라미터)은 leaf이고, 계산 도중 거쳐가는 값들은 non-leaf라서 기본적으로 grad를 안 남긴다고 이해하면 된다.

6. torch.no_grad(), detach(), clone(), detach().clone()
앞서 배운 계산 그래프 개념 위에서 보면, 이 네 가지는 모두 "그래프에서 벗어나거나 메모리를 분리하는" 방법인데 각각 분리하는 대상이 다르다.

핵심 축 두 가지:
    - 그래프 연결이 끊기는가? (grad가 흐르는가)
    - 메모리(데이터)가 공유되는가, 복사되는가?

이 두 축으로 나눠보면 헷갈리지 않는다.

| 구분 | 그래프 연결 | 메모리 |
|---|---|---|
| torch.no_grad() | 그 블록 안에서 아예 그래프를 안 만듦 | 해당 없음 (원본 조작) |
| .detach() | 끊김 (grad 안 흐름) | 공유 (같은 데이터) |
| .clone() | 유지됨 (grad 흐름) | 복사 (별도 데이터) |
| .detach().clone() | 끊김 | 복사 (완전 독립) |

ㄱ) torch.no_grad() — 컨텍스트 자체를 그래프 밖으로

    w = torch.tensor(3.0, requires_grad=True)

    with torch.no_grad():
        y = w * 2   # 이 연산은 그래프에 기록 안 됨
    print(y.requires_grad)   # False

이 블록 안에서 일어나는 모든 연산이 그래프를 아예 안 만든다. 주로 추론(inference)이나 파라미터를 직접 수정할 때 쓴다 (예: optimizer.step() 내부, 수동 업데이트).

    with torch.no_grad():
        w -= lr * w.grad   # 파라미터를 직접 수정할 때, 그래프 기록 없이

ㄴ) detach() — 그래프에서만 분리, 데이터는 공유

    z = x * w + b
    z_detached = z.detach()

    print(z_detached.requires_grad)   # False
    z_detached[0] = 999   # z도 같이 바뀜! (메모리 공유)

같은 메모리를 가리키지만 grad 흐름만 끊긴 새 텐서를 반환한다. z와 z_detached는 값이 연결되어 있어서, 한쪽을 in-place로 바꾸면 다른 쪽도 바뀐다 (주의 필요).

ㄷ) .clone() — 데이터는 복사, 그래프는 유지

    z_cloned = z.clone()

    print(z_cloned.requires_grad)   # True (그래프 유지됨, grad 흐름)
    z_cloned[0] = 999   # z는 안 바뀜 (별도 메모리)

메모리는 독립적이지만, 그래프에는 여전히 연결되어 있어서 z_cloned로 계산해도 grad가 원래 w까지 흘러간다. "값만 복사하고 싶은데 grad는 계속 필요할 때" 쓴다.

ㄹ) .detach().clone() — 완전 독립

    z_independent = z.detach().clone()

    print(z_independent.requires_grad)   # False
    z_independent[0] = 999   # z와 완전 무관, 그래프도 무관

그래프 연결도 끊고 메모리도 분리한, 완전히 독립적인 사본이다. "이 값을 그냥 순수한 데이터로 떼어내서 따로 쓰고 싶다"할 때 (예: 시각화용 numpy 변환 전, 로깅, 별도 계산용 스냅샷) 흔히 쓴다.

    # 흔한 패턴: 텐서를 numpy로 바꿔서 그래프 밖에서 다룰 때
    img = tensor.detach().cpu().numpy()

ㅁ) 선택 기준
    - 모델 추론만 할 때 → torch.no_grad() (블록 전체를 그래프 밖으로, 메모리/속도 이득)
    - grad는 필요없고, 지금 값만 다른 변수로 떼어 쓰고 싶을 때 (원본과 공유돼도 상관없음) → .detach()
    - grad는 계속 필요한데, 원본을 안 건드리는 별도 복사본이 필요할 때 → .clone()
    - grad도 필요없고, 원본과 완전히 분리된 안전한 복사본이 필요할 때 (numpy 변환, 로깅, 시각화 등) → .detach().clone()

7. gradient가 None일 때 확인할 것
loss.backward()를 했는데도 .grad가 None이라면 다음을 확인한다.

| 확인할 항목 | 설명 |
|---|---|
| 파라미터가 loss 계산에 사용되었나? | forward 경로에서 빠진 layer는 gradient를 받지 않는다. |
| requires_grad=True인가? | 학습 파라미터는 보통 True다. |
| 중간에 detach()를 사용했나? | graph가 끊기면 gradient가 전달되지 않는다. |
| torch.no_grad() 안에서 loss를 만들었나? | no_grad 안에서는 graph 추적이 꺼진다. |
| leaf tensor가 맞나? | non-leaf Tensor의 .grad는 기본 저장되지 않는다. |

8. optimizer.zero_grad(), loss.backward(), optimizer.step()
지금까지 배운 개념들(그래프, 체인 룰, grad 누적, leaf tensor)이 실제로 합쳐지는 지점이 바로 이 세 함수다. 보통 학습 루프에서 항상 세트로 등장한다.

    for epoch in range(num_epochs):
        optimizer.zero_grad()   # 1
        pred = model(x)
        loss = loss_fn(pred, y)
        loss.backward()         # 2
        optimizer.step()        # 3

ㄱ) optimizer.zero_grad() — grad 초기화
"이전 스텝에서 쌓인 grad를 0으로 리셋"한다.
앞서 봤듯이 backward()는 grad를 .grad에 누적(더하기)한다. 덮어쓰는 게 아니라 계속 더해지기 때문에, 매 스텝마다 초기화 안 하면 이전 배치의 grad까지 섞여서 잘못된 방향으로 학습된다.

    w.grad  # None → backward() 한 번: 28 → zero_grad() 없이 또 backward(): 56 (잘못 누적!)

loss가 이상하게 튀거나 학습이 발산하면 제일 먼저 의심해볼 부분이다.

ㄴ) loss.backward() — 그래디언트 계산
loss부터 그래프를 거꾸로 타고 올라가며 체인 룰로 각 파라미터(leaf tensor)의 grad를 계산해서 .grad에 더해 넣는다.
이 단계에서는 아직 파라미터 값이 안 바뀐다. "어느 방향으로 얼마나 움직여야 하는지"만 계산해서 저장해두는 단계다.

ㄷ) optimizer.step() — 실제 파라미터 업데이트
.grad에 저장된 값을 이용해서 실제로 파라미터를 갱신한다. 내부적으로는 대략 이런 일을 한다 (SGD 기준):

    with torch.no_grad():          # 파라미터 수정은 그래프 기록 없이
        for param in model.parameters():
            param -= lr * param.grad

Adam 같은 옵티마이저는 여기에 모멘텀, 적응적 학습률 등이 추가되지만, 핵심은 동일하게 "grad를 이용해서 파라미터를 조금 움직인다"이다.

    zero_grad() → 이전 grad 청소
        ↓
    forward + loss 계산 → 그래프 생성
        ↓
    backward() → 그래프 타고 grad 계산 (파라미터 값은 아직 그대로)
        ↓
    step() → 계산된 grad로 파라미터 실제 업데이트

step()을 backward()보다 먼저 부르면 grad가 비어있어서 의미가 없고, zero_grad()를 안 하면 이전 스텝 grad가 계속 섞인다.

| 함수 | 역할 |
|---|---|
| zero_grad() | grad 초기화 ("이전 흔적 지우기") |
| backward() | grad 계산 (체인 룰) ("어디로 움직여야 할지 계산") |
| step() | 파라미터 업데이트 ("실제로 움직이기") |

9. loss.item()
loss.item()은 1개의 값만 담긴 텐서를 순수 파이썬 숫자(float)로 꺼내는 메서드다.

ㄱ) 사용법

    loss = loss_fn(pred, y)
    print(loss)          # tensor(0.4521, grad_fn=<MseLossBackward0>)
    print(loss.item())   # 0.4521 (그냥 float)

loss는 텐서라서 계산 그래프(grad_fn)를 계속 물고 있는 상태다. 로그를 찍거나, 리스트에 저장하거나, 숫자 비교(if loss < best_loss)를 할 때 텐서 그대로 쓰면 문제가 생길 수 있어서 .item()으로 순수 값만 뽑아낸다.

ㄴ) 메모리 누수 방지
이게 사실 .item()을 쓰는 핵심 이유다. 텐서 상태로 계속 들고 있으면 그 텐서가 참조하는 계산 그래프 전체가 메모리에서 안 풀린다.

    # 나쁜 예 — 흔한 메모리 누수 패턴
    loss_history = []
    for epoch in range(1000):
        loss = loss_fn(pred, y)
        loss.backward()
        loss_history.append(loss)          # 그래프 통째로 계속 쌓임 → 메모리 폭발

    # 좋은 예
    loss_history = []
    for epoch in range(1000):
        loss = loss_fn(pred, y)
        loss.backward()
        loss_history.append(loss.item())   # 순수 숫자만 저장, 그래프는 버려짐

.item()으로 뽑아내는 순간 그래프와의 연결이 끊긴 "그냥 숫자"가 되므로, 다음 반복에서 그래프가 정상적으로 메모리 해제된다.

ㄷ) 제약 조건 — 원소가 딱 1개여야 함

    t = torch.tensor([1.0, 2.0])
    t.item()   # ValueError: only one element tensors can be converted to Python scalars

loss처럼 스칼라(scalar, 원소 1개) 텐서에만 쓸 수 있다. 여러 값이 있는 텐서를 파이썬 값으로 바꾸고 싶으면 .tolist()나 .numpy()를 쓴다.

| 상황 | 방법 |
|---|---|
| loss 값 하나를 출력/로깅/비교하고 싶을 때 | .item() |
| 그래디언트가 필요없는 스칼라 값을 안전하게 꺼낼 때 | .item() |
| 여러 값이 있는 텐서를 리스트로 | .tolist() |
| numpy 배열로 (grad 없어야 함) | .detach().numpy() |

loss.backward()와 loss.item()은 같이 자주 쓰인다 — backward()로 grad는 계산해두고, 화면 출력이나 기록용으로는 .item()으로 숫자만 뽑아 쓰는 패턴이 표준이다.

10. train/eval/no_grad
서로 다른 축을 제어한다.

| 구분 | 무엇을 제어하는가 |
|---|---|
| model.train() / model.eval() | 레이어의 동작 모드 (Dropout, BatchNorm 등) |
| torch.no_grad() | 그래디언트 추적 여부 (계산 그래프 생성) |

ㄱ) model.train() / model.eval() — 레이어 동작 모드
Dropout, BatchNorm 같은 레이어는 학습 때와 평가 때 동작이 달라야 한다.
    - Dropout: 학습 땐 무작위로 뉴런을 꺼서 과적합 방지 / 평가 땐 전부 사용해야 함 (꺼지면 예측이 랜덤하게 흔들림)
    - BatchNorm: 학습 땐 현재 배치의 평균/분산 사용 / 평가 땐 학습 중 누적해둔 이동평균(running mean/var) 사용

    model.train()   # Dropout 활성화, BatchNorm이 배치 통계 사용
    model.eval()    # Dropout 비활성화, BatchNorm이 저장된 통계 사용

ㄴ) torch.no_grad() — 그래프/grad 추적 차단
이 블록 안에서는 계산 그래프 자체를 안 만든다. 평가할 때는 어차피 파라미터를 업데이트 안 하니 grad가 필요 없어서, 메모리와 속도를 아끼려고 쓴다.

    # eval()만 하고 no_grad() 안 하면?
    model.eval()
    pred = model(x)   # Dropout/BatchNorm은 올바르게 동작 O
                      # 근데 그래프가 계속 만들어짐 → 메모리 낭비, 느림

    # no_grad()만 하고 eval() 안 하면?
    with torch.no_grad():
        pred = model(x)   # 메모리는 아낌 O
                          # 근데 Dropout이 여전히 랜덤하게 뉴런을 꺼버림 → 예측이 매번 달라짐, 틀린 결과!

하나만 하면 절반만 맞은 상태라서, 평가 코드는 반드시 둘 다 같이 쓴다.

ㄷ) 표준 평가 코드 패턴

    model.eval()                      # 1. 레이어 모드 전환
    with torch.no_grad():             # 2. 그래프 생성 차단
        for x, y in val_loader:
            pred = model(x)
            loss = loss_fn(pred, y)
            total_loss += loss.item()   # 3. 숫자만 뽑아 누적

    model.train()                     # 다시 학습 모드로 복귀 (다음 epoch 학습 대비)

| 함수 | 켜는 이유 | 안 하면 생기는 문제 |
|---|---|---|
| model.eval() | Dropout/BatchNorm을 평가 모드로 | 평가 결과가 매번 흔들리거나 부정확해짐 |
| torch.no_grad() | 그래디언트 계산/그래프 생성 생략 | 불필요한 메모리 사용, 속도 저하 (결과 자체는 맞음) |
| model.train() | 다시 학습 모드로 복귀 | eval 이후 학습 재개 시 Dropout이 꺼진 채로 학습됨 (성능 저하) |

eval()은 "레이어가 어떻게 행동할지", no_grad()는 "grad를 계산할지 말지" — 목적이 다르므로 평가 코드에서는 항상 세트로 쓴다.

11. Autograd 디버깅 체크리스트

grad가 None인가?
 → requires_grad 확인 → leaf 여부 확인 → 중간에 detach/no_grad 있었는지 확인
 → backward() 호출했는지 확인

grad 값이 이상한가? (0, NaN, 튐)
 → zero_grad() 누락 확인 → loss 계산식 자체(0나눗셈 등) 확인 → lr 확인

평가 결과가 들쭉날쭉한가?
 → model.eval() 확인

12. Dataset 과 DataLoader 의 역할
X, y를 손으로 만든 텐서로 다뤘는데, 실제 학습에서는 수천~수백만 개의 데이터를 다뤄야 한다. 이걸 효율적으로 관리해주는 게 Dataset과 DataLoader다. 역할이 명확히 나뉜다.

| 구분 | 역할 |
|---|---|
| Dataset | "데이터가 몇 개 있고, i번째 데이터가 뭔지" 정의 (데이터 창고) |
| DataLoader | Dataset에서 데이터를 배치로 묶고, 섞고, 병렬로 꺼내오는 담당 (배달원) |

ㄱ) Dataset — 데이터 접근 방법 정의
Dataset은 딱 두 가지 메서드만 구현하면 된다.

    from torch.utils.data import Dataset

    class MyDataset(Dataset):
        def __init__(self, x_data, y_data):
            self.x = x_data
            self.y = y_data

        def __len__(self):
            return len(self.x)              # 전체 데이터 개수

        def __getitem__(self, idx):
            return self.x[idx], self.y[idx]  # idx번째 샘플 하나 반환

핵심: Dataset은 "샘플 하나를 어떻게 가져올지"만 알면 된다. 배치로 묶는 것도, 섞는 것도 Dataset의 책임이 아니다.

    dataset = MyDataset(x_data, y_data)
    print(len(dataset))       # 전체 개수
    print(dataset[5])         # 5번째 샘플 (x[5], y[5])

ㄴ) DataLoader — 배치화 + 셔플 + 병렬 로딩

    from torch.utils.data import DataLoader

    loader = DataLoader(
        dataset,
        batch_size=32,     # 32개씩 묶어서 반환
        shuffle=True,       # 매 epoch마다 순서 섞기
        num_workers=4,      # 4개 프로세스로 병렬 로딩
    )

DataLoader는 Dataset을 감싸서 학습 루프에서 바로 쓸 수 있는 배치 텐서를 만들어준다.

    for x_batch, y_batch in loader:
        # x_batch.shape == (32, ...) — 32개가 자동으로 묶여서 나옴
        pred = model(x_batch)
        loss = loss_fn(pred, y_batch)
        ...

ㄷ) 각 파라미터가 하는 일

| 파라미터 | 역할 |
|---|---|
| batch_size | 몇 개씩 묶어서 하나의 배치로 만들지 |
| shuffle=True | 매 epoch마다 데이터 순서를 랜덤하게 섞음 (학습 때는 보통 True, 평가 땐 False) |
| num_workers | 데이터 로딩을 몇 개 프로세스로 병렬 처리할지 (GPU가 노는 시간 줄임) |
| collate_fn | 개별 샘플들을 배치로 합치는 방식을 커스터마이징 (샘플 길이가 다를 때 등) |

ㄹ) 관심사 분리
    - Dataset: "데이터가 어디 있고 어떻게 하나씩 꺼내는지"만 신경 씀 (파일 경로, 전처리 로직 등)
    - DataLoader: "그걸 어떻게 배치로 묶고 효율적으로 공급할지"만 신경 씀

이렇게 나눠두면 데이터 종류(이미지, 텍스트 등)가 바뀌어도 Dataset만 새로 짜면 되고, 배치/셔플/병렬화 로직(DataLoader)은 그대로 재사용된다.

    train_dataset = MyDataset(x_train, y_train)
    train_loader = DataLoader(train_dataset, batch_size=32, shuffle=True)

    model.train()
    for x_batch, y_batch in train_loader:
        optimizer.zero_grad()
        pred = model(x_batch)
        loss = loss_fn(pred, y_batch)
        loss.backward()
        optimizer.step()

Dataset = "샘플 1개를 어떻게 가져올지", DataLoader = "그 샘플들을 배치/순서/병렬 처리까지 관리해서 실제로 떠먹여주는 것"

13. TensorDataset과 Custom Dataset

ㄱ) TensorDataset — 이미 텐서로 준비된 데이터용 (내장, 직접 안 만들어도 됨)
데이터가 이미 텐서 형태로 메모리에 다 올라와 있고, 단순히 x/y를 인덱스로 짝지어 꺼내기만 하면 되는 경우 PyTorch가 기본 제공하는 걸 바로 쓴다.

    from torch.utils.data import TensorDataset, DataLoader

    x_data = torch.randn(1000, 10)   # 1000개 샘플, 특징 10개
    y_data = torch.randint(0, 2, (1000,))

    dataset = TensorDataset(x_data, y_data)   # 클래스 직접 안 만들어도 됨
    loader = DataLoader(dataset, batch_size=32, shuffle=True)

내부적으로 딱 이 정도 일만 한다:

    # TensorDataset이 하는 일 (개념적으로)
    def __getitem__(self, idx):
        return x_data[idx], y_data[idx]

커스텀 클래스를 만드는 대신 텐서 두 개(또는 여러 개)를 그냥 넘기기만 하면 끝나는, "짧은 코드용 지름길"이다.

ㄴ) Custom Dataset — 전처리/로딩 로직이 필요한 경우
데이터가 미리 텐서로 다 올라와 있지 않고, 매번 뭔가 가공/로딩을 해야 하는 경우에는 직접 Dataset을 상속해서 만들어야 한다.

    from torch.utils.data import Dataset
    from PIL import Image

    class ImageDataset(Dataset):
        def __init__(self, file_paths, labels, transform=None):
            self.file_paths = file_paths   # 이미지 경로 리스트 (텐서 아님!)
            self.labels = labels
            self.transform = transform

        def __len__(self):
            return len(self.file_paths)

        def __getitem__(self, idx):
            img = Image.open(self.file_paths[idx])   # 이 시점에 파일에서 읽음
            if self.transform:
                img = self.transform(img)              # 리사이즈, 정규화 등
            return img, self.labels[idx]

핵심 차이: __getitem__이 호출되는 그 순간에 파일 읽기, 이미지 디코딩, 텍스트 토큰화 같은 무거운 작업이 일어난다. 1000개 이미지를 미리 다 텐서로 만들어 메모리에 올려두면 용량이 감당 안 되니까, "필요할 때마다 하나씩" 처리하는 구조다.

ㄷ) 사용 방법

| 상황 | 선택 |
|---|---|
| 데이터가 이미 텐서(x, y)로 준비돼 있음 | TensorDataset |
| 표 형태 데이터(csv 읽어서 텐서 변환 끝난 상태) | TensorDataset |
| 이미지 파일 경로 리스트에서 읽어와야 함 | Custom Dataset |
| 텍스트를 토큰화해야 함 | Custom Dataset |
| 샘플마다 augmentation(랜덤 크롭 등)이 필요함 | Custom Dataset |
| 데이터가 너무 커서 한 번에 메모리에 못 올림 | Custom Dataset |

ㄹ) 관계 정리
TensorDataset도 사실 Dataset을 상속해서 만들어진 미리 만들어진 특수 케이스일 뿐이다.

    Dataset (추상 클래스, __len__/__getitem__ 정의 요구)
    ├── TensorDataset (텐서 짝짓기만 하는 기본 구현체, PyTorch 제공)
    └── ImageDataset, MyCustomDataset, ... (직접 상속해서 원하는 로직 구현)

    - 단순히 텐서 몇 개를 인덱스로 묶어서 꺼내기만 하면 되면 TensorDataset를 사용
    - 파일에서 읽거나 가공(전처리, augmentation)이 필요하면 Dataset을 상속해서 __getitem__에 그 로직을 직접 작성해야 한다.

14. Dataset 반환 구조 디버깅하는 방법
    - dataset[0] 직접 호출 → 타입/shape/dtype 확인
    - len(dataset) 확인 → 실제 데이터 개수와 일치하는지
    - 여러 인덱스(처음/중간/끝) 확인 → shape가 항상 동일한지
    - next(iter(loader)) → batch_size가 맨 앞에 잘 붙는지
    - 모델에 실제로 넣어보고 shape mismatch 없는지
    - y의 dtype이 loss 함수가 기대하는 것과 맞는지

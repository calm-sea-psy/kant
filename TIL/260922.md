1. REST란
REST(Representational State Transfer)는 2000년 로이 필딩(Roy Fielding)이 박사 논문에서 제안한 아키텍처 스타일이다. 세 가지 요소로 요약된다.

| 요소 | 담당 | 예 |
|---|---|---|
| 자원(Resource) | URI가 "무엇을" 다룰지 식별 | /users/123 |
| 행위(Verb) | HTTP 메서드가 "어떻게" 할지 표현 | GET, POST, DELETE |
| 표현(Representation) | 자원의 현재 상태를 담은 데이터 형식 | JSON |

이름 그대로 "자원의 상태를 JSON 같은 표현으로 전송한다"는 뜻이다. DB 행을 그대로 넘기지 않고, 그 상태를 JSON으로 표현해서 주고받는다.

    GET /users/123 HTTP/1.1          ← 메서드 + URI
    Accept: application/json

    HTTP/1.1 200 OK                  ← 상태 코드
    Content-Type: application/json

    {"id": 123, "name": "Kim"}       ← 표현

2. REST의 6가지 제약 조건

필딩이 정한 "이걸 지켜야 REST"라는 원칙이다.

| 제약 조건 | 의미 | 얻는 이점 |
|---|---|---|
| 클라이언트-서버(Client-Server) | 화면(클라이언트)과 데이터·로직(서버)을 분리 | 양쪽을 따로 개발·배포할 수 있음 (예: React 프론트 ↔ FastAPI 백엔드) |
| 무상태(Stateless) | 서버는 요청 사이에 클라이언트 상태를 기억하지 않음. 필요한 정보(인증 토큰 등)는 매 요청에 전부 담아 보냄 | 어느 서버가 받아도 처리 가능 → 서버를 늘리기(수평 확장) 쉬움 |
| 캐시 가능(Cacheable) | 응답이 캐시해도 되는지 스스로 밝힘 (Cache-Control, ETag 헤더) | 중복 요청이 줄고 빨라짐 |
| 균일한 인터페이스(Uniform Interface) | 모든 자원을 같은 방식(URI + 메서드 + 표준 형식)으로 다룸 | API를 예측할 수 있게 됨. REST의 핵심 |
| 계층화 시스템(Layered System) | 중간에 부하 분산기·프록시·게이트웨이가 있어도 클라이언트는 몰라도 됨 | 보안·캐시·부하 분산 계층을 자유롭게 추가 |
| 주문형 코드(Code on Demand) | 서버가 실행 코드(JS)를 내려줄 수 있음 | 6개 중 유일한 선택 조건 |

    - 무상태의 익숙한 예: LLM 채팅 API(예: Ollama의 /api/chat)도 무상태다. 대화를 이어가려면 이전 메시지 전체를 요청마다 다시 보내야 한다. 서버는 앞서 나눈 대화를 기억하지 않는다.

ㄱ) 균일한 인터페이스는 다시 네 가지로 나뉜다.

    - 자원 식별: 자원은 URI로 식별한다
    - 표현을 통한 조작: 자원을 직접 건드리지 않고, JSON 같은 표현을 주고받아 조작한다
    - 자기 서술적 메시지(Self-descriptive Message): 메시지만 보고도 해석할 수 있어야 한다 (Content-Type, 메서드, 상태 코드가 이 역할)
    - HATEOAS(Hypermedia As The Engine Of Application State): 응답에 "다음에 할 수 있는 행동"의 링크를 담는다

(심화·선택) HATEOAS까지 지키는 실무 API는 드물다. 보통 "RESTful하다"고 하면 아래 3절 규칙을 지키는 정도를 말한다.

3. 실무 설계 규칙

ㄱ) URI는 명사(자원), 행위는 메서드
가장 중요한 규칙이다. URI에 동사를 넣지 않는다.

| 나쁜 예 | 좋은 예 |
|---|---|
| GET /getUsers | GET /users |
| POST /createUser | POST /users |
| POST /updateUser/1 | PUT /users/1 또는 PATCH /users/1 |
| GET /deleteUser?id=1 | DELETE /users/1 |

ㄴ) URI 작성 규칙
    - 복수형 명사: 컬렉션은 /users, 개별 자원은 /users/123
    - 계층 관계는 /로: /users/123/orders/456은 123번 사용자의 456번 주문
    - 소문자 + 하이픈(-): /user-profiles. URI 경로는 대소문자를 구분하니 소문자로 통일한다. 밑줄(_)은 링크 밑줄에 묻혀 안 보이니 피한다.
    - 끝에 / 붙이지 않기: /users/ → /users
    - 확장자 넣지 않기: /users/1.json 대신 /users/1 + Accept: application/json 헤더
    - 필터·정렬·페이지 나누기(Pagination)는 쿼리 파라미터로: GET /users?role=admin&sort=created_at&page=2&size=20
    - 버전 표시: /v1/users (경로에 넣는 방식이 가장 흔함)
    - 동사가 꼭 필요한 행위는 하위 자원처럼: POST /orders/123/cancel (자주 쓰는 실용적 타협)

ㄷ) HTTP 메서드와 두 가지 성질

| 메서드 | 의미 | 예 | 안전(Safe) | 멱등(Idempotent) |
|---|---|---|---|---|
| GET | 조회 | GET /users/1 | O | O |
| POST | 생성 (ID는 서버가 부여) | POST /users | X | X |
| PUT | 전체 교체 (없으면 생성 가능) | PUT /users/1 | X | O |
| PATCH | 부분 수정 | PATCH /users/1 | X | X (보장 안 됨) |
| DELETE | 삭제 | DELETE /users/1 | X | O |

a. 안전(Safe): 서버 상태를 바꾸지 않는다(읽기 전용). 여러 번 호출하거나 캐시해도 부작용이 없다.
b. 멱등(Idempotent): 같은 요청을 1번 보내든 10번 보내든 서버 상태는 똑같다.
    - DELETE /users/1을 두 번 보내면 첫 번째는 204, 두 번째는 404다. 응답은 달라도 "1번 사용자가 없는 상태"라는 결과는 같으니 멱등이다.
    - POST /users를 두 번 보내면 사용자가 2명 생긴다. 멱등이 아니다.
    - 왜 중요한가: 네트워크가 끊겨 응답을 못 받았을 때 "다시 보내도 되나?"를 판단하는 기준이다. 멱등 요청은 다시 보내도 안전하다.
c. PUT과 PATCH의 차이

    현재 상태:  {"name": "Kim", "email": "kim@a.com", "age": 30}

    PUT   /users/1  {"name": "Lee"}  →  {"name": "Lee"}
        통째로 교체: 보내지 않은 필드는 사라짐

    PATCH /users/1  {"name": "Lee"}  →  {"name": "Lee", "email": "kim@a.com", "age": 30}
        보낸 필드만 수정

4. HTTP 상태 코드
세 자리 숫자이고 첫 자리가 분류다. 그래서 모르는 코드를 받아도 첫 자리만 보고 처리하면 된다(예: 처음 보는 4xx는 400처럼 취급).

| 범위 | 분류 | 한 줄 의미 |
|---|---|---|
| 1xx | 정보(Informational) | 받았음, 처리 계속 중 |
| 2xx | 성공(Success) | 요청 성공 |
| 3xx | 리다이렉션(Redirection) | 다른 곳으로 가라 / 캐시를 써라 |
| 4xx | 클라이언트 오류(Client Error) | 요청이 잘못됨. 보낸 쪽이 고쳐야 함 |
| 5xx | 서버 오류(Server Error) | 요청은 정상인데 서버가 처리에 실패 |

ㄱ) 1xx 정보: API 개발에서 직접 다룰 일은 거의 없음

| 코드 | 이름 | 의미 |
|---|---|---|
| 100 | Continue | 헤더는 받았으니 본문을 계속 보내라 (큰 파일 업로드 전 확인용) |
| 101 | Switching Protocols | 프로토콜 전환 승인 (HTTP → 웹소켓(WebSocket)) |

ㄴ) 2xx 성공

| 코드 | 이름 | 의미 / 언제 |
|---|---|---|
| 200 | OK | 요청 성공. GET 조회 결과, PUT·PATCH 수정 후 결과 반환 |
| 201 | Created | 새 자원 생성 성공(주로 POST). Location 헤더에 새 자원 주소를 담음 (Location: /users/124) |
| 202 | Accepted | 접수는 했지만 아직 처리 전 (영상 변환, 대량 배치 같은 비동기 작업). 보통 진행 상황을 확인할 주소를 함께 줌 |
| 204 | No Content | 성공했지만 돌려줄 본문 없음 (DELETE 성공 등) |
| 206 | Partial Content | 요청한 범위만 일부 응답 (영상 구간 이동, 다운로드 이어받기) |

ㄷ) 3xx 리다이렉션: 주로 브라우저·캐시가 자동으로 처리

| 코드 | 이름 | 의미 |
|---|---|---|
| 301 | Moved Permanently | 영구 이동. Location의 새 주소로 가고, 앞으로도 그 주소를 써라 |
| 302 | Found | 임시 이동. 이번에만 Location으로 가라 |
| 304 | Not Modified | 가진 캐시가 아직 유효하니 그대로 써라. 본문 없음 (ETag 비교 같은 조건부 요청의 결과) |
| 307 | Temporary Redirect | 302와 같지만 메서드·본문 유지를 보장 (POST는 POST 그대로) |
| 308 | Permanent Redirect | 301과 같지만 메서드·본문 유지를 보장 |

    - 301·302를 받으면 브라우저가 POST를 GET으로 바꿔 다시 요청하는 경우가 있다. 그래서 메서드를 절대 바꾸지 않는 307·308이 따로 생겼다.

ㄹ) 4xx 클라이언트 오류

| 코드 | 이름 | 의미 / 언제 |
|---|---|---|
| 400 | Bad Request | 요청 자체가 잘못됨 (JSON 문법 오류, 필수 값 누락, 타입 불일치) |
| 401 | Unauthorized | 인증 안 됨. "누구세요?" (토큰 없음·만료·위조). 이름은 Unauthorized지만 실제 뜻은 '미인증' |
| 403 | Forbidden | 권한 없음. "누군지는 알지만 안 됩니다" (일반 사용자가 관리자 API 호출) |
| 404 | Not Found | 자원이 없음 (없는 ID, 잘못된 주소). 자원이 있다는 사실 자체를 숨기려고 403 대신 쓰기도 함 |
| 405 | Method Not Allowed | 주소는 있지만 그 메서드는 안 됨 (삭제할 수 없는 자원에 DELETE). Allow 헤더로 가능한 메서드를 알려줌 |
| 409 | Conflict | 자원의 현재 상태와 충돌 (이미 가입된 이메일로 가입, 동시 수정 충돌) |
| 413 | Content Too Large | 요청 본문이 너무 큼 (업로드 용량 초과) |
| 415 | Unsupported Media Type | 지원하지 않는 Content-Type (JSON만 받는데 XML을 보냄) |
| 422 | Unprocessable Content | 형식은 맞는데 내용이 검증에 실패 (이메일 형식이 아님, 나이가 음수). FastAPI는 Pydantic 검증에 실패하면 기본으로 422를 돌려줌 |
| 429 | Too Many Requests | 요청 한도(Rate Limit) 초과. Retry-After 헤더로 언제 다시 보내면 되는지 알려주기도 함 |

    - 400 vs 422: 400은 "아예 읽을 수 없음(문법)", 422는 "읽을 수는 있는데 규칙 위반(의미)"이다. 둘 다 400으로 통일하는 API도 많으니 팀 안에서 일관되게만 쓰면 된다.
    - 401 vs 403: 401은 (다시) 로그인하면 풀릴 수 있고, 403은 로그인해도 권한이 없어서 안 된다.

ㅁ) 5xx 서버 오류

| 코드 | 이름 | 의미 / 언제 |
|---|---|---|
| 500 | Internal Server Error | 서버 내부 오류 (처리하지 못한 예외, 버그). 가장 흔한 서버 오류 |
| 502 | Bad Gateway | 중간 서버(게이트웨이)가 뒤쪽 서버에서 잘못된 응답을 받음 (뒤쪽 앱 서버가 죽어 있음) |
| 503 | Service Unavailable | 일시적으로 처리 불가 (과부하, 점검 중). Retry-After로 복구 예상 시점을 알려주기도 함 |
| 504 | Gateway Timeout | 중간 서버가 뒤쪽 서버의 응답을 기다리다 시간 초과 |

클라이언트 → [게이트웨이 (예: Nginx)] → [앱 서버]
                  ├─ 앱 서버가 연결 거부 / 이상한 응답 → 502
                  └─ 앱 서버가 너무 오래 응답 없음     → 504

    - LLM 응답처럼 생성이 오래 걸리는 요청은 게이트웨이 시간 제한(예: Nginx 기본 60초)에 걸려 504가 나기 쉽다. 스트리밍 응답을 쓰는 이유 중 하나다.

5. 메서드별 대표 응답 코드

| 요청 | 성공 | 대표 실패 |
|---|---|---|
| GET /users (목록) | 200. 결과가 0건이어도 200 + [] (404 아님) | 400 (잘못된 쿼리 파라미터) |
| GET /users/1 | 200 | 404 |
| POST /users | 201 + Location 헤더 (비동기 처리면 202) | 400·422 (검증 실패), 409 (중복) |
| PUT /users/1 | 200 (수정 결과 반환) 또는 204. 새로 만들었으면 201 | 400·422, 404 |
| PATCH /users/1 | 200 또는 204 | 400·422, 404, 409 |
| DELETE /users/1 | 204 | 404 |
| 모든 요청 공통 | — | 401, 403, 429, 500, 503 |

6. HTTP 요청의 구성 요소
HTTP 요청은 정해진 형식을 따르는 텍스트 메시지다. 네 부분으로 이루어져 있다.

    POST /users?notify=true HTTP/1.1      ← ① 요청줄(Request Line)
    Host: api.example.com                 ← ② 헤더(Headers)
    Content-Type: application/json
    Content-Length: 26
    Authorization: Bearer eyJhbGciOi...
                                          ← ③ 빈 줄
    {"name": "Kim", "age": 30}            ← ④ 본문(Body)

| 구성 요소 | 역할 | 필수 여부 |
|---|---|---|
| ① 요청줄 | 무엇을(메서드), 어디에(대상), 어떤 버전으로 | 필수 |
| ② 헤더 | 요청에 대한 부가 정보(메타데이터) | Host는 필수, 나머지는 필요할 때 |
| ③ 빈 줄 | 헤더가 끝나고 본문이 시작된다는 표시 | 필수 |
| ④ 본문 | 실제로 보낼 데이터 | 선택 (GET은 보통 없음) |

    - 택배에 비유하면 요청줄은 "배송 방법과 주소", 헤더는 "송장에 적힌 세부 정보(보낸 사람, 내용물 종류, 무게)", 본문은 "상자 속 물건"이다. 응답도 뼈대가 같고, 첫 줄만 상태줄(HTTP/1.1 200 OK)로 바뀐다.

ㄱ) 요청줄(Request Line)
POST /users?notify=true HTTP/1.1처럼 세 부분이 공백으로 구분된다.

| 부분 | 의미 | 예 |
|---|---|---|
| 메서드(Method) | 무엇을 할지 (앞에서 본 GET·POST 등) | POST |
| 요청 대상(Request Target) | 어떤 자원에 할지. 경로와 쿼리 문자열 | /users?notify=true |
| HTTP 버전 | 어떤 버전의 HTTP 규칙을 따를지 | HTTP/1.1 |

a. URL은 요청 안에서 나뉘어 들어간다
주소창의 URL이 통째로 전송되지는 않는다. https://api.example.com:443/users/123?fields=name#profile을 요청하면 이렇게 나뉜다.

| URL 부분 | 예 | HTTP 요청에서는 |
|---|---|---|
| 스킴(Scheme) | https | 요청 메시지에는 안 들어간다. 암호화 연결(TLS)을 쓸지 정하는 데만 쓴다 |
| 호스트(Host) | api.example.com | Host 헤더로 간다 |
| 포트(Port) | 443 | 연결할 때 쓴다. 기본 포트(http 80, https 443)가 아니면 Host 헤더에 같이 적힌다 (Host: localhost:8000) |
| 경로(Path) | /users/123 | 요청줄로 간다 |
| 쿼리 문자열(Query String) | ?fields=name | 요청줄로 간다 |
| 조각(Fragment) | #profile | 서버로 보내지 않는다. 브라우저가 페이지 안의 위치로 이동할 때만 쓴다 |

b. 경로 파라미터 vs 쿼리 파라미터
    - 경로 파라미터(Path Parameter): 특정 자원을 가리킬 때 쓴다. 예: /users/123
    - 쿼리 파라미터(Query Parameter): 조건이나 옵션을 줄 때 쓴다. 예: /users?role=admin&page=2 (? 뒤에 키=값을 쓰고, 여러 개면 &로 잇는다)
    - 구분하는 법: 빼면 다른 자원이 되면 경로, 빼도 같은 자원이고 결과만 달라지면 쿼리다.
    - URL에는 공백이나 한글을 그대로 넣을 수 없어서 % 코드로 바꾼다(URL 인코딩(Percent-encoding)). 예: ?q=안녕 → ?q=%EC%95%88%EB%85%95

ㄴ) 헤더(Headers)
이름: 값 형식으로 한 줄에 하나씩 쓴다. 이름은 대소문자를 가리지 않는다(content-type과 Content-Type은 같다). 자주 보는 요청 헤더를 용도별로 묶으면 이렇다.

| 용도 | 헤더 | 의미 | 예 |
|---|---|---|---|
| 대상 | Host | 요청을 받을 서버의 도메인. HTTP/1.1에서는 반드시 넣어야 한다. 서버 하나(IP 하나)에서 여러 사이트를 운영해도 어느 사이트로 온 요청인지 구분해 준다 | api.example.com |
| 본문 설명 | Content-Type | 내가 보내는 본문의 형식 | application/json |
| 본문 설명 | Content-Length | 본문 크기(바이트) | 26 |
| 원하는 응답 | Accept | 받고 싶은 응답 형식 | application/json |
| 원하는 응답 | Accept-Language | 선호하는 언어 | ko-KR |
| 인증 | Authorization | 인증 정보. 보통 Bearer 토큰 형태다 (서비스에 따라 X-API-Key 같은 전용 헤더를 쓰기도 한다) | Bearer eyJhbGci... |
| 인증 | Cookie | 서버가 전에 준 쿠키를 브라우저가 자동으로 돌려보낸다 (로그인 세션 등) | session_id=abc123 |
| 보낸 쪽 정보 | User-Agent | 요청을 보낸 프로그램 | Mozilla/5.0 ..., curl/8.21.0 |
| 보낸 쪽 정보 | Origin | 요청을 보낸 웹페이지의 출처. 브라우저가 자동으로 붙이고, CORS(다른 출처 사이의 요청을 허용하는 규칙)를 판단하는 데 쓴다 | http://localhost:5173 |
| 캐시 | If-None-Match | 가지고 있는 캐시의 버전(ETag). 바뀐 게 없으면 서버가 본문 없이 304로 응답한다 | "v3" |

    - Content-Type vs Accept: Content-Type은 "제가 보내는 건 JSON이에요", Accept는 "답은 JSON으로 주세요"라는 뜻이다. 방향이 서로 반대다.
    - CORS: React 개발 서버(localhost:5173)에서 FastAPI(localhost:8000)를 호출하면 포트가 달라서 "다른 출처"가 된다. 서버가 허용해 주지 않으면 브라우저가 응답을 막는다. FastAPI에서는 CORSMiddleware로 허용한다.

ㄷ) 빈 줄
헤더가 끝났다는 표시다. 서버는 빈 줄을 만나면 그 뒤부터를 본문으로 읽는다. 실제로는 줄바꿈 문자 \r\n이 두 번 연달아 온 거다.

ㄹ) 본문(Body)
서버에 보낼 실제 데이터다. 주로 생성·수정 요청(POST·PUT·PATCH)에 담고, 형식은 Content-Type 헤더로 알려준다.

| Content-Type | 본문 모양 | 주로 쓰는 곳 |
|---|---|---|
| application/json | {"name": "Kim", "age": 30} | REST API (가장 흔함) |
| application/x-www-form-urlencoded | name=Kim&age=30 | HTML 폼의 기본 전송 방식 |
| multipart/form-data | 여러 부분으로 나눠 글자와 파일을 함께 보낸다 | 파일 업로드 |
| text/plain | hello | 일반 텍스트 |

    - GET 요청에는 본문을 넣지 말 것. 표준에서 GET 본문의 의미를 정해 두지 않아서 서버나 프록시가 무시하거나 거부할 수 있다. 조회 조건은 쿼리 문자열로 보낸다.

ㅁ) 정리

| 위치 | 담는 것 | 예 |
|---|---|---|
| 경로(Path) | 특정 자원을 가리키는 값 | /users/123 |
| 쿼리 문자열(Query) | 조회 조건과 옵션 (필터·정렬·페이지) | ?role=admin&page=2 |
| 헤더(Header) | 요청에 대한 부가 정보 (인증·형식·언어) | Authorization: Bearer ... |
| 본문(Body) | 생성·수정할 실제 데이터 | {"name": "Kim"} |

    - 비밀번호나 토큰 같은 민감한 값은 URL(경로·쿼리)에 넣지 말 것. URL은 서버 로그, 브라우저 기록, 프록시 기록에 그대로 남는다. 헤더나 본문에 담고 HTTPS로 보내야 한다.

FastAPI는 함수 매개변수를 어떻게 선언하느냐로 이 네 위치를 구분한다.

    @app.post("/users/{user_id}/orders")
    def create_order(
        user_id: int,                   # 경로: 주소의 {user_id} 자리 → /users/123/orders
        order: OrderCreate,             # 본문: Pydantic 모델은 JSON 본문에서 읽음
        notify: bool = False,           # 쿼리: 주소에 없는 단순 값 → ?notify=true
        authorization: str = Header(),  # 헤더: Authorization 헤더에서 읽음
    ):
        ...

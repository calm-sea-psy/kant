1. 클래스 불균형과 혼동행렬 개념 정리

ㄱ) 클래스 불균형 (Class Imbalance)
분류 문제에서 각 클래스(레이블)에 속하는 데이터 개수가 크게 차이나는 상황을 말합니다.
    - 예: 사기 탐지 데이터 10,000건 중 정상거래 9,900건, 사기거래 100건 → 사기 클래스가 전체의 1%
    - 문제점: 모델이 무조건 "다수 클래스(정상)"로만 예측해도 정확도(accuracy)가 99%가 나옴 → 정확도만으로는 모델 성능을 제대로 평가할 수 없음
    - 그래서 정밀도(Precision), 재현율(Recall), F1-score, AUC 같은 지표를 함께 봐야 함

ㄴ) 혼동행렬(Confusion Matrix) 4요소
이진 분류에서 "양성(Positive, 예: 사기/질병 있음)"을 기준으로 예측 결과를 4가지로 나눕니다.

           실제 양성    실제 음성
예측 양성   TP           FP
예측 음성   FN           TN

    - TP (True Positive): 실제 양성인데 양성으로 맞게 예측 → 사기인데 사기로 잡음
    - FP (False Positive): 실제 음성인데 양성으로 잘못 예측 → 정상인데 사기로 오탐 (1종 오류)
    - FN (False Negative): 실제 양성인데 음성으로 잘못 예측 → 사기인데 놓침 (2종 오류)
    - TN (True Negative): 실제 음성인데 음성으로 맞게 예측 → 정상을 정상으로 맞춤

ㄷ) 양성률 (Positive Rate)
문맥에 따라 두 가지로 쓰입니다.
    - 실제 양성 비율 (prevalence): 전체 데이터 중 실제 양성 클래스의 비율
        - 양성률 = (TP + FN) / (TP + FP + FN + TN)
        - 클래스 불균형이 심할수록 이 값이 매우 작아짐 (위 예시라면 1%)
    - 예측 양성 비율: 모델이 양성이라고 예측한 비율 = (TP + FP) / 전체
    - 재현율(Recall, TPR) = TP / (TP + FN) → 실제 양성 중 얼마나 잘 잡았는지
    - 정밀도(Precision) = TP / (TP + FP) → 양성이라 예측한 것 중 실제로 맞은 비율
    - 위양성률(FPR) = FP / (FP + TN) → 실제 음성 중 잘못 양성으로 예측한 비율

클래스 불균형 상황에서는 재현율/정밀도/F1을 accuracy보다 우선해서 봐야 모델이 소수 클래스(보통 더 중요한 클래스, 예: 사기·질병)를 얼마나 잘 잡는지 파악할 수 있습니다.

F1-score
정밀도(Precision)와 재현율(Recall)의 조화평균(harmonic mean)입니다.
일반 평균(산술평균) 대신 조화평균을 쓰는 이유는, 둘 중 하나라도 낮으면 F1도 크게 낮아지도록 하기 위해서입니다.

예: Precision = 1.0, Recall = 0.0
    - 산술평균 = 0.5 (꽤 괜찮아 보임 — 하지만 실제로는 양성을 하나도 못 잡은 모델)
    - F1(조화평균) = 0.0 (모델이 쓸모없다는 걸 정확히 반영)
즉 정밀도와 재현율 중 어느 한쪽만 극단적으로 잘해도 점수가 부풀려지지 않게 막아줍니다.

불균형 데이터에서는 accuracy가 왜곡되기 쉽고, precision과 recall은 서로 trade-off 관계(하나를 올리면 다른 하나가 내려가는 경향)에 있는 경우가 많습니다.
    - 임계값(threshold)을 낮추면 → 양성 예측이 늘어남 → Recall↑, Precision↓
    - 임계값을 높이면 → 반대로 Precision↑, Recall↓

F1은 이 둘을 한 숫자로 균형 있게 요약해주기 때문에, 모델을 비교하거나 최적 threshold를 고를 때 자주 쓰입니다.

2. ROC-AUC와 AP (Average Precision)
둘 다 분류 threshold를 하나로 고정하지 않고, threshold를 0~1까지 쭉 바꿔가면서 모델 성능을 종합적으로 평가하는 지표입니다. (앞서 얘기한 Precision/Recall/F1은 threshold 하나를 정한 뒤의 값이었죠.)

ㄱ) ROC-AUC
ROC 곡선(Receiver Operating Characteristic Curve): threshold를 바꿔가며 아래 두 값을 (x, y)로 찍은 곡선
    - x축: FPR (False Positive Rate) = FP / (FP + TN) — 실제 음성 중 잘못 양성으로 예측한 비율
    - y축: TPR (True Positive Rate) = Recall = TP / (TP + FN) — 실제 양성 중 맞게 예측한 비율
AUC (Area Under the Curve): 이 곡선 아래 면적. 0.5(랜덤 예측) ~ 1.0(완벽한 분류) 사이 값.
직관적 해석: 무작위로 양성 샘플 1개, 음성 샘플 1개를 뽑았을 때, 모델이 양성 샘플에 더 높은 점수를 줄 확률

클래스 불균형에서의 함정
FPR의 분모(FP + TN)는 음성 샘플 수입니다. 음성이 압도적으로 많으면(예: 정상거래 9,900건), FP가 꽤 늘어나도 분모가 워낙 커서 FPR은 거의 변하지 않습니다. 그 결과 ROC-AUC가 실제보다 낙관적으로 좋게 나오는 경향이 있습니다.

ㄴ) AP (Average Precision)
PR 곡선(Precision-Recall Curve): threshold를 바꿔가며
    - x축: Recall
    - y축: Precision
을 찍은 곡선이고, AP는 이 곡선 아래 면적(을 각 recall 지점에서의 precision 가중합으로 근사한 값)입니다.

Precision의 분모(TP + FP)는 모델이 양성이라고 예측한 것들입니다. 음성이 아무리 많아도, FP가 조금만 늘어도 분모(TP+FP) 대비 비중이 크게 잡혀서 Precision이 민감하게 반응합니다. 즉 소수 클래스(양성)를 잘 맞추는지를 훨씬 엄격하게 반영합니다.

| 구분 | ROC-AUC | AP (PR-AUC) |
|---|---|---|
| 축 | FPR vs TPR | Recall vs Precision |
| 분모에 다수 클래스(TN) 포함 여부 | 포함됨 (FPR) | 포함 안 됨 |
| 클래스 불균형 시 | 과대평가되기 쉬움 | 더 현실적인 평가 |
| 적합한 상황 | 클래스가 비교적 균형 | 불균형 데이터, 소수 클래스가 중요 (사기 탐지, 질병 진단 등) |

3. Threshold(임계값)
분류 모델(로지스틱 회귀, 랜덤포레스트, 신경망 등)은 사실 "양성이다/음성이다"를 바로 뱉지 않습니다.
대부분 "이 샘플이 양성일 확률(또는 점수)"를 0~1 사이 숫자로 출력합니다.
예: 어떤 거래에 대해 모델이 사기일 확률 = 0.73 이라고 출력
이 연속적인 확률값을 "양성"과 "음성"이라는 이산적인 클래스로 변환하기 위해 기준선을 긋는데, 그 기준값이 바로 threshold입니다.

    예측 확률 >= threshold  →  양성(Positive)으로 분류
    예측 확률 <  threshold  →  음성(Negative)으로 분류

예: threshold = 0.5 (가장 흔한 기본값)라면:
    - 확률 0.73 → 0.5 이상 → 양성 예측
    - 확률 0.42 → 0.5 미만 → 음성 예측

같은 모델, 같은 확률 출력이라도 threshold를 어디에 긋느냐에 따라 TP/FP/FN/TN이 전부 달라집니다.

threshold를 낮추면 (예: 0.5 → 0.2)
    - 더 많은 샘플이 "양성"으로 분류됨
    - 양성을 놓치는 경우(FN)는 줄어듦 → Recall 상승
    - 대신 사실 음성인데 양성으로 오판하는 경우(FP)도 늘어남 → Precision 하락

threshold를 높이면 (예: 0.5 → 0.8)
    - 확실히 확률 높은 것만 "양성"으로 분류
    - FP는 줄어듦 → Precision 상승
    - 하지만 애매하게 양성이었던 것들을 놓침(FN 증가) → Recall 하락

threshold를 1.0부터 0.0까지 쭉 미끄러뜨리면서, 그때마다 계산되는 (FPR, TPR) 쌍 또는 (Recall, Precision) 쌍을 좌표에 점 찍어 이어놓은 것이 각각 ROC 곡선, PR 곡선입니다. 즉 "threshold 하나를 정하지 않고, 모든 threshold에서의 성능을 한번에 보여주는" 곡선이라서, threshold 선택과 무관하게 모델 자체의 판별력을 비교할 수 있게 해줍니다.

4. SMOTE (Synthetic Minority Over-sampling Technique)
클래스 불균형 문제를 데이터 단계에서 완화하는 대표적인 오버샘플링(over-sampling) 기법입니다. 소수 클래스(예: 사기거래 100건)의 샘플 수를 인위적으로 늘려서 다수 클래스와 비율을 맞춰줍니다.

단순 복제(Random Over-sampling)의 문제
가장 단순한 방법은 소수 클래스 샘플을 그냥 복사해서 늘리는 것인데, 이러면:
    - 완전히 똑같은 데이터가 여러 번 등장 → 모델이 과적합(overfitting) 되기 쉬움
    - 새로운 정보는 전혀 추가되지 않음

SMOTE 의 아이디어: "진짜처럼 보이는 가짜 데이터를 새로 만들자"
단순 복제 대신, 기존 소수 클래스 샘플들 사이(between)의 점을 보간(interpolation)해서 새로운 합성 샘플을 만듭니다.

알고리즘 절차
    - 소수 클래스 샘플 하나(A)를 선택
    - A의 k-최근접이웃(k-NN) 중에서 같은 소수 클래스 샘플 하나(B)를 랜덤하게 선택
    - A와 B를 잇는 선분 위의 임의의 한 점을 새로운 합성 샘플로 생성 (즉, A와 B 사이 어딘가에 새 점을 찍는 것 → 완전히 새로운, 하지만 그럴듯한 소수 클래스 샘플이 생김)
    - 원하는 비율이 될 때까지 이 과정을 반복

장점
    - 단순 복제보다 다양성 있는 소수 클래스 데이터 생성 → 과적합 완화
    - 모델이 소수 클래스의 결정 경계(decision boundary)를 더 폭넓게 학습하도록 도움

단점 / 주의사항
    - 노이즈에 취약: 소수 클래스 샘플 중 이상치(outlier)나 다수 클래스 영역에 섞여 있는 샘플 사이를 보간하면, 오히려 다수 클래스 영역에 잘못된 소수 클래스 합성 샘플이 생길 수 있음
    - 고차원 데이터에서는 k-NN 기반 보간이 덜 의미 있어질 수 있음 (차원의 저주)
    - 반드시 train set에만 적용해야 함 — test/validation set에 SMOTE를 적용하면 합성 샘플의 정보가 원본 샘플에서 유출(data leakage)되어 성능이 부풀려짐
    - Cross-validation 시에도 fold를 나눈 뒤 train fold 안에서만 SMOTE 적용해야 함

대안과 비교
    - 언더샘플링(Under-sampling): 다수 클래스를 줄임 → 정보 손실 위험
    - class_weight 조정: 데이터를 건드리지 않고 손실함수에서 소수 클래스에 더 큰 가중치를 줌 (SMOTE와 함께 쓰기도 함)

5. 봉인 테스트(Sealed Test) 원칙
머신러닝 모델 개발 시 test set을 마지막 최종 평가 전까지 절대 들여다보지도, 사용하지도 않고 "봉인해서" 따로 떼어놓는다는 원칙입니다. 앞서 SMOTE에서 언급한 data leakage(정보 유출) 문제를 막기 위한 핵심 원칙 중 하나입니다.

모델 개발 과정은 보통 이렇게 반복됩니다:
데이터 전처리 → 모델 학습 → 성능 확인 → 하이퍼파라미터 조정 → 다시 학습 → 성능 확인 → ...

이 반복 루프에서 test set으로 성능을 확인하면서 조정을 하면, 개발자가 의식하지 못하는 사이에 모델(또는 개발자의 선택)이 test set에 맞춰지게 됩니다. 이러면 test set은 더 이상 "한 번도 못 본 데이터"가 아니게 되어, 실제 운영 환경(진짜 unseen data)에서는 성능이 뚝 떨어지는 낙관적 편향(optimistic bias)이 생깁니다.

데이터 분할 구조

    전체 데이터
    ├── Train set        → 모델 파라미터 학습
    ├── Validation set    → 하이퍼파라미터 튜닝, 모델 선택, 조기 종료(early stopping) 판단
    └── Test set (봉인!)  → 오직 "마지막에 딱 한 번"만 최종 성능 확인

Train/Validation은 개발 중에 자유롭게, 반복적으로 사용
Test set은 튜닝이 전부 끝나고 모델이 확정된 뒤, 정말 마지막에 딱 한 번만 열어봄

안티패턴
    - Test set 성능을 보고 하이퍼파라미터를 다시 조정 → 사실상 test set이 validation set처럼 쓰이며 봉인이 깨짐
    - 전처리(정규화, 결측치 대체, SMOTE 등)를 전체 데이터에 먼저 적용한 뒤 train/test로 분할 → 앞서 얘기한 것처럼 test set의 통계 정보(평균, 분산 등)가 train 과정에 스며듦
    - Feature selection을 전체 데이터로 한 뒤 분할 → 마찬가지로 test set 정보 유출
    - 여러 모델을 test set으로 비교해서 그중 제일 좋은 걸 최종 선택 → 이것도 test set을 모델 선택에 쓴 것이므로 봉인 위반 (이런 비교는 validation set에서 해야 함)
    - Cross-validation을 쓸 때도, fold 분할 전에 전처리/오버샘플링을 하면 안 됨 — fold마다 train fold 안에서만 처리해야 함 (SMOTE 얘기할 때 언급한 것과 동일한 원칙)
    - 시계열 데이터라면 무작위 분할이 아니라 시간 순서대로 분할해야 합니다. 미래 데이터가 train set에 섞여 들어가면(예: 랜덤 셔플 후 분할) 모델이 미래 정보를 미리 보고 학습하는 셈이라 이것도 일종의 봉인 위반(temporal leakage)입니다.

6. 배포 후 새로 만날 "단위" 기준으로 분할하기 (Splitter 선택 원칙)
봉인 테스트 원칙의 핵심은 "test set이 진짜 처음 보는 데이터여야 한다"는 것이었죠. 그런데 "처음 보는 데이터"가 정확히 무엇을 의미하는지는 문제마다 다릅니다. 이걸 정하는 게 바로 splitter(분할기)의 단위(unit)를 선택하는 문제입니다.

"모델을 배포하고 나면, 실제 운영 환경에서는 어떤 새로운 것을 만나게 되는가?"

이 질문에 대한 답이 곧 train/test를 나눌 때 사용해야 할 분할 단위입니다. 이 단위를 잘못 고르면 test set이 "진짜 새로운 것"을 평가하지 못하고, 실제로는 못 보던 유출된 정보로 성능이 부풀려집니다.

ㄱ) 행(row) 단위로 랜덤 분할 — 흔히 저지르는 실수
예: 사용자별 거래 로그 데이터에서 row(거래 1건) 단위로 무작위 분할
사용자 A의 거래 100건 → train 70건 / test 30건 (랜덤 섞임)

문제: 배포 후 실제로 만나는 상황은 "한 번도 본 적 없는 새로운 사용자"의 거래일 가능성이 높습니다. 그런데 위처럼 분할하면 같은 사용자 A의 데이터가 train과 test 양쪽에 다 있음 → 모델이 "A는 원래 이런 패턴의 사용자"라는 것을 이미 학습한 상태에서 A의 test 거래를 맞히는 셈 → 신규 사용자에 대한 실제 성능보다 낙관적으로 평가됨

ㄴ) 올바른 단위: 사용자(그룹) 단위 분할
사용자 1~700명 → train
사용자 701~1000명 → test (이 사용자들은 train에서 단 1건도 등장 안 함)

이렇게 해야 "배포 후 처음 보는 사용자"를 얼마나 잘 예측하는지 실제와 가깝게 평가됩니다. sklearn의 GroupKFold, GroupShuffleSplit이 이런 그룹 단위 분할을 지원합니다.

ㄷ) 시간 단위 (Time-based split)
배포 후 만나는 새로움이 "미래 시점의 데이터"라면 (대부분의 실무 상황이 그렇습니다), 랜덤/그룹 분할이 아니라 시간순 분할이 맞습니다.
2024-01 ~ 2024-10 데이터 → train
2024-11 ~ 2024-12 데이터 → test (미래)

랜덤하게 섞어서 분할하면 미래 데이터가 train에 섞여 들어가 미래 정보를 미리 학습(temporal leakage)하게 됩니다. sklearn의 TimeSeriesSplit이 이 용도입니다.

ㄹ) 병원/환자 데이터 예시
    - 신약 효과를 새로운 환자에게 적용할 모델 → 환자 ID 단위로 분할 (같은 환자의 여러 방문 기록이 train/test에 나뉘어 들어가면 안 됨)
    - 특정 병원에서 학습해서 다른 병원에 배포할 모델 → 병원 단위로 분할해야 함 (기관 간 분포 차이까지 검증)

| 배포 후 마주치는 새로움의 정체 | 적절한 splitter |
|---|---|
| 완전히 새로운 사용자/고객/환자/기기 | Group 단위 분할 (GroupKFold 등) |
| 미래 시점의 데이터 | 시간 단위 분할 (TimeSeriesSplit) |
| 새로운 지역/매장/기관 | 해당 단위(지역·매장 ID)로 그룹 분할 |
| 정말로 독립적인 개별 관측치 (그룹 개념 없음) | 단순 랜덤 분할(row 단위)도 무방 |

"test set을 어떤 단위로 나눌지"는 통계적 선택이 아니라, "배포 후 모델이 실제로 마주칠 새로움이 무엇인가"에 대한 답이어야 한다. 이 매칭이 틀리면 test 성능이 아무리 좋아도 실제 운영에서는 재현되지 않습니다.

7. Cross-Validation Splitter 4종 비교
모두 데이터를 K개의 fold로 나눠서 번갈아가며 train/validation으로 쓰는 K-겹 교차검증의 변형입니다.

ㄱ) K-Fold (기본형)
가장 단순한 방식. 데이터를 순서대로(또는 랜덤 셔플 후) K등분해서, 매 라운드마다 1개 fold를 validation, 나머지 K-1개를 train으로 사용합니다.

    Fold1 Fold2 Fold3 Fold4 Fold5
    [ V ] [ T ] [ T ] [ T ] [ T ]   → round 1
    [ T ] [ V ] [ T ] [ T ] [ T ]   → round 2
    ...

문제점: 클래스 비율이나 그룹을 전혀 고려하지 않음. 불균형 데이터라면 어떤 fold에는 소수 클래스가 거의 없을 수도 있고, 같은 사용자의 데이터가 train/validation에 섞여 들어갈 수 있음(앞서 얘기한 leakage 위험).

ㄴ) StratifiedKFold (클래스 비율 유지)
각 fold를 나눌 때 클래스(레이블) 비율이 원본 데이터와 동일하게 유지되도록 층화(stratify)해서 분할합니다.
    - 예: 전체 데이터가 양성 10% / 음성 90%라면, 모든 fold도 양성 약 10% / 음성 약 90%가 되도록 배분
    - 불균형 데이터(class imbalance)에서 사실상 필수 — 안 그러면 특정 fold에 소수 클래스가 거의 안 들어가서 그 fold의 평가가 불안정/왜곡됨

ㄷ) GroupKFold (그룹 단위 분리)
같은 그룹(예: 같은 사용자, 같은 환자)의 데이터가 train과 validation에 절대 동시에 들어가지 않도록 그룹 단위로 fold를 나눕니다. 바로 앞에서 얘기한 "배포 후 새로운 사용자를 만난다"는 상황을 재현하는 splitter입니다.
    - 클래스 비율은 신경 쓰지 않음, 오직 그룹이 겹치지 않는 것만 보장
    - 한계: 그룹별 클래스 비율이 원래 들쭉날쭉하다면, 그룹을 나누는 과정에서 어떤 fold는 양성 비율이 확 낮아지거나 높아질 수 있음 (그룹과 클래스를 동시에 고려하지 못함)

ㄹ) StratifiedGroupKFold (2·3번의 결합)
그룹은 겹치지 않게 분리하면서, 동시에 각 fold의 클래스 비율도 최대한 원본과 비슷하게 유지하려고 시도하는 방식입니다.
    - 그룹 단위 분리(leakage 방지) + 클래스 균형(불균형 데이터 대응)을 동시에 만족시키려는 절충안
    - 완벽하게 둘 다 만족시키긴 어렵기 때문에 "최대한 비슷하게(approximately stratified)" 맞추는 휴리스틱 알고리즘
    - 적합한 상황 예시: 사기 탐지 모델에서, 사용자 단위로 그룹핑해야 하고(같은 사용자가 train/test에 섞이면 leakage) 동시에 사기 비율이 1%로 매우 불균형할 때 → 이 splitter가 가장 이상적

| Splitter | 그룹 분리 | 클래스 비율 유지 | 사용 시점 |
|---|---|---|---|
| KFold | ❌ | ❌ | 독립적이고 균형 잡힌 데이터 |
| StratifiedKFold | ❌ | ✅ | 클래스 불균형 있지만 그룹 개념 없음 |
| GroupKFold | ✅ | ❌ | 그룹(사용자 등) leakage 방지가 중요, 클래스는 균형 |
| StratifiedGroupKFold | ✅ | ✅ | 그룹 leakage 방지 + 클래스 불균형 둘 다 해당 |

8. TimeSeriesSplit
시계열 데이터는 랜덤 셔플 기반의 K-Fold류 splitter를 쓰면 안 됩니다. 미래 데이터가 train에 섞여 들어가 모델이 미래 정보를 미리 보고 학습하는 시간 유출(temporal leakage)이 발생하기 때문입니다. TimeSeriesSplit은 이를 막기 위해 항상 과거로 학습하고 미래로 검증하도록 설계된 splitter입니다.

ㄱ) 동작 방식
데이터를 시간 순서대로 K+1등분한 뒤, 매 라운드마다 train 구간이 점점 확장(growing window)되면서 그 바로 다음 구간을 validation으로 씁니다.

    전체 시간축: [1][2][3][4][5][6]  (시간 순서대로 6등분, n_splits=5)

    round 1: train=[1]         val=[2]
    round 2: train=[1,2]       val=[3]
    round 3: train=[1,2,3]     val=[4]
    round 4: train=[1,2,3,4]   val=[5]
    round 5: train=[1,2,3,4,5] val=[6]

train은 항상 validation보다 과거 시점
라운드가 진행될수록 train 데이터 양이 누적되며 늘어남 (마치 실제 운영에서 시간이 지나며 데이터가 쌓이는 것과 동일한 구조)

ㄴ) 주요 파라미터
    - n_splits: 몇 라운드로 나눌지 (fold 개수)
    - max_train_size: train 구간이 무한정 커지지 않도록 최대 크기 제한 (rolling window 방식으로 만들 때 사용 — 오래된 데이터가 최신 패턴과 안 맞을 때 유용)
    - test_size: 각 validation 구간의 크기를 고정
    - gap: train 끝과 validation 시작 사이에 공백(gap)을 둠. 예측 시점과 실제 라벨 확정 시점 사이에 지연(lag)이 있는 경우(예: "30일 후 이탈 여부" 라벨은 30일 지나야 확정됨) leakage를 막기 위해 씀

ㄷ) Expanding window vs Rolling window
    - Expanding window (기본): train이 계속 누적되어 커짐 → 데이터를 최대한 다 활용
    - Rolling(sliding) window: max_train_size를 지정해 항상 일정 크기의 최근 구간만 train으로 사용 → 오래된 패턴이 최신 트렌드와 다를 때(concept drift) 더 현실적

시계열은 test set을 딱 한 구간만 떼어 평가하면, 그 시기(계절성, 이벤트 등)의 특성에 운 좋게/나쁘게 걸릴 수 있어 평가가 불안정합니다. 여러 시점에서 반복 검증함으로써 모델이 다양한 시간대에 걸쳐 일관되게 잘 작동하는지 확인할 수 있습니다.

주의할 점
    - 최종 test set(봉인 구간)은 별도로 가장 마지막 시점을 떼어놓고, TimeSeriesSplit은 그 이전 구간 안에서 하이퍼파라미터 튜닝용 validation으로만 사용해야 함 (봉인 테스트 원칙과 결합)
    - 전처리(정규화 등 통계량 계산)도 각 fold의 train 구간 안에서만 계산해야 함 — 이 역시 미래 정보 유출 방지
    - 그룹(예: 여러 매장의 시계열)과 시간이 동시에 존재하는 데이터라면, sklearn 기본 TimeSeriesSplit만으로는 부족하고 그룹별로 따로 시간 분할을 적용하거나 커스텀 로직이 필요할 수 있음

9. 데이터 유출(Leakage)의 5가지 유형
봉인 테스트, splitter, SMOTE 관련 주의사항들이 사실 전부 "data leakage(정보 유출)"라는 하나의 큰 개념의 각기 다른 측면이었습니다. 이번엔 이걸 5가지 유형으로 정리해서 봅니다.

ㄱ) 분할 누수 (Split Leakage)
어떤 "단위"로 train/test를 나눠야 하는지를 잘못 정해서, 같은 정보가 양쪽에 동시에 들어가는 경우. 앞서 얘기한 splitter 선택 문제 자체입니다.
    - 예: 같은 사용자의 거래가 train/test에 흩어져 들어감 (row 단위 랜덤 분할)
    - 예: 미래 데이터가 train에 섞여 들어감 (시간 무시한 랜덤 분할)
    - 해결: 배포 후 마주칠 "새로움의 단위"에 맞춰 GroupKFold, TimeSeriesSplit 등을 사용

ㄴ) 전처리 누수 (Preprocessing Leakage)
정규화, 결측치 대체, feature selection 같은 전처리 통계량을 train/test 분할 전에 전체 데이터로 계산해서, test set의 정보가 train 과정에 스며드는 경우.

    # 잘못된 예
    scaler.fit(전체_X)  # test 데이터 정보까지 평균/분산 계산에 반영됨
    X_train, X_test = split(scaler.transform(전체_X))

    # 올바른 예
    X_train, X_test = split(전체_X)
    scaler.fit(X_train)              # train으로만 fit
    X_test = scaler.transform(X_test)  # test는 transform만

CV를 쓸 때도 각 fold의 train 구간 안에서만 fit해야 함 (전체 fold 데이터로 fit하면 안 됨)

ㄷ) Target·미래 누수 (Target / Future Leakage)
예측 시점에는 아직 알 수 없어야 할 정보(미래 정보 또는 target과 인과적으로 얽힌 정보)가 feature로 들어가는 경우. 가장 치명적이고 발견하기 어려운 누수입니다.
    - 예: "환자 퇴원 여부"를 예측하는데 feature에 "퇴원 후 처방된 약" 정보가 포함 → 사실상 target이 feature에 숨어있는 것
    - 예: "30일 후 이탈 여부"를 예측하는 모델인데, 라벨이 확정되는 시점(30일 후) 이전 시점 feature에 그 이후 발생한 이벤트 정보가 섞여 들어감 → 앞서 TimeSeriesSplit의 gap 파라미터가 막으려는 것이 바로 이것
    - 예: 집계 feature(예: "고객의 평균 구매액")를 만들 때 test 시점 이후의 구매 데이터까지 포함해서 계산
    - 해결: "이 feature는 실제 예측 시점에 정말로 확보 가능한 정보인가?"를 feature 하나하나 검증

ㄹ) 리샘플링 누수 (Resampling Leakage)
오버샘플링/언더샘플링을 train/test 분할 전(또는 CV fold 분할 전)에 전체 데이터에 적용하는 경우.

    # 잘못된 예
    X_res, y_res = SMOTE().fit_resample(전체_X, 전체_y)
    X_train, X_test = split(X_res, y_res)
    # → SMOTE가 test 샘플을 참고해서 만든 합성 데이터가 train에 들어갈 수 있고,
    #    test 안에도 "인위적으로 생성된" 샘플이 섞여 평가 자체가 왜곡됨

    # 올바른 예
    X_train, X_test = split(전체_X, 전체_y)
    X_train_res, y_train_res = SMOTE().fit_resample(X_train, y_train)  # train에만 적용
    # X_test는 원본 그대로 유지 (실제 운영 데이터 분포를 반영해야 하므로)

test set은 리샘플링하면 안 됨 — 실제 운영에서 만나는 데이터는 원본 분포(불균형)이기 때문에, test는 그 분포를 그대로 반영해야 현실적인 평가가 됨

ㅁ) 선택 누수 (Selection Leakage)
모델/하이퍼파라미터/feature를 "선택"하는 과정에서 test set 성능을 참고하는 경우. 봉인 테스트 원칙이 막으려는 것이 바로 이것입니다.
    - 예: 여러 모델을 학습시킨 뒤 test set 점수를 보고 그중 제일 좋은 걸 최종 채택 → test set이 사실상 모델 선택 기준(=validation)으로 쓰인 것
    - 예: feature selection(어떤 feature를 쓸지 고르는 것)을 전체 데이터 기준 상관관계로 하고 나서 분할 → 이것도 일종의 selection leakage
    - 해결: 모델 선택·하이퍼파라미터 튜닝·feature selection은 전부 validation set(또는 CV)로만 하고, test set은 정말 마지막에 확정된 파이프라인 전체를 딱 한 번 통과시켜 성능만 확인

올바른 파이프라인 순서
    - 전체 데이터
    - 분할 (배포 후 만날 단위에 맞는 splitter로) → train / test 봉인
    - train 안에서:
        - 전처리 통계량 fit (test에는 transform만)
        - 리샘플링(SMOTE 등) — train에만
        - feature selection, 하이퍼파라미터 튜닝 — CV/validation으로만
    - 확정된 모델을 봉인된 test에 "딱 한 번" 적용 → 최종 성능

10. sklearn Pipeline과 누수 방지
앞서 정리한 5가지 누수 중 상당수는 사실 개발자가 매번 "전처리는 train에만 fit해야지"라고 기억해야 하는 수동 규칙이었습니다. Pipeline은 이걸 사람이 기억하지 않아도 구조적으로 강제하는 도구입니다.

ㄱ) Pipeline이란
여러 변환(transformer) 단계와 마지막 모델(estimator)을 하나의 객체로 묶어서, fit/predict를 호출하면 내부적으로 각 단계를 순서대로 실행해주는 sklearn 도구입니다.

    from sklearn.pipeline import Pipeline
    from sklearn.preprocessing import StandardScaler
    from sklearn.linear_model import LogisticRegression

    pipe = Pipeline([
        ('scaler', StandardScaler()),
        ('clf', LogisticRegression())
    ])

    pipe.fit(X_train, y_train)      # scaler.fit_transform(X_train) → clf.fit(...)
    pipe.predict(X_test)            # scaler.transform(X_test) → clf.predict(...)  ← fit 아님, transform만!

핵심은 pipe.fit()을 호출하면 내부의 모든 transformer가 오직 그 호출에 넘긴 데이터에만 fit 되고, 이후 predict/transform을 호출할 때는 transform만 적용되고 다시 fit되지 않는다는 것입니다.

ㄴ) 구조적으로 막아주는 누수

a. 전처리 누수
cross_val_score(pipe, X, y, cv=5)처럼 Pipeline을 CV에 통째로 넣으면, 각 fold마다 scaler/encoder가 그 fold의 train 부분에만 fit되고 validation은 transform만 적용됩니다. Pipeline 없이 수동으로 하면 흔히 "전체 데이터에 scaler.fit 먼저 하고 CV 시작" 하는 실수를 저지르기 쉬운데, Pipeline은 이걸 원천적으로 못 하게 만듭니다.

b. 리샘플링 누수
imblearn.pipeline.Pipeline(sklearn Pipeline의 SMOTE 대응 버전)을 쓰면, SMOTE도 매 fold의 train 부분에만 적용되고 validation/test에는 적용 안 됨.

    from imblearn.pipeline import Pipeline as ImbPipeline
    from imblearn.over_sampling import SMOTE

    pipe = ImbPipeline([
        ('smote', SMOTE()),
        ('scaler', StandardScaler()),
        ('clf', LogisticRegression())
    ])
    cross_val_score(pipe, X, y, cv=StratifiedKFold(5))

(일반 sklearn Pipeline은 fit_resample을 지원 안 하므로 imblearn.pipeline.Pipeline을 써야 합니다.)

c. 선택 누수 (부분적으로)
GridSearchCV/RandomizedSearchCV에 Pipeline을 통째로 넣으면, 하이퍼파라미터 탐색의 각 후보 조합이 내부 CV의 train fold로만 학습되고 validation fold로 평가됩니다. 최종적으로 정말 봉인된 test set에는 손도 안 대게 코드를 짤 수 있어서, "튜닝 중에 실수로 test를 참고하는" 실수를 줄여줍니다.

ㄷ) Pipeline이 자동으로 못 잡는 누수
Pipeline은 "fit이 train에만 걸리는가"라는 기계적인 순서 문제만 해결해줄 뿐, 그 이상의 논리적/의미적 문제는 전혀 못 잡습니다.

a. Target·미래 누수는 못 잡음
Feature 자체에 이미 미래 정보나 target 정보가 숨어 들어가 있으면, Pipeline이 아무리 정직하게 fit/transform을 나눠도 소용없습니다.
    - 예: "환자 퇴원 여부" 예측에 "퇴원 후 처방약" 컬럼이 애초에 X에 포함되어 있다면, Pipeline은 그걸 정상적인 feature로 보고 완벽하게(?) 학습합니다. 이건 도메인 지식으로 feature 하나하나를 검토해야만 발견 가능.
    - 예: 집계 feature(고객 평균 구매액 등)를 만드는 시점에 이미 미래 데이터가 섞여 들어갔다면, 그 feature engineering이 Pipeline 바깥, 즉 raw 데이터 생성 단계에서 일어난 문제라서 Pipeline이 전혀 관여할 수 없음.

b. 분할 누수(단위 선택 오류)는 못 잡음
Pipeline은 CV의 각 fold가 어떻게 나뉘는지는 관여하지 않고, splitter가 넘겨준 fold를 그대로 신뢰합니다.
    - KFold를 잘못 골라서 같은 사용자가 train/validation에 섞여도, Pipeline 입장에서는 "정상적인 두 개의 다른 데이터셋"으로만 보입니다.
    - splitter 선택은 사람이 "배포 후 무엇을 새로 만나는가"를 판단해서 골라야 하는 영역 — Pipeline이 대신 판단해주지 않음.

c. 외부에서 만든 feature의 누수는 못 잡음
DB join, 별도 배치 작업 등 Pipeline 바깥에서 미리 만들어진 feature 테이블에 이미 leakage가 있다면(예: 집계 시 미래 시점 데이터 포함), Pipeline은 그걸 받은 시점엔 이미 늦었습니다. Pipeline은 sklearn fit/transform 인터페이스 안에서 일어나는 일만 통제할 수 있습니다.

d. 라벨 자체의 정의 오류
Target(y)을 정의하는 로직 자체가 미래 시점 정보를 써서 만들어졌다면(예: "이탈 여부"를 계산하는데 관측 시점 이후 데이터를 참조), 이는 Pipeline이 다루는 X 변환과는 완전히 별개의 문제라 감지 불가능.

| 누수 유형 | Pipeline이 구조적으로 막아줌? |
|---|---|
| 전처리 누수 (scaler, encoder fit) | ✅ |
| 리샘플링 누수 (SMOTE) | ✅ (imblearn Pipeline) |
| 선택 누수 (튜닝 중 test 참고) | ✅ (GridSearchCV와 결합 시) |
| 분할 누수 (잘못된 splitter 단위) | ❌ — splitter는 사람이 골라야 함 |
| Target·미래 누수 (feature/라벨 정의 자체의 문제) | ❌ — 도메인 지식으로 직접 검토 필요 |
| 외부 feature 테이블의 누수 | ❌ — Pipeline 바깥 영역 |

Pipeline은 "fit은 train에만, transform은 항상"이라는 기계적 규율을 강제해서 절차적 누수를 없애주지만, "이 feature/라벨이 애초에 의미상 미래 정보를 담고 있는가"라는 질문에는 답해주지 않는다.

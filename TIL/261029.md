1. RAG 파이프라인
RAG 파이프라인에서 이 네 가지는 한 흐름 위에 있다.

    질문 ─▶ Retriever ─▶ top-k개 Document ─▶ context 조립(예산 안에서) ─▶ 프롬프트 ─▶ LLM
                            (k로 거름)          (max_chars로 한 번 더 거름)
                                                └─▶ sources(출처 목록)

핵심은 필터가 두 개 연달아 있다는 점이다. 하나는 k이고 다른 하나는 예산이다.

ㄱ) Top-k
"유사도 상위 k개만 가져온다"는 뜻이다.
k를 고를 때는 트레이드오프가 있다.

| k가 작으면 | k가 크면 |
|---|---|
| 정답 청크가 k+1등이면 놓침 | 관련 없는 청크(잡음)가 섞임 |
| 프롬프트가 짧고 빠르고 쌈 | 프롬프트가 길어지고 비용·지연이 늘어남 |

    - Retriever는 질문과 관련이 없어도 항상 k개를 채워서 돌려준다. 1등도 사실 별로 관련 없는 청크일 수 있다.
    - 디코딩에서 배운 top-k 샘플링과는 이름만 같다. "상위 k개만 남긴다"는 아이디어는 같지만, 대상이 토큰 후보가 아니라 문서 청크다.

ㄴ) context와 sources
Retriever 결과 하나를 두 갈래로 가공한다.

| 구분 | context | sources |
|---|---|---|
| 누가 읽나 | LLM | 사람(UI) 또는 프로그램 |
| 무엇으로 만드나 | page_content를 이어 붙인 문자열 | metadata에서 뽑은 출처 목록 |
| 모양 | "[1] 환불은 7일…\n\n[2] 단, 개봉 시…" | [{"id": 1, "source": "policy.pdf", "page": 3}, …] |

번호 [1], [2]가 둘을 잇는 고리다. 모델이 답에 [2]라고 쓰면 sources의 2번을 찾아 "policy.pdf p.3"으로 보여 줄 수 있다. 이것이 Citation이다.

여기서 중요한 규칙이 하나 있다.
sources는 context에 실제로 들어간 청크만으로 만들어야 한다.
예산 때문에 잘린 청크까지 sources에 넣으면, 모델이 보지도 않은 문서를 출처로 표시하는 불일치가 생긴다.

ㄷ) 문자 예산과 토큰 예산(tokenizer)
예산이 필요한 이유: 모델의 컨텍스트 창은 토큰 단위 한도이고, 그 안에 모든 것이 들어가야 한다.

    context에 쓸 수 있는 몫 = 창 크기 − (시스템 지시 + 질문 + 대화 히스토리 + 답변 생성용 여유)

답변도 같은 창을 쓴다는 점을 자주 잊는다. 그 몫을 무엇으로 세느냐에 따라 두 가지로 나뉜다.

| 구분 | 문자 예산 (max_chars) | 토큰 예산 (max_tokens) |
|---|---|---|
| 세는 법 | len(text) | len(tokenizer.encode(text)) |
| 실제 한도와 단위 | 다름 → 근사치 | 같음 → 정확 |
| 필요한 것 | 없음 | 모델과 같은 토크나이저 |
| 속도 | 매우 빠름 | 상대적으로 느림 |
| 모델을 바꾸면 | 그대로 씀 | 토크나이저도 바꿔야 함 |

문자 예산의 약점은 글자 수와 토큰 수의 비율이 일정하지 않다는 것이다.
한국어는 토크나이저에 따라 그보다 훨씬 잘게 쪼개지는 경우가 많다. 그래서 같은 3000자라도 영어 문서와 한국어 문서의 토큰 수가 크게 다를 수 있다.
문자 예산을 쓸 때는 안전 마진을 넉넉히 두어야 한다.
보통 문자 예산과 안전 마진으로 시작한다. 창을 꽉 채워 써야 하거나 넘치는 문제가 생기면 토큰 예산으로 바꾼다.

ㄹ) 검색 단계 누락(k)과 예산 누락(max_chars)
정답 청크가 모델에게 도달하지 못하는 지점이 두 곳이다.

    전체 청크 수천 개
    │  Retriever (k=8)          ← 여기서 빠지면: 검색 단계 누락
    ▼
    retrieved: 8개
    │  context 조립 (max_chars)  ← 여기서 빠지면: 예산 누락
    ▼
    included: 5개   (6~8등은 dropped)

a. 검색 단계 누락
    - 원인: k가 작음, 질문 표현과 문서 표현이 다름, 청킹이 나빠서 답이 두 청크로 쪼개짐, 임베딩 모델이 의미를 잘 못 잡음
    - 손볼 곳: k, 청크 크기와 겹침, 질문 재작성, 하이브리드 검색이나 리랭커

b. 예산 누락
    - 원인: max_chars가 작음, 앞 청크들이 길음, 비슷한 내용의 청크가 중복으로 자리를 차지함
    - 손볼 곳: 예산(창이 허용하는 범위 안에서), 청크 크기 줄이기, 중복 제거

c. 구분
두 경우 모두 증상이 같다. 모델이 "Context에 없다"라고 하거나 엉뚱한 답을 낸다. 하지만 처방이 다르다.

    - 예산 누락인데 k를 올리면 아무 효과가 없다. 예산이 4개분이면 k를 8로 하든 20으로 하든 실제로 들어가는 건 4개다. 늘어나는 건 버려지는 목록뿐이다. 즉 실제로 들어가는 개수 = min(k, 예산이 허용하는 개수)이다.
    - 반대로 검색 단계 누락인데 예산을 늘려도 소용없다. 애초에 가져오지 못한 청크이기 때문이다.

예산 누락은 조용한 실패다. Retriever는 정답을 제대로 찾았으니 에러가 나지 않고, 검색 로그만 보면 성공한 것처럼 보인다.
진단법: retrieved, included, dropped 세 목록을 로그로 남기고, 정답 청크가 어디에 있는지 본다.

| 목록 | 무엇인가 | 답해 주는 질문 |
|---|---|---|
| retrieved | Retriever가 돌려준 top-k개 전부(순위와 점수 포함) | 검색이 제대로 찾았나? |
| included | 그중 예산 안에 들어가 context에 실제로 실린 것 | 모델이 실제로 본 근거는 무엇인가? |
| dropped | retrieved에서 included를 뺀 나머지, 즉 예산 때문에 버린 것 | 예산 때문에 무엇을 잃었나? |

2. Hybrid Search
Dense 검색(임베딩)과 Sparse 검색(BM25)은 서로 약점이 반대다.

| 질문 예 | Dense(의미) | Sparse(BM25, 키워드) |
|---|---|---|
| "돈 돌려받고 싶다" → 문서에는 "환불 절차" | ✅ 뜻이 같아서 찾음 | ❌ 겹치는 단어가 없어서 놓침 |
| "ERR_4012 뜨는데" → 문서에 "ERR_4012" | ❌ 코드값은 의미 벡터로 잘 안 잡힘 | ✅ 글자가 정확히 일치해서 찾음 |
| 제품 코드, 고유명사, 신조어 | ❌ 임베딩 모델이 모르는 단어 | ✅ |

Hybrid Search는 두 검색을 동시에 돌리고 결과 목록을 하나로 합치는 방식이다.

            ┌─▶ BM25 검색   → 순위 목록 A
    질문 ──────┤
            └─▶ Dense 검색  → 순위 목록 B
                                │
                        합치기(fusion) ← 여기서 RRF를 씀
                                ▼
                        최종 top-k (= retrieved)
                                ▼
                        context 조립 (included / dropped)

Hybrid Search는 검색 단계 누락을 줄이는 처방이다. retrieved 목록이 달라질 뿐이고, 그 뒤의 예산 단계는 그대로다.

ㄱ) 문제점
두 결과를 합치려면 "누가 더 위인가"를 정해야 한다. 그런데 두 검색의 점수는 척도가 전혀 다르다.

    - BM25 점수: 0부터 시작하고 상한이 없다(예: 3.2, 18.7). 질문마다 범위도 달라진다.
    - 코사인 유사도: -1~1 범위이고, 실제로는 0.6~0.9 근처에 몰린다.

정규화한 뒤 가중합하는 방법도 있다. 하지만 질문마다 점수 분포가 달라서 결과가 불안정하고 가중치를 튜닝해야 한다.

ㄴ) RRF (Reciprocal Rank Fusion)
RRF는 이 문제를 점수를 버리고 순위만 쓰는 방식으로 피한다.

    문서의 RRF 점수 = 각 검색 결과에서 [ 1 / (60 + 그 문서의 순위) ]를 모두 더한 값

어떤 검색 결과에 문서가 없으면 그 검색에서는 0을 더한다.

| 문서 | BM25 기여 | Dense 기여 | RRF 합 | 최종 순위 |
|---|---|---|---|---|
| A | 1/61 | 1/62 | 0.0325 | 1 |
| C | 1/63 | 1/61 | 0.0323 | 2 |
| B | 1/62 | 1/64 | 0.0318 | 3 |
| E | 0 | 1/63 | 0.0159 | 4 |
| D | 1/64 | 0 | 0.0156 | 5 |

양쪽 모두에서 상위에 든 문서(A, C, B)가 한쪽에서만 나온 문서(E, D)보다 확실히 위로 올라온다.
"두 검색기가 모두 괜찮다고 본 문서를 믿자"는 것이 RRF의 아이디어다.

a. 60이라는 상수의 역할
상위 순위 사이의 점수 차이를 완만하게 만든다.

    - 상수가 0이면 1위는 1/1 = 1.0, 2위는 1/2 = 0.5로 두 배 차이가 난다. 한 검색기의 1등이 결과를 혼자 결정해 버린다.
    - 60이면 1/61과 1/62의 차이가 아주 작다. 그래서 한쪽에서만 1등인 문서보다 여러 검색기에서 고르게 상위인 문서가 이긴다.
    - 60은 RRF를 처음 제안한 논문에서 쓴 값이고 지금도 사실상 기본값이다. 거의 건드리지 않는다.

(참고) 이 상수도 흔히 k라고 부르지만 top-k의 k와는 다른 값이다. 이름만 같다.

ㄷ) 장.단점

| 장점 | 단점 |
|---|---|
| 점수 정규화가 필요 없음 | 점수의 크기 정보를 버림(1위가 압도적으로 관련 있어도 그냥 1위로만 취급) |
| 튜닝할 것이 거의 없음 | RRF 점수는 상대 순위만 뜻하므로 "관련 없음"을 걸러 내는 임계값으로 쓰기 어려움 |
| 검색기가 3개 이상이어도 그대로 확장 | 질문과 문서를 다시 읽는 것이 아니라 순위를 합칠 뿐임 |

ㄹ) 참고 메모
    - 각 검색기에서는 넉넉히 가져온다. 최종 k가 5라면 BM25와 Dense에서 각각 20개쯤 가져와 RRF로 합친 뒤 상위 5개를 자른다. 각자 5개씩만 가져오면 겹치는 문서가 적어 합치는 의미가 줄어든다.
    - 한국어 BM25는 토큰화가 중요하다. 공백으로만 자르면 "환불은", "환불이", "환불을"이 서로 다른 단어로 취급되어 매칭이 깨진다. 그래서 형태소 분석기(예: Kiwi)로 조사를 떼어 낸 뒤 색인하는 경우가 많다.
    - LangChain에서는 EnsembleRetriever가 이 방식(검색기별 가중치를 줄 수 있는 RRF)으로 BM25 Retriever와 벡터 Retriever를 합친다. import 경로는 버전에 따라 다르니 쓸 때 확인한다. Elasticsearch, Qdrant 같은 일부 벡터 DB는 Hybrid Search와 RRF를 자체 기능으로 제공한다.

3. Re-ranking
1차 검색이 가져온 후보들을 더 정밀하지만 느린 모델로 다시 채점해서 순서를 다시 매기는 단계다. 그 정밀한 모델로 주로 쓰는 것이 Cross-Encoder다.

질문 ─▶ 1차 검색 (BM25 + Dense → RRF)  ─▶ 후보 50개       ← 넓게, 빠르게
                                              │
                                 Cross-Encoder로 50개 재채점   ← 정밀하게, 느리게
                                              ▼
                                         상위 5개 ─▶ context 조립 (included / dropped)

ㄱ) Bi-Encoder와 Cross-Encoder의 차이
Dense 검색에 써 온 임베딩 모델(Sentence-BERT 계열)이 Bi-Encoder다. 둘은 질문과 문서를 따로 읽느냐, 같이 읽느냐가 다르다.

    Bi-Encoder (Dense 검색)                  Cross-Encoder (리랭커)

    질문 ─▶ [인코더] ─▶ 벡터 q              [CLS] 질문 [SEP] 문서 [SEP]
    문서 ─▶ [인코더] ─▶ 벡터 d                         │
                                                    [인코더]   ← 질문 토큰과 문서 토큰이
        점수 = 코사인(q, d)                            │          서로 attention
                                            [CLS] → head → 점수 0.93

a. Bi-Encoder
    - 질문과 문서를 각각 따로 벡터 하나로 압축한 뒤, 두 벡터를 코사인으로 비교한다.
    - 문서 벡터는 질문과 상관없이 미리 계산해 벡터 DB에 저장할 수 있다. 그래서 수백만 개 중에서도 빠르게 찾는다.
    - 대신 인코딩하는 동안 질문과 문서가 서로를 보지 못한다. 문서 전체가 벡터 하나로 눌리면서 세부 정보도 손실된다.

b. Cross-Encoder
    - 질문과 문서를 한 입력으로 이어 붙여 모델에 넣는다. NOTE에서 본 BERT 문장쌍 입력과 같은 형태다(질문은 Token Type 0, 문서는 1).
    - self-attention이 질문의 모든 토큰과 문서의 모든 토큰을 서로 연결해서 본다. 마지막에 [CLS] 위의 head가 관련도 점수 하나를 낸다. NOTE의 "[CLS] 위에 분류 head" 구조 그대로다.
    - 질문이 들어와야 계산할 수 있으므로 미리 계산해 둘 수 없다. 후보 하나마다 모델을 한 번씩 돌려야 해서 느리다.

| 구분 | Bi-Encoder | Cross-Encoder |
|---|---|---|
| 입력 | 질문, 문서 따로 | 질문 + 문서 한 쌍 |
| 출력 | 벡터(질문 1개, 문서 1개) | 관련도 점수 1개 |
| 미리 계산 | 가능(문서 벡터 저장) | 불가능 |
| 속도 | 매우 빠름 | 느림(후보 수만큼 추론) |
| 정확도 | 보통 | 높음 |
| 측정하는 것 | "비슷한 주제인가?" | "이 문서가 이 질문에 답하는가?" |

ㄴ) 넓게 찾고, 정밀하게 고르기
Cross-Encoder만으로 검색하면 문서가 100만 개일 때 질문마다 모델을 100만 번 돌려야 한다. 현실적으로 불가능하다. 그래서 역할을 나눈다.

| 단계 | 담당 | 목표 |
|---|---|---|
| 1차 검색 (BM25 / Bi-Encoder) | 100만 → 50 | 재현율: 정답을 후보 안에 일단 넣기 |
| 리랭킹 (Cross-Encoder) | 50 → 5 | 정밀도: 그중 진짜 답하는 것만 위로 |

리랭커는 이미 가져온 후보의 순서만 바꿀 수 있다. 정답이 1차 후보 50개 안에 없으면 리랭커도 살릴 수 없다.
그래서 리랭킹을 쓸 때는 1차 검색 k를 최종 개수보다 넉넉하게(5가 아니라 30~50) 잡는다.

ㄷ) 3개의 필터

    1차 검색 (k=50) → 리랭킹 후 상위 n (n=5) → 예산 (max_chars) → included

정답 청크가 빠진 위치에 따라 판정도 하나 늘어난다.

| 정답 청크 위치 | 판정 | 손볼 곳 |
|---|---|---|
| 1차 후보 50개에 없음 | 검색 단계 누락 | k, 청킹, Hybrid Search |
| 50개 안에 있지만 리랭킹 후 상위 n 밖 | 리랭킹 누락 | n, 리랭커 모델 |
| 상위 n 안인데 예산으로 잘림 | 예산 누락 | max_chars, 청크 크기 |

리랭커는 예산 누락도 줄여 준다. RRF 점수는 상대 순위일 뿐이라 임계값으로 쓰기 어렵다고 했다.
리랭커 점수는 "이 쌍이 얼마나 관련 있는가"에 가까운 값이라 "일정 점수 미만은 버린다"는 컷에 쓸 수 있다.
관련 없는 청크가 예산을 차지하지 않게 되고, 가장 관련 있는 청크가 맨 앞에 오니 break 방식 예산에서도 유리하다.
다만 점수 척도는 모델마다 다르다(0~1 확률일 수도, 상한 없는 로짓일 수도 있음). 임계값은 쓰는 모델로 직접 재서 정해야 한다.

ㄹ) 참고 메모
    - 지연: 후보 수만큼 추론하므로 후보를 50개에서 200개로 늘리면 그만큼 느려진다. 1차 k는 재현율과 지연 사이의 절충이다. 리랭커 모델은 LLM보다 훨씬 작고 쌍을 배치로 묶으면 빠르다.
    - 입력 길이 한도: Cross-Encoder도 토크나이저 기준 최대 길이가 있다. 질문과 청크를 합친 길이가 그보다 길면 뒷부분이 잘린 채로 채점된다. 청크 크기를 정할 때 리랭커 한도도 같이 봐야 한다.
    - 언어: 영어 전용 리랭커에 한국어를 넣으면 성능이 크게 떨어진다. 다국어 또는 한국어로 학습된 모델을 고른다.

4. Query Rewrite · Multi-Query
RAG 파이프라인에서 검색 바로 앞에 들어가는 단계다.
이 두 기법은 그보다 앞에서 검색에 넣을 질문 자체를 LLM으로 고친다.

    사용자 질문 ─▶ [LLM] ─┬─▶ 검색 질의 1개   (Query Rewrite) ─▶ 검색 1번
                        └─▶ 검색 질의 N개   (Multi-Query)   ─▶ 검색 N번 ─▶ 합치기(RRF)
                                                                    ▼
                                                    (리랭킹) ─▶ context 조립 ─▶ LLM 답변

둘 다 검색 단계 누락을 줄이기 위한 처방이다.
중요한 원칙이 하나 있다. 고친 질문은 검색에만 쓰고, 답변을 만드는 프롬프트에는 보통 원래 질문을 넣는다.
사용자의 의도와 말투를 그대로 보존하기 위해서이고, 고친 질문이 조금 빗나가더라도 답변은 원래 질문을 기준으로 쓰게 하려는 것이다.

ㄱ) 사용자 질문의 문제점

| 문제 | 예 | 검색에서 생기는 일 |
|---|---|---|
| 대화 맥락에 의존 | "그럼 그건 며칠 걸리나?" | Retriever는 대화를 모르고 이 문장만 받음. "그건"이 무엇인지 알 수 없음 |
| 잡음, 구어체 | "아 어제 산 거 뜯었는데 돈 돌려받을 수 있음?? ㅠㅠ" | 핵심과 상관없는 단어가 벡터와 키워드를 흐림 |
| 문서와 다른 용어 | "돈 돌려받기" ↔ 문서에는 "환불" | Dense는 어느 정도 버티지만 BM25는 놓침 |
| 질문 여러 개가 섞임 | "환불 기간이랑 배송비 누가 내는지" | 벡터 하나에 두 주제가 섞여 양쪽 다 어중간하게 매칭됨 |

Retriever도 마찬가지로 상태가 없다. 게다가 Retriever는 히스토리를 받지 않고 질문 문자열 하나만 받는다.
그래서 멀티턴 챗봇에서는 질문을 고치지 않으면 두 번째 질문부터 검색이 무너진다.

ㄴ) Query Rewrite
질의 하나로 고쳐 쓰기
LLM이 질문을 검색하기 좋은 질의 하나로 다시 쓴다. 크게 두 가지 용도가 있다.

    - 맥락 복원(독립 질문, standalone question): 대화 히스토리와 마지막 질문을 받아, 대화 없이도 이해되는 질문으로 바꾼다.
    - 정제: 잡음을 빼고, 핵심어만 남기고, 문서에서 쓰는 용어로 바꾼다.

재작성용 LLM이 질문을 고치는 대신 답을 해 버리는 실수를 방지하기 위해서 프롬프트를 작성해야 한다.

a. 위험과 비용

    - 의도 왜곡: 고치는 과정에서 뜻이 바뀔 수 있다. 예를 들어 "개봉한"이 빠지면 미개봉 규정만 검색된다. 고친 질문 하나가 틀리면 검색 전체가 빗나간다. 그래서 앞에서 본 retrieved/included/dropped 로그에 원래 질문과 고친 질문을 함께 남겨야 한다.
    - LLM 호출 1번 추가: 그만큼 지연과 비용이 늘어난다. 질문을 고치는 일은 비교적 쉬워서 답변용보다 작은 모델로도 충분한 경우가 많다.
    - 조건부로 돌리기: 대화의 첫 질문이고 이미 깔끔하다면 굳이 고칠 필요가 없다. 히스토리가 있을 때만 돌리는 식으로 조건을 둘 수 있다.

ㄷ) Multi-Query
질의 여러 개로 넓게 찾기
LLM이 질문 하나를 검색 질의 여러 개로 만들고, 각각 검색한 뒤 결과를 합친다. 이것도 두 가지 용도가 있다.

a. 다양화(바꿔 말하기): 같은 질문을 다른 표현과 관점으로 여러 개 만든다. 한 표현이 놓친 문서를 다른 표현이 잡아 주어 재현율이 오른다.
b. 분해: 여러 질문이 섞인 질문을 하위 질문으로 쪼갠다. 주제마다 따로 정확하게 매칭된다.
c. 합치기: 질의 N개에서 나온 결과 목록 N개를 하나로 만들어야 한다.
    - 가장 단순한 방법은 합집합에서 중복을 빼는 것이다. LangChain의 MultiQueryRetriever가 이렇게 동작한다.
    - RRF로 합칠 수도 있다. 앞에서 본 RRF 함수를 그대로 쓴다. 여러 질의에서 공통으로 상위에 든 문서가 위로 올라온다. Multi-Query와 RRF를 묶은 조합을 따로 RAG-Fusion이라고 부르기도 한다.

    - 후보가 많아진다. 질의가 4개이고 k가 10이면 후보가 최대 40개다. 그래서 합치기와 리랭킹이 뒤에 붙는 경우가 많다.
    - 예산 압박이 커진다. 바꿔 말한 질의 중 하나가 엉뚱한 청크를 끌고 오면 그 청크가 예산을 차지한다. 리랭커가 뒤에서 걸러 주면 이 문제가 줄어든다.
    - 분해 질의는 예산 누락에 취약하다. "환불 기간" 청크들이 예산을 다 써 버리면 "배송비" 청크가 전부 dropped될 수 있다. 하위 질문마다 예산 몫을 나눠 주는 방식으로 막기도 한다.
    - 비용: LLM 호출 1번에 검색 N번이 추가된다. 검색은 싸고 RunnableParallel이나 batch로 동시에 돌릴 수 있어서, 지연의 대부분은 LLM 호출에서 나온다.

참고) 여기서 말하는 Multi-Query는 어텐션에서 배운 MQA(Multi-Query Attention)와는 이름만 같고 전혀 다른 개념이다.

ㄹ) 비교

| 구분 | Query Rewrite | Multi-Query |
|---|---|---|
| 출력 | 질의 1개 | 질의 N개 |
| 주 목적 | 검색할 수 있는 형태로 고치기(맥락 복원, 정제) | 여러 표현으로 넓게 찾기, 복합 질문 분해 |
| 검색 횟수 | 1번 | N번 |
| 합치기 | 필요 없음 | 필요(합집합 또는 RRF) |
| 주된 위험 | 의도가 왜곡되면 검색 전체가 빗나감 | 잡음 질의가 엉뚱한 청크를 끌고 옴, 후보와 비용 증가 |
| 잘 맞는 상황 | 멀티턴 챗봇, 구어체 입력 | 짧고 모호한 질문, 여러 질문이 섞인 질문 |

둘은 함께 쓸 수 있다. 먼저 Query Rewrite로 독립 질문을 만들고, 그 질문으로 Multi-Query를 돌리는 순서다.

5. Golden Dataset
질문과 그 질문의 정답 근거(어느 청크에 답이 있는지)를 미리 짝지어 둔 고정 평가 세트다. "Golden"은 사람이 검증한 정답(gold label)이라는 뜻이다.

ㄱ) 만들 때 주의할 점
    - 청킹을 바꾸면 청크 ID가 바뀐다. 청크 크기는 우리가 튜닝하려는 손잡이 중 하나인데, 정답을 청크 ID로만 적어 두면 청킹을 바꿀 때마다 골든셋이 깨진다. 그래서 정답 구절(텍스트)을 같이 저장해 두고 "그 구절을 포함하는 청크면 정답"으로 판정하거나, 문서·페이지 단위로 정답을 매기기도 한다.

    - 질문 유형을 나눠 둔다(slice). 단순 사실, 멀티턴, 코드·고유명사, 복합 질문처럼 유형을 붙여 두면 "Hybrid Search는 코드 질문에서만 효과가 컸다" 같은 결과가 보인다. 전체 평균만 보면 이런 차이가 묻힌다.

    - 실제 질문 분포를 반영한다. 가능하면 실제 사용자 질문 로그에서 뽑는다. 개발자가 머릿속으로 만든 질문은 실제보다 깔끔하고 쉬운 경우가 많다.

    - LLM으로 만들 수도 있지만 검수가 필요하다. 청크를 LLM에게 보여 주고 질문을 만들게 하면 빠르다. 대신 LLM이 청크 문장을 거의 그대로 베낀 질문을 만드는 경향이 있다. 그러면 질문이 너무 쉬워지고 특히 BM25에 유리해진다. 사람이 검수하고 구어체로 바꿔 줘야 한다.

    - 답이 없는 질문도 넣어 둔다. 문서에 답이 없는 질문은 검색 지표에서는 제외하지만, 나중에 생성 단계에서 "모른다고 답하는가"를 평가할 때 쓴다.
    - 크기: 많을수록 좋지만 처음에는 50~100개만 있어도 설정끼리 비교할 수 있다.
    - 한 번 정하면 고정한다. 모든 실험을 같은 세트로 돌려야 비교가 된다. 세트를 바꿀 때는 버전을 올린다.

6. Hit@k, Recall@k

ㄱ) Hit@k
상위 k개 안에 정답 근거가 하나라도 있으면 1점, 없으면 0점이다. 모든 질문의 평균을 낸다.
뜻은 "질문 중 몇 %에서 검색이 정답을 건드렸는가"이다. 맞혔는지 못 맞혔는지만 본다.

ㄴ) Recall@k
질문 하나의 정답 근거 중 상위 k개 안에 들어온 비율이다. 역시 모든 질문의 평균을 낸다.

    질문 하나의 Recall@k = (상위 k개 안에 들어온 정답 수) ÷ (그 질문의 전체 정답 수)

ML의 재현율과 같은 개념이다. "실제 양성"이 정답 청크이고, "모델이 잡아낸 것"이 상위 k개다.

ㄷ) 둘의 차이(예시)
k=5로 질문 세 개를 평가해 본다.

| 질문 | 정답 근거 | 상위 5개에 들어온 것 | Hit@5 | Recall@5 |
|---|---|---|---|---|
| q001 | A | A | 1 | 1/1 = 1.0 |
| q002 | B, C | B만 | 1 | 1/2 = 0.5 |
| q003 | D | 없음 | 0 | 0/1 = 0.0 |
| 평균 | | | 0.67 | 0.50 |

    - 정답이 하나인 질문에서는 Hit@k와 Recall@k가 같다(q001, q003).
    - 정답이 여러 개인 질문에서 차이가 난다(q002). Hit@5는 q002를 성공으로 센다. 하지만 실제로는 배송비 근거(C)를 못 찾았으니 답이 반쪽이 된다. Recall@5는 이를 0.5로 정직하게 보여 준다.

| 상황 | 쓸 지표 |
|---|---|
| FAQ처럼 질문마다 정답 청크가 대부분 하나 | Hit@k로 충분하고 직관적 |
| 여러 근거를 모아야 답하는 질문이 많음(복합, 분해) | Recall@k |

주의점) 자료나 도구마다 Hit@k를 Recall@k라고 부르는 경우가 꽤 있다. 정답이 하나뿐이라고 가정하면 둘이 같기 때문이다. 수치를 볼 때는 정의를 꼭 확인한다.
여기서 말하는 Recall@k는 "사람이 정한 정답" 대비다.

| 측정 지점 | 지표 | 보이는 문제 | 효과가 보이는 기법 |
|---|---|---|---|
| 1차 후보(k=50) | Recall@50 | 검색 단계 누락 | Query Rewrite, Multi-Query, Hybrid Search, 청킹 |
| 리랭킹 후(n=5) | Recall@5 | 리랭킹 누락 | Cross-Encoder |
| context(included) | included 기준 재현율 | 예산 누락 | max_chars, 청크 크기 |

ㄹ) 실험 루틴
    - 골든셋을 고정한다.
    - 현재 설정으로 지표를 재서 기준선으로 삼는다.
    - 한 번에 하나만 바꾼다(k, 청크 크기, Hybrid 켜고 끄기 등). 여러 개를 동시에 바꾸면 무엇이 효과를 냈는지 알 수 없다.
    - 같은 골든셋으로 다시 재서 비교한다. 전체 평균과 함께 slice별로도 본다.
    - 지연과 비용도 함께 기록한다. Recall@5가 0.02 올랐는데 지연이 두 배라면 쓸지 말지 판단이 필요하다.

7. RAGAS와 기본 지표
RAGAS는 RAG 시스템 평가용 라이브러리이자 지표 모음이다.
앞에서 배운 Hit@k, Recall@k가 검색만 쟀다면, RAGAS는 검색과 답변 생성을 함께 잰다. 기본 지표는 네 개다.

RAGAS 기본 지표는 질문, context, 답변, 정답 사이의 관계를 잰다.

ㄱ) 네 가지 재료 사이의 관계를 잰다
RAG 한 번에는 재료가 네 가지 있다. 질문, 검색된 context, 모델의 답변, 그리고 골든셋의 정답 답변이다. 기본 지표 네 개는 각각 이 중 두 재료 사이의 관계를 잰다.

                질문 ◀──── Answer Relevancy ────▶ 답변
                │                                │
        Context Precision                    Faithfulness
                │                                │
                ▼                                ▼
                context ◀───────────────────────────┘
                ▲
            Context Recall
                │
            정답 답변(reference)

| 지표 | 비교하는 것 | 평가 대상 | 정답 답변 필요? |
|---|---|---|---|
| Faithfulness | 답변 ↔ context | 생성: 근거에 충실한가(환각이 없는가) | 불필요 |
| Answer Relevancy | 답변 ↔ 질문 | 생성: 질문에 맞는 답인가 | 불필요 |
| Context Precision | context ↔ 질문(또는 정답) | 검색: 관련 있는 청크가 위에 있는가 | 버전에 따라 둘 다 있음 |
| Context Recall | context ↔ 정답 | 검색: 답에 필요한 근거를 다 가져왔는가 | 필요 |

점수는 모두 0~1이고 높을수록 좋다. 대부분 LLM이 판정자(LLM-as-a-judge) 역할을 해서 계산한다. 사람 대신 LLM이 "이 문장이 context로 뒷받침되는가?" 같은 판정을 내린다.

ㄴ) Faithfulness
답변 속 주장 중 context로 뒷받침되는 비율이다.
    - LLM이 답변을 개별 주장으로 쪼갠다.
    - 주장마다 context에서 그 내용을 이끌어 낼 수 있는지 LLM이 판정한다.
    - 뒷받침되는 주장 수를 전체 주장 수로 나눈다.

    context:  [1] 개봉한 상품은 하자가 있는 경우에만 환불된다.
            [2] 환불은 접수 후 3영업일 내 처리된다.
    답변:     개봉한 상품은 하자가 있을 때만 환불된다. 처리는 3영업일 걸리고,
            환불 시 포인트도 함께 돌려드린다.

| 주장 | 근거 |
|---|---|
| ① 개봉 상품은 하자가 있을 때만 환불 | ✅ [1] |
| ② 처리 기간 3영업일 | ✅ [2] |
| ③ 포인트도 함께 반환 | ❌ context에 없음 |

Faithfulness = 2/3 ≈ 0.67
③은 모델이 지어낸 내용(환각)이다. 프롬프트의 "Context만으로 답하라" 지시가 실제로 지켜지는지를 수치로 보는 지표다.

참고) Faithfulness가 높다고 정답이라는 뜻은 아니다. context가 엉뚱한 문서라면 모델은 그 문서에 충실하게 틀린 답을 낼 수 있다. 그래서 검색 지표와 함께 봐야 한다.

ㄷ) Answer Relevancy
답변이 질문에 얼마나 맞는 내용인가를 잰다. 정답 여부는 보지 않는다.
계산 방식이 독특하다. 답변을 보고 질문을 거꾸로 만들어 본다.
    - LLM이 답변을 읽고 "이 답변은 어떤 질문에 대한 답일까?"를 몇 개 생성한다.
    - 생성된 질문들과 원래 질문의 임베딩 코사인 유사도를 잰다.
    - 그 평균이 점수다.

질문에 딱 맞게 답했다면 역생성된 질문이 원래 질문과 비슷하게 나온다. 답변이 딴소리를 하거나, 질문의 일부에만 답하거나, 관련 없는 정보로 장황하면 역생성 질문이 원래 질문에서 멀어져 점수가 떨어진다. "잘 모르겠다"처럼 답을 회피하는 답변도 낮게 나온다.

ㄹ) Context Precision
검색된 청크 중 관련 있는 것이 얼마나 상위 순위에 몰려 있는가를 잰다.
    - 청크마다 관련 있음(1)인지 없음(0)인지 LLM이 판정한다.
    - 관련 있는 청크가 나온 각 위치에서 "그 위치까지의 정밀도"를 구한다.
    - 그 값들을 평균 낸다.

같은 청크 3개라도 순서에 따라 점수가 달라진다.

| 순서(1=관련, 0=무관) | 계산 | Context Precision |
|---|---|---|
| [1, 1, 0] | (1/1 + 2/2) ÷ 2 | 1.00 |
| [1, 0, 1] | (1/1 + 2/3) ÷ 2 | 0.83 |
| [0, 1, 1] | (1/2 + 2/3) ÷ 2 | 0.58 |

Hit@k와 Recall@k는 k 안에서 몇 등인지 보지 않는다고 했다. Context Precision은 순위를 본다.
그래서 리랭커 효과가 잘 드러나는 지표다. 잡음 청크가 많아도 점수가 내려가므로 k가 너무 큰지도 알 수 있다.

ㅁ) Context Recall
정답 답변의 주장 중 context에서 찾을 수 있는 비율이다.

    정답 답변:  하자가 있는 경우에만 환불되며, 반품 배송비는 회사가 부담한다.
    context:    [1] 개봉한 상품은 하자가 있는 경우에만 환불된다.
                [2] 환불은 접수 후 3영업일 내 처리된다.

| 정답의 주장 | context에 있나 |
|---|---|
| ① 하자가 있을 때만 환불 | ✅ [1] |
| ② 반품 배송비는 회사 부담 | ❌ |

Context Recall = 1/2 = 0.5

배송비 근거 청크를 가져오지 못한 것이다. 1차 검색에서 놓쳤을 수도 있고, 가져왔는데 예산 때문에 dropped됐을 수도 있다.

Recall@k와의 관계: 개념은 같다(필요한 근거 중 몇 %를 가져왔나). 다른 점은 청크 ID가 아니라 정답 답변의 주장으로 판정한다는 것이다. 앞에서 "청킹을 바꾸면 청크 ID가 바뀌어 골든셋이 깨진다"는 문제를 말했는데, Context Recall은 정답 답변 텍스트만 있으면 되므로 청킹을 바꿔도 골든셋을 그대로 쓸 수 있다. 대신 LLM 판정이라 Recall@k보다 비싸고 결과가 덜 안정적이다. RAGAS에는 청크 ID로 계산하는 LLM 없는 버전도 있다.

ㅂ) 지표 조합으로 진단하기

| 관찰 | 판정 | 손볼 곳 |
|---|---|---|
| Context Recall 낮음 | 검색 문제: 근거를 못 가져옴 | k, Hybrid Search, Query Rewrite, 예산 |
| Context Precision 낮음 | 검색 문제: 잡음이 많거나 정답이 아래 순위 | 리랭커, k 줄이기 |
| Context Recall 높음 + Faithfulness 낮음 | 생성 문제: 근거는 있는데 지어냄 | 프롬프트 지시, 모델 |
| Faithfulness 높음 + Answer Relevancy 낮음 | 생성 문제: 근거에 충실하지만 질문과 어긋남 | 프롬프트(질문에만 답하라, 간결하게) |

정답 답변 없이 돌릴 수 있는 지표: Faithfulness와 Answer Relevancy는 정답 답변이 없어도 계산된다. 그래서 골든셋 밖의 실제 운영 로그에도 돌릴 수 있다.
Context Recall은 골든셋이 있어야 한다.

ㅅ) 주의할점
    - 판정 모델을 고정한다. 판정 모델이 바뀌면 점수의 기준도 바뀐다. 실험끼리 비교하려면 판정 모델, 설정(temperature 0), 골든셋을 모두 고정해야 한다.
    - 절대값보다 비교가 중요하다. "Faithfulness 0.82"라는 숫자 자체보다 "설정 A에서 B로 바꿨더니 0.82에서 0.88로 올랐다"가 의미 있다.
    - 비용: 샘플 하나에 LLM 호출이 여러 번 들어간다(주장 분해, 주장별 판정, 질문 역생성 등). 골든셋 100개를 돌리면 호출이 수백 번이다.
    - 판정 품질: 작은 로컬 모델을 판정자로 쓰면 출력 형식이 깨지거나 판정이 부정확해지기 쉽다. 한국어 데이터라면 판정 모델이 한국어를 잘해야 한다. RAGAS의 판정 프롬프트는 기본이 영어인데, 다른 언어에 맞추는 기능이 있다.
    - 사람이 일부를 확인한다. 샘플 몇 개는 직접 보고 LLM 판정이 사람 판단과 맞는지 확인한다. 판정자가 틀리면 지표 전체를 믿을 수 없다.

8. Parent-Child · Context Compression

ㄱ) Parent-Child
문서를 두 단계 크기로 자른다.
    - parent(부모): 큰 조각이다. 예를 들어 섹션이나 1500자 단위로, LLM에게 넘길 단위다.
    - child(자식): parent를 다시 잘게 자른 조각이다. 예를 들어 문장 몇 개나 200자 단위로, 검색할 단위다.

    [색인할 때]
    문서 ─▶ parent로 자름 ─▶ 각 parent를 child로 자름
                            │
            child만 임베딩해서 벡터 DB에 저장 (metadata에 parent_id)
            parent는 별도 저장소에 원문 그대로 보관

    [검색할 때]
    질문 ─▶ child 검색(정밀) ─▶ parent_id로 parent 찾기 ─▶ 중복 제거 ─▶ parent를 LLM에

예시: "개봉 상품 환불" 섹션 하나가 parent이고, 문장 세 개가 각각 child라고 해 보자.

    parent:  개봉한 상품은 하자가 있는 경우에만 환불된다.          ← child 1
            하자 판정은 수령 후 7일 이내 접수된 건에 한한다.       ← child 2
            반품 배송비는 회사가 부담한다.                       ← child 3

질문이 "반품 배송비 누가 내나?"라면 이렇게 된다.
    - child 3이 정확히 매칭된다. 짧아서 벡터에 주제가 하나만 담겨 있기 때문이다.
    - 그런데 child 3만 LLM에게 주면 "모든 반품의 배송비를 회사가 낸다"고 오해할 수 있다. "하자가 있을 때"라는 조건이 다른 child에 있기 때문이다.
    - parent를 넘기면 조건까지 함께 읽으므로 "하자가 있는 경우의 반품 배송비는 회사가 부담한다"라고 정확히 답한다.

a. 변형
    - 문서 전체를 parent로 삼기: 문서가 짧을 때(FAQ 한 항목, 짧은 공지) 쓴다.
    - 문장 창(sentence window): 고정된 parent 경계 대신, 매칭된 문장의 앞뒤 n문장만 붙여서 가져온다.

b. trade-off
    - 중복 때문에 실제 개수가 줄어든다. child 10개가 같은 parent 3~4개에서 나올 수 있다. 위 예시처럼 중복을 제거하면 parent는 몇 개뿐이다.
    - 예산 압박이 커진다. parent는 크기 때문에 같은 max_chars에 몇 개 못 들어간다. included가 줄고 dropped가 늘어 예산 누락이 생기기 쉽다. 이 문제를 아래의 Context Compression이 다룬다.
    - 리랭커 입력 길이: parent를 리랭커에 넣으면 리랭커의 최대 입력 길이를 넘을 수 있다. child로 리랭킹할지 parent로 할지 정해야 한다.
    - sources: 인용 범위가 parent 단위로 넓어진다. 출처 표시에는 parent의 metadata를 쓴다.

ㄴ) Context Compression
검색된 청크에서 질문과 관련 없는 부분을 빼고 LLM에 넘기는 단계다. 위치는 검색과 리랭킹 뒤, 예산 단계 앞이다.

    retrieved ─▶ [Context Compression] ─▶ 덜어 낸 청크들 ─▶ 예산 ─▶ included

목적은 세 가지다.
    - 같은 예산에 관련 정보를 더 많이 싣는다. 예산 누락이 줄어든다.
    - 잡음을 줄인다. LLM이 관련 없는 내용에 흔들리지 않아 Faithfulness에 도움이 된다.
    - 답변 LLM의 입력 토큰이 줄어든다. 비용과 지연이 줄어든다.

a. 방식

| 방식 | 단위 | 어떻게 | 비용 | 위험 |
|---|---|---|---|---|
| 중복 제거 | 청크 통째 | 서로 너무 비슷한 청크는 하나만 남김 | 쌈 | 거의 없음 |
| 점수 필터 | 청크 통째 | 임베딩 유사도나 리랭커 점수가 기준 미만이면 버림 | 쌈 | 기준을 잘못 잡으면 정답 청크도 버림 |
| LLM 필터 | 청크 통째 | LLM이 청크마다 "관련 있나?" 예/아니오 판정 | 청크 수만큼 LLM 호출 | 비용 |
| LLM 추출 | 청크 안의 문장 | LLM이 관련 있는 문장만 원문 그대로 뽑음 | 비쌈 | 조건·예외 문장을 잘라 뜻이 바뀜 |

b. LLM 추출 프롬프트 예시

    아래 문서에서 질문에 답하는 데 필요한 문장만 원문 그대로 출력하라.
    문장을 바꾸거나 요약하지 마라. 관련 문장이 없으면 NO_OUTPUT이라고만 출력하라.

    질문: 반품 배송비 누가 내나?
    문서: (parent 원문)

요약하지 말고 원문 그대로 뽑게 하는 것이 중요하다. 요약하면 LLM이 표현을 바꾸거나 내용을 덧붙일 수 있다. 그러면 출처 인용이 부정확해지고, RAGAS Faithfulness 판정도 "원문이 아니라 요약본"을 기준으로 하게 되어 왜곡된다.

과한 압축은 Parent-Child가 되찾은 맥락을 다시 잃게 한다.

위 예시에서 추출기가 질문 "반품 배송비 누가 내나?"에 맞춰 "반품 배송비는 회사가 부담한다." 한 문장만 남겼다고 해 보자. "하자가 있는 경우에만"이라는 조건이 다시 사라진다. Parent-Child로 일부러 가져온 맥락을 압축이 다시 잘라 낸 것이다. LLM 추출은 질문과 겉으로 비슷한 문장만 남기고, 조건, 예외, 단서처럼 뜻을 한정하는 문장을 버리는 경향이 있다.

참고) 적용 순서
    - 중복 제거
    - 점수 필터(리랭커 점수 등)
    - 그래도 예산이 부족할 때만 LLM 추출

LLM 추출은 청크마다 LLM을 부르므로, 압축에 쓴 토큰이 줄인 토큰보다 많을 수도 있다. 압축용으로는 작은 모델을 쓰는 경우가 많다.
sources 유지: 압축된 청크도 원래 metadata를 그대로 들고 있어야 [n] 인용과 sources가 맞는다.

ㄷ) 함께보기

| 구분 | Parent-Child | Context Compression |
|---|---|---|
| 방향 | context를 넓힘 | context를 좁힘 |
| 해결하는 문제 | 작은 청크의 맥락 부족 | 큰 청크의 잡음, 예산 압박 |
| 들어가는 위치 | 색인 설계 + 검색 직후 | 검색·리랭킹 후, 예산 전 |
| 주로 개선되는 것 | 답변 정확도(조건·예외 보존) | included 수, Faithfulness, 비용 |
| 과하면 생기는 일 | 예산 누락 | 맥락 손실(Parent-Child를 쓰기 전으로 되돌아감) |

두 기법을 함께 쓰는 흔한 조합은 "작은 child로 찾고, parent로 넓힌 뒤, 중복 제거와 점수 필터로 덜어 낸다"이다. LLM 추출은 그래도 예산이 모자랄 때만 조심스럽게 쓴다.

a. 골든셋으로 확인하기
켜기 전과 후를 같은 골든셋으로 비교한다.
    - included 기준 재현율이 오르면 압축이 예산 누락을 줄인 것이다. 내려가면 압축이 필요한 내용까지 자르고 있는 것이다.
    - Faithfulness와 정답 일치도로 답변 품질을 본다.
    - 답변 LLM 입력 토큰 수와 지연도 함께 기록한다.

9. 검색 단계 전체 흐름

    [색인]  문서 → parent 분할 → child 분할 → child만 임베딩 (parent는 저장소)

    질문
    │ Query Rewrite / Multi-Query      ← 질문을 고치고 넓히기
    ▼
    │ Hybrid Search (child 대상) + RRF  ← 작게, 정밀하게 찾기
    ▼
    │ Parent-Child 확장                 ← 크게 넓히기
    │ Cross-Encoder Re-ranking          ← 정밀하게 다시 고르기
    │ Context Compression               ← 덜어 내기
    ▼
    │ 예산                               → included / dropped
    ▼
    LLM 답변 + sources          [평가: Hit@k · Recall@k · RAGAS]

    - 리랭킹과 Parent 확장 중 무엇을 먼저 하는지는 구현마다 다르다.
    - Query Rewrite는 검색기가 알아들을 수 있게 질문을 고쳐 쓰는 것이고, Multi-Query는 질문을 여러 갈래로 바꿔 말하거나 쪼개서 더 넓게 찾는 것이다. 둘 다 검색을 바꾸는 것이 아니라 검색에 넣는 질문을 바꾼다.

10. Corrective / Agentic RAG

    질문 → 검색 → (리랭킹 · 압축 · 예산) → 생성

이 흐름은 검색 결과가 엉망이어도 그대로 생성으로 넘어간다. 파이프라인 안에 "방금 가져온 게 쓸 만한가?"를 묻는 지점이 없기 때문이다. 앞에서 예산 누락을 조용한 실패라고 했는데, 고정 파이프라인에서는 검색 실패 전체가 조용히 지나간다. 그 결과가 근거 없는 답(환각)이나 엉뚱한 답이다.

두 방식은 "흐름을 누가 정하느냐"의 스펙트럼 위에 있다.

        고정 RAG ─────────────── Corrective RAG ─────────────── Agentic RAG
        코드가 흐름을 전부 정함    정해진 지점에서 검사하고,         LLM이 언제·무엇을·몇 번
                                결과에 따라 정해진 대안으로 분기    검색할지 스스로 정함

ㄱ) Corrective RAG
검색 직후에 평가 단계를 넣고, 평가 결과에 따라 다른 길로 보낸다. 원래 논문(CRAG)의 구조는 이렇다.

    질문 → 검색 → [평가: 가져온 청크가 질문에 맞나?]
                    ├─ 맞음   → 관련 부분만 추려 정제 → 생성
                    ├─ 틀림   → 검색 결과를 버림 → 질문 재작성 → 다른 출처 검색(웹 등) → 생성
                    └─ 애매   → 정제한 내부 결과 + 다른 출처 결과를 합침 → 생성

새로 보이지만 부품은 대부분 이미 배운 것들이다.

| CRAG의 부품 | 앞에서 배운 것 |
|---|---|
| 청크가 질문에 맞는지 평가 | Context Compression의 LLM 필터, 또는 리랭커 점수 컷 |
| 관련 부분만 추려 정제 | Context Compression의 LLM 추출 |
| 질문 재작성 후 다시 검색 | Query Rewrite |

Corrective RAG는 새 부품이라기보다, 이미 있는 부품을 "검사 결과에 따라 분기한다"는 흐름으로 엮은 것이다.

a. 장.단점
    - 장점: 검색 실패가 조용히 지나가지 않는다. 근거가 없을 때 지어내는 대신 다시 찾거나 거절한다.
    - 단점: 청크마다 평가하면 LLM 호출이 그만큼 늘어 지연과 비용이 증가한다. 평가자가 틀리면 멀쩡한 정답 청크를 버린다.
    - 반드시 필요한 것: 최대 재시도 횟수다. 없으면 "재작성 → 검색 실패 → 재작성"이 끝없이 반복될 수 있다.

ㄴ) Agentic RAG
검색을 도구로 주고 LLM이 결정하게 하기
검색을 도구(tool)로 만들어 LLM에게 주고, 에이전트 루프 안에서 돌린다. 모델을 호출하고, 도구 호출이면 하네스가 실행해서 결과를 tool 메시지로 붙이고, 다시 호출하는 루프다.

    사용자 질문
    ▼
    LLM ──(도구 호출: search_policy("전자기기 개봉 후 환불"))──▶ [검색 파이프라인 전체]
    ▲                                                    Hybrid + RRF → Parent-Child
    │                                                    → 리랭킹 → 압축 → 예산
    └──────────────(tool 메시지: 청크 + 출처)───────────────┘
    │  충분하다고 판단하면
    ▼
    답변 + sources

a. LLM이 스스로 정하는 것

    - 검색할지 말지: "고맙다" 같은 말에는 검색하지 않는다.
    - 무엇으로 검색할지: 질의를 LLM이 직접 쓴다. Query Rewrite가 내장된 셈이다.
    - 어느 도구를 쓸지: 정책 문서 검색, 주문 DB 조회 API, 웹 검색 중 무엇을 쓸지 고른다(라우팅).
    - 몇 번 검색할지: 결과를 보고 부족하면 다른 질의로 다시 찾는다.
    - 언제 멈추고 답할지

고정 파이프라인으로는 안 되는 질문: "지난주에 주문한 상품을 개봉했는데 환불되나?"

    1단계  order_lookup(user_id)              → 블루투스 이어폰, 카테고리: 전자기기
    2단계  search_policy("전자기기 개봉 후 환불") → "전자기기는 개봉 시 하자가 있는 경우에만…"
    3단계  답변

두 번째 검색어가 첫 번째 결과에 달려 있다. 첫 검색 전에는 "전자기기"라는 말을 알 수 없으므로, 질문을 미리 고쳐 쓰는 Query Rewrite나 Multi-Query로도 만들 수 없다.
이렇게 단계를 거쳐야 하는 질문(multi-hop)이 Agentic RAG가 진짜 필요한 경우다.

    - Agentic RAG는 지금까지 배운 것을 대체하지 않는다. Hybrid Search, 리랭킹, 압축, 예산이 모두 도구 안쪽으로 들어갈 뿐이다. 도구가 엉뚱한 결과를 돌려주면 에이전트도 좋은 답을 낼 수 없다.
    - docstring이 곧 LLM의 판단 근거다. LLM은 도구 설명을 읽고 언제 그 도구를 쓸지 결정한다. 설명이 모호하면 도구 선택이 흔들린다.

b. 위험과 비용

    - 비용과 지연이 커지고 들쭉날쭉하다. 루프를 돌 때마다 LLM을 호출하고, NOTE에 정리했듯이 매번 전체 대화와 도구 결과를 통째로 다시 넣는다. 그래서 예산 문제가 루프 전체로 번진다. 도구가 돌려주는 결과의 길이를 도구 안에서 max_chars로 묶어 두는 것이 더 중요해진다.
    - 검색을 건너뛰고 자기 지식으로 답해 버린다. 가장 흔한 실패다. "정책 질문은 반드시 search_policy로 확인한 뒤 답하라"처럼 시스템 프롬프트에 명시하거나, 첫 검색을 코드로 강제한다.
    - 끝없이 돈다. 최대 반복 횟수와 종료 조건이 필요하다. NOTE에 "에이전트 루프는 언제 멈출지가 핵심"이라고 정리한 그 부분이다.
    - 모델 능력에 크게 좌우된다. 도구 선택과 인자 작성을 잘하는 모델이 필요하다. 작은 로컬 모델은 이 부분이 불안정한 경우가 많다.
    - 같은 질문이라도 경로가 매번 달라질 수 있다. 그래서 디버깅이 어렵다. 각 단계의 도구 호출과 결과를 추적(콜백, LangSmith 등)해야 한다.

c. 비교

| 구분 | 고정 RAG | Corrective RAG | Agentic RAG |
|---|---|---|---|
| 흐름을 정하는 주체 | 코드 | 코드가 정한 분기 + LLM 판정 | LLM |
| 검색 횟수 | 1번 | 1번 + 실패 시 재시도 | 0~N번(LLM이 결정) |
| 검색 실패 시 | 그대로 생성 | 평가 후 정해진 대안 | 스스로 다시 찾거나 다른 도구 사용 |
| 구현 | LCEL 체인 | LangGraph(조건 분기 + 반복) | 에이전트 루프(tool calling) |
| 비용·지연 | 낮고 일정함 | 중간 | 높고 들쭉날쭉함 |
| 예측 가능성·디버깅 | 쉬움 | 중간 | 어려움 |
| 잘 맞는 질문 | 단순 FAQ | 검색 실패가 잦은 도메인 | 여러 단계, 여러 출처가 필요한 질문 |

에이전트가 항상 더 좋은 것은 아니다. 실무 순서는 대개 이렇다.
    - 고정 파이프라인으로 시작해서 골든셋으로 잰다.
    - Context Recall이 낮은 질문이 특정 유형에 몰려 있고 재검색으로 풀린다면 Corrective를 붙인다.
    - 여러 단계 검색이나 여러 도구(DB, API)가 꼭 필요한 질문이 많을 때 Agentic으로 간다.

d. 평가
    - 최종 답변은 그대로 골든셋과 RAGAS로 잰다.
    - Corrective RAG는 평가자(grader) 자체의 정확도도 잰다. 골든셋에 relevant_ids가 있으므로 "grader가 정답 청크를 버린 비율"을 바로 계산할 수 있다.
    - Agentic RAG는 경로(trajectory)도 본다. 필요한 검색을 건너뛰지 않았는지, 맞는 도구를 골랐는지, 몇 번 돌았는지를 본다. 도구 호출마다 retrieved/included/dropped 로그를 따로 남겨야 어느 단계에서 잘못됐는지 보인다. RAGAS의 에이전트용 지표(도구 호출 정확도 등)가 이 용도다.

    - Corrective RAG는 "가져온 게 쓸 만한지 검사하고, 아니면 정해진 방법으로 고친다"이고, Agentic RAG는 "검색을 도구로 쥐여 주고 언제·무엇을·몇 번 찾을지 LLM이 정한다"이다. 둘 다 지금까지 만든 검색 파이프라인을 버리지 않고, 그 위에 판단과 반복을 얹는 것이다.

11. GraphRAG
청크를 벡터로 저장하는 대신, 문서에서 개체와 관계를 뽑아 그래프로 저장한다.

ㄱ) 벡터 RAG가 약한 두 종류의 질문

① 연결을 따라가야 하는 질문

    문서 1: BX-200 이어폰은 B-12 배터리 셀을 사용한다.
    문서 2: B-12 셀은 한빛셀이 공급한다.
    문서 3: B-12 셀은 과열 위험으로 2026년 9월 리콜되었다.

    질문: "BX-200 이어폰 안전 문제 있나?"

답을 하려면 "BX-200 → B-12 사용 → B-12 리콜"을 이어야 한다. 그런데 문서 3에는 "BX-200"이라는 말이 없다. 벡터 검색은 BX-200이 나오는 문서 1은 찾지만, 문서 3은 놓치기 쉽다. 비슷한 글을 찾을 뿐, 문서 사이의 연결을 알지 못하기 때문이다.

② 전체를 봐야 하는 질문(전역 질문)

    질문: "지난 분기 상담 기록 3000건에서 반복되는 불만 주제는?"

답이 특정 청크에 있지 않고 전체에 흩어져 있다. top-k로 5개, 50개를 가져와도 3000건 중 일부만 본다. 아무리 잘 찾아도 "전체의 경향"은 볼 수 없다.

GraphRAG는 이 두 문제를 색인할 때 미리 풀어 둔다. ①은 그래프의 연결로, ②는 묶음별로 미리 만든 요약으로 푼다.

ㄴ) 지식 그래프의 기본

    - 개체(entity, 노드): 사람, 제품, 부품, 회사, 정책, 사건 같은 "것"이다.
    - 관계(relationship, 엣지): 개체 사이의 연결이다. "사용한다", "공급한다", "리콜되었다" 같은 것이다.
    - 둘을 합친 (주어, 관계, 대상) 세 쌍을 트리플(triple)이라고 부른다.

    (BX-200) ──사용 부품──▶ (B-12 셀) ──공급사──▶ (한빛셀)
                            │
                            리콜
                            ▼
                    (2026-09 과열 리콜)

이렇게 저장해 두면 "BX-200"에서 출발해 선을 따라 두 칸만 가면 리콜 사건에 도착한다. 문서 3에 BX-200이라는 말이 없어도 상관없다.

ㄷ) GraphRAG 색인: 문서를 그래프로 바꾸기
GraphRAG라는 이름을 널리 알린 Microsoft의 방식을 기준으로 보면 색인은 이렇게 진행된다.

    문서 → 청크 → [LLM: 청크마다 개체·관계 추출] → 같은 개체 병합 → 그래프
                                                            │
                                            [커뮤니티 탐지: 촘촘히 연결된 무리 찾기]
                                                            ▼
                                            [LLM: 커뮤니티마다 요약 보고서 작성]

    - 개체·관계 추출: LLM이 청크마다 "어떤 개체가 나오고, 서로 어떤 관계인가"를 뽑는다. 설명도 함께 붙인다.
    - 병합: 여러 청크에서 나온 같은 개체를 하나의 노드로 합친다.
    - 커뮤니티 탐지: 그래프에서 서로 촘촘하게 연결된 개체 무리를 알고리즘으로 찾는다. 예를 들어 "이어폰·배터리·충전·과열" 무리, "환불·배송비·반품 기간" 무리처럼 나뉜다. 큰 무리 안에 작은 무리가 있는 계층 구조로 만든다.
    - 커뮤니티 보고서: LLM이 무리마다 "이 묶음은 무엇에 관한 것이고, 핵심 사실은 무엇인가"를 요약해 둔다.

이렇게 하면 3000건 전체가 수십 개 주제 요약으로 미리 압축된다. 이것이 ② 전역 질문을 푸는 열쇠다.

ㄹ) GraphRAG 검색: Local과 Global

a. Local Search: 특정 개체에 관한 질문에 쓴다(① 유형).

    질문 → 질문 속 개체("BX-200")를 그래프에서 찾기
        → 이웃 개체와 관계(B-12, 리콜 사건) + 그 관계가 나온 원문 청크 + 관련 커뮤니티 보고서
        → context로 조립 → 생성

Parent-Child와 비교하면 이해가 쉽다. 둘 다 "찾은 지점에서 넓히기"다. Parent-Child는 문서 구조를 따라 위로(child → parent) 넓히고, Local Search는 관계를 따라 옆으로(개체 → 이웃 개체) 넓힌다.

b. Global Search: 전체에 관한 질문에 쓴다(② 유형).

    질문 → 커뮤니티 보고서마다 "이 보고서 기준 부분 답 + 중요도 점수" 생성   (map)
        → 중요한 부분 답들을 모아 최종 답 작성                              (reduce)

원문 3000건이 아니라 미리 만든 요약 보고서 수십 개를 훑기 때문에 전체를 볼 수 있다. 나눠서 부분 답을 만들고 합치는 방식을 map-reduce라고 부른다.

ㅁ) 벡터 RAG와 비교

| 구분 | 벡터 RAG | GraphRAG |
|---|---|---|
| 색인 | 청크 임베딩(쌈, 빠름) | 청크마다 LLM 추출 + 그래프 + 요약 보고서(매우 비쌈) |
| 검색 단위 | 비슷한 청크 | 개체, 관계, 커뮤니티 요약 |
| 강한 질문 | 특정 사실 | 관계를 따라가는 질문, 전체 요약 질문 |
| 문서 추가·수정 | 새 청크만 임베딩하면 됨 | 그래프, 커뮤니티, 보고서까지 다시 계산해야 할 수 있음 |
| 출처 추적 | 청크가 곧 원문 | 요약을 거치므로 원문 청크와의 연결을 따로 유지해야 함 |

a. 질문 유형별로 맞는 방식

| 질문 유형 | 예 | 맞는 방식 |
|---|---|---|
| 특정 사실 | "개봉 상품도 환불되나?" | 벡터·하이브리드 RAG(GraphRAG는 과함) |
| 관계 연결 | "BX-200 안전 문제 있나?" | GraphRAG Local, 그래프 질의 |
| 전체 요약·공통 패턴 | "반복되는 불만 주제는?" | GraphRAG Global |
| 숫자 집계 | "지난달 환불 건수는?" | SQL·DB 도구(그래프도 벡터도 아님) |

"전체를 본다"고 해서 GraphRAG가 정확한 개수를 세 주지는 않는다. 요약은 경향을 말해 줄 뿐이다. 숫자는 데이터베이스에 물어야 한다.

ㅂ) 위험과 비용

    - 색인 비용: 모든 청크에 LLM을 호출하고, 개체 요약과 커뮤니티 보고서에도 LLM을 쓴다. 문서가 많을수록 벡터 RAG보다 훨씬 비싸고 오래 걸린다.
    - 추출 오류가 그래프에 굳어진다. LLM이 관계를 잘못 뽑으면 그 오류가 그래프에 저장되고, 이후 모든 질문에 영향을 준다. 벡터 RAG는 원문을 그대로 저장하므로 이런 일이 없다.
    - 같은 개체를 다르게 부른다(개체 병합 문제). "한빛셀", "한빛셀(주)", "Hanbit Cell"이 서로 다른 노드가 되면 연결이 끊긴다. 한국어 문서는 영문·한글 표기가 섞이고 약칭이 많아 특히 신경 써야 한다.
    - 요약을 거친 답의 근거: 앞에서 압축은 "요약하지 말고 원문 그대로 뽑으라"고 했다. Global Search는 LLM이 쓴 요약 보고서를 근거로 답하므로, 원문까지 출처를 되짚기 어렵고 요약 단계의 오류가 답에 섞일 수 있다. 보고서에서 개체로, 개체에서 원문 청크로 이어지는 연결을 유지해야 한다.
    - 평가가 어렵다. 전역 질문에는 "정답 청크"가 따로 없어서 Hit@k나 Recall@k를 쓰기 어렵다. 보통 LLM 판정자로 "얼마나 포괄적인가", "얼마나 다양한 관점을 담았나"를 비교 평가한다.

ㅅ) 참고

    - 벡터 RAG와 함께 쓴다. 벡터 검색으로 진입할 개체나 청크를 찾고, 그래프로 이웃을 넓히는 조합이 흔하다. 그래프를 따라 몇 칸까지 넓힐지는 반드시 제한한다. 이웃의 이웃까지 가면 context가 폭발해 예산 누락이 바로 생긴다.
    - 질문 유형에 따라 경로를 나눈다. 앞의 표처럼 특정 사실은 벡터로, 관계와 전체 요약은 그래프로 보낸다. Agentic RAG라면 그래프 검색을 도구 하나로 만들어 LLM이 고르게 할 수 있다.
    - Agentic RAG와의 관계: 둘 다 multi-hop 질문을 풀지만 시점이 다르다. Agentic RAG는 질문할 때 LLM이 검색을 여러 번 하며 연결을 찾고, GraphRAG는 색인할 때 연결을 미리 만들어 둔다. 색인 비용을 먼저 낼지, 질문마다 비용을 낼지의 차이다.
    - 이미 구조화된 데이터가 있으면 LLM으로 추출하지 않는다. 제품-부품-공급사 관계가 이미 DB에 있다면 거기서 바로 그래프를 만드는 게 싸고 정확하다. LLM 추출은 비정형 텍스트에서만 쓴다.

ㅇ) 주의
"GraphRAG"는 좁게는 위에서 설명한 Microsoft의 방식(커뮤니티 요약 + Local/Global)을 가리키고, 넓게는 그래프를 쓰는 RAG 전반을 가리킨다. 자료를 읽을 때 어느 쪽인지 확인한다.

12. Multimodal RAG · ColPali
"문서가 텍스트만으로 되어 있지 않을 때" 쓰는 RAG다. ColPali는 그중 가장 주목받는 방법이고, 리랭킹 설명 때 참고로만 짚었던 Late Interaction이 핵심 원리다.

ㄱ) 이미지 문서
지금까지는 PyPDFLoader 같은 로더가 PDF에서 텍스트를 잘 뽑아 준다고 가정했다. 실제 문서에는 표, 차트, 그림, 슬라이드, 스캔본이 많다. 텍스트만 뽑으면 이런 일이 생긴다.

        [PDF 원본: 요금표]                         [텍스트 추출 결과]
        ┌────────┬────────┬─────────┐
        │        │ 기본    │ 프리미엄  │   →   "기본 프리미엄 월 9,900 19,900 연 99,000 199,000"
        │ 월     │ 9,900  │ 19,900  │
        │ 연     │ 99,000 │ 199,000 │        어느 숫자가 어느 칸인지 알 수 없음
        └────────┴────────┴─────────┘

| 문서 요소 | 텍스트만 뽑으면 |
|---|---|
| 표 | 행과 열 관계가 깨져 숫자가 뒤섞임 |
| 차트, 그래프 | 이미지 속 숫자와 추세가 아예 사라짐 |
| 스캔본 | 텍스트 레이어가 없어서 아무것도 안 나옴 |
| 레이아웃(다단, 각주, 박스) | 읽는 순서가 꼬이고 본문과 각주가 섞임 |

"2분기 환불 건수가 얼마인가?"의 답이 차트에만 있다면, 텍스트 RAG는 검색을 아무리 잘해도 답할 수 없다. 색인 단계에서 이미 정보가 사라졌기 때문이다.

ㄴ) Multimodal RAG: 세 가지 접근

a. 전부 텍스트로 바꾸기

    PDF → OCR(스캔본) + 레이아웃 파서(표 → Markdown) + VLM 캡션(그림 → 설명 글) → 텍스트 RAG

    - 장점: 지금까지 배운 파이프라인(BM25, Hybrid, 리랭커, RAGAS)을 그대로 쓴다. 답변도 텍스트 LLM으로 된다.
    - 단점: 변환 단계가 많고 느리다. OCR 오류, 표 파싱 오류가 그대로 남는다. 캡션이 놓친 정보는 다시는 찾을 수 없다.

b. 텍스트와 이미지를 같은 벡터 공간에 임베딩하기
텍스트와 이미지를 같은 공간에 넣는 임베딩 모델(CLIP 계열)로, 텍스트 질문을 던져 이미지를 찾는다.
    - 장점: 이미지 자체를 검색할 수 있다.
    - 단점: 사진("빨간 운동화")에는 강하지만, 글자가 빽빽한 문서 페이지에는 약하다.

c. 페이지를 통째로 이미지로 보고 검색하기 = ColPali

    PDF → 페이지마다 이미지로 렌더링 → 이미지를 그대로 임베딩 → 검색 → 찾은 페이지 이미지를 VLM이 읽고 답변

OCR도, 표 파싱도, 캡션도 없다. 사람이 페이지를 눈으로 보듯 모델이 페이지를 본다.

ㄷ) ColPali의 핵심: Late Interaction
ColPali를 이해하려면 리랭킹 때 배운 두 인코더 사이에 세 번째 방식을 놓아야 한다.

| 구분 | Bi-Encoder | Late Interaction (ColBERT, ColPali) | Cross-Encoder |
|---|---|---|---|
| 문서 저장 | 문서당 벡터 1개 | 토큰(패치)마다 벡터 하나씩, 수백~천 개 | 저장 없음 |
| 미리 계산 | 가능 | 가능 | 불가능 |
| 비교의 세밀함 | 낮음(통째로 비교) | 높음(조각 단위로 비교) | 가장 높음 |
| 저장 공간 | 작음 | 큼 | 없음 |
| 주 용도 | 1차 검색 | 1차 검색, 리랭킹 | 리랭킹 |

Late Interaction은 두 방식의 장점을 섞은 것이다.
    - Bi-Encoder처럼 문서 쪽을 미리 계산해 저장한다. 다만 벡터 하나로 누르지 않고 조각마다 벡터를 하나씩 남긴다.
    - 질문이 들어오면 Cross-Encoder처럼 조각 단위로 맞대어 본다. 그래서 "늦게(late) 상호작용한다"고 부른다.

맞대어 보는 방법(MaxSim): 질문 토큰마다 가장 잘 맞는 페이지 조각 하나를 찾고, 그 유사도를 모두 더한다.

    질문: "2분기 환불 건수"

    질문 토큰       가장 잘 맞는 페이지 패치            유사도
    "2분기"    →   차트 x축의 "Q2" 라벨 부분           0.81
    "환불"     →   차트 제목 "환불 추이" 부분          0.88
    "건수"     →   y축 "건" 단위 라벨 부분             0.74
                                            합계 = 2.43  ← 이 페이지의 점수

세 토큰이 모두 잘 맞는 조각을 가진 페이지(환불 차트가 있는 페이지)가 높은 점수를 받는다. 본문에 "환불"이라는 말만 한 번 나오는 페이지는 "2분기"와 "건수"에 맞는 조각이 없어 점수가 낮다.

ㄹ) ColPali 파이프라인
ColPali는 VLM(이미지를 읽는 언어 모델)을 검색용 임베딩 모델로 개조한 것이다. 페이지 이미지를 작은 정사각형 조각(패치)으로 나누고, 패치마다 벡터를 하나씩 만든다.

    [색인]
    PDF → 페이지 이미지 → ColPali → 페이지당 패치 벡터 약 1000개 → multi-vector를 지원하는 벡터 DB에 저장

    [질문]
    질문 텍스트 → 토큰마다 벡터 → 페이지마다 MaxSim 점수 → 상위 k개 페이지 이미지
            → VLM에 "질문 + 페이지 이미지" 입력 → 답변 + 출처(문서명, 페이지)

ColPali는 검색만 한다. 찾아 오는 것이 페이지 이미지이므로, 답변 단계에도 이미지를 읽을 수 있는 VLM이 필요하다. 텍스트 전용 LLM으로는 답할 수 없다.

ㅁ) 장점과 비용

a. 장점
    - 색인이 단순하다. OCR, 레이아웃 파싱, 캡션 생성이 없다. 페이지를 이미지로 렌더링해서 넣기만 하면 된다.
    - 정보 손실이 적다. 표의 칸 구조, 차트 모양, 굵은 글씨, 박스 같은 시각 정보가 그대로 남는다.
    - 스캔본도 그대로 다룬다.
    - 어디가 맞았는지 보여 줄 수 있다. 패치별 점수를 페이지 위에 겹치면, 질문이 페이지의 어느 영역과 맞았는지 히트맵으로 볼 수 있다.

b. 비용과 위험
    - 저장 공간: 페이지당 벡터가 1개가 아니라 약 1000개다. 문서가 많으면 저장 공간이 수십~100여 배로 커진다. 그래서 벡터를 줄이거나 압축하는 기법이 따로 연구되고 있다.
    - 검색 단위가 페이지다. 청크보다 훨씬 크다. 한 페이지에 주제가 여러 개 섞여 있으면 Parent-Child에서 말한 "큰 청크의 잡음" 문제가 그대로 생긴다.
    - 예산은 반드시 토큰으로 센다. VLM 입력에서 이미지 한 장은 수백~수천 토큰을 차지한다. 페이지 5장이면 그것만으로 컨텍스트 창의 상당 부분을 쓴다. 이미지에는 글자 수가 없으니 max_chars는 의미가 없고, 토큰 예산으로 "몇 장까지 넣을지"를 정해야 한다.
    - 답변 품질이 VLM에 달려 있다. VLM이 페이지 속 작은 글씨나 한국어를 잘 못 읽으면, 검색이 맞아도 답이 틀린다. VLM은 텍스트 LLM보다 비싸고 느린 편이다.
    - 정확한 문자열 매칭에는 약할 수 있다. 제품 코드나 에러 코드처럼 글자가 정확히 일치해야 하는 검색은 여전히 텍스트 인덱스(BM25)가 강하다.
    - 한국어 성능은 모델마다 차이가 크다. 원조 ColPali는 주로 영어 문서로 평가되었다. 다국어 VLM을 바탕으로 만든 후속 모델(ColQwen 계열 등)이 있으니, 한국어 문서라면 골든셋으로 직접 비교해야 한다.

c. 기타
    - RRF: 텍스트 인덱스와 페이지 이미지 인덱스를 함께 두는 경우가 많다. 두 검색의 점수는 척도가 전혀 다르므로, 순위만으로 합치는 RRF가 딱 맞다.
    - Parent-Child와 같은 아이디어: a와 c를 섞어 "캡션이나 표를 텍스트로 바꾼 것으로 검색하고, 답변할 때는 원본 페이지 이미지를 VLM에 넘기는" 방식도 흔하다. 검색에 좋은 표현과 답변에 좋은 표현을 분리한다는 점에서 Parent-Child와 같은 발상이다.
    - 리랭킹: Late Interaction은 1차 검색 뒤에 리랭커로도 쓸 수 있다.
    - 평가: 골든셋의 relevant_ids를 페이지 ID(문서명 + 페이지 번호)로 적으면 Hit@k, Recall@k를 그대로 쓸 수 있다. 출처도 페이지 단위라서 인용이 단순하다.
    - 로컬 실행: ColPali급 임베딩 모델은 수십억 파라미터 규모라 16GB GPU에서도 돌아간다. 답변용 VLM도 7B급이면 로컬에서 시험해 볼 수 있다.

ㅂ) 사용처

| 문서 특성 | 추천 |
|---|---|
| 텍스트 위주(정책, FAQ, 매뉴얼 본문) | 텍스트 RAG를 그대로 |
| 표가 많지만 깔끔한 디지털 PDF | 레이아웃 파서로 표를 Markdown으로 바꾼 뒤 텍스트 RAG |
| 차트, 도표, 슬라이드, 스캔본, 복잡한 레이아웃 | ColPali류 페이지 이미지 검색 + VLM |
| 여러 종류가 섞여 있음 | 텍스트 인덱스와 이미지 인덱스를 함께 두고 RRF로 합치기 |

1. LCEL pipe 와 Runnable 인터페이스
Runnable은 LangChain의 모든 구성요소(프롬프트, 모델, 파서, 검색기 등)가 따르는 공통 인터페이스이고, LCEL pipe(|)는 이 Runnable들을 순서대로 이어 붙여 새로운 Runnable을 만드는 문법이다.

ㄱ) Runnable 인터페이스: "모두가 같은 모양의 플러그"
LangChain에는 부품이 많다. 이들이 같은 방식으로 호출되도록 약속한 것이 Runnable이다.

| 메서드 | 의미 |
|---|---|
| invoke(input) | 입력 1개 → 출력 1개 (기본) |
| batch([inputs]) | 여러 입력을 한 번에 (내부적으로 병렬 처리) |
| stream(input) | 출력을 조각(chunk) 단위로 흘려보냄 |
| ainvoke / abatch / astream | 위의 비동기(async) 버전 |

핵심은 입력 → 출력 변환기라는 점이다. 부품마다 입력과 출력의 타입만 다르다.

| 부품 | 입력 | 출력 |
|---|---|---|
| ChatPromptTemplate | dict ({"topic": "..."}) | 메시지 목록 (PromptValue) |
| ChatModel | 메시지 목록 | AIMessage |
| StrOutputParser | AIMessage | str |

모두 invoke를 가지고 있으므로, 앞 부품의 출력 타입이 뒤 부품의 입력 타입과 맞기만 하면 이어 붙일 수 있다.

ㄴ) LCEL pipe |: 이어 붙이기

    chain = prompt | model | parser
    chain.invoke({"topic": "고양이"})

이는 아래 코드와 같은 의미이다.

    x = prompt.invoke({"topic": "고양이"})
    x = model.invoke(x)
    x = parser.invoke(x)

    - 동작 원리: Runnable이 파이썬의 __or__ 연산자를 재정의해 두었기 때문에, a | b를 쓰면 RunnableSequence(a, b)라는 새로운 Runnable이 만들어진다.
    - 그래서 체인 자체도 Runnable이다. chain.invoke, chain.batch, chain.stream을 모두 별도 구현 없이 바로 쓸 수 있고, 이 체인을 다른 체인 안에 또 끼워 넣을 수도 있다(합성 가능성, composability).
    - 비유하면 유닉스 셸의 cat file | grep x | sort와 같다. 각 단계가 "입력 받아서 출력 내보내기"라는 같은 규칙을 지키기 때문에 자유롭게 연결된다.

ㄷ) 자주 함께 쓰는 Runnable 부품

| 부품 | 역할 |
|---|---|
| RunnableLambda(f) | 일반 파이썬 함수를 Runnable로 감쌈 (파이프 안에서는 함수만 써도 자동으로 변환됨) |
| RunnableParallel({...}) | 같은 입력을 여러 갈래로 동시에 보내고 결과를 dict로 모음. 파이프 안에서는 dict만 써도 자동으로 변환됨 |
| RunnablePassthrough() | 입력을 그대로 통과시킴 (RAG에서 원래 질문을 보존할 때 사용) |

대표적인 RAG 패턴

    chain = (
        {"context": retriever, "question": RunnablePassthrough()}   # 병렬: 검색 + 질문 보존
        | prompt
        | model
        | StrOutputParser()
    )
    chain.invoke("LCEL이 뭐야?")

ㄹ) 설계 이유
    - 통일성: 어떤 부품이든 호출 방법이 같다.
    - 공짜 기능: 체인만 조립하면 스트리밍, 배치, 비동기 처리가 자동으로 지원된다. 특히 stream은 파서까지 조각 단위로 흘러가서, 채팅 UI에 토큰이 하나씩 표시되는 동작을 쉽게 만들 수 있다.
    - 관찰 가능성: 체인 구조가 명확하게 드러나므로 LangSmith 같은 도구로 단계별 추적(tracing)이 쉽다.

ㅁ) 한계 (참고)
LCEL은 한 방향으로 흐르는 파이프라인(DAG)에 잘 맞는다. 반면 반복, 조건 분기가 많은 에이전트 루프나 상태 관리가 필요하면 표현이 금방 복잡해진다. 이런 경우에는 보통 LangGraph(노드와 엣지로 이루어진 상태 그래프)로 넘어간다. 지금은 "LCEL은 직선형 조립용"이라는 정도만 알아두면 충분하다.

2. RunnableSequence와 RunnableParallel
    - RunnableSequence: Runnable을 직렬로 연결한다. 앞 단계의 출력이 뒤 단계의 입력이 된다.
    - RunnableParallel: 같은 입력을 여러 Runnable에 동시에 보내고, 결과를 dict로 모은다.

둘 다 그 자체로 Runnable이므로 서로 안에 넣어 자유롭게 조합할 수 있다.

ㄱ) RunnableSequence: 직렬 연결

    입력 → [A] → [B] → [C] → 출력

    chain = prompt | model | parser

    # 위 코드는 아래와 같음
    chain = RunnableSequence(prompt, model, parser)

a. 특징
    - | 연산자를 쓰면 자동으로 만들어진다. 직접 RunnableSequence(...)로 만드는 경우는 드물다.
    - 타입 연결 조건: A의 출력 타입이 B의 입력 타입과 맞아야 한다. 맞지 않으면 실행할 때 에러가 난다.
    - 스트리밍: 각 단계가 조각(chunk)을 받아 처리할 수 있으면 조각이 파이프를 따라 계속 흘러간다. 그래서 prompt | model | StrOutputParser()로 만든 체인을 stream()하면 토큰이 하나씩 출력된다.
    - 배치: chain.batch([...])를 호출하면 각 단계의 batch가 차례로 호출된다.

내부 구조 개념: first, middle(리스트), last 단계를 가지며, invoke 때 순서대로 호출하는 단순한 반복문이다.

ㄴ) RunnableParallel: 병렬 분기

            ┌→ [A] → "a": ...
    입력 ─────┼→ [B] → "b": ...     → {"a": ..., "b": ..., "c": ...}
            └→ [C] → "c": ...

    from langchain_core.runnables import RunnableParallel

    p = RunnableParallel(
        summary=summary_chain,
        keywords=keyword_chain,
    )
    p.invoke({"text": "..."})
    # → {"summary": "...", "keywords": "..."}

a. 특징
    - 모든 분기가 똑같은 입력을 받는다.
    - 동기 실행이면 스레드 풀로, 비동기 실행이면 asyncio.gather로 동시에 실행된다. 그래서 LLM을 여러 번 호출할 때 걸리는 시간이 "합"이 아니라 "가장 느린 분기의 시간" 정도로 줄어든다.
    - 출력은 항상 dict이고, 키 이름은 사용자가 정한다.

dict 자동 변환: 파이프 안에 dict를 쓰면 자동으로 RunnableParallel로 바뀐다.

    chain = {"context": retriever, "question": RunnablePassthrough()} | prompt
    #        └──────────── 이 dict가 RunnableParallel이 됨 ────────────┘

ㄷ) 둘을 조합하는 전형적인 패턴 (RAG)

    chain = (
        {"context": retriever | format_docs, "question": RunnablePassthrough()}
        | prompt
        | model
        | StrOutputParser()
    )

a. 데이터 흐름

| 단계 | 종류 | 입력 | 출력 |
|---|---|---|---|
| 1 | Parallel | "LCEL이 뭐야?" | {"context": "문서들...", "question": "LCEL이 뭐야?"} |
| 1-a | (분기 안의 Sequence) | 질문 | 검색 → 문자열로 정리된 문서 |
| 1-b | Passthrough | 질문 | 질문 그대로 |
| 2 | prompt | dict | 메시지 목록 |
| 3 | model | 메시지 | AIMessage |
| 4 | parser | AIMessage | str |

    - Parallel은 "dict를 만드는 장치"이다. 프롬프트 템플릿은 dict를 입력으로 받기 때문에, Parallel이 프롬프트 바로 앞에 자주 온다.
    - 분기 안에 Sequence가 들어갈 수 있다 (retriever | format_docs). 반대로 Sequence 안에 Parallel이 들어가는 것도 가능하다. 둘 다 Runnable이라서 서로 중첩할 수 있다.

ㄹ) 비교 정리

| 구분 | RunnableSequence | RunnableParallel |
|---|---|---|
| 연결 방식 | 직렬 (A → B → C) | 병렬 분기 (A, B, C 동시에) |
| 각 단계가 받는 입력 | 이전 단계의 출력 | 모두 같은 원본 입력 |
| 최종 출력 | 마지막 단계의 출력 | {키: 각 분기의 출력} dict |
| 만드는 방법 | a \| b | dict 리터럴 또는 RunnableParallel(...) |
| 주 용도 | 처리 파이프라인 | 여러 정보를 모아 프롬프트 입력 만들기, 동시 호출 |

ㅁ) 핵심: "조립한 결과물도 다시 부품이 된다"
Sequence나 Parallel로 여러 Runnable을 묶으면, 그 결과물도 똑같이 invoke, batch, stream을 가진 Runnable이 된다. 그래서 바깥에서 보면 원래 부품인지, 여러 부품을 묶은 덩어리인지 구분할 필요가 없다. 둘 다 "입력을 받아 출력을 내는 상자"일 뿐이다.

레고로 비유하면, 블록 여러 개를 붙여 만든 덩어리도 아래에 똑같은 돌기와 구멍이 있어서 다른 블록에 그대로 끼울 수 있는 것과 같다.

ㅂ) 단계별로 보기
a. 1단계: 작은 부품으로 Sequence 만들기

    summarize = summary_prompt | model | StrOutputParser()   # Sequence

summarize는 이제 "텍스트 dict를 받아 요약 문자열을 내는 Runnable" 하나다.

b. 2단계: 그 Sequence를 Parallel의 분기로 넣기

    analyze = RunnableParallel(
        summary=summarize,                                    # Sequence가 분기 하나가 됨
        keywords=keyword_prompt | model | StrOutputParser(),  # 여기도 Sequence
    )

Parallel 입장에서는 분기로 들어온 것이 모델 하나이든 세 단계짜리 체인이든 상관없다. 그냥 invoke를 호출할 뿐이다.

c. 3단계: 그 Parallel을 다시 Sequence의 한 단계로 넣기

    report = analyze | report_prompt | model | StrOutputParser()

analyze가 {"summary": ..., "keywords": ...} dict를 내면, report_prompt가 그것을 받아 최종 보고서를 만든다.

d. 구조도

    report (Sequence)
    ├── analyze (Parallel)
    │   ├── summary  → (Sequence) summary_prompt | model | parser
    │   └── keywords → (Sequence) keyword_prompt | model | parser
    ├── report_prompt
    ├── model
    └── parser

e. 장점
    - 재사용: summarize를 한 번 만들어 두면 다른 체인 어디에든 부품으로 다시 쓸 수 있다.
    - 기능이 자동으로 따라옴: 가장 바깥의 report.stream()이나 report.batch()를 호출하면 안쪽 모든 단계에 알아서 전달된다. 중첩된 곳마다 따로 구현할 필요가 없다.
    - 이해하기 쉬움: 큰 체인을 "요약 + 키워드 분석 → 보고서"처럼 작은 덩어리 단위로 나눠서 생각하고 테스트할 수 있다. 예를 들어 summarize.invoke(...)만 따로 실행해 볼 수 있다.

3. RunnablePassthrough/RunnableLambda/assign

| 도구 | 한 줄 정의 | 비유 |
|---|---|---|
| RunnablePassthrough | 입력을 아무것도 바꾸지 않고 그대로 내보냄 | 그냥 뚫린 파이프 |
| RunnableLambda | 일반 파이썬 함수를 Runnable로 감쌈 | 직접 만든 부품에 규격 어댑터를 붙이기 |
| .assign() | 입력 dict는 그대로 두고 새 키를 추가함 | 기존 서류에 첨부 문서를 덧붙이기 |

세 가지 모두 체인 안에서 데이터의 모양을 다듬는 보조 부품이다.

ㄱ) RunnablePassthrough: 입력을 그대로 통과

    from langchain_core.runnables import RunnablePassthrough
    RunnablePassthrough().invoke("안녕")   # → "안녕"

혼자 쓰면 의미가 없어 보이지만, Parallel 안에서 원래 입력을 보존할 때 필요하다.

    chain = {"context": retriever, "question": RunnablePassthrough()} | prompt

| 분기 | 입력 | 출력 |
|---|---|---|
| context | "LCEL이 뭐야?" | 검색된 문서 |
| question | "LCEL이 뭐야?" | "LCEL이 뭐야?" (그대로) |

결과: {"context": 문서, "question": "LCEL이 뭐야?"}

Parallel은 모든 분기에 같은 입력을 주고 각 분기의 출력만 모은다. 그래서 원래 질문을 프롬프트까지 전달하려면 "아무것도 안 하는 분기"가 하나 필요한데, 그 역할을 Passthrough가 한다.

ㄴ) RunnableLambda: 파이썬 함수를 체인에 끼우기
LangChain이 제공하지 않는 처리(문자열 정리, 형식 변환 등)를 직접 넣고 싶을 때 쓴다.

    from langchain_core.runnables import RunnableLambda

    def format_docs(docs):
        return "\n\n".join(d.page_content for d in docs)

    chain = retriever | RunnableLambda(format_docs) | ...

자동 변환: 파이프 안에서는 함수만 써도 자동으로 RunnableLambda가 된다.

    chain = retriever | format_docs | ...    # 위와 같은 의미

a. 주의할 점
함수는 인자를 하나만 받아야 한다. 여러 값이 필요하면 dict 하나로 받아서 꺼내 쓴다.

    def combine(x):          # x = {"a": ..., "b": ...}
        return x["a"] + x["b"]

함수로 감싸면 invoke, batch, ainvoke가 생긴다. 다만 일반 함수는 결과를 한 번에 반환하므로, 이 단계에서는 스트리밍이 조각 단위로 흐르지 않고 한 번에 전달된다.

ㄷ) .assign(): 기존 dict에 키 추가
RunnablePassthrough.assign(...) 형태로 가장 많이 쓴다.

    chain = RunnablePassthrough.assign(
        context=lambda x: retriever.invoke(x["question"])
    )

    chain.invoke({"question": "LCEL이 뭐야?", "user": "민수"})
    # → {"question": "LCEL이 뭐야?", "user": "민수", "context": [문서들]}

a. Parallel과의 차이

| 구분 | RunnableParallel | .assign() |
|---|---|---|
| 출력 | 지정한 키만 담긴 새 dict | 원래 dict + 새 키 |
| 기존 키 | 직접 Passthrough로 넘기지 않으면 사라짐 | 자동으로 유지됨 |

.assign()은 "Passthrough + Parallel을 합친 편의 기능"이라고 보면 된다. 입력 dict가 단계를 지날수록 키가 하나씩 쌓여 가는 체인을 만들 때 특히 편하다.

    chain = (
        RunnablePassthrough.assign(context=get_context)        # + context
        | RunnablePassthrough.assign(answer=answer_chain)      # + answer
    )
    # 최종: {"question", "context", "answer"} 모두 남아 있음

마지막에 답변과 함께 근거 문서도 반환할 수 있다. RAG에서 출처를 표시할 때 자주 쓰는 패턴이다.

b. 세 가지를 함께 쓰는 예

    chain = (
        RunnablePassthrough.assign(
            context=itemgetter("question") | retriever | format_docs   # Lambda 자동 변환
        )
        | prompt
        | model
        | StrOutputParser()
    )

| 단계 | 하는 일 | 데이터 |
|---|---|---|
| assign | 질문을 유지한 채 context 추가 | {"question"} → {"question", "context"} |
| format_docs (Lambda) | 문서 리스트를 문자열로 정리 | [Doc, Doc] → "..." |
| prompt → model → parser | 답변 생성 | dict → str |

    - Passthrough는 보존, Lambda는 사용자 정의 변환, assign은 보존하면서 추가하는 도구이다.

4. Pydantic schema와 structured output
    - Pydantic 스키마: "데이터가 어떤 모양이어야 하는지"를 파이썬 클래스로 적은 설계도이다. 어떤 필드가 있고, 각 필드의 타입이 무엇인지 정한다.
    - Structured output(구조화된 출력): LLM이 자유로운 문장 대신 그 설계도에 맞는 데이터를 내놓도록 만드는 기법이다.

둘을 합치면 "LLM 답변을 바로 파이썬 객체로 받아 코드에서 쓸 수 있게" 된다.

ㄱ) 사용하는 이유
LLM은 기본적으로 글을 내놓는다.

    "이 리뷰는 긍정적이고, 점수는 대략 8점 정도로 보입니다."

사람이 읽기에는 좋지만, 프로그램이 점수 > 7인지 판단하려면 이 문장에서 숫자를 직접 파싱해야 한다. 그런데 모델이 매번 표현을 바꾸기 때문에("8/10", "여덟 점", "약 8점") 파싱이 쉽게 깨진다.

원하는 것은 이런 결과이다.

    Review(sentiment="positive", score=8)

ㄴ) Pydantic 스키마: 데이터의 설계도

    from pydantic import BaseModel, Field
    from typing import Literal

    class Review(BaseModel):
        sentiment: Literal["positive", "negative", "neutral"] = Field(description="리뷰의 감정")
        score: int = Field(description="1~10 사이 평점", ge=1, le=10)
        keywords: list[str] = Field(description="핵심 키워드 3개 이내")

Pydantic이 해 주는 일은 두 가지다.

| 역할 | 의미 |
|---|---|
| 구조 정의 | 필드 이름, 타입, 설명을 한곳에 적음 |
| 검증(validation) | 들어온 데이터가 설계도와 맞는지 검사. score="많이"처럼 틀리면 에러를 냄. "8" 같은 문자열은 가능하면 8로 변환해 줌 |

그리고 이 클래스는 JSON 스키마로 바꿀 수 있다. LLM에게 "이 모양으로 답해"라고 알려줄 때 이 JSON 스키마가 전달된다.

ㄷ) Structured output: 모델이 설계도대로 답하게 하기
LangChain에서는 한 줄이면 된다.

    structured_model = model.with_structured_output(Review)

    result = structured_model.invoke("배송은 느렸지만 제품은 정말 좋아요!")
    # → Review(sentiment='positive', score=8, keywords=['배송', '제품 품질'])

    result.score   # 8  (int)

with_structured_output이 반환하는 것도 Runnable이므로 체인에 그대로 넣을 수 있다.

    chain = prompt | model.with_structured_output(Review)

ㄹ) 내부 실행
모델이 설계도를 따르게 만드는 방법은 크게 세 가지이고, with_structured_output이 모델에 맞는 방법을 골라 준다.

| 방식 | 원리 | 신뢰도 |
|---|---|---|
| 도구 호출(tool calling) | 스키마를 "도구"처럼 등록하고, 모델이 그 도구의 인자를 채우게 함 | 높음 (가장 흔한 방식) |
| JSON 모드 / 네이티브 스키마 | API가 출력 자체를 JSON 스키마에 맞도록 강제함 | 매우 높음 |
| 프롬프트 지시 + 파싱 | "이 JSON 형식으로 답해"라고 글로 지시하고 결과를 파싱 (PydanticOutputParser) | 낮음 (모델이 어길 수 있음) |

도구 호출은 원래 "모델이 함수 인자를 구조화된 형태로 채워서 내놓는" 기능이므로, structured output은 그 기능을 "데이터 추출"용으로 재활용한 것이라고 볼 수 있다.

모든 방식에서 마지막에 Pydantic이 결과를 검증해 최종 객체로 만들어 준다.

ㅁ) 알아두면 좋은 점
    - Field(description=...)도 프롬프트이다. 이 설명이 스키마에 담겨 모델에게 전달되므로, 설명을 명확하게 쓸수록 결과가 정확해진다.
    - 검증 실패는 일어날 수 있다. 특히 작은 로컬 모델은 필드를 빠뜨리거나 타입을 틀리기도 한다. 실무에서는 재시도하거나, include_raw=True 옵션으로 원본 응답과 에러를 함께 받아서 처리한다.
    - 스키마는 단순할수록 안정적이다. 중첩이 깊거나 필드가 많으면 실패 확률이 올라간다.

ㅂ) 정리

| 구분 | 역할 |
|---|---|
| Pydantic 스키마 | 무엇을 받을지 정의하고 검증 |
| Structured output | 모델이 그 형태로 답하도록 강제 |
| 결과 | 자유 텍스트 → 바로 쓸 수 있는 파이썬 객체 |

에이전트 개발에서는 분류, 정보 추출, 라우팅(다음에 어떤 단계로 갈지 결정) 등 LLM 출력을 코드가 받아서 판단해야 하는 모든 곳에 이 조합이 쓰인다.

5. with_structured_output 과 PydanticOutputParser 차이
둘 다 LLM 답변을 Pydantic 객체로 받는 도구이다. 차이는 모델이 형식을 지키게 만드는 방법에 있다.
    - PydanticOutputParser: 프롬프트에 "이 형식으로 답해"라고 글로 부탁한 뒤, 모델이 쓴 글을 나중에 파싱한다.
    - with_structured_output: 모델 API의 도구 호출이나 JSON 모드 기능을 사용해 처음부터 형식에 맞는 답을 받는다.

비유하면, Parser는 "양식대로 써 주세요"라고 말로 부탁하는 것이고, with_structured_output은 빈칸이 정해진 서식지를 건네주는 것이다.

ㄱ) PydanticOutputParser: 부탁하고 파싱하기

    from langchain_core.output_parsers import PydanticOutputParser

    parser = PydanticOutputParser(pydantic_object=Review)

    prompt = ChatPromptTemplate.from_template(
        "리뷰를 분석하세요.\n{format_instructions}\n리뷰: {review}"
    ).partial(format_instructions=parser.get_format_instructions())

    chain = prompt | model | parser

| 단계 | 하는 일 |
|---|---|
| 1 | get_format_instructions()가 "다음 JSON 스키마에 맞춰 답하세요: {...}" 같은 지시문을 만듦 |
| 2 | 그 지시문이 프롬프트에 글로 들어감 |
| 3 | 모델은 일반 텍스트로 답함 (JSON을 잘 쓰기를 기대할 뿐) |
| 4 | parser가 텍스트에서 JSON을 찾아 Pydantic으로 검증 |

약점: 모델이 지시를 어길 수 있다. "물론이죠! 결과는 다음과 같습니다: json ..."처럼 앞뒤에 말을 붙이거나, 따옴표를 빠뜨리거나, 필드를 빼먹으면 파싱이 실패한다.

ㄴ) with_structured_output: 모델 기능으로 강제하기

    chain = prompt | model.with_structured_output(Review)

| 단계 | 하는 일 |
|---|---|
| 1 | 스키마를 API 요청의 별도 항목(도구 정의나 JSON 스키마 설정)으로 전달 |
| 2 | 모델은 글이 아니라 구조화된 인자/JSON으로 답함 (모델이 그렇게 학습되었거나, API가 출력을 제약함) |
| 3 | 결과를 Pydantic으로 검증 |

프롬프트에 형식 지시문을 넣을 필요가 없고, 파서도 따로 붙이지 않는다.

ㄷ) 비교 정리

| 구분 | PydanticOutputParser | with_structured_output |
|---|---|---|
| 형식 전달 방법 | 프롬프트 안의 글 | API의 도구/JSON 스키마 기능 |
| 모델 요구 조건 | 아무 모델이나 가능 | 도구 호출이나 JSON 모드를 지원하는 모델만 |
| 신뢰도 | 낮음 (모델이 어길 수 있음) | 높음 |
| 코드 | 지시문 삽입 + 파서 연결 | 한 줄 |
| 체인에서 위치 | model \| parser (모델 뒤) | model.with_structured_output(...) (모델 자체를 감쌈) |
| 스트리밍 | 부분 JSON 파싱으로 가능 | 모델과 방식에 따라 다름 |

    - 기본은 with_structured_output이다. 요즘 주요 모델과 Ollama의 많은 모델이 도구 호출이나 JSON 스키마 출력을 지원하므로 더 안정적이고 간단하다.
    - PydanticOutputParser는 도구 호출이나 JSON 모드를 지원하지 않는 모델을 써야 할 때 대안으로 쓴다. LangChain에 structured output 기능이 나오기 전의 방식이라 예전 튜토리얼에서 자주 보인다.

6. LangChain 에서 Document
Document는 LangChain에서 "텍스트 한 조각 + 그 조각에 대한 정보"를 담는 기본 데이터 단위이다. RAG 파이프라인의 모든 단계(불러오기 → 자르기 → 저장 → 검색)가 이 형태로 데이터를 주고받는다.

ㄱ) 구조

    from langchain_core.documents import Document

    doc = Document(
        page_content="LCEL은 Runnable을 | 로 연결하는 문법이다.",
        metadata={"source": "TIL/260930.md", "page": 1, "date": "2026-09-30"},
    )

| 필드 | 의미 | 비유 |
|---|---|---|
| page_content | 실제 본문 텍스트 (문자열) | 책의 한 페이지 내용 |
| metadata | 본문에 대한 부가 정보 (dict, 키는 자유롭게) | 페이지 번호, 책 제목, 출판일이 적힌 라벨 |
| id (선택) | 문서 고유 식별자 | 도서관 청구기호 |

모델이 읽는 것은 page_content이고, metadata는 주로 프로그램이 활용하는 정보이다.

ㄴ) RAG 파이프라인에서의 흐름

    파일/웹/DB
    │  Document Loader
    ▼
    [Document, Document, ...]          ← 파일 하나, 또는 페이지 하나 = Document 하나
    │  Text Splitter
    ▼
    [Document, Document, Document, ...] ← 작은 조각(chunk)들, metadata는 물려받음
    │  Embedding + Vector Store
    ▼
    벡터 DB에 저장
    │  Retriever.invoke("질문")
    ▼
    [관련 Document 몇 개]               ← 검색 결과도 Document 리스트
    │  format_docs
    ▼
    프롬프트의 {context}에 들어갈 문자열

| 단계 | 입력 | 출력 |
|---|---|---|
| Loader (PyPDFLoader, TextLoader 등) | 파일 경로, URL | list[Document] |
| Text Splitter | list[Document] | 더 잘게 나뉜 list[Document] |
| Vector Store | list[Document] | 저장 (본문은 임베딩, metadata는 함께 보관) |
| Retriever | 질문 문자열 | list[Document] |

모든 부품이 같은 형태(Document)를 주고받으므로 Loader나 벡터 DB를 바꿔도 나머지 코드는 그대로 쓸 수 있다. 앞에서 배운 Runnable의 "공통 인터페이스" 아이디어가 데이터 쪽에도 적용된 것이라고 보면 된다.

ㄷ) metadata가 중요한 이유
    - 출처 표시: 답변과 함께 "이 내용은 TIL/260930.md에서 가져왔습니다"라고 보여줄 수 있다.
    - 검색 필터링: "2026년 9월 문서 중에서만 검색", "source가 LLM 노트인 것만"처럼 조건을 걸 수 있다. (벡터 DB가 지원하는 경우)
    - 자동 상속: Text Splitter가 문서를 자를 때 원본의 metadata가 모든 조각에 복사된다. 그래서 잘게 나뉜 조각도 어디서 왔는지 알 수 있다.

ㄹ) format_docs와의 연결
Retriever는 list[Document]를 반환하지만, 프롬프트의 {context}에는 문자열이 필요하다. 그래서 중간에 변환 함수를 둔다.

    def format_docs(docs):
        return "\n\n".join(d.page_content for d in docs)

출처도 모델에게 보여주고 싶다면 metadata를 함께 넣을 수 있다.

    def format_docs(docs):
        return "\n\n".join(f"[출처: {d.metadata['source']}]\n{d.page_content}" for d in docs)

ㅁ) 정리

| 구분 | 설명 |
|---|---|
| 정체 | 텍스트(page_content) + 부가 정보(metadata)를 묶은 객체 |
| 역할 | RAG 전 단계가 주고받는 공통 데이터 형식 |
| 핵심 포인트 | 모델은 본문을 읽고, 프로그램은 metadata로 출처 표시와 필터링을 함 |

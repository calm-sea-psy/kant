1. 프리토큰(FreeToken)
[논문](https://arxiv.org/pdf/2608.16157)
[코드](https://github.com/FlashML-org/FreeToken)

개인용 PC(8GB 노트북 GPU ~ 워크스테이션 GPU 1장)를 GPU·CPU·호스트 메모리·인터커넥트를 묶은 하나의 탄력적 추론 플랫폼으로 보고, 프론티어급 대형 MoE 모델을 실사용 속도로 서빙하는 엔진.

ㄱ) 문제의식

a. 오픈웨이트 모델은 "누가 받을 수 있는가"만 정할 뿐 "누가 돌릴 수 있는가"는 여전히 데이터센터 GPU에 묶여 있음 → 접근성 격차.
b. MoE는 기회이자 과제: 토큰당 일부 expert만 활성(예: DeepSeek-V4-Flash는 284B 중 13B만) → 연산량은 소비자 GPU로 감당 가능하지만, 전체 expert 풀은 VRAM을 크게 초과해서 호스트 메모리/디스크에 두고 on-demand로 끌어와야 함.
c. 기존 엣지 엔진(llama.cpp, Ollama, KTransformers)의 3대 한계
    - Prefill이 희소성을 파괴 — 긴 프롬프트는 레이어별로 거의 모든 expert를 활성화 → prefill마다 전체 expert 풀을 PCIe로 스트리밍(예: DSV4-Flash FP4는 ~140GB, RTX 5090에서 +2초, 노트북 x8 링크에선 10초+). 에이전트 툴콜로 컨텍스트가 계속 자라 재-prefill이 빈번.
    - Decode는 반대로 희소하지만 캐시 미스 — 라우팅이 토큰마다 바뀌어 정적 배치가 대부분의 트래픽을 놓침. 소비자 CPU 대역폭(DDR5 80~90GB/s)은 GPU VRAM(1~1.8TB/s)에 한참 못 미쳐 CPU 단독 실행도 불가. 미스를 PCIe 전송 vs CPU 실행으로 어떻게 나눌지는 기기마다 최적점이 다름.
    - 엣지 자원의 변동성 — VRAM을 브라우저·게임과 공유, 세션이 길어지며 KV 캐시 수요 증가, 엔진을 자주 껐다 켜서 startup 비용(140GB 풀 로딩 ~20초)이 반복.

ㄴ) 핵심 설계 (2 실행 원리 + 1 자원 정책)

a. Bandwidth-adaptive execution — 대역폭을 병목이 아니라 스케줄링 신호로
    - Prefill: full-layer double buffering. GPU가 layer l을 계산하는 동안 전송 스트림이 layer l+1의 전체 expert를 미리 로드(라우팅 결과 전에 시작 가능) → 가중치 이동을 연산 뒤에 완전히 숨김. 슬롯 풀을 decode 캐시와 공유해 phase 전환·별도 캐시 없음.
    - Decode: q* 정책. PCIe 전송과 CPU 실행이 같은 호스트 메모리 대역폭을 쓴다는 점에서 출발해, 각 스텝의 미스 m개를 cache-fill 집합 F와 CPU-실행 집합 C로 분할:
        - q* ≈ m · B_PCIe / B_Host (두 대역폭은 배포 기기에서 실측)
        - 예: B_PCIe : B_Host ≈ 1:4 → 미스 4개 중 1개는 PCIe로 캐시에 채우고 3개는 CPU에서 즉석 실행
        - GPU/CPU 부분합을 정확히 병합 — 근사·모델 변형 없음. 항상 최소 1개는 fill해 캐시가 계속 데워짐.

b. Semantic-aware caching — 부족한 메모리에 무엇을 남길지
    - 에이전트 하네스(OpenClaw, OpenCode, SWE-agent)는 thinking 블록·tool call·tool output·대화 턴 같은 special-token 경계에서 컨텍스트를 잘라냄. FreeToken은 그 경계에 recurrent-state 체크포인트를 앵커링 → 편집 후 새 suffix만 재-prefill.
    - 하이브리드 어텐션 대응: full-attention KV는 radix prefix tree로, recurrent layer(gated DeltaNet 등)는 상태 체크포인트로 재사용.
    - Decode의 인접 토큰 간 expert 겹침(temporal locality)을 전 레이어 공유 LRU expert 캐시로 흡수 → 대부분 VRAM 히트, 잔여 미스만 q*로.

c. Elastic memory management
    - CPU-resident expert 풀이 항상 "정답 원본"이므로 GPU 메모리는 성능에만 영향, 정확도엔 무관.
    - 런타임 캐시 재구성: 스케줄러 안전 지점에서 VRAM 예산 변화에 맞춰 GPU expert 캐시를 재빌드 — 엔진 재시작·호스트 풀 재로딩 없이, KV↔expert 분배도 런타임 조정.
    - 빠른 부팅: expert를 최종 호스트 레이아웃으로 디스크에서 바로 읽고 채운 뒤 pin. GPU 워밍업 생략(첫 요청은 콜드 캐시로 서빙). FTW 포맷으로 텐서 탐색/재패킹을 사전에 제거.

ㄷ) 구현
    - vLLM/SGLang식 GPU-중심 substrate + FlashInfer, Flash Linear Attention 커널.
    - CUDA Graph 호환 LRU 캐시: 라우팅 의존 제어를 전부 GPU에 두고 정적 캡처 그래프 내부에 데이터로 표현. 단일 패스로 LRU victim K개 선정, 미스 경로는 그중 앞 q개만 소비.
    - CPU 브랜치도 같은 그래프에 캡처(영구 C++ 스레드 풀, 물리 코어 pin, 아키텍처별 SIMD + 커널 내 역양자화).
    - pinning/DMA 불가 OS에선 pure-CPU MoE 백엔드로 폴백.

ㄹ) 평가
    - 하드웨어 6대: RTX 4060 노트북(8GB, PCIe x8) → 3090/4090/5090 → RTX PRO 6000(96GB) 워크스테이션.
    - 모델: Qwen3.6-35B-A3B(BF16), DeepSeek-V4-Flash(284B/13B active, MXFP4), GLM-5.2(753B/40B active, NVFP4, 433GB).
    - 워크로드 4종: W1 수학추론(AIME, 싱글턴) · W2 코딩(OpenCode+SWE-bench) · W3 코딩(Claude Code 네이티브 프로토콜, 56–65k 토큰) · W4 이메일/캘린더(OpenClaw, 13턴).
    - 베이스라인: llama.cpp, Ollama, KTransformers, MoE-Infinity.

ㅁ) 주요 결과
    - RTX 5090: Qwen3.6 77–83 tok/s, DSV4-Flash 22–25 tok/s → 최강 베이스라인 대비 decode 1.5–2.3×.
    - 에이전트화될수록 안정적: 싱글턴 대비 12% 이내 하락 (KTransformers는 W2에서 이미 31% 하락).
    - Tail TTFT: FreeToken 최악 44초 미만 vs 베이스라인은 어딘가에서 150초 초과(llama.cpp 232s, Ollama 179s, KTransformers 946s) — 실제 에이전트 클라이언트 타임아웃 경계.
    - 소비자 시스템 5대에서 decode 1.3–2.1×.
    - 8GB RTX 4060 노트북에서 35B 모델 39.3 tok/s (Codex 프로덕션 중앙값 33 tok/s 상회).
    - 32GB 게이밍 데스크톱에서 284B 모델 인터랙티브 서빙.
    - 워크스테이션 GPU 1장에서 753B GLM-5.2를 llama.cpp의 2배(14.9 vs 7.3 tok/s).
    - 세부 분석: overlap prefill은 8192토큰 청크를 PCIe 링크 한계 속도(1.19–1.22초)로 처리, 끄면 8k에서 25% 손실. LRU 캐시 미스율(5090 용량 기준) 16%/39% vs KTransformers 41%/59% vs llama.cpp 62%/89%.

ㅂ) 관련 연구 대비 차별점
    - 기존 expert offloading/prefetching은 미스 예측만 개선 → 미스는 결국 PCIe 전송이라 링크 대역폭에 바운드. FreeToken은 라우팅 연산을 정확히 유지한 채 "잔여 미스를 어떻게 서빙하는가"를 바꿈(전송 vs 그 자리 CPU 실행).
    - 기존 하이브리드 CPU-GPU(Fiddler, KTransformers, HybriMoE 등)는 작업 분배가 startup에 고정되거나 CUDA Graph에 못 담기는 호스트 휴리스틱. FreeToken은 두 실측 대역폭에서 closed-form 비율로 도출해 그래프 내부 device-resident로 유지하고, 멀티턴 에이전트용 cross-request prefix 재사용을 서빙 런타임에 통합.


2. 하네스 엔지니어링(Harness Engineering)
LLM 모델 자체가 아니라, 모델을 감싸고 있는 실행 환경(하네스)을 설계·최적화하는 작업이다. 모델은 그대로 두고 그 주변부를 바꿔서 에이전트의 실제 성능을 끌어올린다.

ㄱ) "하네스"란?
원래 하네스(harness)는 말이나 낙하산에 채우는 장비 벨트를 뜻한다. 소프트웨어에서는 어떤 핵심 부품을 실제로 동작시키기 위해 둘러싸는 코드를 말한다(예: test harness).

LLM 에이전트에서 하네스는 모델 호출을 감싸는 모든 것이다.

    ┌─────────────────────────── 하네스 ───────────────────────────┐
    │  시스템 프롬프트 / 컨텍스트 구성                              │
    │  에이전트 루프 (모델 호출 → 도구 실행 → 결과 주입 → 반복)     │
    │  도구 정의 (tool schema, 설명문, 파라미터)                    │
    │  컨텍스트 관리 (요약, 압축, 잘라내기, 검색 주입)             │
    │  권한 / 안전 게이트                                          │
    │  에러 처리 / 재시도 / 폴백                                   │
    │  서브에이전트 오케스트레이션                                 │
    │        ┌───────────────────────────────┐                    │
    │        │        LLM 모델 (가중치)        │                    │
    │        └───────────────────────────────┘                    │
    └────────────────────────────────────────────────────────────┘

Claude Code, Cursor, Devin 같은 도구가 같은 모델을 쓰면서도 결과가 다른 이유가 대부분 이 하네스 차이다.

ㄴ) 엔지니어링
모델 성능을 올리는 길은 두 가지다.
    - 모델을 더 크게/똑똑하게 학습한다 → 비싸고 느리고 대부분의 사람이 못 한다.
    - 하네스를 개선한다 → 학습 없이, 반복 주기가 분 단위이고, 즉시 배포된다.

투자 대비 효과가 훨씬 크다. 그래서 "프롬프트 엔지니어링"보다 넓은 개념으로 하네스 엔지니어링이라는 말이 자리잡았다. 프롬프트는 하네스의 한 구성요소일 뿐이다.

ㄷ) 주요 작업 항목

a. 컨텍스트 엔지니어링
제한된 컨텍스트 윈도우에 무엇을, 어떤 순서로, 얼마나 넣을지 결정한다. 대화가 길어지면 요약·압축하고, 필요한 파일만 검색해서 주입한다.

b. 도구 설계
도구 개수, 이름, 설명문, 파라미터 스키마를 다듬는다. 도구 설명 한 줄만 바꿔도 호출 정확도가 크게 달라진다. 도구를 너무 많이 주면 모델이 헷갈리므로 묶거나 지연 로딩(deferred tools)한다.

c. 에이전트 루프
모델 출력 파싱, 도구 실행, 결과 포맷팅, 종료 조건 판단. 루프가 언제 멈출지, 실패를 어떻게 모델에게 알릴지가 핵심이다.

d. 검증·피드백 루프
코드를 짰으면 테스트를 돌려서 실패 로그를 다시 모델에 넣는 식으로, 모델이 스스로 고칠 재료를 준다.

e. 서브에이전트 구조
큰 작업을 쪼개 별도 컨텍스트를 가진 에이전트에게 위임하고 결과만 회수한다.

f. 안전·권한 게이트
되돌리기 어려운 행동(파일 삭제, 외부 전송) 앞에 확인 단계를 넣는다.

g. 프롬프트 엔지니어링과의 관계
    - 프롬프트 엔지니어링 : 모델에게 보내는 텍스트를 잘 쓰는 것
    - 컨텍스트 엔지니어링 : 그 텍스트에 무엇을 담을지 관리하는 것
    - 하네스 엔지니어링   : 위 둘을 포함해, 모델을 실제로 굴리는 시스템 전체를 설계하는 것

범위는 하네스 ⊃ 컨텍스트 ⊃ 프롬프트 순으로 넓다.

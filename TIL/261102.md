1. Langfuse
Langfuse는 LLM 애플리케이션을 위한 오픈소스 관측·평가 플랫폼이다. 앱 안에서 LLM이 무엇을 입력받아 어떤 단계를 거쳐 무엇을 답했는지 기록하고, 그 품질을 평가하고 개선하도록 돕는다.

ㄱ) 사용하는 이유
일반 서버는 로그와 에러율만으로도 문제를 어느 정도 찾을 수 있다. 하지만 LLM 앱은 에러 없이 틀린 답을 내놓을 수 있어서 각 단계의 입출력을 봐야 한다.

예를 들어 RAG 답변이 이상하다면 원인은 다음 중 어디에든 있을 수 있다.

    - 쿼리 재작성이 잘못됐다.
    - 검색에서 필요한 문서를 놓쳤다.
    - 리랭킹에서 정답 문서가 밀려났다.
    - 문서는 맞는데 LLM이 잘못 해석했다.

Langfuse를 쓰면 이 흐름을 한눈에 보고 어느 단계가 문제인지 좁힐 수 있다.

ㄴ) 핵심 구조
기록은 트리 형태로 쌓인다.

    Session: 한 사용자의 대화 전체
    └─ Trace: 질문 하나를 처리한 전체 과정
       ├─ Span: 쿼리 재작성 (LLM이면 Generation)
       ├─ Span: 벡터 검색 (120ms, 문서 5개)
       ├─ Span: 리랭킹 (80ms)
       └─ Generation: 답변 생성 (모델명, 토큰 수, 비용, 2.1s)

| 개념 | 의미 |
|---|---|
| Trace | 요청 하나의 처음부터 끝까지 |
| Span | 그 안의 작업 한 단계 (검색, 툴 호출 등) |
| Generation | LLM 호출을 기록하는 특수한 Span (프롬프트, 응답, 토큰, 비용) |
| Session | 여러 Trace를 대화 단위로 묶은 것 |
| Score | Trace 등에 붙이는 품질 점수 |

ㄷ) 주요 기능
    - 추적(Tracing): 위 트리를 UI에서 보며 단계별 입출력, 지연 시간, 비용을 확인한다.
    - 프롬프트 관리: 프롬프트를 코드 밖에서 버전으로 관리하고, 재배포 없이 바꾸거나 되돌릴 수 있다.
    - 평가(Evaluation): 사용자 피드백, 사람의 직접 라벨링, LLM 채점(LLM-as-a-Judge)으로 점수를 매긴다.
    - 데이터셋과 실험: 고정된 테스트셋으로 프롬프트나 모델을 바꾼 전후를 비교한다. 공부한 골든셋을 실제로 굴리는 자리다.
    - 대시보드: 비용, 지연 시간, 점수 추이를 모델이나 사용자별로 본다.

ㄹ) 다른 도구와 비교

| 도구 | 특징 |
|---|---|
| Langfuse | 오픈소스이고 셀프호스팅이 가능하며, 특정 프레임워크에 묶이지 않음 |
| LangSmith | LangChain 공식 도구로, LangChain·LangGraph와 연동이 매끄러움 |
| RAGAS | 관측 플랫폼이 아니라 RAG 평가 지표 라이브러리라서, Langfuse와 함께 쓸 수 있음 |

ㅁ) 사용방식
클라우드 버전을 쓰거나 Docker로 직접 띄울 수 있다.
셀프호스팅하면 프롬프트와 응답 데이터를 내 환경에 둘 수 있어 사내 데이터를 다룰 때 유리하다. 다만 Postgres, ClickHouse, Redis, S3 호환 저장소까지 함께 운영해야 하고, 클라우드든 셀프호스팅이든 프롬프트에 든 개인정보가 그대로 기록될 수 있어 마스킹을 고려해야 한다.

2. 요청 단위 관측
요청 단위 관측(Request-level Observability)은 시스템을 평균이나 전체 지표로만 보지 않고, 요청 하나하나가 무엇을 거쳐 어떤 결과를 냈는지 기록해서 보는 방식이다. Langfuse의 Trace가 바로 이 방식의 기록 단위다.

ㄱ) 집계 지표와의 차이

| 구분 | 집계 지표 | 요청 단위 관측 |
|---|---|---|
| 답하는 질문 | 시스템 전체가 괜찮은가? | 이 요청은 왜 이렇게 됐는가? |
| 예시 | 평균 응답 3초, 에러율 1% | 요청 abc123은 리랭킹에서 9초가 걸림 |
| 강점 | 이상 징후를 빠르게 발견 | 원인을 구체적으로 추적 |
| 한계 | 원인을 알려주지 못함 | 전체 추세를 보려면 집계가 필요 |

둘은 대체 관계가 아니다. 보통 집계 지표로 이상을 발견하고, 요청 기록을 열어 원인을 찾는다.
평균이 가리는 문제를 예로 들면, 100건 중 95건이 1초, 5건이 30초 걸려도 평균은 약 2.5초다. 평균만 보면 괜찮아 보이지만, 5명은 사실상 서비스가 멈춘 것처럼 느낀다. 이 5건을 열어 봐야 공통 원인을 찾을 수 있다.

ㄴ) 작동 방식
핵심은 요청마다 고유한 ID를 부여하고, 처리 과정의 모든 기록에 그 ID를 붙이는 것이다.

    요청 수신 → trace_id = abc123 발급
        ├─ 분류기      [abc123] 경로=문서검색, 40ms
        ├─ 벡터 검색   [abc123] 문서 5개, 120ms
        ├─ 답변 생성   [abc123] 토큰 1,850개, 2.1s
        └─ 응답 반환   [abc123] 성공, 총 2.3s

ID가 없으면 동시에 들어온 요청들의 로그가 뒤섞여 어느 줄이 어느 요청의 것인지 알 수 없다. 서비스가 여러 개로 나뉘어 있다면 ID를 다음 서비스로 함께 넘겨야 하는데, 이를 컨텍스트 전파(Context Propagation)라고 한다.

ㄷ) 기록하는 내용

a. 공통
    - 식별 정보: 요청 ID, 사용자, 세션, 앱 버전
    - 실행 경로: 거친 단계와 순서, 선택된 분기나 툴
    - 성능: 단계별 소요 시간, 재시도 횟수
    - 결과: 성공 여부, 에러 내용

b. LLM (정상 응답도 틀릴 수 있어서 추가 항목이 더 필요하다.)
    - 입출력: 최종 프롬프트와 모델의 응답
    - 모델 정보: 모델명, 파라미터, 프롬프트 버전
    - 검색 결과: 가져온 문서와 점수
    - 사용량: 토큰 수와 비용
    - 품질: 사용자 피드백, 평가 점수

c. 디버깅
    - 발견: 대시보드에서 어제부터 평가 점수가 하락한 것을 확인한다.
    - 필터링: 점수가 낮은 요청만 추린다.
    - 공통점 찾기: 대부분 프롬프트 v7을 쓴 요청임을 확인한다.
    - 상세 확인: 요청을 열어 보니 v7에서 검색 문서가 프롬프트에 제대로 들어가지 않았다.
    - 조치와 재발 방지: v6으로 되돌리고, 실패한 요청을 테스트셋에 추가한다.

d. 주의할 점
    - 민감 정보: 입출력 원문에 개인정보나 비밀값이 섞일 수 있어 마스킹과 접근 권한 관리가 필요하다.
    - 저장 비용: 프롬프트와 응답은 일반 로그보다 훨씬 커서 보관 기간을 정해야 한다.
    - 샘플링: 일부만 저장해 비용을 줄일 수 있지만, 드문 실패를 놓치지 않도록 에러나 저품질 요청은 가능하면 모두 남기는 편이 좋다.

3. Trace 재조회
Trace 재조회는 이미 저장된 Trace를 나중에 ID나 조건으로 다시 불러와 확인하는 것이다. 업계 표준 용어라기보다 일반적인 표현이라, 여기서는 이 뜻으로 설명한다. 혹시 특정 자료나 코드에서 본 표현이라면 맥락에 따라 의미가 조금 다를 수 있다.
요청을 처리하는 순간에 기록하는 것이 관측의 절반이라면, 재조회는 그 기록을 꺼내 쓰는 나머지 절반이다.

ㄱ) 하는 이유
    - 문제 조사: 사용자가 신고한 요청의 실제 프롬프트, 검색 문서, 응답을 확인한다.
    - 사후 평가: 저장된 요청을 나중에 꺼내 LLM이나 사람이 채점하고 Score를 붙인다.
    - 데이터셋 구축: 실패한 요청을 골라 테스트셋에 추가한다.
    - 패턴 분석: 특정 기간, 프롬프트 버전, 낮은 점수 등의 조건으로 모아 공통 원인을 찾는다.
    - 자동화 검증: 테스트 코드에서 요청을 실행한 뒤, 기대한 단계를 거쳤는지 Trace로 확인한다.

ㄴ) 조회 방식

| 방식 | 사용 시점 | 예시 |
|---|---|---|
| ID 조회 | 특정 요청 하나를 볼 때 | abc123의 전체 트리 |
| 조건 조회 | 여러 요청을 찾을 때 | 어제 점수가 0.5 미만인 요청 |

Langfuse에서는 UI나 API로 조회할 수 있다. Python SDK의 메서드 이름과 인자는 버전에 따라 다를 수 있으니 문서를 확인한다.

ㄷ) 주의할 점

a. 기록 직후에는 조회되지 않을 수 있다.

b. Trace ID를 찾을 수 있어야 한다.

c. 사용자 ID와 태그를 기록 시점에 붙여야 한다.
    - user_id, 세션 ID, 프롬프트 버전 같은 값을 넣지 않았다면 나중에 그 조건으로 찾을 수 없다. 재조회할 방법을 미리 생각하고 기록해야 한다.

d. 운영 로직이 재조회에 의존하면 안 된다.
    - 조회 API는 분석용이다. 시차와 호출 제한이 있을 수 있으므로, 대화 기록처럼 서비스 동작에 꼭 필요한 데이터는 자체 저장소에 따로 두는 것이 안전하다.

4. 업무 도구 추적
업무 도구 추적은 AI 에이전트가 주문 조회, 환불, 일정 등록 같은 업무 도구를 언제, 왜, 어떤 값으로 호출했고 어떤 결과를 얻었는지 기록하는 것이다.

ㄱ) 추적하는 이유
도구를 쓰는 에이전트는 답변만 하는 LLM과 달리 실제 시스템의 데이터를 바꿀 수 있다. 잘못된 답변은 다시 물으면 되지만, 잘못된 환불은 실제 피해로 이어진다. 또 최종 답변만 봐서는 도구를 제대로 썼는지 알 수 없다.

ㄴ) Trace 구조
LLM의 판단과 도구 실행을 나눠 기록해야 어느 쪽이 문제인지 구분할 수 있다.

    Trace: "지난주 주문 환불해줘"
    ├─ Generation: 도구 선택 → order_search 호출 결정
    ├─ Tool: order_search → 주문 2건, 200ms
    ├─ Generation: 도구 선택 → refund 호출 결정
    ├─ Tool: refund → 성공, 450ms
    └─ Generation: 최종 답변 생성

| 위치 | 실패 유형 | 예시 |
|---|---|---|
| LLM 판단 | 도구 선택 오류 | 조회해야 하는데 환불을 호출 |
| LLM 판단 | 인자 오류 | 없는 주문 번호를 지어냄 |
| 도구 실행 | 시스템 오류 | 시간 초과, 권한 없음 |
| 결과 해석 | 결과를 잘못 이해 | 실패 응답을 받고 "완료했습니다"라고 답함 |

ㄷ) 기록하는 내용
    - 호출 정보: 도구 이름, 인자, 호출 순서
    - 결과: 응답 내용, 성공 여부, 에러 내용
    - 성능: 소요 시간, 재시도 횟수
    - 권한과 승인: 누구의 권한으로 실행했는지, 사람이 승인했는지
    - 영향 범위: 읽기 작업인지 쓰기 작업인지, 변경된 대상의 ID

ㄹ) 주의할 점

a. 기술적 성공과 업무적 성공은 다르다.

b. 도구 쪽 시스템과 ID로 연결해야 한다.

c. 재시도 기록이 중복 실행을 드러낸다.
    - 응답이 시간 초과돼도 작업은 실제로 처리됐을 수 있고, 이때 재시도하면 이중 환불이 발생한다. 이를 막는 것은 추적이 아니라 멱등성 키(Idempotency Key)이지만, 어떤 호출이 재시도였는지는 추적 기록으로 확인한다.

d. 민감 정보가 더 많이 남는다.
    - 업무 도구의 입출력에는 고객 정보, 결제 정보, 인증 토큰이 들어가기 쉽다. 저장 전에 마스킹하고, 토큰이나 비밀번호 같은 비밀값은 아예 기록하지 않아야 한다.

e. Trace는 감사 로그를 대신하지 않는다.
    - 샘플링이나 보관 기간 때문에 Trace는 사라질 수 있다. 환불처럼 중요한 작업의 공식 기록은 변경이 제한된 별도의 감사 로그(Audit Log)에 남겨야 한다.

ㅁ) 기록의 활용
    - 도구 선택 정확도: 골든셋에 기대하는 도구와 인자를 정해 두고 실제 호출과 비교한다.
    - 도구별 지표: 실패율, 지연 시간, 호출 빈도를 보고 불안정하거나 쓰이지 않는 도구를 찾는다.
    - 도구 설명 개선: 잘못 고르는 패턴이 반복되면 도구 설명이나 인자 정의를 고친다.
    - 비정상 동작 탐지: 같은 도구를 반복 호출하는 무한 루프를 찾아낸다.

5. 실패 분류
실패 분류는 실패한 요청을 원인이나 유형별로 나눠서 무엇부터 고칠지 판단할 수 있게 만드는 작업이다. 앞서 설명한 Trace가 개별 실패의 기록이라면, 실패 분류는 그 기록을 모아 패턴으로 바꾸는 단계다.
"실패 200건"만으로는 할 일을 정할 수 없다. 반면 "검색 누락 120건, 시간 초과 50건, 인자 오류 30건"이면 검색부터 고쳐야 한다는 결론이 나온다.

ㄱ) 분류 기준 예시
어느 단계에서 문제가 생겼는지를 기준으로 나누면 담당 영역과 해결책이 바로 연결된다.

| 단계 | 실패 유형 | 예시 | 주요 대응 |
|---|---|---|---|
| 입력 | 의도 분류 오류 | 환불 문의를 배송 문의로 분류 | 분류기 개선 |
| 검색 | 문서 누락 | 정답 문서를 찾지 못함 | 청킹, Hybrid 검색, 리랭킹 |
| 컨텍스트 | 컨텍스트 잘림 | 토큰 예산 초과로 문서가 빠짐 | 예산 조정, 압축 |
| 생성 | 환각 | 문서에 없는 내용을 답함 | 프롬프트 수정, 근거 검증 |
| 생성 | 형식 오류 | JSON 파싱 실패 | 구조화 출력 |
| 도구 | 선택·인자 오류 | 없는 주문 번호로 호출 | 도구 설명 개선, 인자 검증 |
| 시스템 | 인프라 오류 | 시간 초과, 호출 제한 | 재시도, 폴백 |
| 안전 | 정책 위반 | 프롬프트 인젝션에 넘어감 | 가드레일, 권한 제한 |

ㄴ) 기술적 실패와 품질 실패

a. 기술적 실패
    - 시간 초과나 파싱 오류처럼 시스템이 에러로 드러낸다. 규칙으로 자동 분류하기 쉽다.
    - 일시적 실패: 시간 초과나 호출 제한은 재시도할 만하다.
    - 영구적 실패: 권한 없음이나 잘못된 인자는 같은 요청을 재시도해도 소용없으므로, 수정하거나 사람에게 넘긴다.

b. 품질 실패
    - 응답은 정상인데 내용이 틀린 경우다. 에러가 나지 않아 평가 점수, 사용자 피드백, 사람의 검토로 찾아야 한다.

ㄷ) 분류 체계를 만드는 방법
    - 실제 실패 데이터를 읽으면서 만드는 편이 정확하다.
    - 표본 수집: 실패 Trace를 50~100건 정도 모은다.
    - 자유 메모: 한 건씩 읽으며 무엇이 잘못됐는지 적는다.
    - 묶기: 비슷한 메모를 모아 유형으로 정리한다.
    - 라벨링: 정해진 유형으로 다시 분류하고 건수를 센다.
    - 우선순위 결정: 빈도와 피해 규모로 순서를 정한다.
    - 유지: 새로운 실패를 보며 체계를 계속 고친다.

ㄹ) 주의할 점

a. 첫 번째 원인을 기록한다.
    - 실패는 연쇄적으로 나타난다. 검색이 문서를 놓치자 LLM이 환각을 일으켰다면, 겉모습은 환각이지만 고칠 곳은 검색이다. 그래서 흐름상 가장 먼저 잘못된 단계를 대표 원인으로 삼는다.

b. 유형은 서로 겹치지 않게, 행동으로 이어지게 만든다.
    - "답변 이상함" 같은 라벨은 해결책으로 이어지지 않는다. 유형을 보면 어디를 고칠지 알 수 있어야 한다. 분류가 애매한 "기타"가 커지면 체계를 다시 나눌 신호다.

c. 빈도만으로 우선순위를 정하지 않는다.
    - 잘못된 환불은 드물어도 어조 문제보다 훨씬 치명적이다. 빈도와 피해 규모를 함께 봐야 한다.

d. LLM 자동 분류는 검증해야 한다.
    - 유형이 안정되면 LLM에게 분류를 맡길 수 있다. 다만 일부를 사람이 직접 검토해 분류 정확도를 확인해야 한다. 사람 라벨과 비교한 뒤에 믿고 쓰는 것이 안전하다.

ㅁ) Langfuse에서의 활용
    - 기록: 실패 유형을 Trace의 태그나 범주형 Score로 붙인다.
    - 추이 확인: 대시보드에서 유형별 건수를 보고 배포 후 어떤 실패가 늘었는지 본다.
    - 회귀 방지: 유형별 실패 사례를 데이터셋에 넣어, 고친 뒤에도 재발하지 않는지 실험으로 확인한다.

전체 흐름은 Trace 수집 → 실패 분류 → 우선순위 결정 → 수정 → 데이터셋으로 재검증의 반복이다.

6. Golden Dataset
입력과 기대 결과를 짝지어 둔, 검증된 고정 시험 문제집이다. 같은 문제로 채점해야 버전 간 점수를 비교할 수 있다.
    - 구성: 자주 들어오는 질문, 경계 사례, 실제 실패 사례, 답하면 안 되는 질문을 섞는다.
    - 규모: 처음에는 수십 건으로 시작해, 실패 분류에서 나온 사례를 추가하며 키운다.
    - 관리: 정답이 바뀌면 함께 갱신하고, 데이터셋에도 버전을 붙인다. 데이터셋이 바뀌면 이전 점수와 직접 비교하기 어렵기 때문이다.
    - 주의: 이 문제만 맞히도록 프롬프트를 고치면 점수만 오르고 실제 성능은 그대로일 수 있다. 튜닝에 쓰지 않는 평가용 데이터를 따로 두면 이를 확인할 수 있다.

7. 프롬프트 버전
프롬프트의 각 변경본에 번호를 붙여 구분하고 추적하는 것이다. 그래야 어떤 변경이 결과를 바꿨는지 알 수 있고 문제가 생기면 되돌릴 수 있다.

    - 불변성: v7을 직접 고치지 않고 수정본을 v8로 새로 만든다.
    - 기록 범위: 결과에 영향을 주는 모델명, 온도, 도구 정의도 함께 기록한다. 프롬프트가 같아도 이 값이 바뀌면 결과가 달라지기 때문이다.
    - 배포 라벨: Langfuse에서는 production 같은 라벨을 버전에 붙여, 코드 배포 없이 운영 버전을 바꾸거나 되돌릴 수 있다.
    - Trace 연결: 각 Trace에 프롬프트 버전을 남겨야 버전별 성능을 비교할 수 있다.

8. Python 평가
결과가 맞는지 코드로 채점하는 방식이다. 빠르고 비용이 들지 않으며, 같은 출력에는 항상 같은 점수를 준다.

| 평가 방식 | 적합한 대상 | 한계 |
|---|---|---|
| Python 평가 | 분류 라벨, 도구 이름, JSON 형식, 필수 문구 | 의미가 맞는지는 판단하기 어려움 |
| LLM 채점 | 답변의 정확성, 근거 충실도 | 비용이 들고 채점 결과가 흔들릴 수 있음 |
| 사람 검토 | 미묘한 품질, 채점 기준 검증 | 느리고 비용이 큼 |

코드로 확인할 수 있는 것은 Python으로 먼저 처리하고, 나머지에 LLM 채점을 쓰는 것이 효율적이다.
단순 문자열 비교는 "환불 기한"과 같은 다른 표현을 틀렸다고 판정할 수 있으니, 이런 항목은 기준을 신중히 정해야 한다.

9. 회귀 판정
새 버전이 기존에 되던 것을 망가뜨렸는지 판단해 배포 여부를 정하는 것이다. 전체 점수만 보면 문제가 가려질 수 있다.

    전체 정확도: v7 90% → v8 92%   ← 좋아 보임

    사례별 비교:
        새로 맞힘: 5건
        새로 틀림: 3건 (그중 1건은 critical 환불 사례)

전체 점수는 올랐지만 환불 사례가 깨졌으므로 배포하면 안 된다. 그래서 판정 규칙을 미리 정해 둔다.

    - 기준선: 비교 대상은 현재 운영 중인 버전이다.
    - 규칙은 사전에: 결과를 본 뒤 기준을 바꾸면 판정이 의미를 잃으므로, 실행 전에 정한다.
    - 허용 오차: LLM 출력은 실행마다 달라질 수 있어, 작은 차이는 우연일 수 있다. 사례를 여러 번 실행해 비교하면 더 믿을 만하다.
    - 표본 크기: 50건이면 1건이 2%포인트이므로, 작은 점수 변화에 큰 의미를 두면 안 된다.
    - 조건별 확인: 전체 점수와 함께 태그별 점수와 새로 틀린 사례를 직접 본다.
    - 자동화: 이 판정을 CI에 넣으면 프롬프트 변경 때마다 자동으로 검사할 수 있다.

운영 중 실패가 발견되면 Trace를 재조회하고 실패를 분류한 뒤, 그 사례를 Golden Dataset에 추가한다.
프롬프트를 고쳐 새 버전을 만들고, Python 평가로 채점한 뒤 회귀 판정을 통과하면 배포한다.
이 과정을 반복할수록 같은 실수가 다시 배포될 가능성이 줄어든다.

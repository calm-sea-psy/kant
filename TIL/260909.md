0. 다섯 접근의 스펙트럼
가중치를 안 건드림 → 조금 건드림 → 다 건드림 순서로 놓으면 이 다섯 개념이 하나의 스펙트럼으로 정리된다.

Prompt Engineering / Prompt-only  │  Prompt-tuning  │  PEFT (LoRA 등)  │  Full Fine-tuning
────────────────────────────────────────────────────────────────────────────────────────►
가중치 변경 없음                    │ soft prompt만   │ 파라미터 1~5%     │ 전체 파라미터
추론 시점에만 개입                  │ 학습 O (극소)    │ 학습 O           │ 학습 O (무거움)

1. Prompt Engineering
모델 가중치는 그대로 두고 입력 텍스트(프롬프트)를 설계해서 원하는 출력을 끌어내는 기법
    - 방법: 명확한 지시·역할 부여, Few-shot 예시(in-context learning), Chain-of-Thought("단계별로 생각해"), 출력 형식 지정(JSON/표), 제약·톤 지정
    - 장점: 학습 비용 0, 즉시 반영, API만으로도 가능
    - 한계: 매 호출마다 토큰 비용, 컨텍스트 윈도우 차지, 프롬프트에 담을 수 있는 예시·지식의 양에 한계, 모델 본래 능력을 넘는 성능은 안 나옴
    - 언제: 거의 모든 작업의 출발점. RAG를 붙이면 지식 부족 문제도 상당 부분 해결됨

2. Prompt-only
독립된 기법이라기보다 "학습(gradient descent)을 전혀 하지 않고 프롬프트만 쓴다"는 접근을 가리키는 말. 
문맥에 따라 나뉜다.
    - (a) 사람이 자연어로 작성한 하드 프롬프트(discrete prompt)만 사용 → 실질적으로 Prompt Engineering + In-context Learning
    - (b) 논문 비교표에서 baseline: fine-tuning·adapter 없이 frozen 모델 + 프롬프트

핵심은 파라미터 업데이트가 0이라는 점. 다음에 나올 prompt-tuning(소프트 프롬프트 학습)과 대비하려고 쓰는 용어다.

3. Prompt-tuning (Soft Prompt Tuning)
모델 전체를 freeze하고, 입력 앞에 붙는 학습 가능한 연속 벡터(soft prompt / virtual tokens) 수십 개만 backprop으로 업데이트.
    - 자연어 토큰이 아니라 임베딩 벡터라서 사람이 읽을 수 없음
    - 과제(task)마다 이 작은 벡터 세트(수 KB~수 MB)만 저장
    - 관련: Prefix-tuning(모든 레이어의 key/value에 학습 벡터 추가, 표현력↑), P-tuning v2
    - 특징: 학습 파라미터가 모델의 0.01~0.1% 수준. 모델이 클수록 full fine-tuning과 성능 격차가 줄어듦(Lester et al. 2021). 작은 모델에서는 아쉬울 수 있음
    - 위치: PEFT의 한 종류

4. PEFT (Parameter-Efficient Fine-Tuning)
사전학습 가중치는 대부분 freeze하고 소수 파라미터(기존 일부 또는 새로 추가한 것)만 학습하는 방법들의 총칭    

| 기법 | 아이디어 |
|---|---|
| LoRA | 가중치 행렬에 저랭크 행렬 A·B를 더하고 A·B만 학습 |
| QLoRA | 베이스 모델을 4bit 양자화 + LoRA → 소비자 GPU에서도 대형 모델 튜닝 |
| Adapter | 레이어 사이에 작은 병목 MLP 삽입 |
| Prompt / Prefix-tuning | 위 3번 |
| (IA)³, BitFit | 스케일링 벡터만 / bias만 학습 |

    - 장점: 메모리·연산 대폭 절감(옵티마이저 상태가 작음), 체크포인트가 작아 과제별 교체가 쉬움, catastrophic forgetting 완화, 성능은 full fine-tuning에 근접
    - 언제: 도메인·스타일 적응이나 특정 과제 최적화가 필요한데 GPU 예산이 제한적일 때. 현재 오픈모델 커스터마이징의 사실상 표준

5. (Full) Fine-tuning
과제·도메인 데이터로 모델의 모든 가중치를 backprop으로 업데이트.
    - 가장 높은 잠재 성능, 모델 행동을 근본적으로 바꿀 수 있음(새 도메인 지식 주입 등)
    - 비용 최대: gradient + optimizer state까지 올리면 Adam 기준 파라미터당 ~3배 메모리 → 7B 모델도 수십~수백 GB VRAM
    - 과제마다 전체 모델 사본이 생김(저장·배포 부담)
    - 작은 데이터셋에서 overfitting·catastrophic forgetting 위험. 보통 수천~수만+ 예시와 하이퍼파라미터 튜닝 필요

|  | Prompt Eng. / Prompt-only | Prompt-tuning | PEFT (LoRA 등) | Full Fine-tuning |
|---|---|---|---|---|
| 가중치 업데이트 | 없음 | soft prompt만 | 1~5% 내외 | 100% |
| 학습 필요 | ✗ | ✓ (경미) | ✓ | ✓ (무거움) |
| 데이터 요구량 | 예시 몇 개 | 수백~수천 | 수백~수만 | 수천~수십만 |
| GPU 비용 | 없음 | 낮음 | 중간 | 높음 |
| 산출물 크기 | 프롬프트 텍스트 | KB~MB | 수십 MB | 전체 모델 |
| 추론 비용 | 프롬프트 토큰만큼 ↑ | 약간 ↑ | 거의 없음 | 없음 |
| 지식 주입력 | 제한적 | 제한적 | 중간 | 강함 |

일반적으로 Prompt Eng. > RAG > PEFT > Full FT 순으로 비용 대비 효과가 좋아서 이 순서로 시도한다.
    - Prompt Engineering (+RAG) 부터 — 대부분 여기서 충분
    - 형식 일관성·특정 스타일·반복 과제 정확도에서 한계가 명확하고 라벨 데이터가 있으면 → LoRA / QLoRA
    - 한 모델로 다중 과제(multi-task) 서빙 + 초경량 스위칭이 목적이면 → prompt-tuning 계열
    - 데이터가 대규모이고 모델 행동을 근본적으로 바꿔야 하며 예산이 되면 → Full Fine-tuning / continued pretraining

6. Prompt-only baseline
여러 튜닝 기법(prompt-tuning, LoRA, adapter, full fine-tuning...)의 성능을 비교할 때 맨 윗줄에 놓는 "아무것도 학습하지 않은 대조군"이다.
    - 사전학습 모델을 완전히 freeze (가중치·gradient 업데이트 0)
    - 사람이 손으로 만든 프롬프트 / 템플릿만 붙여서 그대로 추론
    - 다른 이름: frozen LM, no-tuning, prompt design, in-context learning baseline, zero-shot / few-shot baseline    

ㄱ) 사용하는 이유

| 목적 | 설명 |
|---|---|
| 하한선 측정 | "이 과제를 모델이 이미 얼마나 알고 있나"를 확인 |
| 한계 이득(marginal gain) 계산 | prompt-tuning이 이걸 1점밖에 못 이기면 → 학습할 가치가 낮다는 신호 |
| 기여 분리 | 성능 향상이 학습된 파라미터 덕인지, 그냥 프롬프트 형식 덕인지 구분 |
| 공짜 기준점 | 연산·데이터 비용 0이므로 항상 비교 가능 |

ㄴ) 구성하는 방법
PET / LM-BFF 스타일

    템플릿:     "{문장}  전체적으로 이 리뷰는 ___ 이다."
    Verbalizer: 좋다 → 긍정,  나쁘다 → 부정
    채점:       ___ 자리에 들어갈 라벨 단어들의 확률을 비교해 argmax

    - 예시를 하나도 안 넣으면 → zero-shot prompt-only
    - 컨텍스트에 데모 k개를 넣으면 → few-shot prompt-only (여전히 가중치 고정, in-context learning)    

ㄷ) 강점
    - 데이터·GPU 없이 즉시 측정, 재현 부담이 적음
    - 대형 모델에서는 의외로 경쟁력 있음 (때로 PEFT에 근접)
    - "학습이 정말 필요한가?"를 판단하는 첫 관문    

ㄹ) 약점    
    - 템플릿·verbalizer 문구에 매우 민감 → 분산이 크고, "진짜 baseline 성능"을 특정하기 어려움
    - 프롬프트 엔지니어링 노력이 표준화되지 않아 불공정 비교 소지 (baseline을 대충 만들면 다른 기법이 과대평가됨)
    - 작은 모델·어려운 과제에서는 약함
    - 새 지식 주입, 데이터셋 고유 분포 학습 불가
    - few-shot은 컨텍스트 길이에 k가 제한됨

ㅁ) Baseline 설계 4요소
a. 평가셋 (Evaluation set)    
성능을 재는 데이터

| 항목 | 내용 |
|---|---|
| 대표성 | 실제로 관심 있는 입력 분포(운영 트래픽, 타깃 도메인)를 반영해야 함 |
| 크기 | 이진 지표 기준 신뢰구간 폭 ≈ 1/√n. 대략 차이를 보려면 100+, 몇 점 차이를 구분하려면 1,000+ |
| 오염 방지 | 프롬프트 설계·few-shot 예시·(추후) 학습 데이터와 겹치면 안 됨. 공개 벤치마크는 사전학습 오염도 의심 |
| 라벨 품질 | gold 라벨 신뢰도 확인, annotator 간 일치도(IAA) 측정. 모호한 항목은 noise ceiling |
| 슬라이스 분할 | 언어·난이도·카테고리·길이·경계 사례(edge case)별로 쪼개서 어디서 실패하는지 확인 (총합 숫자만 보면 안 됨) |
| dev / test 분리 | dev로 프롬프트 반복, test는 거의 안 건드림 (test에 과적합 방지) |
| 버전 고정 | 잠그고 버전 태그. 중간에 바꾸면 비교 무효 |
| 하드 케이스 포함 | 알려진 실패 모드·적대적 예시를 일부러 넣기 |

b. Prompt template
각 평가 예시를 모델 입력으로 감싸는 고정된 틀. 입력 슬롯만 바뀌고 나머지는 전부 상수.

    [시스템/지시]  과제 정의 + 제약 + 경계 사례 규칙
    [few-shot]    데모 k개 (평가셋과 분리된 풀에서, 라벨 균형, 순서 고정)
    [입력]        {여기만 예시마다 치환}
    [출력 큐]     "정답만 'yes' 또는 'no'로 답하라" 같은 형식 지시

    - 통제 변수: 동일한 시스템 프롬프트, 구분자 스타일, 필드명, 데모 개수·순서
    - 민감도: 프롬프트는 문구에 민감 → 정확한 템플릿을 문서화하고, 가능하면 말바꿔쓰기(paraphrase) 2~3개에 대한 분산도 보고
        (말바꿔쓰기 : 뜻은 같지만 표현을 바꿔 쓴 문장. "다른 말로 하기".)
    - 모델별 포맷: chat template·role 마커는 모델에 맞추되, 의미 내용은 비교 대상 모델 간 동일하게
    - 템플릿은 실험 config의 일부 — 바꾸면 새 baseline    

c. Output schema
유효한 응답의 계약, 그리고 raw 텍스트 → 채점 가능한 예측으로 바꾸는 규칙.

| 항목 | 내용 |
|---|---|
| 구조 정의 | 단일 라벨 토큰 / 타입 있는 JSON / 랭킹 리스트 / "근거 + 마지막 줄에 최종답" 등 |
| 파싱 규칙 | 출력 문자열 → 예측으로 가는 결정적 함수. Answer:\s*(\w+) 정규식, JSON parse, 마지막 줄 추출, verbalizer(라벨어→클래스) |
| 제약 디코딩 | logit bias, grammar/regex 제약 생성, function calling / structured output으로 파싱 실패 자체를 차단 |
| 실패 처리 | 파싱 안 되면? → 오답 처리 / 재시도 / "format error"로 별도 집계. 사전에 정하고 균일 적용 |
| 정규화 | 소문자화, 공백 trim, 동의어 매핑, 숫자 허용오차를 비교 전에 적용 |

    - 파서가 약하면 정답을 산문으로 말한 똑똑한 모델이 오답으로 집계됨. format-error 비율 자체가 보고할 만한 지표.

d. Metric
예측을 gold와 대조해 점수화하고 집계하는 방식.

| 과제 | 지표 |
|---|---|
| 분류 | accuracy, F1(macro/micro/weighted), precision/recall, MCC |
| 불균형 분류 | macro-F1, balanced accuracy, PR-AUC |
| 생성 | exact match, token-F1, (약함: ROUGE/BLEU), BERTScore, LLM-as-judge |
| 추출 | span-F1 |
| 검색·랭킹 | Recall@k, MRR, nDCG |
| 멀티라벨 | subset accuracy, per-label F1 |

    - 집계: micro(예시 단위) vs macro(클래스·슬라이스 평균) 구분. 슬라이스별로도 보고
    - 불확실성: bootstrap 신뢰구간, 두 시스템 비교 시 paired test (분류는 McNemar)
    - primary 1개 고정: 실행 전에 최적화·비교 기준 지표 하나를 정함. 나머지는 진단용
    - 디코딩 설정 명시: temperature 0 (또는 고정 seed). 비결정적이면 n회 평균 ± 표준편차
    - 효율 축 필수: 예시당 비용·지연·토큰 사용량. 이거 없으면 baseline 비교가 미완성    

ㅂ) Prompt template의 구성요소

a. Role(역할)
모델이 취할 관점·페르소나·전문성을 지정. chat 모델에서는 보통 system 메시지에 들어감.

| 넣을 것 | 예 |
|---|---|
| 전문 영역 | "너는 제품 리뷰 감성 분류기다" |
| 관점·기준 | 따라야 할 표준, 판단 시 우선순위 |
| 경계 | 범위를 벗어난 요청은 어떻게 처리하는지 |
| 톤·문체 | 격식/간결/사실 위주 등 |

    주의할점 
        - 효과는 있지만 한계가 분명 — 역할 부여만으로 없던 능력이 생기진 않음
        - "세계 최고의..." 같은 과장은 cargo cult, 이득 거의 없고 가끔 역효과
        - 최신 instruct 모델은 역할극(roleplay) 의존도가 낮음 → 명확한 Task 명세가 더 중요
        - baseline에서는 모든 예시에 동일하게, 문서화 필수

b. Task(지시)
실제로 무엇을 할지 — 과제 정의, 절차, 판단 규칙, 제약, 경계 사례. 정답 행동을 좌우하는 가장 중요한 부분.    
    - 목표를 명령형으로 명확하게 한 문장
    - 핵심 용어·라벨의 정의 ("neutral은 긍/부정 성향이 전혀 없을 때만")
    - 다단계면 절차, 또는 "단계별로 생각하라"
    - 경계·tie-break 규칙: "모호하면 X를 선택", "문장별이 아니라 전체 기준으로 판단"
    - 제약: 길이, 언어, 제외할 것, 금지 행동
    - 경계 사례: 빈 입력, 범위 밖 입력, 정답이 여러 개일 때

    모범 사례 / 권장 방식
        - 모호하면 그 모호함이 결과의 노이즈가 됨 → 구체적·비중의적으로
        - 중요한 지시는 맨 앞 또는 맨 뒤 (primacy/recency)
        - 부정문만 쓰지 말고 긍정형으로 ("영어로 답하라")
        - few-shot 데모를 쓴다면 여기 또는 바로 뒤에 배치 (Task를 예시로 구체화)
        - baseline에서 "프롬프트 엔지니어링 노력"의 대부분이 여기 들어감 — 부실하면 불공정한 baseline

c. Input(입력)
예시마다 바뀌는 유일한 부분 — 평가셋에서 채워 넣는 변수.

| 항목 | 내용 |
|---|---|
| 구분 표시 | 입력의 시작/끝을 구분자로 명확히 (삼중 백틱, XML 태그, ### 등) → 지시와 혼동 방지 + 프롬프트 인젝션 경계 |
| 일관된 필드 구조 | 입력이 여러 부분(질문+맥락+선택지)이면 매번 같은 라벨 포맷 |
| 위치 | 보통 지시 뒤·프롬프트 끝 근처 (recency). 단, 아주 긴 문서 맥락은 지시 앞이 나을 때도 |
| 전처리 | 잘라내기 규칙, 정규화, 초장문 처리 — 결정적이고 균일하게 |
| 이스케이프 | 입력에 구분자 비슷한 텍스트가 들어갈 수 있으면 처리 (삼중 백틱보다 XML 태그가 견고) |

d. Output Schema(출력스키마)
프롬프트 안에서 응답 형식을 정확히 지정하는 부분. (실제 파싱 함수는 별도 harness에 있고, 이 명세와 일치해야 함.)
    - 정확한 형식: "정확히 한 단어로: positive, negative, neutral", {"label": ..., "confidence": ...} JSON
    - 허용값·enum
    - 근거 서술 허용 여부와 최종답 표시법: "마지막 줄을 Answer: <X>로 끝내라"
    - 군더더기 금지: "설명 없이", "마크다운 없이", "서론 없이"
    - 잘 만든 출력 예시 하나 (미니 one-shot)

    기법
        - 출력 큐: 프롬프트를 Answer:로 끝내서 모델이 이어 쓰게
        - structured output / function calling / 제약 디코딩으로 파싱 실패 원천 차단
        - 스키마는 최소로 — 필드 하나 늘 때마다 실패 지점 하나 늘어남
        - CoT vs 파싱 용이성 긴장 → 태그 블록에 근거 먼저, 그다음 엄격한 최종답 줄로 해소

    출력 형식을 고정하는 이유
        - 목적은 "출력을 무조건 최소화"가 아니라 "측정 대상만 바뀌고 형식은 모든 비교군에 동일"하게 만드는 것. 형식 고정이 기준선에 불리하게 작용할 수도 있다(모델이 자연스럽게 근거 추론(chain-of-thought)을 하고 싶은데 막는 경우). 그래서 형식은 비교군 전체에 똑같이 적용하고, 필요하면 "근거는 태그 블록 안에, 마지막 줄에 최종답" 구조로 절충한다.

| 이유 | 설명 |
|---|---|
| 채점 자동화 | 자유 텍스트에서는 예측을 뽑아낼 수 없다. 형식이 고정돼야 결정적 파서(deterministic parser) 하나로 정답과 대조 가능 |
| 공정한 비교의 전제 | 기준선과 이후 기법(prompt-tuning, PEFT, 미세조정(fine-tuning))이 같은 파서·같은 채점 규칙을 공유해야 한다. 형식이 흔들리면 "성능 차이"에 "형식 준수율 차이"가 섞여 교란 변수(confounding variable)가 된다 |
| 측정 잡음 축소 | 같은 뜻의 답을 매번 다른 문장으로 말하면 파싱 실패가 무작위로 발생 → 신뢰구간이 넓어지고 기법 간 차이를 구분하기 어려워진다 |
| 능력 부족 오인 방지 | 모델이 정답을 알지만 산문으로 답하면 파서가 놓쳐 오답 집계 → 기준선이 실제보다 약해 보이고, 그 위에서 다른 기법이 과대평가된다 |
| 비용·지연 통제 | 근거를 장황하게 붙이면 토큰 수·지연(latency)이 커지고 예시 간 편차도 커진다. 형식 고정으로 출력 길이를 예측 가능하게 |
| 재현성(reproducibility) | 형식이 프롬프트에 명시돼 있어야 다른 사람이 같은 기준선을 재현할 수 있다 |
| 라벨 공간 제약 | 분류에서 허용값(enum)을 고정하면 범위 밖 답("약간 긍정")이 줄어든다 |

    검증 방법
        - 형식 준수율(format adherence rate) 측정: 파서가 유효 예측을 뽑은 비율. 기준선에서 99%+ 목표, 결과표에 항상 병기. 낮으면 스키마 지시·파서부터 수정
        - 파싱 실패 케이스 수집·분류: 실패 원문을 저장해 유형 태깅 (서두 붙임 / 라벨 다르게 표현 / 빈 출력·거부 / 여러 답 나열 / 마크다운·따옴표로 감쌈) → 유형별로 프롬프트나 파서 수정
        - 파서 단위 테스트(parser unit test): 손으로 만든 응답 문자열 20~50개(정상 + 경계 사례 + 이상 입력)에 대해 파서 출력이 기대값과 일치하는지 자동 검증. 파서 수정 시마다 회귀 확인
        - 결정성(determinism) 확인: temperature 0 또는 고정 seed / max_tokens가 형식을 자르지 않는지 / 같은 입력 2회 호출 시 출력 동일한지
        - 프롬프트 민감도(prompt sensitivity): 출력 스키마 지시 문구를 2~3가지로 바꿔 준수율·정확도 분산 측정. 크게 흔들리면 지시가 불안정
        - 제약 디코딩(constrained decoding)과 대조: structured output / logit bias / 문법 제약으로 강제한 버전과 자유 생성 버전의 정확도 비교. 비슷하면 형식이 성능을 왜곡하지 않는다는 근거, 자유 생성이 유의미하게 높으면 형식 고정이 기준선에 불이익 → 스키마 완화 검토
        - 부분집합별(slice) 준수율: 입력 길이·언어·난이도·라벨별로 쪼갬. 특정 구간만 형식 붕괴하면 그 부분 프롬프트 보강
        - 주 지표(primary metric)의 형식 민감도 범위: 파싱 실패를 "전부 정답 가정"한 점수와 "전부 오답 가정"한 점수를 계산. 간격이 좁아야(예: 1%p 이내) 결과가 형식에 안 휘둘린다고 말할 수 있음
        - 실패 처리 정책의 일관성: 오답 처리 / 재시도 / 별도 집계 중 무엇으로 정했든 모든 비교군에 동일 적용됐는지 코드로 확인. 재시도 허용 시 평균 재시도 횟수도 지표로

e. 종합 예시

┌─ Role ─────────────────────────────────────────────

│
├─ Task ─────────────────────────────────────────────

7. PEFT 상세 (Trainable/Frozen parameters, LoRA, Adapter)

ㄱ) 동결 파라미터(frozen parameters) vs 학습 파라미터(trainable parameters)
모든 PEFT의 토대가 되는 구분.

| 구분 | 정의 | PyTorch |
|---|---|---|
| 학습 파라미터 | 학습 중 경사(gradient)를 계산하고 최적화기(optimizer)가 값을 갱신하는 가중치 | requires_grad=True |
| 동결 파라미터 | 순전파에는 쓰이지만 경사를 계산하지 않고 값이 고정되는 가중치 | requires_grad=False |

    for p in model.parameters():
        p.requires_grad = False          # 전체 동결
    for p in model.lora_layers.parameters():
        p.requires_grad = True           # 일부만 학습

    - 왜 메모리를 좌우하나: 학습 파라미터 1개 ≈ 가중치(4B) + 경사(4B) + Adam 상태 2개(8B) = 파라미터당 약 16B. 동결 파라미터는 가중치만
    - 학습 대상을 전체의 1%로 줄이면 최적화기 메모리가 거의 100배 감소 → 소비자 GPU로 대형 모델 튜닝 가능
    - 단, 활성값(activation) 메모리는 별개. 역전파 경로에 있는 레이어의 활성값은 동결이어도 저장해야 함 (LoRA가 완전히 공짜가 아닌 이유)
    - 부수 효과: 파국적 망각(catastrophic forgetting) 완화, 작은 체크포인트, 과적합(overfitting) 감소

ㄴ) PEFT 세 갈래

| 갈래 | 방식 | 대표 기법 |
|---|---|---|
| 추가형(additive) | 새 모듈을 끼워 넣고 그것만 학습 | Adapter, LoRA, 소프트 프롬프트(prompt/prefix-tuning) |
| 선택형(selective) | 기존 파라미터 중 일부만 학습 | BitFit(편향만), 특정 레이어만 |
| 재매개변수화(reparameterization) | 가중치 갱신을 저차원으로 표현 | LoRA |

허깅페이스 peft 라이브러리가 사실상 표준 구현.

ㄷ) LoRA (Low-Rank Adaptation, 저계수 적응)
가중치 행렬 W(d×k)의 갱신량 ΔW를 직접 학습하지 않고 두 작은 행렬 곱으로 분해.

    ΔW = B · A        A: r×k,  B: d×r,  r ≪ min(d, k)
    h  = W·x + (α/r)·B·A·x

    - W는 동결, A와 B만 학습
    - A는 가우시안 랜덤, B는 0으로 초기화 → 학습 시작 시 ΔW=0, 원본 모델과 동일하게 출발
    - r(계수, rank)은 보통 4~64, α는 스케일링 하이퍼파라미터
    - 보통 어텐션의 q·v 투영 행렬에 부착, 최근에는 모든 선형 레이어에도
    - 수치 감각: 7B + r=16 + q·v만 → 학습 파라미터 0.1% 미만, 체크포인트 수십 MB (전체 모델은 fp16로 14GB)

    장점
        - 추론 시 BA를 W에 병합(merge) 가능 → 추가 지연 0 (Adapter와의 결정적 차이)
        - 병합하지 않고 런타임에 여러 LoRA를 교체 → 다중 과제 서빙
        - QLoRA: 베이스 모델을 4비트로 양자화(quantization)해 동결 + 그 위에서 LoRA 학습 → 단일 24GB GPU로 65B급 튜닝
    한계
        - r이 너무 작으면 표현력 부족, 완전히 새로운 능력 습득은 전체 미세조정보다 약할 수 있음

ㄹ) Adapter (어댑터)
트랜스포머 각 층 안(보통 어텐션 뒤, FFN 뒤)에 작은 병목(bottleneck) 모듈을 삽입.

    x → 하향 투영(d→m) → 비선형 → 상향 투영(m→d) → + x(잔차 연결)      m ≪ d

    - 이 모듈만 학습, 나머지 동결. 최초 제안 Houlsby et al. 2019
    - 파라미터: 층당 약 2·d·m, 전체의 1~5%. 성능은 전체 미세조정에 근접

    LoRA와의 비교

| 구분 | Adapter | LoRA |
|---|---|---|
| 삽입 방식 | 층 사이에 순차 모듈 추가 | 기존 가중치와 병렬로 보정 |
| 추론 지연 | 항상 추가 연산 발생 | 병합하면 0 |
| 비선형 | 있음 | 없음(선형 갱신) |
| 계산 그래프 | 새 층이 생김 | 기존 행렬만 수정 |

    - 변형: AdapterFusion(여러 어댑터 조합), Parallel adapter(순차 대신 병렬), (IA)³(활성값에 스케일링 벡터만 곱함)
    - Adapter가 LoRA에 밀린 이유는 추론 지연. 프로덕션에서 LoRA는 병합으로 부담이 사라지는데 어댑터는 매 순전파마다 추가 비용

ㅁ) 종합

|  | 전체 미세조정 | Adapter | LoRA | QLoRA |
|---|---|---|---|---|
| 학습 파라미터 비율 | 100% | 1~5% | 0.1~1% | 0.1~1% |
| 베이스 가중치 | 갱신 | 동결(fp16) | 동결(fp16) | 동결(4비트) |
| 추론 지연 추가 | 없음 | 있음 | 없음(병합 시) | 없음(병합 시) |
| 7B 튜닝 VRAM(대략) | 60GB+ | 16~20GB | 14~18GB | 6~10GB |
| 체크포인트 크기 | 전체 모델 | 수백 MB | 수십 MB | 수십 MB |

8. Fine-tuning 상세

여기서의 미세조정(fine-tuning)은 보통 전체 미세조정(full fine-tuning) — 베이스 모델의 가중치를 실제로 갱신. "fine-tuned 모델"은 가중치가 영구적으로 바뀐 새 체크포인트.

ㄱ) 사전학습과의 차이

| 구분 | 사전학습(pre-training) | 미세조정(fine-tuning) |
|---|---|---|
| 데이터 | 대규모 원문, 비지도 | 소규모, 과제·형식·도메인 특화 |
| 규모 | 수천억~수조 토큰 | 수백~수십만 예시 |
| 목적 | 일반 언어 능력 획득 | 그 능력을 특정 용도로 조정 |
| 학습률 | 상대적으로 큼 | 훨씬 작음 (보통 1e-5 ~ 5e-5) |

이미 학습된 표현을 살짝 미는 작업이라 학습률을 낮게, 에폭(epoch)도 1~3회로 짧게.

ㄴ) 종류

| 종류 | 데이터 | 목적 |
|---|---|---|
| 지도 미세조정(supervised fine-tuning, SFT) | 프롬프트–정답 쌍 | 특정 과제·응답 스타일 학습 |
| 명령어 튜닝(instruction tuning) | 다양한 과제의 지시–응답 | 지시를 따르는 일반 능력 |
| 계속 사전학습(continued pre-training) | 도메인 원문 코퍼스 (비지도) | 새 도메인 지식·용어 주입 |
| 선호 최적화(preference optimization) | 선호 비교 데이터 | 사람 선호에 정렬 — RLHF, DPO, ORPO |
| 다운스트림 과제 적응 | 라벨 데이터 + 분류 헤드 | 분류·추출 등 특정 출력 |

공개된 "instruct" 모델은 이미 명령어 튜닝 + 선호 최적화를 거친 상태. 사용자는 그 위에 자기 SFT를 얹음.

ㄷ) SFT 데이터 형식과 손실 마스킹(loss masking)

    {"messages": [
      {"role": "user",      "content": "다음 리뷰의 감성은? ..."},
      {"role": "assistant", "content": "negative"}
    ]}

    - 베이스 모델의 채팅 템플릿(chat template)에 정확히 맞춰 토큰화 (안 맞으면 형식 붕괴)
    - 손실은 assistant 응답 토큰에만. 프롬프트 부분은 마스킹해 "질문을 외우는" 방향으로 학습되지 않게

ㄹ) 비용과 학습 기법
전체 미세조정은 파라미터당 약 16B(가중치 + 경사 + Adam 상태 2개). 7B 모델이면 100GB를 넘어 다음이 동원됨.
    - 분산: DeepSpeed ZeRO-3, FSDP
    - 경사 체크포인팅(gradient checkpointing): 활성값을 버리고 역전파 때 재계산
    - 혼합 정밀도(mixed precision): bf16
    - 8비트 최적화기(optimizer)
실무에서는 대부분 LoRA/QLoRA로 대체. 전체 미세조정은 데이터가 크고 모델 행동을 근본적으로 바꿔야 할 때만.

ㅁ) 위험 요소

| 위험 | 설명 | 완화 |
|---|---|---|
| 파국적 망각(catastrophic forgetting) | 좁은 데이터에 과적응하며 일반 능력·안전성 저하 | 낮은 학습률, 1~3 에폭, 원본·일반 데이터 섞어 재생(replay) |
| 정렬 비용(alignment tax) | instruct 모델을 SFT하면 안전 정렬이 후퇴할 수 있음 | 안전 데이터 포함, 학습 후 안전성 재평가 |
| 과적합(overfitting) | 작은 데이터 + 많은 에폭 | 조기 종료(early stopping), held-out 검증 손실 모니터링 |
| 데이터 품질 민감 | 소량의 나쁜 예시·라벨 노이즈가 큰 악영향 | 예시 직접 검수, 평가셋 누수 제거 |
| 분포 이동 취약 | 학습 분포 밖 입력에서 급락 | 다양성 확보, 실패 케이스 추가 |

ㅂ) 언제
    하는 경우
        - 프롬프트 + RAG로 한계가 명확할 때 (형식 일관성, 특정 스타일·톤, 프롬프트로 표현 안 되는 암묵적 과제)
        - 짧은 프롬프트로 같은 성능 → 지연·비용 절감
        - 도메인 특화 용어·지식 + 충분한 고품질 데이터(보통 수백~수천+ 예시)
    안 하는 경우
        - 지식이 자주 바뀜 → RAG가 낫다
        - 데이터 부족 / 빠른 반복 필요
        - 프롬프트 개선 여지가 아직 남음

ㅅ) 작업 흐름
    - 베이스 모델 선택 (base vs instruct)
    - 데이터 준비: 채팅 템플릿 통일, 품질 검수, 학습/검증 분리, 평가셋 오염 제거
    - 방법 선택: 전체 미세조정 vs LoRA/QLoRA
    - 하이퍼파라미터: 학습률, 에폭, 배치 크기, warmup, 최대 시퀀스 길이
    - 학습 + 검증 손실 모니터링 (학습 손실만 보면 과적합 놓침)
    - 평가: 타깃 과제 + 일반 능력 회귀 + 안전성 (세 축 모두)
    - 서빙: LoRA는 병합 후 배포, 전체 미세조정은 새 체크포인트

9. 보조 지표 — format success, latency, cost, regression

주 지표(primary metric) 옆에 항상 같이 놓는 가드레일 지표. 주 지표만 보면 "좋아졌다"인데 이쪽에서 문제가 드러나는 경우가 많음.

ㄱ) Format success (형식 준수율)
전체 응답 중 파서가 유효 예측을 뽑은 비율 = 파싱 성공 / 전체. 실패는 유형별 태깅.
    사례
        - 미세조정이 형식을 깬 경우: SFT 후 타깃 정확도 82→87%인데 준수율 99.5→91%. 원인은 학습 데이터가 채팅 템플릿과 안 맞아 "Sure! " 서두를 붙이기 시작. 8.5%가 오답 처리 → 실제 정확도는 더 높았음
        - 긴 입력에서만 붕괴: 전체 98%인데 2000토큰 초과 구간만 84%. 근거를 늘어놓다 최종답 줄 누락
        - 제약 디코딩의 역효과: structured output으로 준수율 100% 달성했지만 정확도 3%p 하락 → 근거 블록 허용으로 완화
    임계값: 기준선에서 99%+ 목표. 그 아래면 스키마 지시·파서부터 수정

ㄴ) Latency (지연)
요청부터 응답 완료까지. 쪼개서 봄.

| 지표 | 의미 |
|---|---|
| 첫 토큰까지 시간(time to first token, TTFT) | 프리필(prefill) 비용 — 입력이 길수록 증가 |
| 토큰당 생성 시간(time per output token) | 디코딩 속도 |
| 전체 완료 시간(end-to-end) | TTFT + 토큰당 시간 × 출력 토큰 수 |

평균이 아니라 분포(p50/p90/p99)로 봐야 함 — 평균은 꼬리를 숨김.
    사례
        - 프롬프트 기법 vs 미세조정: prompt-only 기준선이 16-shot + 근거 추론으로 정확도는 좋으나 p90 4.2초. 같은 정확도를 LoRA + zero-shot + 단답으로 내니 p90 0.6초
        - 꼬리 지연: 평균 800ms로 SLA(1초) 통과처럼 보였으나 p99 3.5초. 일부 입력에서 종료 토큰을 못 내고 max_tokens까지 생성 → stop 시퀀스 추가로 해결
        - 형식 강제의 부작용: JSON 스키마를 키우니 출력 토큰이 늘어 지연 40% 증가 → 필드 최소화

ㄷ) Cost (비용)
예시(또는 1000건)당 비용. API면 입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가, 자체 호스팅이면 GPU 시간 비용 / 처리량(throughput).
    사례
        - few-shot의 숨은 비용: 32-shot이 zero-shot 대비 정확도 +5%p인데 예시당 입력 토큰 200→3800, 월 1000만 건이면 비용 약 19배. 그 5%p를 LoRA로 흡수하면 학습은 1회 비용, 추론은 zero-shot 단가
        - 근거 추론 비용: chain-of-thought로 +3%p인데 출력 토큰 평균 15→220, 출력 단가가 높아 총비용 2.5배 → "근거는 내부적으로, 최종답만 반환"으로 비용 절반
        - 재시도 폭증: 준수율 92%에서 실패분 2회 재시도. 유효 호출은 1.09배로 보이나 재시도가 어려운 부분집합에 몰려 그 구간 비용 3배
    손익분기: 프롬프트 개선 → RAG → PEFT → 전체 미세조정 순으로 초기 비용은 커지지만 추론 단가는 내려감. 어느 쪽이 유리한지는 호출량이 결정

ㄹ) Regression (회귀)
어떤 변경이 기존에 잘되던 것을 망가뜨리는 현상. 총합 지표는 개선처럼 보여도 특정 부분이 후퇴할 수 있음.

| 종류 | 내용 |
|---|---|
| 과제 내 회귀 | 특정 부분집합·라벨·난이도에서만 하락 |
| 일반 능력 회귀 | 타깃은 좋아졌는데 무관한 능력(추론·코딩·다국어) 저하 — 파국적 망각 |
| 안전성 회귀 | 유해 요청 거부율 하락 — 정렬 비용(alignment tax) |
| 형식·표현 회귀 | 톤·길이·형식이 의도치 않게 변함 |

잡는 법: 부분집합별 지표를 항상 같이 봄 / 변경 전후를 같은 예시에서 짝지어 비교(paired) → 개선 예시 수 vs 악화 예시 수 / 반드시 통과해야 하는 회귀 스위트(regression suite) 고정 / 일반 능력 벤치마크를 소규모라도 학습 전후로 실행.
    사례
        - 총합은 +, 부분집합은 -: 프롬프트에 "간결하게 답하라" 추가로 전체 정확도 +2%p인데 다중 근거가 필요한 부분집합은 -9%p (필요한 추론까지 생략) → 그 부분집합에만 예외 지시
        - 파국적 망각: 고객 지원 말투로 SFT 후 타깃 91%인데 held-out 일반 지시 따르기 78→64%, 코드 생성 저하. 원인은 좁은 데이터 3에폭 → 학습률 낮추고 1에폭, 일반 지시 데이터 20% 혼합 재학습 → 타깃 89%, 일반 능력 76% 회복
        - 안전성 회귀: DPO로 유용성(helpfulness)을 올리자 거부해야 할 요청의 거부율 12%p 하락. 선호 데이터에 안전 쌍 부족 → 안전 선호쌍 추가
        - 모델 버전 교체: 공급자가 모델을 업데이트하자 전체 정확도 +1%p인데 JSON 출력에 후행 쉼표가 생겨 파서 5% 실패. 회귀 스위트가 배포 전에 포착

ㅁ) 결과표에 함께 두기

| 변경 | 주 지표 | 형식 준수율 | p90 지연 | 1k건 비용 | 회귀 스위트 |
|---|---|---|---|---|---|
| 기준선(prompt-only) | 0.81 | 99.4% | 4.2s | $12.0 | 기준 |
| + few-shot 32 | 0.86 | 99.1% | 4.8s | $228 | 통과 |
| LoRA + zero-shot | 0.87 | 99.6% | 0.6s | $0.9 | 1건 악화 |

주 지표 한 칸만 보면 few-shot과 LoRA가 비슷하지만, 네 축을 같이 놓으면 선택이 분명해짐.

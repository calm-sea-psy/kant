1. HumanMessage, AIMessage, InMemoryChatMessageHistory

ㄱ) 메시지 객체: 대화의 한 줄을 표현하는 단위
채팅 모델(Chat Model)은 문자열 하나가 아니라 누가 말했는지(역할, role)가 붙은 메시지들의 리스트를 입력으로 받는다. LangChain은 각 역할을 클래스로 나눠 두었다.

| 클래스 | 역할(role) | 의미 |
|---|---|---|
| SystemMessage | system | 모델의 성격이나 규칙을 정하는 지시 |
| HumanMessage | user | 사용자가 한 말 |
| AIMessage | assistant | 모델이 한 대답 |
| ToolMessage | tool | 도구 실행 결과 (나중에 에이전트를 배울 때 등장) |

    from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

    messages = [
        SystemMessage(content="너는 친절한 수학 선생님이야."),
        HumanMessage(content="2 더하기 2는?"),
        AIMessage(content="4입니다."),
        HumanMessage(content="거기에 3을 곱하면?"),
    ]

    response = llm.invoke(messages)   # response 자체가 AIMessage 객체
    print(response.content)           # "12입니다."

    - llm.invoke()의 반환값은 AIMessage이다. 그래서 .content로 텍스트를 꺼낸다. 전에 배운 StrOutputParser는 이 .content를 꺼내 주는 역할을 한다.
    - AIMessage에는 텍스트 말고도 response_metadata(토큰 사용량, 모델명 등)나 tool_calls(도구 호출 요청) 같은 정보가 함께 들어 있다.
    - 모델은 기억이 없다(stateless). 위 예시에서 "거기에"가 무엇을 가리키는지 알 수 있는 이유는, 이전 대화를 HumanMessage와 AIMessage로 리스트에 직접 넣어 줬기 때문이다.

ㄴ) InMemoryChatMessageHistory: 대화 기록을 담는 저장소
모델이 기억을 못 하니, 멀티턴 대화를 하려면 지금까지 주고받은 메시지를 어딘가에 쌓아 두었다가 매번 함께 보내야 한다. 그 "어딘가"를 추상화한 것이 ChatMessageHistory 계열이고, 그중 가장 단순한 구현이 메모리(파이썬 리스트)에 저장하는 InMemoryChatMessageHistory이다.

    from langchain_core.chat_history import InMemoryChatMessageHistory

    history = InMemoryChatMessageHistory()

    history.add_user_message("내 이름은 필수야.")      # HumanMessage로 저장됨
    history.add_ai_message("반가워요, 필수님!")        # AIMessage로 저장됨

    print(history.messages)
    # [HumanMessage(content='내 이름은 필수야.'), AIMessage(content='반가워요, 필수님!')]

    # 다음 질문을 할 때 기록 + 새 질문을 함께 보냄
    history.add_user_message("내 이름이 뭐였지?")
    response = llm.invoke(history.messages)
    history.add_ai_message(response.content)

    - 내부적으로는 그냥 메시지 객체의 리스트이다. .messages로 꺼내고, add_message() / add_user_message() / add_ai_message()로 추가하고, clear()로 비운다.
    - 프로그램이 종료되면 기록이 사라진다. 이름의 "InMemory"가 그 뜻이다. 오래 유지해야 하면 Redis, SQL 같은 다른 저장소 구현으로 바꿔 끼우면 된다. 인터페이스가 같아서 교체가 쉽다.
    - 사용자마다 대화를 따로 관리하려면 보통 session_id를 키로 하는 딕셔너리에 history 객체를 여러 개 담아 둔다.

ㄷ) 관계

    HumanMessage / AIMessage   →  대화의 "한 줄"
    InMemoryChatMessageHistory →  그 줄들을 차곡차곡 쌓는 "공책"
    모델 호출 시               →  공책 전체(.messages)를 통째로 넘겨서 맥락을 전달

즉 LLM의 "기억"은 모델 안에 있는 게 아니라, 애플리케이션이 메시지 기록을 관리해서 매번 다시 보여 주는 것이다. AI 엔지니어 관점에서 꼭 잡아둘 원리이다. 대화가 길어지면 컨텍스트 윈도우를 넘거나 비용이 커지기 때문에, 오래된 메시지를 자르거나 요약하는 전략이 따로 필요해진다.

2. RunnableWithMessageHistory

ㄱ) 사용하는 이유

    ① history에서 이전 메시지 꺼내기
    ② 이전 메시지 + 새 질문을 모델에 넘기기
    ③ 새 질문과 모델 답변을 history에 다시 저장하기

반복되는 3단계를 자동화
이 코드를 매번 쓰는 건 번거롭고 실수하기도 쉽다. RunnableWithMessageHistory는 기존 체인(Runnable)을 감싸서(wrapper) ①과 ③을 자동으로 처리해 주는 Runnable이다. 우리는 ②, 즉 체인을 호출하는 것만 신경 쓰면 된다.

ㄴ) 구성 요소 3가지

① 프롬프트에 기록이 들어갈 자리 만들기: MessagesPlaceholder

    from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

    prompt = ChatPromptTemplate.from_messages([
        ("system", "너는 친절한 비서야."),
        MessagesPlaceholder(variable_name="history"),   # ← 여기에 이전 대화가 통째로 삽입됨
        ("human", "{question}"),
    ])

    chain = prompt | llm | StrOutputParser()

{question}에는 문자열 하나가 들어가지만, MessagesPlaceholder에는 메시지 리스트가 들어간다.

② 세션별 기록을 돌려주는 함수: get_session_history

    from langchain_core.chat_history import InMemoryChatMessageHistory

    store = {}   # session_id → history 객체

    def get_session_history(session_id: str):
        if session_id not in store:
            store[session_id] = InMemoryChatMessageHistory()
        return store[session_id]

"이 세션의 공책을 줘"라고 하면 공책을 꺼내 주고, 처음 온 세션이면 새 공책을 만들어 주는 함수이다.

③ 체인 감싸기

    from langchain_core.runnables.history import RunnableWithMessageHistory

    chat = RunnableWithMessageHistory(
        chain,                                  # 감쌀 체인
        get_session_history,                    # 기록 저장소를 주는 함수
        input_messages_key="question",          # 입력 중 어떤 값이 '사용자의 새 메시지'인지
        history_messages_key="history",         # 기록을 프롬프트의 어느 변수에 넣을지
    )

두 개의 키(key) 이름이 프롬프트의 변수 이름과 정확히 일치해야 한다. 처음 쓸 때 가장 흔히 틀리는 부분이다.

ㄷ) 사용하기: session_id는 config로 전달

    config = {"configurable": {"session_id": "user_A"}}

    chat.invoke({"question": "내 이름은 필수야."}, config=config)
    chat.invoke({"question": "내 이름이 뭐였지?"}, config=config)
    # → "필수님이라고 하셨어요." 같은 답

    chat.invoke({"question": "내 이름이 뭐였지?"},
                config={"configurable": {"session_id": "user_B"}})
    # → "아직 이름을 알려주지 않으셨어요."  (다른 공책을 쓰기 때문)

session_id는 입력 딕셔너리가 아니라 config의 configurable 안에 넣는다. 입력은 "무엇을 물을지", config는 "어떤 환경에서 실행할지"를 나타낸다고 구분하면 기억하기 쉽다.

ㄹ) 내부 동작 흐름

    chat.invoke({"question": ...}, config={session_id: "user_A"})
    │
    ├─ get_session_history("user_A")  → history 객체 획득
    ├─ history.messages를 입력의 "history" 키에 끼워 넣음       ← 자동 ①
    ├─ chain.invoke({"question": ..., "history": [...]})       ← 우리가 만든 체인
    └─ 새 질문(HumanMessage) + 답변(AIMessage)을 history에 추가  ← 자동 ③

LCEL 방식의 Runnable로 포장해 놓았을 뿐이다. 그래서 invoke, stream, batch를 다른 Runnable과 똑같이 쓸 수 있다.

ㅁ) 정리

| 구성 요소 | 역할 |
|---|---|
| MessagesPlaceholder | 프롬프트 안에 대화 기록이 들어갈 자리 |
| get_session_history | session_id로 해당 세션의 history 객체를 반환 |
| input_messages_key | 기록에 저장될 사용자 입력의 키 |
| history_messages_key | 기록이 주입될 프롬프트 변수의 키 |
| config["configurable"]["session_id"] | 어떤 대화방(세션)인지 지정 |

(참고) RunnableWithMessageHistory는 LangChain 문서에서 레거시(legacy) 방식으로 분류된다. 새 프로젝트에서는 LangGraph의 체크포인터(checkpointer)와 thread_id로 대화 메모리를 관리하라고 권장한다. 다만 "세션 ID로 기록을 찾아서, 주입하고, 저장한다"는 원리는 LangGraph에서도 그대로 쓰인다. 그래서 지금 이 구조를 이해해 두면 나중에 LangGraph로 넘어갈 때 그대로 연결된다.

3. BaseCallbackHandler

ㄱ) 콜백(Callback)
체인을 invoke()하면 내부에서 여러 단계가 순서대로 실행된다. 체인 시작, 프롬프트 처리, LLM 호출, 토큰 생성, LLM 종료, 체인 종료 같은 단계들이다. 지금까지는 이 과정이 블랙박스였고 최종 결과만 받아 봤다.

콜백은 "이 사건이 일어나면 내 함수를 불러 줘"라고 미리 등록해 두는 장치이다. BaseCallbackHandler는 그 사건(이벤트)별 메서드들을 모아 둔 부모 클래스이다. 상속한 뒤 관심 있는 메서드만 재정의(override)하면 된다.

용도
    - 로깅/디버깅: 어떤 프롬프트가 실제로 모델에 들어갔는지 확인
    - 스트리밍 출력: 토큰이 생성될 때마다 화면에 바로 표시
    - 비용 추적: 호출마다 토큰 사용량 집계
    - 모니터링: 에러 감지, 실행 시간 측정

ㄴ) 주요 이벤트 메서드
이벤트 이름은 on_<대상>_<시점> 규칙을 따른다.

| 메서드 | 언제 호출되나 |
|---|---|
| on_chat_model_start / on_llm_start | 모델 호출 직전 (입력 메시지/프롬프트 전달됨) |
| on_llm_new_token | 스트리밍 중 토큰이 하나 생성될 때마다 |
| on_llm_end | 모델 응답 완료 (결과와 토큰 사용량 전달됨) |
| on_llm_error | 모델 호출 중 에러 발생 |
| on_chain_start / on_chain_end | 체인(Runnable) 시작과 종료 |
| on_tool_start / on_tool_end | 도구 실행 시작과 종료 (에이전트에서 사용) |

필요한 것만 구현하면 되고, 구현하지 않은 메서드는 아무 일도 하지 않는다.

ㄷ) 핸들러를 붙이는 두 가지 방법
① 실행할 때 붙이기 (요청 단위, 권장)

    chain.invoke({"question": "하늘은 왜 파래?"},
                 config={"callbacks": [MyHandler()]})

이렇게 붙이면 체인 안의 모든 하위 단계(프롬프트, 모델, 파서)에 전파된다. 그래서 on_chain_start부터 on_llm_new_token까지 전부 받을 수 있다. 지난번 session_id처럼 config로 넘긴다는 점도 같다.

② 객체를 만들 때 붙이기 (생성자 단위)

    llm = ChatOllama(model="...", callbacks=[MyHandler()])

이 방식은 그 객체에서 일어나는 이벤트만 받는다. 하위로 전파되지 않는다. 모델 호출만 항상 감시하고 싶을 때 쓰면 된다.

| 방식 | 범위 | 언제 쓰나 |
|---|---|---|
| config={"callbacks": [...]} | 체인 전체 + 모든 하위 단계 | 요청별 로깅, 스트리밍, 추적 |
| 생성자 callbacks=[...] | 그 객체 하나만 | 특정 컴포넌트를 항상 감시 |

ㄹ) 정리

    체인 실행 ──┬─ on_chain_start
                ├─ on_chat_model_start   ← 실제 입력 확인
                ├─ on_llm_new_token ×N   ← 실시간 출력
                ├─ on_llm_end            ← 결과·토큰 사용량
                └─ on_chain_end
                    ↑
            BaseCallbackHandler를 상속해서 원하는 시점에만 코드 삽입

    - 비동기 체인(ainvoke, astream)에서는 AsyncCallbackHandler를 상속해 async def로 구현한다.
    - 기본 제공 핸들러로 StdOutCallbackHandler(콘솔 출력) 등이 있다.
    - LangSmith 같은 추적(tracing) 도구도 내부적으로 이 콜백 시스템 위에서 동작한다. run_id/parent_run_id로 실행 트리를 구성한다.
    - 스트리밍 이벤트만 필요하다면 콜백을 직접 만드는 대신 chain.astream_events()로 이벤트를 받아 처리하는 방법도 있다. 최근에는 이쪽을 더 많이 쓴다.

4. Retry와 Fallback
LLM은 외부 서비스나 무거운 로컬 프로세스에 의존한다. 그래서 일반 함수보다 실패할 일이 훨씬 많다.
    - 일시적 실패: 네트워크 끊김, 타임아웃(timeout), 요청 한도 초과(rate limit), 서버 과부하
    - 지속적 실패: 모델 서버 다운, 모델 미설치, API 키 만료
    - 출력 실패: 모델이 형식에 안 맞는 응답을 내서 파서(parser)가 에러를 냄

LangChain의 모든 Runnable에는 이런 상황에 대응하는 메서드가 두 개 있다.

| 구분 | Retry | Fallback |
|---|---|---|
| 메서드 | .with_retry() | .with_fallbacks() |
| 전략 | 같은 것을 다시 시도 | 다른 것으로 대체 |
| 비유 | 전화가 안 되면 다시 걸기 | 계속 안 되면 다른 사람에게 걸기 |
| 적합한 실패 | 일시적 실패 | 지속적 실패, 출력 실패 |

ㄱ) Retry: 같은 Runnable을 다시 실행

    llm_with_retry = llm.with_retry(
        retry_if_exception_type=(TimeoutError, ConnectionError),  # 이 에러일 때만 재시도
        stop_after_attempt=3,                                     # 최대 3번 시도
        wait_exponential_jitter=True,                             # 재시도 간격을 점점 늘림
    )

    chain = prompt | llm_with_retry | StrOutputParser()

a. 핵심 파라미터

| 파라미터 | 의미 | 기본값 |
|---|---|---|
| stop_after_attempt | 최대 시도 횟수 (첫 시도 포함) | 3 |
| retry_if_exception_type | 어떤 에러일 때 재시도할지 | 모든 에러(Exception) |
| wait_exponential_jitter | 대기 시간을 1초, 2초, 4초…로 늘리고 약간의 무작위성을 더함 | True |

b. 생각해 볼 점
    - 지수 백오프(exponential backoff)를 쓰는 이유: 서버가 과부하일 때 즉시 재요청을 퍼부으면 상황이 더 나빠진다. 간격을 점점 벌려서 서버가 회복할 시간을 준다. 무작위성(jitter)은 여러 클라이언트가 동시에 재시도하는 것을 막아 준다.
    - 재시도할 에러를 좁혀야 한다. 입력이 잘못된 경우처럼 다시 해도 결과가 같은 에러(결정적 에러)는 재시도해 봤자 시간만 버린다. retry_if_exception_type으로 일시적 에러만 지정하는 게 좋다.
    - 어디에 붙이느냐가 재시도 범위를 정한다. llm.with_retry()는 모델 호출만 다시 하고, chain.with_retry()는 체인 전체를 처음부터 다시 실행한다. 실패할 수 있는 단계에만 좁게 붙이는 편이 효율적이다.

ㄴ) Fallback: 실패하면 대체 Runnable로 넘어가기

    primary = ChatOllama(model="qwen3:14b")
    backup  = ChatOllama(model="qwen3:4b")       # 더 가볍고 안정적인 예비 모델

    llm_with_fallback = primary.with_fallbacks([backup])

    chain = prompt | llm_with_fallback | StrOutputParser()

a. 동작 방식

    primary 실행 ──성공──→ 결과 반환
         │
        실패
         ↓
    backup 실행 ──성공──→ 결과 반환
         │
        실패 → 마지막 에러를 그대로 발생

fallbacks에는 리스트를 넘긴다. 그래서 [backup1, backup2, ...]처럼 여러 단계의 예비책을 순서대로 지정할 수 있다. exceptions_to_handle=(...) 파라미터를 주면 특정 에러에서만 대체하도록 제한할 수도 있다.

b. 활용 패턴
① 모델 대체: 비싼/큰 모델이 실패하면 저렴한/작은 모델로 넘어간다. 다른 제공자(provider)로 넘어가게 할 수도 있다. 예를 들면 클라우드 API가 실패할 때 로컬 Ollama로 넘어가는 구성이다.

② 체인 전체 대체: 출력 파싱 실패까지 대비하려면 체인 단위로 대체해야 한다.

    strict_chain = prompt | llm | JsonOutputParser()          # JSON을 기대
    loose_chain  = prompt | llm | StrOutputParser()           # 실패하면 그냥 텍스트로

    chain = strict_chain.with_fallbacks([loose_chain])

여기서 흔히 실수하는 점이 있다. llm.with_fallbacks(...)처럼 모델에만 Fallback을 붙이면, 그 뒤에 있는 파서의 에러는 잡히지 않는다. Fallback은 자신이 감싼 범위 안의 에러만 처리한다. Retry를 어디에 붙이느냐와 같은 원리이다.

ㄷ) 함께 쓰기
"몇 번 다시 해 보고, 그래도 안 되면 다른 걸로"처럼 둘을 조합한다.

    robust_llm = (
        primary.with_retry(stop_after_attempt=2)       # 주 모델로 2번까지 시도
               .with_fallbacks([backup])               # 그래도 실패하면 예비 모델
    )

    primary 1차 실패 → (대기) → primary 2차 실패 → backup 실행

주의할 점이 하나 있다. 많은 모델 클래스(예: ChatOpenAI의 max_retries)는 클라이언트 내부에 자체 재시도 기능을 이미 갖고 있다. 이걸 켠 채로 Fallback을 붙이면 주 모델이 내부에서 한참 재시도하느라 예비 모델로 늦게 넘어간다. Fallback을 쓸 때는 주 모델의 내장 재시도를 줄이거나 끄는 것(max_retries=0 등)이 일반적이다.

ㄹ) 정리

| 질문 | 답 |
|---|---|
| 잠깐 문제였을 수도 있다면? | Retry: 같은 걸 간격을 두고 다시 |
| 이 방법 자체가 안 된다면? | Fallback: 준비해 둔 다른 방법으로 |
| 어디에 붙여야 하나? | 감싼 범위의 에러만 처리되므로, 실패 가능한 범위를 정확히 감싸야 함 |
| 둘 다 쓰려면? | .with_retry(...).with_fallbacks([...]) |

두 메서드 모두 Runnable을 받아서 Runnable을 돌려준다. 그래서 |로 연결하거나 다른 체인 안에 넣는 등 LCEL 조합을 그대로 쓸 수 있다. 앞에서 배운 "모든 것은 Runnable" 원리가 여기서도 적용된다.

ㅁ) 참고
    - with_fallbacks(..., exception_key="error")를 지정하면 앞 단계에서 난 에러 객체가 입력에 담겨 예비 Runnable로 전달된다. "이런 에러가 났으니 고쳐서 다시 답해" 같은 자기 수정(self-correction) 패턴에 쓸 수 있다.
    - Retry나 Fallback이 실제로 일어났는지 확인하고 싶으면, 지난번에 배운 콜백의 on_llm_error로 실패 시점을 로깅하면 된다.

5. 예외 유형과 그에 따른 정책

ㄱ) 출발점: 에러마다 대응이 달라야 한다
with_retry()의 기본값은 모든 에러(Exception)에서 재시도이다. 편해 보이지만 실제로는 위험하다.
    - API 키가 틀렸는데 3번 재시도하면 시간만 낭비하고 결과는 같다.
    - 코드에 오타(KeyError)가 있는데 재시도하면 버그가 가려진다.
    - 요청 한도 초과(rate limit)인데 즉시 재시도하면 한도에 더 빨리 걸린다.

그래서 실전에서는 에러를 먼저 분류하고, 분류별로 정책을 정해 둔다. 분류할 때는 두 가지만 물어보면 된다.

    질문 1: 똑같이 다시 하면 결과가 달라질 수 있나?    → 예: Retry
    질문 2: 다른 방법(모델, 입력, 파서)으로 하면 되나?  → 예: Fallback
    둘 다 아니오                                        → 즉시 실패(Fail fast) + 알림

ㄴ) 예외 유형 분류
① 일시적 에러(Transient Error): 시간이 지나면 풀린다

| 상황 | 대표 신호 |
|---|---|
| 요청 한도 초과(Rate limit) | HTTP 429, RateLimitError |
| 서버 과부하/일시 장애 | HTTP 500, 502, 503, 529 |
| 타임아웃 | TimeoutError, httpx.ReadTimeout |
| 네트워크 끊김 | ConnectionError, httpx.ConnectError |

정책: Retry (지수 백오프). 429 응답에는 Retry-After 헤더로 "몇 초 뒤에 다시 와"를 알려 주는 경우가 많고, 이걸 따르는 게 가장 정확하다. 재시도를 다 써도 실패하면 Fallback으로 넘어간다.

② 영구적 에러(Permanent Error): 다시 해도 똑같다

| 상황 | 대표 신호 | 정책 |
|---|---|---|
| 인증 실패 | 401, 403, AuthenticationError | Fail fast + 알림. 사람이 키를 고쳐야 함 |
| 모델 없음/이름 오타 | 404, Ollama의 "model not found" | 설정 오류면 Fail fast. 운영 중 모델이 내려간 것이면 Fallback |
| 잘못된 요청 형식 | 400, BadRequestError | Fail fast. 코드를 고쳐야 함 |

이 유형은 절대 Retry하지 않는다. 결과가 바뀌지 않으니 재시도는 지연과 비용만 늘린다.

③ 입력 문제: 요청 내용 자체가 한도를 넘었다

| 상황 | 대표 신호 |
|---|---|
| 컨텍스트 길이 초과 | 400 + "context length exceeded" 계열 메시지 |

정책: 입력을 줄이거나, 더 큰 모델로 Fallback. 같은 입력으로 재시도하면 반드시 다시 실패한다. 대신 대화 기록(history)에서 오래된 메시지를 자르거나 요약하고 다시 보내거나, 컨텍스트 윈도우가 더 큰 모델로 넘긴다.
"대화가 길어지면 자르거나 요약하는 전략"이 바로 이 에러를 예방하는 장치이다.

④ 출력 문제: 모델이 기대와 다른 형식으로 답했다

| 상황 | 대표 신호 |
|---|---|
| JSON 파싱 실패 | OutputParserException |
| 스키마 불일치 | Pydantic ValidationError |

정책: 조건부 Retry, 그다음 Fallback. 이 유형은 특이하다. LLM은 같은 입력에도 매번 조금씩 다르게 답하므로(비결정적, temperature > 0) 다시 하면 성공할 수도 있다. 그래서 1~2번 정도는 재시도할 가치가 있다.

그다음 단계로 쓸 수 있는 방법은 이렇다.
    - 에러를 피드백하는 재시도: "방금 응답이 이런 이유로 파싱에 실패했으니 형식을 고쳐서 다시 답해"라고 에러 내용을 같이 보낸다. 자기 수정(self-correction) 패턴이다.
    - 느슨한 파서로 Fallback: JSON을 포기하고 텍스트로라도 받는다.
    - 구조화된 출력(Structured Output) 사용: 앞에서 배운 with_structured_output()처럼 모델 자체 기능으로 형식을 강제하면 이 에러가 애초에 줄어든다.

⑤ 프로그래밍 버그: 우리 코드가 틀렸다

| 상황 | 대표 신호 |
|---|---|
| 프롬프트 변수 누락 | KeyError (예: {question}을 안 넘김) |
| 타입 실수 | TypeError, AttributeError |

정책: 무조건 Fail fast. 재시도나 Fallback으로 감싸면 버그가 조용히 숨겨진다. with_retry()의 기본값(Exception 전체)이 위험한 이유가 바로 이것이다.

ㄷ) 정책 한눈에 보기

| 유형 | Retry | Fallback | Fail fast | 핵심 대응 |
|---|---|---|---|---|
| ① 일시적 | ✅ | 재시도 소진 후 | | 백오프 후 재시도 |
| ② 영구적 | ❌ | 모델 장애면 ✅ | ✅ | 설정 수정, 알림 |
| ③ 입력 초과 | ❌ | 큰 모델로 ✅ | | 입력 줄이기 |
| ④ 출력 형식 | 1~2회 | 느슨한 파서로 ✅ | | 에러 피드백, 구조화 출력 |
| ⑤ 코드 버그 | ❌ | ❌ | ✅ | 코드 수정 |

ㄹ) 코드로 옮기기: 계층으로 쌓는다

    import httpx
    from langchain_core.exceptions import OutputParserException

    # ① 일시적 에러만 재시도 대상으로 지정
    TRANSIENT = (httpx.ConnectError, httpx.ReadTimeout, TimeoutError)

    robust_llm = (
        primary.with_retry(
            retry_if_exception_type=TRANSIENT,   # 범위를 좁게
            stop_after_attempt=3,
        )
        .with_fallbacks(
            [backup],
            exceptions_to_handle=TRANSIENT,      # 버그는 대체하지 않고 그대로 터지게
        )
    )

    # ④ 출력 문제는 체인 단위로 대응
    strict = prompt | robust_llm | JsonOutputParser()
    loose  = prompt | robust_llm | StrOutputParser()
    chain = strict.with_fallbacks([loose], exceptions_to_handle=(OutputParserException,))

    # 마지막 방어선: 애플리케이션 경계
    try:
        result = chain.invoke({"question": q})
    except Exception as e:
        log_error(e)                                   # 기록 + 필요하면 알림
        result = "지금은 답변을 드릴 수 없어요. 잠시 후 다시 시도해 주세요."

a. 구조

    안쪽   Retry          일시적 에러를 조용히 흡수
     ↓     Fallback       같은 방법이 안 되면 대안으로
     ↓     체인 Fallback  출력 형식 문제 대응
    바깥   try/except     사용자에게는 친절한 메시지, 개발자에게는 로그

exceptions_to_handle과 retry_if_exception_type으로 범위를 명시하는 것이 이 전체 설계의 핵심이다. 지정하지 않은 에러(버그 등)는 계층을 통과해서 그대로 드러나야 한다.

ㅁ) 원칙
    - 타임아웃은 직접 설정해야 한다. 타임아웃이 없으면 응답 없는 서버를 무한정 기다리느라 에러 자체가 안 난다. 그러면 Retry도 Fallback도 작동할 기회가 없다.
    - 부작용(side effect)이 있는 작업은 재시도를 조심해야 한다. 메일 전송이나 결제 같은 도구 호출을 재시도하면 두 번 실행될 수 있다. 여러 번 실행해도 결과가 같은 성질(멱등성, idempotency)이 보장될 때만 재시도한다. 나중에 에이전트에서 도구를 다룰 때 중요해진다.
    - 우아한 성능 저하(Graceful Degradation)를 고려한다. 최선의 결과가 안 되면 조금 못한 결과라도 주는 것이 아무것도 안 주는 것보다 낫다. 작은 모델의 답, 텍스트 형태의 답, 캐시된 답 등이 해당된다. Fallback은 이 원칙을 구현하는 도구이다.

6. UserAnswer

ㄱ) 문제: Fallback을 붙이면 출력 형태가 경로마다 달라질 수 있다

    strict = prompt | llm | JsonOutputParser()    # → dict 반환
    loose  = prompt | llm | StrOutputParser()     # → str 반환
    chain  = strict.with_fallbacks([loose])

with_fallbacks()는 실패하면 실행할 Runnable만 바꿔 줄 뿐, 출력 타입을 맞춰 주지는 않는다. 그래서 이 체인은 성공 경로에 따라 dict를 줄 때도 있고 str을 줄 때도 있다. 이 체인을 쓰는 쪽 코드는 결국 이렇게 된다.

    result = chain.invoke(...)
    if isinstance(result, dict):
        text = result["answer"]
    else:
        text = result            # 경로마다 분기... 새 Fallback이 추가되면 또 분기

체인 내부 사정(어느 경로로 성공했는지)이 바깥으로 새어 나온 상태이다. 해결책은 "어떤 경로로 가든 최종 출력은 반드시 같은 형태"라는 약속, 즉 출력 계약(Output Contract)을 정하는 것이다.

ㄴ) 출력 계약 정의: UserAnswer
Pydantic 모델로 계약을 정의한다.

    from typing import Literal
    from pydantic import BaseModel

    class UserAnswer(BaseModel):
        answer: str                                        # 사용자에게 보여줄 내용
        source: Literal["primary", "fallback", "static"]   # 어느 경로에서 나왔나
        degraded: bool = False                             # 품질이 낮아진 답인가

필드는 두 종류로 나뉜다.
    - 내용 필드(answer): 사용자가 실제로 보는 데이터이다.
    - 메타데이터 필드(source, degraded): 어떤 경로로 만들어졌는지 기록한다. 형태는 통일하되 어디서 왔는지에 대한 정보는 잃지 않기 위한 장치이다.

ㄷ) 구조: 각 경로의 끝에서 계약 형태로 변환한다
핵심은 각 경로(branch)의 마지막 단계에 어댑터(adapter)를 두어, 경로 안에서 직접 UserAnswer로 바꾸는 것이다.

    from langchain_core.runnables import RunnableLambda

    # ── Primary: 구조화된 출력으로 풍부하게 ──
    class AnswerBody(BaseModel):          # LLM이 채울 스키마 (메타데이터는 제외)
        answer: str

    primary_branch = (
        prompt
        | primary_llm.with_structured_output(AnswerBody)
        | RunnableLambda(lambda b: UserAnswer(answer=b.answer, source="primary"))
    )

    # ── Fallback: 작은 모델 + 단순 텍스트 ──
    fallback_branch = (
        prompt
        | backup_llm
        | StrOutputParser()
        | RunnableLambda(lambda s: UserAnswer(answer=s, source="fallback", degraded=True))
    )

    # ── 최후의 방어선: 절대 실패하지 않는 고정 응답 ──
    static_branch = RunnableLambda(
        lambda _: UserAnswer(
            answer="지금은 답변을 드릴 수 없어요. 잠시 후 다시 시도해 주세요.",
            source="static",
            degraded=True,
        )
    )

    chain = primary_branch.with_fallbacks([fallback_branch, static_branch])

a. 구조

                      ┌─ primary_branch ── 구조화 출력 ──→ [어댑터] ─┐
    입력(같은 dict) ──┼─ fallback_branch ─ 텍스트 ───────→ [어댑터] ─┼──→ UserAnswer
                      └─ static_branch ── 고정 메시지 ───→ [어댑터] ─┘
                           (내부 방식은 제각각)                (출구는 하나)

이제 쓰는 쪽 코드는 경로를 신경 쓰지 않는다.

    result: UserAnswer = chain.invoke({"question": q})
    show(result.answer)
    if result.degraded:
        show_badge("간이 답변")         # 필요하면 메타데이터로만 구분

ㄹ) 이 구조의 설계 포인트

① 계약은 입구와 출구 양쪽에 있다
    - 모든 경로는 같은 입력(예: {"question": ...})을 받아야 한다. Fallback이 실행될 때는 Primary가 받았던 입력이 그대로 전달되기 때문이다. 그리고 모든 경로는 같은 출력(UserAnswer)을 내야 한다. 입력과 출력이 같으니 바깥에서 보면 세 경로는 서로 바꿔 끼워도 되는 부품이 된다.

② 변환은 소비자가 아니라 각 경로 안에서 한다
    - 경로마다 출력이 다른 이유는 그 경로의 사정이다. 예를 들어 구조화 출력을 쓰느냐, 텍스트를 쓰느냐 같은 것이다. 그러니 그 사정을 정리하는 책임도 경로 안에 둔다. 새 Fallback을 추가할 때 그 경로의 끝에 어댑터만 붙이면 되고, 소비자 코드는 한 줄도 바뀌지 않는다.

③ Fallback은 어댑터까지 포함해서 감싼다
    - prompt | llm | parser | 어댑터 전체를 하나의 경로로 묶어야 한다. 그래야 파싱 실패나 계약 위반(ValidationError)도 에러로 취급되어 다음 경로로 넘어간다. Pydantic은 객체를 만드는 순간 검증하기 때문에, 어댑터가 일종의 "계약 검문소" 역할을 하게 된다. 계약을 지키지 못한 출력은 밖으로 나가지 못한다.

④ LLM용 스키마와 앱용 계약을 분리한다
    - Primary에서 with_structured_output(UserAnswer)를 바로 쓰지 않고 AnswerBody를 따로 둔 이유가 여기 있다. source나 degraded는 시스템이 아는 사실이지 모델이 판단할 내용이 아니다. 모델에게 채우게 하면 틀린 값을 넣을 수도 있다. 그래서 모델은 내용만 만들고, 메타데이터는 어댑터가 확정한다.

⑤ 마지막 경로는 실패하지 않게 만든다
    - static_branch는 LLM을 부르지 않아서 실패할 일이 없다. 그래서 이 체인은 어떤 상황에서도 UserAnswer를 반환한다. 지난번 구조에서 맨 바깥의 try/except가 하던 "사용자에게 친절한 메시지" 역할을 체인 안의 정식 경로로 옮긴 것이다. 우아한 성능 저하(Graceful Degradation)를 계약 수준에서 보장하는 셈이다.
    - 단, 실전에서는 exceptions_to_handle로 처리할 에러 범위를 좁혀서 코드 버그까지 고정 메시지로 덮어 버리지 않게 해야 한다.

⑥ 메타데이터로 관찰 가능성을 유지한다
    - 형태를 통일하면 "어떤 경로가 실행됐는지"가 감춰지기 쉽다. source 필드가 있으면 로그에서 Fallback 발생 비율을 집계할 수 있다. 예를 들어 "오늘 요청의 30%가 fallback으로 처리됨"이라는 사실은 Primary 모델에 문제가 있다는 신호이다. 계약은 통일하되 정보는 숨기지 않는 것이 중요하다.

ㅁ) 정리

| 요소 | 역할 |
|---|---|
| UserAnswer | 모든 경로가 지켜야 할 출력 계약 |
| 경로별 어댑터 | 경로마다 다른 출력을 계약 형태로 변환하고 검증 |
| with_fallbacks | 실패 시 경로 전환 (타입 변환은 하지 않음) |
| static_branch | 절대 실패하지 않는 마지막 경로 → 항상 계약 형태 반환 보장 |
| source, degraded | 통일된 형태 안에서 경로 정보를 보존 |

    - 한 문장으로 요약하면 이렇다. "내부 구현은 경로마다 달라도 되지만, 출구는 하나의 계약으로 모은다." 객체지향에서 인터페이스(interface)를 정의하고 여러 구현체를 바꿔 끼우는 것과 같은 원리이다. 덕분에 Fallback을 추가하거나 빼도 체인을 쓰는 쪽은 영향을 받지 않는다.

7. 우아한 성능 저하(Graceful Degradation)

ㄱ) 개념: 일부가 망가져도 전체는 계속 돌아가게
Graceful Degradation은 시스템의 일부 구성 요소가 실패했을 때 전체가 멈추는 대신, 기능이나 품질을 조금 낮춰서라도 계속 서비스하는 설계 원칙이다.
    - 엘리베이터가 고장 나도 건물은 폐쇄되지 않는다. 계단으로 다닐 수 있다.
    - 쌍발 비행기는 엔진 하나가 꺼져도 속도는 줄지만 착륙할 수 있게 설계된다.
    - 쇼핑몰의 개인화 추천 서비스가 죽으면 페이지 전체가 에러가 나는 대신 "인기 상품 목록"을 보여 준다.

반대 개념은 전면 실패(Total Failure)이다. 부품 하나의 문제가 전체 서비스 중단으로 번지는 상황이다.

    전면 실패:        [정상] ─────────────── 💥 → [아무것도 안 됨]
    우아한 성능 저하: [정상] → [조금 낮은 품질] → [최소 기능] → [안내 메시지]
                              단계적으로 내려가며 끝까지 무언가를 제공

ㄴ) 핵심 질문: 무엇이 "핵심"이고 무엇이 "부가"인가
설계는 기능을 두 종류로 나누는 데서 시작한다.

| 구분 | 의미 | 실패 시 |
|---|---|---|
| 핵심 기능 | 이게 안 되면 서비스의 존재 이유가 없음 | 어떻게든 지켜야 함 |
| 부가 기능 | 있으면 좋지만 없어도 핵심은 동작 | 끄거나 단순화해도 됨 |

예를 들어 RAG 기반 질의응답 서비스라면 이렇게 나눌 수 있다.
    - 핵심: 사용자 질문에 답한다.
    - 부가: 출처 표시, 후속 질문 추천, 대화 기록 반영, 스트리밍 출력, 답변 서식 꾸미기

부가 기능이 실패하면 그 기능만 조용히 빼고 핵심을 계속 제공한다. 출처 추출이 실패했다고 답변 전체를 버릴 이유는 없다.

ㄷ) LLM 애플리케이션에서의 성능 저하 사다리
UserAnswer 구조가 바로 이 사다리를 구현한 것이었다. 더 일반화하면 다음과 같은 단계를 생각할 수 있다.

| 단계 | 방법 | 잃는 것 |
|---|---|---|
| 0 | 큰 모델 + 전체 기능 (정상) | 없음 |
| 1 | 작은 모델/다른 제공자로 대체 | 답변 품질 일부 |
| 2 | 컨텍스트 축소 (오래된 대화 기록 자르기, 검색 문서 수 줄이기) | 맥락 반영 정도 |
| 3 | 부가 기능 끄기 (도구 호출, 구조화 출력, 출처 표시) | 편의 기능 |
| 4 | 캐시된 답변 반환 (같거나 비슷한 질문의 이전 답) | 최신성 |
| 5 | 생성 없이 검색 결과만 보여 주기 ("관련 문서는 이것입니다") | 요약·자연스러운 답변 |
| 6 | 고정 안내 메시지 | 답변 자체 (하지만 시스템은 살아 있음) |

아래로 내려갈수록 품질은 낮아지지만 실패 가능성도 낮아진다. 마지막 단계는 외부 의존성이 전혀 없어서 실패하지 않는다. 지난번 static_branch가 이 역할이었다.

ㄹ) 설계 원칙
① 사용자에게 알린다 (투명성)
    - 품질이 낮아졌다면 사용자도 알아야 한다. "간이 답변", "일부 기능이 일시적으로 제한됨" 같은 표시를 붙인다. UserAnswer.degraded 필드가 이 정보를 UI까지 전달하는 통로이다. 낮은 품질의 답을 정상 답인 척 내보내면 신뢰가 깨진다.

② 개발자에게도 알린다 (관찰 가능성)
    - 성능 저하는 사용자 입장에서는 "그럭저럭 동작"이지만, 시스템 입장에서는 장애가 발생 중이라는 신호이다. 성능 저하가 너무 매끄러우면 아무도 문제를 모른 채 몇 주가 지날 수 있다. source 필드로 경로를 기록하고, 콜백의 on_llm_error로 실패를 로깅하고, Fallback 비율이 높아지면 알림이 오게 해야 한다.

③ 틀린 답보다 "모른다"가 나을 때가 있다
    - 이 원칙의 한계이자 가장 중요한 주의점이다. 성능 저하는 "낮은 품질이라도 주는 게 낫다"는 전제를 깔고 있지만, 항상 그런 것은 아니다.

| 성능 저하가 적절한 경우 | 오히려 위험한 경우 |
|---|---|
| 잡담, 요약, 아이디어 제안 | 의료, 법률, 금융 판단 |
| 추천, 검색 보조 | 정확한 수치나 계산이 필요한 답 |
| 틀려도 사용자가 쉽게 알아챔 | 틀린 답이 그럴듯해서 믿고 행동하게 됨 |

    - 작은 모델이 그럴듯하지만 틀린 답을 내놓는 것은 고정 안내 메시지보다 해로울 수 있다. 이런 영역에서는 단계 1~5를 건너뛰고 곧바로 정직한 안내 메시지(단계 6)로 가는 것이 올바른 설계이다.

④ Fail fast와 충돌하지 않는다
    - "코드 버그는 Fail fast"라고 했는데, 성능 저하와 모순처럼 보일 수 있다. 둘은 적용되는 위치가 다르다.

        내부(개발자 쪽) : Fail fast            → 버그는 숨기지 않고 즉시 드러냄 (로그, 알림)
        경계(사용자 쪽) : Graceful Degradation → 사용자에게는 무너진 화면 대신 안내를 보여 줌

    - 버그를 성능 저하로 덮어서 아무도 모르게 하면 안 된다. 그렇다고 사용자에게 스택 트레이스(stack trace)를 보여 줘도 안 된다. 문제는 개발자에게 크게 알리고, 사용자에게는 부드럽게 보여 주는 것이 두 원칙을 함께 쓰는 방법이다.

⑤ 회복은 자동으로
    - Primary가 다시 살아나면 별도 조치 없이 정상 경로로 돌아와야 한다. with_fallbacks()는 요청마다 Primary부터 시도하므로 이 성질을 기본으로 갖고 있다.

ㅁ) 정리

| 질문 | 답 |
|---|---|
| 무엇인가? | 일부 실패 시 전체를 멈추지 않고 품질을 낮춰 계속 서비스하는 원칙 |
| 출발점은? | 핵심 기능과 부가 기능을 구분하는 것 |
| LangChain에서 구현 도구는? | with_fallbacks()로 만드는 단계적 경로 + 같은 출력 계약 |
| 사용자에게는? | 품질 저하 사실을 알림 (degraded 표시) |
| 개발자에게는? | 장애 신호로 기록하고 알림 (source, 콜백, Fallback 비율) |
| 언제 쓰면 안 되나? | 틀린 답이 답 없음보다 해로운 영역 |

Retry/Fallback은 도구, 예외 정책은 언제 어떤 도구를 쓸지에 대한 규칙, 출력 계약은 경로가 바뀌어도 형태를 지키는 장치이다. 그리고 Graceful Degradation은 이 모든 것이 향하는 설계 목표이다.

8. 백오프(Backoff)와 지터(Jitter)
두 개념 모두 "재시도할 때 얼마나 기다렸다가 다시 할 것인가"에 대한 답이다. Retry에서 "몇 번 할지"만큼 중요한 것이 "언제 할지"이다.

ㄱ) 기다리지 않고 재시도하면 생기는 문제
서버가 과부하로 응답을 못 하는 상황을 생각해 보자.

    요청 실패 → 즉시 재시도 → 실패 → 즉시 재시도 → 실패 → ...

서버는 이미 요청이 너무 많아서 쓰러졌는데, 클라이언트는 실패할 때마다 바로 요청을 또 보낸다. 재시도가 부하를 더 늘려서 회복을 방해한다. 요청 한도 초과(429)라면 한도가 풀리기도 전에 남은 시도 횟수를 다 써 버린다.

그래서 재시도 사이에 기다리는 시간이 필요하다. 이 대기 전략이 백오프(Backoff, 물러서기)이다.

ㄴ) 백오프: 실패할수록 더 오래 기다린다

| 전략 | 대기 시간 (1차, 2차, 3차, 4차, 5차) | 특징 |
|---|---|---|
| 즉시 재시도 | 0, 0, 0, 0, 0초 | 서버에 부담, 거의 쓰지 않음 |
| 고정(Fixed) | 2, 2, 2, 2, 2초 | 단순하지만 장애가 길면 소용없음 |
| 선형(Linear) | 1, 2, 3, 4, 5초 | 조금씩 늘어남 |
| 지수(Exponential) | 1, 2, 4, 8, 16초 | 실패할수록 빠르게 늘어남 |

a. 지수 백오프(Exponential Backoff)
    - 표준이다. 매번 대기 시간을 두 배로 늘리는 방식이다.
    - 첫 실패는 순간적인 문제일 가능성이 크니 금방 다시 해 본다. 그런데 계속 실패한다면 장애가 생각보다 심각하다는 증거이다. 그러니 점점 더 크게 물러나서 서버가 회복할 시간을 준다. "실패가 반복될수록 상황 판단을 보수적으로 바꾼다"는 원리이다.

b. 상한(Cap)
    - 지수는 금방 커진다. 10번째 시도에서는 대기가 512초(약 8.5분)가 된다. 사용자가 그만큼 기다려 줄 리 없으니 최대 대기 시간을 정해 둔다.

        대기 = min(초기값 × 2^(시도 횟수 - 1), 상한)

        초기값 1초, 상한 10초:  1 → 2 → 4 → 8 → 10 → 10 → ...

ㄷ) 지터: 대기 시간에 무작위성을 섞는다

a. 몰려드는 무리(Thundering Herd)
    - 지수 백오프만으로는 부족한 이유는 클라이언트가 하나라면 백오프만으로 충분하다. 하지만 실제 서비스에는 클라이언트가 수백, 수천 개 있다. 서버가 잠깐 멈췄다면 모든 클라이언트가 같은 순간에 실패한다. 그리고 모두 같은 백오프 규칙을 쓰니 이렇게 된다.

                        0초    1초    3초         7초
    클라이언트 A~Z:     💥     💥     💥          💥
                       실패   동시   동시        동시
                              재시도 재시도      재시도
                       (1000개 요청이 같은 순간에 한꺼번에 몰림)

    - 대기 시간은 늘었지만 재시도가 정확히 같은 시점에 몰린다. 서버가 회복하자마자 1000개의 요청이 동시에 들이닥쳐서 다시 쓰러진다. 이것을 몰려드는 무리 문제(Thundering Herd Problem)라고 한다.

b. 해결: 무작위로 흩뿌린다
    - 지터(Jitter, 흔들림)는 대기 시간에 무작위 값을 섞어서 재시도 시점을 분산시키는 기법이다.

    지터 적용 후:
    시간 →  0초 ────── 1초 ────── 2초 ────── 3초 ────── 4초
            💥     ·  ·· · ·  ·  · ·  · ·  ·  · ·  ·   · ·
            실패       재시도가 시간축 위에 고르게 흩어짐

    - 같은 수의 요청이라도 한순간에 몰리지 않고 퍼져서 도착하므로, 서버가 감당할 수 있다.

c. 지터를 섞는 방식

| 방식 | 대기 시간 계산 | 특징 |
|---|---|---|
| 더하기 지터(Additive) | 지수 백오프 값 + 0~1초 사이 무작위 | 단순함, 분산 효과는 약한 편 |
| 전체 지터(Full Jitter) | 0 ~ 지수 백오프 값 사이에서 무작위 | 분산 효과가 가장 큼, 널리 권장됨 |
| 절반 지터(Equal Jitter) | 지수 백오프 값의 절반 + 나머지 절반 범위에서 무작위 | 최소 대기 시간을 보장하면서 분산 |

지수 백오프로 4초를 기다릴 차례라면 이렇게 된다.

    더하기 지터:  4.0 ~ 5.0초 사이 중 하나
    전체 지터:    0.0 ~ 4.0초 사이 중 하나
    절반 지터:    2.0 ~ 4.0초 사이 중 하나

ㄹ) LangChain
with_retry()의 wait_exponential_jitter=True가 바로 이 두 가지를 합친 옵션이다. 기본값이 켜져 있어서 따로 지정하지 않아도 지수 백오프와 지터가 적용된다.

    llm.with_retry(
        stop_after_attempt=4,
        wait_exponential_jitter=True,             # 지수 백오프 + 지터 (기본값)
        exponential_jitter_params={
            "initial": 1,    # 첫 대기 시간(초)
            "max": 10,       # 상한(초)
            "exp_base": 2,   # 몇 배씩 늘릴지
            "jitter": 1,     # 더할 무작위 값의 최대치(초)
        },
    )

    - LangChain은 내부적으로 tenacity라는 재시도 라이브러리를 쓴다. 이 옵션은 위 표의 더하기 지터 방식에 해당한다.

ㅁ) 유의할 점
    - 서버가 기다릴 시간을 알려 주면 그게 우선이다. 429 응답의 Retry-After 헤더처럼 서버가 "N초 뒤에 와"라고 하면, 직접 계산한 백오프보다 그 값이 정확하다. 많은 공식 SDK가 이를 자동으로 처리한다.
    - 총 대기 시간을 사용자 관점에서 계산해 본다. 4번 시도에 1, 2, 4초를 기다리면 응답 대기만 7초 이상이다. 여기에 각 요청의 타임아웃 시간까지 더해진다. 사용자가 기다려 줄 수 있는 시간을 넘는다면 시도 횟수를 줄이고 일찍 Fallback으로 넘어가는 것이 낫다. Graceful Degradation과 연결되는 판단이다.
    - 백오프는 일시적 에러에만 의미가 있다. 영구적 에러(인증 실패 등)는 아무리 오래 기다려도 결과가 같다. 예외 정책에서 재시도 대상을 좁혀야 하는 이유가 여기서도 적용된다.

ㅂ) 정리

| 개념 | 해결하는 문제 | 핵심 |
|---|---|---|
| 백오프 | 재시도가 서버 부하를 키움 | 실패할수록 더 오래 기다림 (지수 증가) |
| 상한 | 대기 시간이 끝없이 커짐 | 최대 대기 시간 제한 |
| 지터 | 여러 클라이언트의 재시도가 같은 순간에 몰림 | 대기 시간에 무작위성을 섞어 분산 |

백오프는 "얼마나" 기다릴지를, 지터는 "다 같이 기다리지 않도록" 하는 장치이다. 백오프는 클라이언트 하나의 입장에서, 지터는 시스템 전체의 입장에서 생각한 해법이다.

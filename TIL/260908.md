1. 텍스트 분류 fine-tuning 문제 정의
이진 분류 기준의 클래스 불균형·confusion matrix·F1·임계값·leakage·봉인 테스트는 260814·260818 에 있다. 트랜스포머 입력 표현·재현성 메타데이터는 260902·260907 에 있다. 이 파일은 텍스트 분류와 다중클래스, Hugging Face 도구로 확장되는 부분만 남긴다.

ㄱ) 입력 정의
분류 단위를 먼저 정한다 — 무엇 하나에 라벨을 붙이는가. 문장 / 문단 / 문서 전체 / 문장쌍.

| 항목 | 정해야 할 것 |
|---|---|
| 텍스트 형태 | 원문 그대로인가, 제목과 본문을 합치는가, 이모지·URL·HTML 처리 방식 |
| 부가 정보 | 작성자·시각·카테고리 등 메타데이터를 넣을지, 넣으면 텍스트에 녹일지 별도 feature 로 둘지 |
| 길이 분포 | 토큰 길이 히스토그램을 보고 max_length 와 truncation 정책을 정함 (BERT 계열 512 상한) |
| 언어·도메인 | 구어체·전문용어·오탈자 포함 여부 |
| 단일 vs 쌍 | 문장쌍이면 token_type_ids 로 세그먼트를 구분하고 SEP 로 경계를 넣음 |

학습 때 보는 입력과 배포 후 들어올 입력이 같아야 한다. 전처리도 학습과 추론에서 똑같이 적용한다.

ㄴ) 출력 정의
분류 유형(이진·다중클래스·다중레이블)과 그에 따른 손실 함수는 260811 에 있다. fine-tuning 에서 추가로 정할 것.

    - 순서형(ordinal) 라벨: 별점 1~5처럼 순서가 있는 경우. 분류로 풀면 순서 정보가 버려진다. "먼 오류"가 "가까운 오류"보다 나쁘므로 회귀도 고려하고 MAE 를 같이 본다 (7절)
    - id2label / label2id 매핑을 처음에 고정하고 config 에 저장한다. 순서가 바뀌면 조용히 틀린다 (260907)
    - 범위 밖(out-of-scope) 입력용 "기타 / 판단보류" 클래스를 둘지 결정한다. 안 두면 모델이 모든 입력을 억지로 분류한다
    - 출력을 argmax 라벨로 쓸지, 확률값으로 임계값 튜닝까지 할지 결정한다 (이진 임계값은 260814)

ㄷ) 라벨링 가이드라인
데이터 품질의 상한을 정하는 부분이다. 모델은 라벨보다 정확해질 수 없다.

    - 각 클래스를 문장으로 정의하고 대표 예시를 포함·불포함 모두 단다
    - 경계 사례 규칙: 애매하면 어디로 보내는가, 두 클래스에 다 걸리면 우선순위는 무엇인가 (tie-breaking)
    - 일관성: 같은 입력은 항상 같은 라벨. 라벨링 기간이 길면 기준이 흐려지는 drift 를 막는다
    - 주석자(annotator) 간 일치도를 측정한다 (Cohen's kappa 등). 낮으면 가이드라인이 모호하다는 신호다
    - 골드셋: 전문가 합의로 만든 소량의 정답 셋. 평가와 주석자 검증에 쓴다
    - 클래스 분포를 기록한다. 심한 불균형이면 지표 선택과 샘플링에 영향을 준다
    - 라벨 노이즈 수준을 추정해 둔다. 이게 달성 가능한 성능의 천장이다

ㄹ) 성공 기준 — 텍스트·다중클래스 특유분
비교 기준·held-out·시간 분리·test 1회 원칙은 260818 봉인 테스트와 같다. 여기에 더할 것.

    - 코드 짜기 전에 결정 지표(primary metric) 하나를 못 박는다. 다중클래스면 macro-F1 이나 per-class recall 이 흔하다 (6절)
    - 슬라이스별 성능을 본다. 도메인별·길이별·(해당되면) 집단별로 쪼개서 확인한다
    - 운영 조건(지연시간·메모리·비용)도 성공 기준의 일부다

2. 클래스 불균형의 학습 역학과 텍스트식 대응
정의·imbalance ratio·accuracy paradox·오버/언더샘플링·SMOTE·임계값 조정은 260814·260818 에 있다. 여기서는 학습이 실제로 어떻게 망가지는지와 텍스트 fine-tuning 에서의 대응만 남긴다.

ㄱ) 왜 학습이 망가지나
    - 손실이 다수 클래스에 지배된다. cross-entropy 총합은 샘플 수에 비례한다. 배치에 다수 클래스가 훨씬 많으니 gradient 도 다수 클래스를 잘 맞추는 방향으로 쏠린다. 소수 클래스는 틀려도 전체 손실이 별로 안 늘어난다
    - 결정 경계가 소수 클래스 쪽으로 밀린다. 애매하면 다수 클래스로 찍는 게 안전하다고 학습한다. 소수 클래스 recall 이 급락한다
    - 확률이 왜곡된다 (calibration). 소수 클래스의 예측 확률이 실제보다 낮게 나온다. argmax 기준으로는 아예 안 뽑히는 클래스가 생긴다

ㄴ) 텍스트 fine-tuning 에서의 대응
    - 클래스 가중치. cross-entropy 에서 소수 클래스 오류에 더 큰 페널티를 준다. Trainer 의 compute_loss 를 오버라이드해 넣는다. 보통 가중치는 전체수 나누기 (클래스수 곱하기 클래스별 샘플수)
    - focal loss. 이미 잘 맞추는 쉬운 샘플의 손실을 줄이고 어려운 샘플에 집중한다. 극단적 불균형에서 쓴다
    - 텍스트 증강. 소수 클래스 문장을 역번역·동의어 치환·LLM 생성으로 변형해 늘린다. 변형 후 라벨이 유지되는지 확인한다
    - 지표. macro-F1(클래스 동등), balanced accuracy(클래스별 recall 평균) (6절)

ㄷ) 사전학습 모델은 불균형에 덜 취약하다
사전학습 모델은 이미 언어를 알고 있어서 소수 클래스도 적은 예시로 어느 정도 학습된다. scratch 학습보다 불균형에 덜 취약하다. 그래서 클래스 가중치와 임계값 조정과 macro 지표 조합이면 충분한 경우가 많고, 복잡한 리샘플링까지 안 가도 되는 경우가 흔하다.

3. 텍스트 데이터 점검 — 결측·중복
leakage 다섯 유형·봉인 테스트·group/temporal split 은 260818 에 있다. 여기서는 텍스트에서 특히 문제되는 결측·중복과, 타깃 누수의 텍스트 사례만 남긴다. 순서는 정규화 → 결측·이상 제거 → 중복 제거 → split → 전처리 fit(train만) → 분포 재확인.

ㄱ) 결측
텍스트나 라벨이 비어 있는 행.

| 위치 | 형태 |
|---|---|
| 텍스트 | 빈 문자열, None/NaN, 공백만, 한두 글자, 인코딩 깨짐(mojibake), "N/A"·"-"·"null" 같은 placeholder 문자열 |
| 라벨 | 라벨 없는 행, 정의 밖 라벨 값, 표기 불일치(positive / Positive / pos) |

    - 점검: null 개수, 빈·공백 문자열 개수, 텍스트 길이 최솟값 분포, 라벨 unique 값 확인
    - 대응: 텍스트 결측 행은 보통 제거, 라벨 결측은 제거하거나 재라벨링, 라벨 표기 정규화(대소문자·공백 통일), placeholder 문자열을 실제 결측으로 변환

ㄴ) 중복

| 종류 | 설명 |
|---|---|
| 완전 중복 (exact) | 텍스트가 문자열로 100% 일치. 이분법 판단 |
| near-duplicate | 거의 같음. 공백·대소문자·구두점 차이, 리트윗, 템플릿 문장, 잘린 버전, 오타 교정본. 임계값이 필요 |
| 라벨 충돌 중복 | 텍스트는 같은데 라벨이 다름. 주석(annotation) 불일치 신호 |

    - exact 탐지: 해시, 또는 정규화 후 exact(소문자화·strip·공백 축약 뒤 비교)
    - near-dup 탐지: edit distance, Jaccard 유사도, MinHash + LSH(대규모), 문장 임베딩 코사인 유사도. 유사도가 임계값 이상이면 중복으로 간주
    - 대응: 완전 중복은 1개만 남기고 제거, 라벨 충돌은 검수·재라벨, near-dup 은 임계값을 정해 제거. 모두 split 전에
    - 실무 순서: 정규화 후 exact 로 1차 제거 → 남은 것에 near-dup 탐지

ㄷ) 타깃 누수의 텍스트 사례
입력 안에 라벨이 사실상 들어있는 경우 (260818 target 누수의 텍스트판).

    - 라벨링 후 본문에 "[SPAM]" 태그가 남아 있음
    - 라벨 근거가 된 메타데이터(감사자 코멘트 등)가 텍스트에 포함됨
    - 대응: 라벨 흔적·근거 컬럼을 제거한다

4. DatasetDict 와 재현 가능한 split
train/valid/test 의 역할·분할 이유·stratify 개념은 260811·260813·260818 에 있다. 여기서는 Hugging Face datasets 의 자료구조와, seed 가 실제로 하는 일만 남긴다.

ㄱ) 두 객체

| 객체 | 정체 |
|---|---|
| Dataset | 하나의 테이블. 행은 샘플, 열은 feature. Apache Arrow 기반이라 컬럼 지향이고 메모리맵으로 큰 데이터도 RAM 을 안 넘긴다 |
| DatasetDict | split 이름에서 Dataset 으로 가는 매핑. 파이썬 dict 처럼 동작 |

    DatasetDict({
        train:      Dataset({features: ['text', 'label'], num_rows: 8000}),
        validation: Dataset({features: ['text', 'label'], num_rows: 1000}),
        test:       Dataset({features: ['text', 'label'], num_rows: 1000}),
    })

features 가 ClassLabel(names=["neg","pos"]) 이면 라벨을 정수로 저장하고 int2str / str2int, id2label 을 자동 제공한다.

ㄴ) DatasetDict 에 걸면 모든 split 에 일괄 적용
map(), filter(), rename_column(), cast_column(), remove_columns(), with_format("torch") 는 DatasetDict 에 걸면 train·validation·test 모두에 적용된다.

ㄷ) seed 가 하는 일
split 은 행을 무작위로 섞어 나눈다. 난수 생성기(RNG)의 시작 상태가 seed 다. seed 가 같으면 같은 난수열이 나오고, 같은 셔플이 되고, 같은 split 이 된다.

    - datasets: ds.train_test_split(test_size=0.2, seed=42, stratify_by_column="label")
    - 전역(python·numpy·torch): transformers.set_seed(42)
    - seed 는 무작위를 없애는 게 아니라 "고정된 무작위"로 만드는 것이다. 여전히 잘 섞인다
    - 라이브러리·버전이 바뀌면 같은 seed 라도 결과가 달라질 수 있다
    - 무작위 지점이 여러 개다 (split, 모델 초기화, dropout, DataLoader shuffle). split seed 는 고정하되 최종 평가는 학습 seed 를 여러 개로 돌려 평균과 표준편차를 본다
    - GPU 비결정 연산 때문에 seed 를 고정해도 완전 재현이 안 될 수 있다 (torch.use_deterministic_algorithms(True))

ㄹ) seed 재현에 기대지 말고 split 결과 자체를 저장
원본 데이터·버전·전처리 순서가 다르면 같은 seed 라도 다른 split 이 나온다.

    - 각 행의 id 를 train_ids.txt / val_ids.txt / test_ids.txt 로 저장
    - 또는 ds.save_to_disk() / parquet 로 고정
    - 데이터가 크면 id 목록·해시만 git 에 커밋
    - 함께 기록: 원본 데이터 해시·행 수·Hub revision, split 파라미터(test_size·seed·stratify 기준), 라이브러리 버전, 전처리 순서, 결과 분포(split별 행 수·클래스별 개수)

재현성 메타데이터 일반론(revision·torch_dtype·generation_config 등)은 260907 에 있다.

5. 텍스트를 모델 입력으로 — map 과 DataCollatorWithPadding
input_ids·attention_mask·token_type_ids 의 의미, 패딩·어텐션 마스크 개념은 260902·260907 에 있다. 여기서는 토큰화를 언제 어디서 하느냐, 두 도구의 분업만 남긴다.

ㄱ) 두 단계로 나눈다

    "이 영화 재밌다"
      |
      |  (1) Dataset.map(tokenize)   한 번만, 캐시됨
      v
    input_ids  [2, 1234, 5678, 9012, 3]   행마다 길이 다름, 패딩 없음
      |
      |  (2) DataCollatorWithPadding   배치 만들 때마다
      v
    {input_ids (B,L), attention_mask (B,L), labels (B,)}   → model

토큰화는 예시당 한 번만 하면 되니 미리 해서 디스크에 캐시한다. 패딩은 한 배치에 어떤 예시들이 묶이느냐에 따라 달라지니 로드 시점에 한다.

ㄴ) Dataset.map() 으로 토큰화

    def tokenize(batch):
        return tokenizer(batch["text"], truncation=True, max_length=256)

    tokenized = ds.map(tokenize, batched=True, remove_columns=["text"])

map 에 넘긴 함수가 dict 를 반환하면 그 dict 의 각 키가 Dataset 의 새 열이 된다. 토크나이저 호출 결과가 바로 그 dict 다.

| 인자 | 역할 |
|---|---|
| batched=True | batch["text"] 가 문자열 리스트로 들어옴. fast tokenizer 가 한 번에 처리해서 수십 배 빠름 |
| truncation=True + max_length | 상한 넘으면 자름. max_length 생략 시 모델 기본값 |
| remove_columns=["text"] | 원본 텍스트 열 제거. 안 지우면 나중에 텐서화하다 에러 |
| num_proc=4 | 멀티프로세스 |

    - 결과는 행마다 길이가 다른 input_ids 다. Arrow 로 디스크 캐시되어 같은 함수·데이터면 재실행 시 재사용된다
    - map 에서 패딩하지 않는 이유: padding="max_length" 로 모든 행을 256까지 채우면 짧은 문장도 256 토큰이 되어 저장·연산이 낭비된다. 패딩 토큰도 attention 계산에 들어간다

ㄷ) DataCollatorWithPadding
DataLoader 가 뽑은 예시 리스트를 받아 그 배치 안에서 제일 긴 길이에 맞춰 패딩하고 텐서로 묶는다.

    from transformers import DataCollatorWithPadding
    collator = DataCollatorWithPadding(tokenizer)

    trainer = Trainer(..., data_collator=collator)

    - input_ids 를 배치 최대 길이에 맞춰 pad_token_id 로 채운다
    - attention_mask 도 확장한다. 패딩 자리는 0
    - token_type_ids 등 다른 시퀀스 필드도 패딩한다
    - labels 는 패딩하지 않는다 (시퀀스 분류는 예시당 스칼라)
    - 전부 torch.Tensor 로 스택한다

ㄹ) dynamic padding vs max_length 패딩

| 구분 | map(padding="max_length") | DataCollatorWithPadding |
|---|---|---|
| 시점 | 전처리 시 1회 | 배치 로드마다 |
| 길이 | 모든 예시 동일 (max_length) | 배치별 최댓값 |
| 효율 | 짧은 문장도 꽉 채움, 낭비 | 낭비 적음 |
| 쓰는 경우 | 고정 shape 필요 (TPU, torch.compile, ONNX export) | 일반 GPU 학습, 기본 권장 |

pad_to_multiple_of=8 을 주면 텐서코어 효율을 위해 길이를 8의 배수로 맞춘다.

6. 다중클래스 평가 지표

ㄱ) 평균 방식 세 가지
다중클래스는 클래스별로 precision·recall·F1 을 따로 구한 뒤 하나로 합친다. 합치는 방식이 셋이다.

| 방식 | 계산 | 성격 |
|---|---|---|
| macro | 클래스별 지표의 단순 평균 | 클래스 동등. 소수 클래스가 중요할 때 |
| weighted | 클래스별 지표를 support(샘플 수)로 가중 평균 | 전체 성능 요약. 불균형을 가림 |
| micro | 전체 TP/FP/FN 를 합산해 한 번 계산 | 샘플 동등. 단일라벨 다중클래스에선 accuracy 와 같음 |

ㄴ) per-class
per-class 는 지표 종류가 아니라 계산 단위다. precision·recall·F1 을 하나로 합치지 않고 클래스마다 한 줄씩 낸 것이다. sklearn 의 classification_report 출력이 전형적인 예다.

                    precision   recall   f1-score   support
        긍정          0.91      0.94      0.92        500
        중립          0.62      0.55      0.58        120
        부정          0.88      0.85      0.86        380

        accuracy                          0.87       1000
        macro avg      0.80      0.78      0.79       1000
        weighted avg   0.87      0.87      0.87       1000

    - 위 3줄이 per-class 지표, support 는 그 클래스의 실제 샘플 수
    - macro avg 는 per-class 값들의 단순 평균. (0.92 + 0.58 + 0.86) 나누기 3 은 약 0.79
    - per-class 가 원자료, macro 가 그 요약이다

ㄷ) Macro-F1
클래스마다 F1 을 따로 계산한 뒤 클래스 수로 단순 평균한 것. macro-F1 = (F1_1 + F1_2 + ... + F1_K) 나누기 K. 각 F1_k 는 그 클래스 자기 자신의 precision·recall 로 계산한다. 클래스 크기는 평균에 안 들어간다. 모든 클래스가 1/K 로 동등하다.

a. 예시
3클래스 불균형: 긍정 800 / 중립 50 / 부정 150 (총 1000)

| 클래스 | precision | recall | F1 |
|---|---|---|---|
| 긍정 | 0.90 | 0.95 | 0.924 |
| 중립 | 0.50 | 0.30 | 0.375 |
| 부정 | 0.80 | 0.75 | 0.774 |

    - macro-F1 = (0.924 + 0.375 + 0.774) 나누기 3 = 0.691
    - weighted-F1 = (800 곱 0.924 + 50 곱 0.375 + 150 곱 0.774) 나누기 1000 = 0.874
    - micro-F1 은 accuracy 와 같고 약 0.89

전체 지표는 0.87~0.89 로 좋아 보이지만 중립 클래스가 망가진 걸(F1 0.375) macro-F1 만 0.69 로 드러낸다. 다수 클래스에 묻힌 소수 클래스 성능을 표면화하는 게 macro-F1 의 존재 이유다.

b. 함정
    - 모델이 어떤 클래스를 한 번도 예측 안 하면 그 클래스 precision 이 0, F1 이 0 이 되어 macro-F1 이 1/K 만큼 통째로 깎인다 (sklearn 은 zero_division 경고와 함께 0 처리)
    - 희소 클래스에 민감하다. 20개짜리 클래스가 800개짜리와 같은 가중치다. 그 클래스 F1 이 샘플이 적어 들쭉날쭉하면 macro-F1 도 불안정해진다
    - 너무 희소한 클래스는 병합하거나 평가에서 제외할지 판단한다

c. 사용 여부

| 쓴다 | 안 쓴다 |
|---|---|
| 모든 클래스가 똑같이 중요 (소수 클래스 포함) | 클래스 중요도가 실제 빈도에 비례하면 weighted·micro |
| 불균형에서 묻힌 성능을 드러내고 싶을 때 | 아주 희소한 클래스가 노이즈면 macro 가 불안정 |
| 클래스 간 공정성 | |

7. 다중클래스 confusion matrix 와 오류 유형

ㄱ) 다중클래스 행렬 읽기
행은 실제 클래스, 열은 예측 클래스. 셀 [i, j] 는 실제 i 인데 j 로 예측한 샘플 수 (sklearn 관례, 축이 반대인 자료도 있으니 확인). 대각선이 맞은 것, 대각선 밖이 틀린 것. K개 클래스면 K×K.

| 실제 \ 예측 | 긍정 | 중립 | 부정 | 합(실제) |
|---|---|---|---|---|
| 긍정 | 760 | 30 | 10 | 800 |
| 중립 | 20 | 15 | 15 | 50 |
| 부정 | 25 | 13 | 112 | 150 |
| 합(예측) | 805 | 58 | 137 | 1000 |

    - 행으로 나누면 recall. 중립 recall = 15/50 = 0.30
    - 열로 나누면 precision. 중립 precision = 15/58 = 0.26
    - 비대각 셀이 구체적 오류. 중립을 긍정으로 20개, 부정으로 15개. 중립이 양쪽으로 새고 있음
    - normalize="true"(행 정규화)로 보면 클래스 크기와 무관하게 오류율을 비교할 수 있음

ㄴ) 오분류의 방향
    - K개 클래스면 오류 종류가 K(K-1)개다 (i 에서 j 로 가는 모든 순서쌍)
    - "A를 B로 착각"과 "B를 A로 착각"은 다른 오류이고 비용도 다를 수 있다
    - 큰 비대각 셀이 자주 나는 오류이고 우선 고칠 대상이다

ㄷ) 원인별 분류
자주 나는 오류 셀에서 예시 10~20개를 직접 읽으며 분류한다.

| 원인 | 증상 | 대응 |
|---|---|---|
| 라벨 오류 | 모델이 맞았는데 정답이 틀림 | 데이터 정제, 재라벨 |
| 모호한 경계 | 사람도 애매 | 라벨 가이드 보완, 성능 상한으로 인정 |
| 데이터 부족 | 그 패턴의 학습 예시가 적음 | 데이터 추가 수집·증강 |
| shortcut 학습 | 표면 단서(특정 단어)에 의존 | 반례 데이터 추가 |
| 분포 밖(OOD) | 학습에 없던 유형 | 범위 정의, "기타" 클래스 |
| truncation | 긴 문서가 잘려 핵심 누락 | max_length 조정 |
| 전처리 손상 | 이모지·인코딩 깨짐 | 전처리 수정 |

ㄹ) 심각도 — cost matrix 와 순서형
    - 모든 오분류의 비용이 같지 않다. 비용 행렬(cost matrix)로 셀마다 비용을 부여해 기대 비용을 최소화한다
    - 예: 의료 3단계(정상/경증/중증)에서 "중증을 정상으로"가 "경증을 정상으로"보다 훨씬 비싸다
    - 순서형(ordinal) 라벨이면 축을 순서대로 배열했을 때 대각선에서 멀리 떨어진 오류일수록 나쁘다. accuracy·F1 은 이걸 무시하므로 MAE(라벨을 숫자로 보고 절댓값 오차의 평균)를 같이 본다. 실제 5, 예측 4 는 오차 1, 실제 5, 예측 1 은 오차 4

8. Hugging Face 파인튜닝 파이프라인 (텍스트 분류)

ㄱ) 전체 순서
    - 데이터 로드: load_dataset 또는 Dataset.from_pandas → DatasetDict 
    - split: train/validation/test 로 나누고 stratify·seed 고정 
    - 토크나이저 로드: AutoTokenizer.from_pretrained(ckpt) 
    - 토큰화: ds.map(tokenize, batched=True, remove_columns=["text"]) 
    - 라벨 열 이름 맞추기: rename_column("label", "labels"). 모델이 손실 계산에 labels 를 찾는다
    - 모델 로드: AutoModelForSequenceClassification.from_pretrained(ckpt, num_labels, id2label, label2id) 
    - collator: DataCollatorWithPadding(tokenizer) 
    - compute_metrics 정의: logits → argmax → macro_f1 등 
    - TrainingArguments 설정 (ㄴ)
    - Trainer 조립 후 trainer.train()
    - 최종 평가: trainer.evaluate(tokenized["test"]). 딱 한 번
    - 저장: trainer.save_model(path). 추론용

ㄴ) TrainingArguments
학습에 관한 모든 설정을 담는 객체. 하이퍼파라미터 + 언제 평가·저장·로깅할지 + 정밀도·분산학습 옵션.

| 범주 | 주요 인자 |
|---|---|
| 경로·저장 | output_dir, save_strategy("no"/"steps"/"epoch"), save_total_limit, load_best_model_at_end, save_safetensors |
| 평가 | eval_strategy, eval_steps, per_device_eval_batch_size, metric_for_best_model, greater_is_better |
| 로깅 | logging_strategy, logging_steps, report_to("tensorboard"/"wandb"/"none"), run_name |
| 최적화 | learning_rate(분류 2e-5~5e-5), per_device_train_batch_size, gradient_accumulation_steps, num_train_epochs(2~4), weight_decay(0.01), warmup_ratio(0.1), lr_scheduler_type, max_grad_norm(1.0) |
| 성능·정밀도 | bf16/fp16(Blackwell 이면 bf16), gradient_checkpointing, group_by_length, dataloader_num_workers |
| 재현성 | seed, data_seed |

유효 배치 크기는 per_device_train_batch_size 곱하기 gradient_accumulation_steps 곱하기 GPU 수다.

ㄷ) Trainer 의 역할
직접 짜야 할 학습 루프를 대신 돌린다.

    - DataLoader 생성, epoch·step 반복, 배치 순회(iteration)
    - forward → loss → backward → optimizer.step → scheduler.step → zero_grad
    - gradient accumulation, gradient clipping
    - mixed precision(bf16·fp16), 멀티 GPU·분산학습(DDP·FSDP·DeepSpeed)
    - 평가 루프 (eval_dataset 예측 수집 후 compute_metrics 호출)
    - 로깅 (loss·lr·metric 을 콘솔·TensorBoard·W&B 로)
    - 체크포인트 저장·재개, best model 추적
    - callback (early stopping 등)

모델이 labels 를 받으면 loss 를 반환하는 Hugging Face 모델이면 그대로 동작한다. 커스텀 손실은 compute_loss 를 오버라이드한다.

ㄹ) 조립과 logging · evaluation · save 동작
Trainer 에 model, args(TrainingArguments), train_dataset, eval_dataset(validation), data_collator, tokenizer, compute_metrics, callbacks 를 넘겨 조립한다. train() 으로 학습하고, evaluate(test) 로 최종 평가하고, save_model(path) 로 저장한다.

a. logging 동작
    - 정해둔 주기마다 train loss, learning rate, epoch, gradient norm 을 콘솔과 로깅 대상(TensorBoard·W&B)에 출력한다
    - 평가 시점엔 eval loss 와 compute_metrics 결과가 함께 기록된다 (eval_ 접두사)
    - 전체 로그 이력이 Trainer 내부에 쌓여 나중에 직접 plot 할 수 있다

b. evaluation 동작
    - eval 주기(epoch 또는 step)마다 validation 전체로 예측하고 compute_metrics 를 호출한다
    - compute_metrics 는 예측 logits 과 정답 라벨을 받는다. logits 이므로 argmax 는 직접 한다
    - metric_for_best_model 로 지정한 지표가 best 체크포인트 판정 기준이 된다
    - 개발 중에는 validation 만 본다. test 는 학습이 끝난 뒤 한 번만 평가한다

c. save 동작
    - 저장 주기마다 체크포인트 폴더가 생긴다. 모델 가중치 + optimizer·scheduler 상태 + RNG + 학습 상태(재개용 풀 세트)
    - 보관 개수를 제한하면 오래된 체크포인트는 지워지고 best 는 보호된다
    - load_best_model_at_end 를 켜면 학습이 끝날 때 best 지표 체크포인트를 메모리로 되돌린다. 저장 주기와 평가 주기가 같아야 동작한다
    - save_model 은 추론용 최소 파일만 저장한다 (config, 가중치, 토크나이저). optimizer 상태는 없다. 배포용이다
    - 체크포인트에서 학습을 이어서 재개할 수 있다

ㅁ) 학습 후 추론 (저장된 모델 사용)
save_model 로 저장한 폴더에는 config, 가중치, 토크나이저가 들어 있다.

    - pipeline 의 text-classification 에 저장 경로를 주면 토크나이즈 → 모델 → softmax → id2label 매핑까지 한 번에 처리한다. 라벨이 "긍정" 처럼 이름으로 나오는 건 저장된 config 의 id2label 덕분
    - 직접 하려면 토크나이저와 AutoModelForSequenceClassification 로 로드하고 logits 에 argmax 한 뒤 config 의 id2label 로 매핑한다
    - 다중레이블이나 임계값 튜닝이 필요하면 pipeline 대신 직접 로드해 sigmoid 후 클래스별 임계값을 적용한다
    - 배포 재현성: 저장 전 예측과 재로드 후 예측이 같은지 확인한다 

ㅂ) 파인튜닝 도구 지형

| 상황 | 실무 도구 |
|---|---|
| 작은 encoder 분류 (BERT·RoBERTa·DeBERTa) | transformers + Trainer, full fine-tune. GPU 1장, 저렴 |
| 생성형 LLM 파인튜닝 (Llama·Qwen) | peft(LoRA·QLoRA) + trl(SFTTrainer), 또는 Axolotl·Llama-Factory·Unsloth. 전부 transformers 위 |
| 인프라 없이 | 매니지드 파인튜닝 API (JSONL 업로드) |

LLM 애플리케이션에서 도구를 꺼내는 순서는 보통 프롬프트 → RAG → 파인튜닝이다. 큰 모델 full fine-tune 은 앱 개발 실무에서 드물고, 작은 분류기 파인튜닝이 라우팅·유해성 필터·의도 분류 같은 에이전트 부품에 실제로 들어간다.

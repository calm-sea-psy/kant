1. LangChain
LangChain은 LLM 애플리케이션을 만들 때 반복되는 작업을 부품으로 표준화한 프레임워크다.

LLM을 직접 호출하면 보통 이런 코드를 매번 새로 짜게 된다.
    - 사용자 입력을 받아 프롬프트 문자열을 만든다
    - 모델 API(OpenAI, Ollama 등)를 호출한다
    - 응답 텍스트에서 필요한 부분을 꺼내거나 JSON으로 파싱한다

LangChain은 이 단계들을 같은 인터페이스를 가진 부품으로 만들어서 레고처럼 이어 붙일 수 있게 해준다.
    - Runnable: 모든 부품이 따르는 공통 규약이다. 어떤 부품이든 invoke()(1건 실행), stream()(스트리밍), batch()(여러 건 실행)를 똑같이 쓸 수 있다.
    - LCEL(LangChain Expression Language): | 연산자로 부품을 연결하는 문법이다. 앞 부품의 출력이 다음 부품의 입력으로 넘어간다. 유닉스 파이프(cat file | grep x)와 같은 개념이다.

    chain = prompt | model | parser
    result = chain.invoke({"topic": "고양이"})

이 한 줄이 가장 기본이 되는 Prompt → Model → Parser 체인이다.

ㄱ) Prompt: 입력을 모델이 읽을 메시지로 바꾸는 단계
역할: 변수가 들어갈 자리를 비워 둔 템플릿에 사용자 입력을 채워서, 모델에 보낼 메시지 목록을 만든다.

    from langchain_core.prompts import ChatPromptTemplate

    prompt = ChatPromptTemplate.from_messages([
        ("system", "너는 {role}이다. 한국어로 짧게 답해라."),
        ("human", "{question}"),
    ])

    - 입력: 딕셔너리 {"role": "수학 선생님", "question": "미분이 뭐야?"}
    - 출력: PromptValue. 실제로는 [SystemMessage(...), HumanMessage(...)] 형태의 메시지 목록이다.

프롬프트를 코드 로직과 분리해서 재사용하고 버전을 관리할 수 있다.
system/human/ai 같은 역할(role) 구분을 자동으로 처리해 준다.
Few-shot 예시, 대화 기록(MessagesPlaceholder) 같은 것도 템플릿 안에 끼워 넣을 수 있다.

ㄴ) Model: 메시지를 받아 응답을 생성하는 단계
역할: 실제 LLM을 호출한다. LangChain은 여러 제공자를 같은 인터페이스로 감싸 두었다.

    from langchain_ollama import ChatOllama
    model = ChatOllama(model="qwen3:8b", temperature=0)

    # OpenAI로 바꿔도 체인의 나머지 코드는 그대로
    # from langchain_openai import ChatOpenAI
    # model = ChatOpenAI(model="gpt-...")

    - 입력: Prompt 단계가 만든 메시지 목록
    - 출력: AIMessage 객체. 답변 텍스트(.content)와 함께 토큰 사용량, tool call 정보 같은 메타데이터가 들어 있다.

모델을 교체하기 쉽다. 로컬 Ollama에서 클라우드 API로 바꿀 때 이 한 줄만 고치면 된다. 모델을 비교하는 테스트베드를 만들 때 특히 유용하다.
temperature 같은 생성 파라미터, 재시도, 스트리밍을 모델 단계 안에서 처리한다.

ㄷ) Parser: 모델의 응답을 프로그램이 쓸 수 있는 형태로 바꾸는 단계
역할: AIMessage는 사람이 읽기에는 괜찮지만 코드에서 바로 쓰기는 불편하다. Parser는 응답을 문자열, 딕셔너리, 객체 같은 형태로 바꿔 준다.

| Parser | 출력 | 용도 |
|---|---|---|
| StrOutputParser | str | 그냥 텍스트만 필요할 때 (가장 흔함) |
| JsonOutputParser | dict | 모델에게 JSON으로 답하게 했을 때 |
| PydanticOutputParser | Pydantic 객체 | 필드와 타입까지 검증하고 싶을 때 |

파서 다음에 오는 코드(DB 저장, 다음 체인, UI)는 정해진 형식을 기대한다. Parser는 모델의 자유로운 텍스트와 형식을 요구하는 프로그램 사이를 연결한다.
일부 파서는 get_format_instructions()를 제공한다. 이걸 프롬프트에 넣으면 "이런 JSON 형식으로 답해라"라는 지시가 자동으로 만들어진다. 그래서 Parser와 Prompt는 짝을 이룬다.

참고: 요즘은 model.with_structured_output(MySchema)처럼 모델의 tool calling이나 JSON 모드를 이용해 구조화된 출력을 직접 받는 방식도 많이 쓴다. 파싱을 텍스트에서 사후 처리하는 대신 모델 단계에서 강제하는 것이라 더 안정적이다. 다만 개념상 역할은 Parser와 같다.

ㄹ) 전체 흐름 정리

{"role": "...", "question": "..."}      ← dict
        │  Prompt  (템플릿 채우기)
        ▼
[SystemMessage, HumanMessage]          ← 메시지 목록
        │  Model   (LLM 호출)
        ▼
AIMessage(content="...", 메타데이터)     ← 모델 응답 객체
        │  Parser  (형식 변환)
        ▼
"미분은 ..."  또는  {"answer": ...}      ← 코드가 쓰기 좋은 값

Prompt는 "무엇을 물을지", Model은 "누가 답할지", Parser는 "답을 어떤 모양으로 받을지"를 담당한다.

세 단계가 모두 Runnable이라서 chain.stream(...)으로 체인 전체를 스트리밍할 수 있다. 나중에 RAG를 할 때는 앞에 Retriever를, 에이전트를 만들 때는 Tool을 같은 방식으로 |로 이어 붙이면 된다.

2. langchain, langchain-core, langchain-openai
초기 LangChain은 langchain 패키지 하나에 모든 것이 들어 있었다. 핵심 개념, OpenAI·Anthropic·수백 개의 외부 서비스 연동, 체인과 에이전트까지 전부였다. 그러다 보니 이런 문제가 생겼다.
    - OpenAI 하나만 쓰려 해도 무거운 패키지 전체를 설치해야 했다.
    - 외부 서비스 SDK가 바뀔 때마다 전체 패키지를 다시 배포해야 했고, 버전 충돌이 잦았다.

그래서 "뼈대(core)"와 "연동(integration)"과 "고수준 기능(langchain)"을 분리했다.

┌───────────────────────────────────────────┐
│  langchain          (고수준: 에이전트 등)      │
├───────────────────────────────────────────┤
│  langchain-openai / langchain-ollama /     │
│  langchain-anthropic ...   (제공자별 연동)    │
├───────────────────────────────────────────┤
│  langchain-core     (공통 인터페이스·뼈대)     │
└───────────────────────────────────────────┘
        ↑ 모든 패키지가 core에 의존

ㄱ) langchain-core: 모든 것의 공통 규약
역할: LangChain 생태계 전체가 따르는 추상 인터페이스와 기본 부품을 정의한다. 특정 모델 회사에 대한 코드는 들어 있지 않다.

a. 주요 구성 요소
    - Runnable / LCEL: invoke, stream, batch와 | 연결 문법
    - 메시지: SystemMessage, HumanMessage, AIMessage, ToolMessage
    - 프롬프트: ChatPromptTemplate, MessagesPlaceholder
    - 출력 파서: StrOutputParser, JsonOutputParser, PydanticOutputParser
    - 추상 클래스: BaseChatModel, Embeddings, BaseRetriever, BaseTool

핵심 개념: core는 "채팅 모델이라면 이런 메서드를 가져야 한다"는 약속(인터페이스)만 정한다. 실제 구현은 아래의 연동 패키지가 채운다. 그래서 의존성이 가볍고 안정적이며, 버전이 자주 깨지지 않도록 관리된다.

Prompt와 Parser는 전부 core에 있는 부품이다.

ㄴ) langchain-openai: OpenAI 연동 구현체
역할: core가 정한 인터페이스를 OpenAI API에 맞게 구현한 "파트너 패키지"다. 내부적으로 OpenAI 공식 openai SDK를 사용한다.

a. 주요 클래스
    - ChatOpenAI: BaseChatModel의 OpenAI 구현
    - OpenAIEmbeddings: Embeddings의 OpenAI 구현
    - AzureChatOpenAI: Azure에 배포된 OpenAI 모델용

핵심 개념: 같은 계층에 다음과 같은 형제 패키지들이 있다.

| 패키지 | 모델 클래스 |
|---|---|
| langchain-openai | ChatOpenAI |
| langchain-ollama | ChatOllama |
| langchain-anthropic | ChatAnthropic |
| langchain-google-genai | ChatGoogleGenerativeAI |

모두 같은 BaseChatModel을 구현하므로 import 한 줄만 바꾸면 모델을 교체할 수 있다. Model 단계가 바로 이 계층이다.
    - 참고: ChatOpenAI는 base_url을 바꾸면 OpenAI 호환 API를 제공하는 다른 서버(vLLM, LM Studio, Ollama의 /v1 엔드포인트 등)에도 붙일 수 있다. 로컬 모델에 쓸 때도 자주 보게 된다.

ㄷ) langchain: 부품을 조합한 고수준 기능
역할: core의 부품을 조합해서 애플리케이션 수준의 기능을 제공한다. 대표적인 것이 에이전트다.
    - LangChain 1.0(2025년 10월) 이후 langchain 패키지는 에이전트 중심으로 정리되었다. 대표 API는 create_agent이고, 에이전트 실행 중간에 로직을 끼워 넣는 middleware 개념도 여기에 있다. 내부적으로는 LangGraph 위에서 동작한다.
    - 예전의 LLMChain, RetrievalQA 같은 레거시 체인들은 langchain-classic으로 분리되었다. 인터넷의 오래된 튜토리얼 코드가 잘 안 돌아가는 이유가 대부분 이것이다.

핵심 개념: 단순한 Prompt → Model → Parser 체인이라면 langchain 없이 langchain-core + 연동 패키지만으로 충분하다. langchain은 에이전트처럼 한 단계 위의 기능이 필요할 때 추가한다.

ㄹ) 정리

| 패키지 | 한 줄 요약 | 지난 답변과의 연결 |
|---|---|---|
| langchain-core | 공통 인터페이스와 기본 부품 (뼈대) | Prompt, Parser, \| 연결 |
| langchain-openai | core 인터페이스의 OpenAI 구현 | Model |
| langchain | 부품을 조합한 고수준 기능 (에이전트) | 체인 위의 다음 단계 |

core는 "콘센트 규격", langchain-openai는 "그 규격에 맞춘 OpenAI 제품", langchain은 "그 제품들을 엮어 만든 가전 시스템"이다. 규격이 같기 때문에 제품을 바꿔 꽂아도 시스템이 그대로 동작한다.

3. PromptTemplate과 ChatPromptTemplate
두 템플릿이 따로 있는 이유는 LLM이 입력을 받는 방식이 두 가지였기 때문이다.

| 방식 | 입력 형태 | 예시 |
|---|---|---|
| 완성형(Completion) 모델 | 문자열 하나 | "다음 문장을 이어 써라: 옛날 옛적에" |
| 채팅(Chat) 모델 | 역할이 붙은 메시지 목록 | [system: "너는 선생님", human: "미분이 뭐야?"] |

초기 GPT-3 시절에는 완성형이 기본이었고, 지금은 거의 모든 모델이 채팅 방식이다. PromptTemplate은 문자열용이고, ChatPromptTemplate은 메시지 목록용이다.

ㄱ) PromptTemplate: 문자열 하나를 만드는 템플릿
역할: 빈칸({변수})이 있는 문자열에 값을 채워 완성된 문자열 하나를 만든다.

    from langchain_core.prompts import PromptTemplate

    prompt = PromptTemplate.from_template(
        "{topic}에 대해 초등학생도 이해할 수 있게 3문장으로 설명해줘."
    )

    prompt.invoke({"topic": "광합성"})
    # → StringPromptValue(text="광합성에 대해 초등학생도 이해할 수 있게 3문장으로 설명해줘.")

    - 입력: 딕셔너리 {"topic": "광합성"}
    - 출력: StringPromptValue (속은 그냥 문자열)
    - 특징: 역할(system/human) 구분이 없다. 모든 내용이 한 덩어리 텍스트다.

채팅 모델에 넣으면? 에러가 나지 않는다. LangChain이 문자열을 자동으로 HumanMessage 하나로 감싸서 보낸다. 다만 system 메시지를 따로 줄 방법이 없어서 역할 설정이 약해진다.

ㄴ) ChatPromptTemplate: 메시지 목록을 만드는 템플릿
역할: 역할별 메시지 여러 개를 템플릿으로 정의하고, 값을 채워 메시지 목록을 만든다.

    from langchain_core.prompts import ChatPromptTemplate

    prompt = ChatPromptTemplate.from_messages([
        ("system", "너는 {level} 눈높이에 맞춰 설명하는 과학 선생님이다."),
        ("human", "{topic}이 뭐야?"),
    ])

    prompt.invoke({"level": "초등학생", "topic": "광합성"})
    # → ChatPromptValue(messages=[
    #       SystemMessage("너는 초등학생 눈높이에 맞춰 설명하는 과학 선생님이다."),
    #       HumanMessage("광합성이 뭐야?"),
    #   ])

    - 입력: 딕셔너리
    - 출력: ChatPromptValue (속은 메시지 목록)
    - 역할 종류: "system"(규칙·페르소나), "human"(사용자 발화), "ai"(모델의 이전 답변. few-shot 예시에 사용)

ㄷ) ChatPromptTemplate만 할 수 있는 것

a. 대화 기록 끼워 넣기: MessagesPlaceholder
챗봇은 이전 대화를 매번 같이 보내야 한다. 메시지 목록이 통째로 들어갈 자리를 비워 둘 수 있다.

    from langchain_core.prompts import MessagesPlaceholder

    prompt = ChatPromptTemplate.from_messages([
        ("system", "너는 친절한 도우미다."),
        MessagesPlaceholder("history"),     # ← 여기에 이전 대화들이 들어감
        ("human", "{question}"),
    ])

b. Few-shot을 대화 형식으로 넣기
human/ai 쌍으로 예시를 주면, 모델은 "이렇게 물으면 이렇게 답하는구나"를 실제 대화처럼 학습한다.

    ("human", "사과"), ("ai", "과일"),
    ("human", "당근"), ("ai", "채소"),
    ("human", "{word}"),

ㄹ) 공통점
    - 둘 다 Runnable이라서 prompt | model | parser로 연결할 수 있다.
    - 둘 다 출력이 PromptValue라는 공통 타입이다. PromptValue는 .to_string()과 .to_messages()를 모두 가지고 있어서, 어느 모델에 넣든 알맞은 형태로 변환된다. 모델 쪽에서 형식을 맞춰 준다는 뜻이다.
    - 변수 문법이 같다. 기본은 파이썬 f-string 스타일 {변수}다.
    - 주의: 프롬프트 안에 JSON 예시처럼 진짜 중괄호를 쓰려면 {{ }}로 두 번 써야 한다. 그렇지 않으면 변수로 인식되어 "변수가 없다"는 에러가 난다.
    - partial()로 일부 변수를 미리 채워 둘 수 있다. 예를 들어 prompt.partial(level="초등학생")처럼 쓴다.

ㅁ) 정리

| 구분 | PromptTemplate | ChatPromptTemplate |
|---|---|---|
| 만드는 것 | 문자열 하나 | 역할별 메시지 목록 |
| 출력 타입 | StringPromptValue | ChatPromptValue |
| 생성 방법 | from_template("...") | from_messages([...]) |
| system 역할 분리 | ✗ | ✓ |
| 대화 기록 (MessagesPlaceholder) | ✗ | ✓ |
| 주 용도 | 단순 텍스트 생성, 완성형 모델, 다른 템플릿의 부품 | 현재 채팅 모델 기반 앱의 기본값 |

지금은 거의 모든 모델이 채팅 모델이므로 기본은 ChatPromptTemplate이다. PromptTemplate은 역할 구분이 필요 없는 짧은 한 줄 지시나, 문자열 조각을 만드는 보조 용도로 쓴다고 생각하면 된다.

4. ChatModel
ChatModel은 LangChain에서 채팅형 LLM을 감싸는 표준 인터페이스다. langchain-core의 BaseChatModel이라는 추상 클래스가 규칙을 정하고, 각 제공자 패키지가 그 규칙을 구현한다.

    BaseChatModel  (langchain-core: "채팅 모델은 이렇게 동작해야 한다")
    ├── ChatOpenAI      (langchain-openai)
    ├── ChatOllama      (langchain-ollama)
    ├── ChatAnthropic   (langchain-anthropic)
    └── ...

한 줄로 말하면 "메시지 목록을 받아서 AI 메시지 하나를 돌려주는 부품"이다. Prompt → Model → Parser에서 Model 자리에 들어간다.

LLM 클래스와의 차이: LangChain에는 LLM이라는 클래스도 있다. 이것은 문자열을 받아 문자열을 돌려주는 완성형 모델용이고, 앞에서 본 PromptTemplate과 ChatPromptTemplate의 관계와 같다. 지금은 거의 쓰지 않으므로 ChatModel이 기본이라고 보면 된다.

ㄱ) 만들기: 주요 파라미터

    from langchain_ollama import ChatOllama

    model = ChatOllama(
        model="qwen3:8b",     # 어떤 모델을 쓸지
        temperature=0,        # 무작위성 (0 = 가장 결정적)
    )

a. 공통 파라미터

| 파라미터 | 의미 |
|---|---|
| model | 모델 이름 |
| temperature | 출력의 무작위성. 낮을수록 일관되고, 높을수록 다양함 |
| max_tokens | 생성할 최대 토큰 수. 응답 길이와 비용의 상한 |
| timeout | 응답을 기다릴 최대 시간 |
| max_retries | 네트워크 오류 등으로 실패했을 때 재시도할 횟수 |
| base_url | API 서버 주소. 로컬 서버나 호환 API에 붙일 때 사용 |

제공자에 상관없이 만들기: init_chat_model을 쓰면 문자열 설정만으로 모델을 고를 수 있다. 여러 모델을 바꿔 가며 비교할 때 편하다.

    from langchain.chat_models import init_chat_model
    model = init_chat_model("ollama:qwen3:8b", temperature=0)

ㄴ) 입력: 여러 형태를 받아 준다
ChatModel의 입력은 원래 메시지 목록이지만, 편의를 위해 여러 형태를 알아서 변환한다.

    model.invoke("안녕?")                              # 문자열 → HumanMessage 하나로 변환
    model.invoke([("system", "짧게 답해"), ("human", "안녕?")])   # (역할, 내용) 튜플 목록
    model.invoke([SystemMessage("짧게 답해"), HumanMessage("안녕?")])  # 메시지 객체 목록
    model.invoke(prompt.invoke({...}))                  # PromptValue (체인에서 자동으로 이 경로)

ㄷ) 출력: AIMessage
ChatModel은 문자열이 아니라 AIMessage 객체를 돌려준다. 텍스트 외에도 정보가 많이 들어 있다.

    res = model.invoke("광합성을 한 문장으로 설명해줘")

    res.content            # "광합성은 식물이 빛 에너지로..."  ← 답변 텍스트
    res.usage_metadata     # {"input_tokens": 15, "output_tokens": 32, "total_tokens": 47}
    res.response_metadata  # 모델 이름, 종료 이유(finish reason) 등 제공자별 정보
    res.tool_calls         # 모델이 도구 호출을 요청했다면 그 내용 (아래 ㅁ)

    - usage_metadata는 토큰 사용량을 제공자 구분 없이 같은 형식으로 보여 준다. 비용과 성능을 비교할 때 유용하다.
    - 이 AIMessage에서 텍스트만 꺼내 주는 것이 StrOutputParser의 역할이다.

ㄹ) 실행 방법: Runnable 메서드
ChatModel도 Runnable이므로 공통 메서드를 모두 가지고 있다.

| 메서드 | 동작 | 언제 쓰나 |
|---|---|---|
| invoke(x) | 1건 실행하고 완성된 결과를 반환 | 기본 |
| stream(x) | 토큰이 생성되는 대로 조각(AIMessageChunk)을 하나씩 반환 | 채팅 UI처럼 글자가 흘러나오게 할 때 |
| batch([x1, x2, ...]) | 여러 입력을 병렬로 실행 | 평가 데이터셋을 한꺼번에 돌릴 때 |
| ainvoke, astream, abatch | 위의 비동기 버전 | FastAPI 같은 비동기 서버 안에서 |

    for chunk in model.stream("바다에 대한 짧은 시를 써줘"):
        print(chunk.content, end="", flush=True)

ㅁ) ChatModel의 확장 기능
기본적인 대화 외에, 모델이 가진 기능을 표준화된 방식으로 꺼내 쓰는 메서드가 있다.

a. bind_tools(): 도구 호출(Tool Calling)
모델에게 "이런 함수들을 쓸 수 있다"고 알려 준다. 모델은 직접 함수를 실행하지 않고, "이 함수를 이 인자로 호출해 달라"는 요청을 AIMessage.tool_calls에 담아 돌려준다. 실제 실행은 우리 코드(또는 에이전트)가 한다.

    def get_weather(city: str) -> str:
        """도시의 현재 날씨를 알려준다."""
        ...

    model_with_tools = model.bind_tools([get_weather])
    res = model_with_tools.invoke("서울 날씨 어때?")
    res.tool_calls   # [{"name": "get_weather", "args": {"city": "서울"}, ...}]

이것이 에이전트의 기초다. 에이전트는 "모델이 도구를 요청 → 코드가 실행 → 결과를 다시 모델에게 전달"을 반복하는 구조다.

b. with_structured_output(): 구조화된 출력
응답을 정해진 스키마의 객체로 받는다. 텍스트를 받아 파서로 해석하는 대신, 모델의 도구 호출이나 JSON 모드를 이용해 처음부터 형식을 강제한다.

    from pydantic import BaseModel

    class Review(BaseModel):
        sentiment: str   # "긍정" / "부정"
        score: int       # 1~5

    structured = model.with_structured_output(Review)
    structured.invoke("배송은 느렸지만 제품은 정말 좋다")
    # → Review(sentiment="긍정", score=4)

이 경우 Parser 단계가 필요 없다. Model 단계가 Parser 역할까지 맡는다고 보면 된다.
    - 주의: 이 두 기능은 모델 자체가 도구 호출을 지원해야 제대로 동작한다. 작은 로컬 모델은 지원하지 않거나 정확도가 떨어질 수 있다. 모델을 고를 때 확인할 부분이다.

ㅂ) 정리

| 항목 | 내용 |
|---|---|
| 정체 | BaseChatModel 인터페이스를 따르는 채팅 LLM 래퍼 |
| 입력 | 메시지 목록 (문자열, 튜플, PromptValue도 자동 변환) |
| 출력 | AIMessage (텍스트 + 토큰 사용량 + 메타데이터 + 도구 호출) |
| 실행 | invoke / stream / batch (+ 비동기 버전) |
| 확장 | bind_tools() → 도구 호출, with_structured_output() → 구조화된 출력 |
| 핵심 장점 | 제공자가 달라도 쓰는 법이 같아서 모델 교체와 비교가 쉬움 |

ChatModel은 "어떤 회사의 LLM이든 같은 콘센트에 꽂을 수 있게 만든 어댑터"이고, 그 위에서 스트리밍, 도구 호출, 구조화된 출력까지 같은 방식으로 쓸 수 있게 해 준다.

5. Runnable
Runnable은 LangChain에서 "실행할 수 있는 모든 것"이 따르는 공통 인터페이스다. langchain-core에 정의되어 있다.

ChatPromptTemplate   ─┐
ChatOllama           ─┤
StrOutputParser      ─┼─→  전부 Runnable
Retriever, Tool      ─┤
체인(prompt|model|…) ─┘   ← 부품을 연결한 결과도 Runnable

부품마다 사용법이 다르면 연결할 때마다 접착 코드가 필요하다. 그래서 "모든 부품은 입력 하나를 받아 출력 하나를 내고, 같은 메서드로 실행된다"는 규칙을 정했다. 이 규칙 덕분에 부품을 |로 자유롭게 이어 붙일 수 있다.

ㄱ) 공통 메서드: 무엇이든 같은 방법으로 실행
Runnable은 다음 메서드를 가지고 있다. 각 부품이 따로 구현하지 않아도 기본 동작이 제공된다.

| 메서드 | 동작 |
|---|---|
| invoke(input) | 입력 1개를 실행하고 결과 1개를 반환 |
| batch([in1, in2, ...]) | 여러 입력을 병렬로 실행하고 결과 목록을 반환 |
| stream(input) | 결과를 조각 단위로 흘려보냄 |
| ainvoke / abatch / astream | 위 메서드들의 비동기 버전 |

    chain = prompt | model | parser

    chain.invoke({"topic": "광합성"})                       # 1건
    chain.batch([{"topic": "광합성"}, {"topic": "중력"}])     # 여러 건 병렬
    for chunk in chain.stream({"topic": "광합성"}):          # 스트리밍
        print(chunk, end="")

체인 전체에 stream()을 호출하면 스트리밍이 체인을 따라 전달된다. 모델이 토큰을 하나 만들면 파서가 바로 처리해서 내보낸다. 스트리밍을 지원하는 부품들로만 이어져 있다면 체인 전체가 자연스럽게 스트리밍된다.

ㄴ) 조합: Runnable을 이어 붙이는 방법
Runnable끼리 조합한 결과도 Runnable이다. 그래서 작은 체인을 큰 체인의 부품으로 다시 쓸 수 있다.

a. RunnableSequence: 순서대로 연결 (|)
앞 단계의 출력이 다음 단계의 입력이 된다.

    chain = prompt | model | parser   # 내부적으로 RunnableSequence 생성

b. RunnableParallel: 동시에 실행해서 딕셔너리로 모으기
같은 입력을 여러 Runnable에 동시에 넣고, 결과를 키별로 모은다.

    from langchain_core.runnables import RunnableParallel

    both = RunnableParallel(
        summary=summary_chain,
        keywords=keyword_chain,
    )
    both.invoke({"text": "..."})
    # → {"summary": "...", "keywords": "..."}

체인 안에서는 그냥 딕셔너리를 써도 자동으로 RunnableParallel로 변환된다.

c. RunnableLambda: 일반 함수를 Runnable로 만들기
직접 만든 파이썬 함수를 체인 중간에 끼워 넣을 때 쓴다.

    from langchain_core.runnables import RunnableLambda

    to_upper = RunnableLambda(lambda s: s.upper())
    chain = prompt | model | parser | to_upper

체인 안에서는 함수를 그냥 넣으면 자동 변환된다. (| (lambda s: s.upper()))

d. RunnablePassthrough: 입력을 그대로 통과시키기
입력을 변형 없이 다음 단계로 넘긴다. 주로 RunnableParallel 안에서 "원래 입력도 같이 넘기고 싶을 때" 쓴다.

e. 조합 예시: RAG 체인의 뼈대
위의 조합 도구들이 실제로 함께 쓰이는 대표적인 예가 RAG다.

    from langchain_core.runnables import RunnablePassthrough

    rag_chain = (
        {
            "context": retriever,               # 질문으로 문서 검색
            "question": RunnablePassthrough(),  # 질문은 그대로 전달
        }                                       # ← 딕셔너리 = RunnableParallel
        | prompt                                # {context}, {question}을 채움
        | model
        | parser
    )
    rag_chain.invoke("광합성에 필요한 조건은?")

f. 데이터 흐름

"광합성에 필요한 조건은?"
        │
   ┌────┴─────────────┐            (RunnableParallel: 동시에 실행)
retriever        Passthrough
   │                  │
[관련 문서들]    "광합성에 필요한..."
   └────┬─────────────┘
{"context": [...], "question": "..."}
        │ prompt → model → parser
        ▼
      답변 문자열

ㄷ) 공통 부가 기능: 어떤 Runnable에든 붙일 수 있는 옵션
Runnable이 공통 규약이라서, 어떤 부품이든 같은 방식으로 기능을 덧붙일 수 있다.

| 메서드 | 기능 |
|---|---|
| .with_retry() | 실패하면 자동으로 재시도 |
| .with_fallbacks([...]) | 실패하면 대체 Runnable로 넘어감 (예: 로컬 모델 실패 → 클라우드 모델) |
| .with_config(run_name=..., tags=...) | 실행 이름이나 태그를 붙여서 추적·디버깅을 쉽게 함 |
| .bind(...) | 호출 인자를 미리 고정 (앞에서 본 bind_tools도 같은 계열) |

    safe_model = local_model.with_fallbacks([cloud_model])
    chain = prompt | safe_model | parser

    - 참고: 실행할 때 config={"max_concurrency": 4}처럼 RunnableConfig를 넘기면 batch 동시 실행 수, 콜백, 태그 등을 체인 전체에 전달할 수 있다. LangSmith 같은 추적 도구가 체인 내부 단계를 하나하나 기록할 수 있는 것도 이 구조 덕분이다.

ㄹ) 정리

| 구분 | 내용 |
|---|---|
| 정체 | 입력 하나를 받아 출력 하나를 내는 부품의 공통 인터페이스 |
| 공통 실행 | invoke / batch / stream (+ 비동기 버전) |
| 조합 | \| 순차 연결, 딕셔너리 병렬 실행, 함수 끼워 넣기, 입력 통과 |
| 부가 기능 | 재시도, 대체 경로, 설정/태그, 인자 고정 |
| 핵심 성질 | 조합한 결과도 Runnable이므로 작은 체인이 큰 체인의 부품이 됨 |

Runnable은 LangChain 부품들의 "공통 규격 플러그"다. 규격이 하나이기 때문에 Prompt, Model, Parser, Retriever를 |로 자유롭게 연결할 수 있고, 연결한 체인에도 스트리밍, 병렬 실행, 재시도 같은 기능이 그대로 적용된다.

1. NLP
자연어 처리(Natural Language Processing)는 사람이 쓰는 언어를 컴퓨터가 이해·분석·생성하도록 만드는 분야다. 언어학, 통계학, 머신러닝/딥러닝이 겹치는 영역이고, 최근에는 사실상 딥러닝(특히 Transformer 기반) 중심으로 재편됐다.

ㄱ) 대표 태스크

| 유형 | 예시 | 출력 형태 |
|---|---|---|
| 분류 | 감성분석, 스팸 판별, 주제 분류 | 문장 1개 → 라벨 1개 |
| 시퀀스 레이블링 | 개체명 인식(NER), 품사 태깅(POS) | 토큰마다 라벨 |
| 시퀀스→시퀀스 | 번역, 요약, 문법 교정 | 텍스트 → 텍스트 |
| 언어 모델링 | 다음 토큰 예측 | 다음 토큰 확률분포 (GPT 계열의 근간) |
| 문장 임베딩/검색 | 의미 유사도, RAG의 retrieval | 문장 → 벡터 |
| 생성 | 대화, 글쓰기, 코드 | 자유 텍스트 |

ㄴ) 역사 흐름
규칙 기반 → 통계 기반(n-gram, HMM, CRF) → 단어 임베딩(Word2Vec, GloVe) → RNN/LSTM/seq2seq+attention → Transformer → 사전학습 LM(BERT, GPT) → LLM

RNN·LSTM은 이 흐름에서 "가변 길이 시퀀스를 순차적으로 처리"하는 단계였고, Transformer가 그 자리를 대체하면서 병렬 처리와 긴 문맥이 가능해졌다.

ㄷ) 핵심 문제
모델이 먹는 건 숫자 텐서다. 그래서 NLP 데이터 구조의 대부분은 "텍스트 → 숫자"로 가는 중간 단계의 표현들이다. 파이프라인으로 보면:

    원문(raw text)
    → 정규화(normalization)      소문자화, 유니코드 정리, 특수문자 처리
    → 토큰화(tokenization)        문장을 토큰 단위로 쪼갬
    → 정수 인코딩(numericalize)   토큰 → 정수 ID (vocab 사용)
    → 수치 표현(representation)   희소(BoW/TF-IDF) 또는 밀집(임베딩)
    → 배치화(batching)           패딩 + 마스크 → (batch, seq_len) 텐서

단계마다 등장하는 자료구조가 다르다.


2. NLP 데이터 구조

ㄱ) 텍스트 계층 구조
    - 코퍼스(corpus): 텍스트 모음 전체 (학습 데이터셋)
    - 문서(document) → 문장(sentence) → 토큰(token)
    - 토큰(token): 최소 처리 단위. 단어일 수도, 서브워드("자연어처리" → "자연", "##어", "##처리")일 수도, 문자일 수도 있다.
    - 타입(type) vs 토큰(token): "the cat sat on the mat" → 토큰 6개, 타입 5개("the"가 2번). 어휘 크기를 셀 때는 타입 기준.

ㄴ) 어휘 사전 (Vocabulary)
토큰과 정수 ID를 잇는 매핑. 두 개의 딕셔너리로 관리한다.

    token2id = {"[PAD]": 0, "[UNK]": 1, "안녕": 2, "세상": 3, ...}
    id2token = {0: "[PAD]", 1: "[UNK]", 2: "안녕", ...}

| 토큰 | 역할 |
|---|---|
| [PAD] | 길이 맞추는 채움용 |
| [UNK] | 사전에 없는 단어(OOV) |
| [CLS] | 문장 전체 요약 위치 (BERT 분류용) |
| [SEP] | 문장 경계 구분 |
| [BOS] / [EOS] | 시퀀스 시작/끝 (생성 모델) |
| [MASK] | 가림 학습용 (BERT) |

OOV 문제: 사전에 없는 단어는 전부 [UNK]로 뭉개진다. 서브워드 토큰화(BPE, WordPiece, SentencePiece)가 이걸 해결한다 — 모르는 단어도 아는 조각으로 분해하니 [UNK]가 거의 안 나온다.

ㄷ) 정수 시퀀스 (input_ids)
토큰 리스트를 vocab으로 변환한 결과.

    "나는 밥을 먹었다" → ["나는", "밥을", "먹었다"] → [45, 128, 903]

문장마다 길이가 다르다. 이걸 배치로 묶으려면 길이를 맞춰야 한다.

ㄹ) 패딩된 텐서 + 마스크 (모델의 실제 입력)
배치 안에서 가장 긴 문장에 맞춰 짧은 문장을 [PAD](=0)로 채운다.

    input_ids = [[45, 128, 903, 0,  0],      # (batch_size=3, seq_len=5)
                [12, 77,  0,   0,  0],
                [5,  88,  201, 34, 9]]

    attention_mask = [[1, 1, 1, 0, 0],        # 1=실제 토큰, 0=패딩 → 무시하라
                    [1, 1, 0, 0, 0],
                    [1, 1, 1, 1, 1]]

a. 추가항목
    - token_type_ids (segment ids): 문장 A/B 구분 (BERT의 문장쌍 입력)
    - position_ids: 각 토큰의 위치
    - labels: 정답 (분류면 라벨 1개, 시퀀스 레이블링이면 토큰마다, 언어모델이면 input을 한 칸 민 것)

여기까지가 어떤 NLP 모델이든 공통으로 만나는 자료구조다. 아래부터는 "텍스트를 어떻게 수치로 표현하느냐"에 따라 갈린다.

ㅁ) 희소 표현 (Sparse) — 전통적 방식
단어를 세는 방식. 벡터 대부분이 0이라 희소행렬(CSR 등)로 저장한다.

ㅂ) 밀집 표현 (Dense) — 임베딩
단어를 저차원 실수 벡터로. 의미가 가까운 단어는 벡터도 가깝다.

ㅅ) 벡터 인덱스 / 벡터 DB — LLM 앱 관점
임베딩 벡터를 대량으로 저장하고 "질의 벡터와 가장 가까운 것 k개"를 빠르게 찾는 자료구조.

ㅇ) 구조적 표현 — 전통 NLP
    - 구문 분석 트리 (parse tree): 문장의 문법 구조를 트리로
    - 의존 구문 트리 (dependency tree): 어떤 단어가 어떤 단어를 수식/지배하는지의 방향 그래프
    - 지식 그래프: (개체, 관계, 개체) 트리플의 모음
LLM 이전에는 이런 명시적 구조를 많이 썼지만, 지금은 모델이 내부적으로 학습하는 쪽으로 넘어갔다.

ㅈ) Transformer 내부 자료구조
    - 어텐션 행렬: (seq_len × seq_len). i번째 토큰이 j번째 토큰을 얼마나 참조하는지의 가중치.
    - Q, K, V 행렬: 각 토큰의 query/key/value 표현.
    - KV 캐시: 텍스트 생성 시 이미 계산한 과거 토큰들의 K, V를 저장해두는 버퍼. 매 토큰마다 전체를 다시 계산하지 않게 해줘서 추론 속도의 핵심이다. (NOTE 09 FreeToken에서 다루는 서빙 최적화의 중심 주제)


3. token·subword·vocabulary·ID
이 네 개는 한 파이프라인의 연속된 고리다.

    텍스트 → [토큰화] → 토큰(subword) → [vocab 조회] → ID → [임베딩 룩업] → 벡터
    "재밌다"    →    ["▁재밌", "다"]    →    [8890, 9]    →    벡터 2개

    - 토큰: 텍스트를 쪼갠 조각
    - 서브워드: 그 조각을 "단어보다 작고 문자보다 큰" 단위로 잡는 방식
    - vocabulary: 모델이 아는 모든 토큰의 고정된 목록
    - ID: vocab에서 각 토큰에 매긴 정수 번호

ㄱ) 토큰 (Token)
텍스트를 처리하려고 나눈 최소 단위. 나누는 작업을 토큰화(tokenization)라고 한다.

a. 쪼개는 단위 선택지

| 단위 | 예 ("unhappiness") | vocab 크기 | OOV | 시퀀스 길이 |
|---|---|---|---|---|
| 단어(word) | ["unhappiness"] | 수십만+ | 자주 발생 | 짧음 |
| 서브워드(subword) | ["un", "happi", "ness"] | 3만~20만 | 거의 없음 | 중간 |
| 문자(character) | ["u","n","h",...] | 수백 | 없음 | 매우 김 |
| 바이트(byte) | [117, 110, ...] | 256 | 없음 | 가장 김 |

b. 단어 토큰화의 문제
    - vocab 폭발: run / runs / running / ran을 전부 다른 단어로 취급
    - OOV(out-of-vocabulary): 학습 때 못 본 단어는 [UNK]로 뭉개짐
    - 한국어는 더 심하다. 교착어라서 공백 단위가 "단어"가 아니라 "어절"이다. "먹었다 / 먹는다 / 먹겠다"가 전부 별도 항목이 되고, 조사·어미 조합까지 곱해지면 폭발한다.

c. 문자 토큰화의 문제
vocab은 작고 OOV는 없지만, 시퀀스가 너무 길어지고("apple" → 5토큰) 토큰 하나에 의미가 거의 없다. Transformer 연산량은 시퀀스 길이의 제곱이라 이게 치명적이다. 그래서 대부분 서브워드를 쓴다.

d. 토큰 개수가 중요한 이유
토큰 수 = 시퀀스 길이. 모델 연산량, 컨텍스트 윈도우 한도, API 과금이 전부 토큰 단위다

ㄴ) 서브워드 (Subword)
자주 나오는 것은 통째로, 드문 것은 조각으로 쪼개는 절충안

    "playing"       → ["play", "ing"]
    "tokenization"  → ["token", "ization"]
    "antidisestablishmentarianism" → ["anti", "dis", "establish", "ment", "arian", "ism"]

a. 장점
    - vocab 크기를 원하는 값으로 고정할 수 있다
    - OOV가 사실상 사라진다 — 최악의 경우 문자/바이트 단위까지 떨어지므로 표현 못 하는 텍스트가 없다
    - 형태소 규칙을 자연스럽게 학습한다 (-ing, -ness, un-이 반복 등장하는 조각이 됨)

b. 주요 알고리즘

| 알고리즘 | 병합 기준 | 대표 모델 |
|---|---|---|
| BPE (Byte Pair Encoding) | 가장 자주 붙어 나오는 인접 쌍을 반복 병합 | GPT 계열, Llama |
| Byte-level BPE | 유니코드가 아니라 바이트에서 시작 → 모든 문자 커버, 진짜 OOV 없음 | GPT-2 이후 |
| WordPiece | 빈도가 아니라 "합쳤을 때 likelihood 증가량"이 큰 쌍 | BERT |
| Unigram LM | 큰 vocab에서 시작해 덜 유용한 토큰을 확률적으로 제거 | ALBERT, T5, 다국어 모델 |
| SentencePiece | 위 알고리즘(BPE/Unigram)을 공백 포함 raw text에서 바로 학습 | Llama, Gemma, 한·일 모델 |

c. BPE 학습 과정(개념)

    1. 코퍼스를 문자 단위로 분해
    2. 가장 자주 인접하는 쌍을 찾음  (예: "e"+"s" → "es")
    3. 그 쌍을 하나의 토큰으로 병합
    4. 목표 vocab 크기에 도달할 때까지 2~3 반복
    → 병합 규칙 목록이 곧 vocab

d. 표기 관습 (조각 경계 표시 방법이 툴마다 다름)
    - WordPiece(BERT): 이어지는 조각에 ## → ["token", "##ization"]
    - SentencePiece: 단어 시작에 ▁(U+2581) → ["▁Hello", "▁world"]. 공백을 문자처럼 취급하므로 디코딩이 정확히 복원된다.

한국어 예시 (SentencePiece 가정)

    "자연어처리를 배운다"
    → ["▁자연", "어", "처리", "를", "▁배운", "다"]

같은 문장이라도 토크나이저마다 쪼개는 결과가 다르다. 한국어는 영어보다 토큰 효율이 나쁘다 — 같은 내용에 토큰을 더 많이 쓴다. 최근 토크나이저(Llama 3의 128k, GPT-4o의 o200k)가 이 격차를 많이 줄였다.

ㄷ) 어휘 사전 (Vocabulary)
모델이 아는 모든 토큰의 유한하고 고정된 집합. 토크나이저를 코퍼스로 학습시키는 단계에서 만들어진다(= BPE 병합 규칙을 학습하는 것).

a. 크기는 하이퍼파라미터

| 선택 | 시퀀스 길이 | 임베딩 행렬 (V × d) | 출력 softmax 비용 |
|---|---|---|---|
| 작은 vocab | 길어짐 | 작음 | 쌈 |
| 큰 vocab | 짧아짐 | 큼 | 비쌈 |

b. 실제 값

| 모델 | vocab 크기 |
|---|---|
| BERT (base, uncased) | 30,522 |
| GPT-2 / GPT-3 | 50,257 |
| Llama 1 / 2, Mistral | 32,000 |
| GPT-4 (cl100k) | 약 100,277 |
| Llama 3 | 128,256 |
| GPT-4o (o200k) | 약 200,019 |
| Gemma | 256,000 |

c. 구성 요소
    - 일반 토큰: 학습으로 얻은 서브워드들
    - 특수 토큰: [PAD] [UNK] [CLS] [SEP] [BOS] [EOS] [MASK], 그리고 채팅 템플릿용 <|im_start|> <|eot_id|> 같은 것들

d. 저장 형태

    vocab.json       token → id 매핑
    merges.txt       BPE 병합 규칙 (순서 중요)
    tokenizer.json   위를 통합한 단일 파일 (HF tokenizers)

핵심 제약: 학습과 추론에서 반드시 같은 토크나이저·vocab을 써야 한다. vocab이 다르면 같은 ID가 다른 토큰을 가리켜서 모델이 완전히 망가진다. 모델 체크포인트와 토크나이저를 항상 짝으로 배포하는 이유다.

ㄹ) ID (정수 인덱스)
vocab에서 각 토큰에 부여된 정수 번호(0 ~ vocab_size−1).

    token → id : 인코딩(encode)
    id → token : 디코딩(decode)

a. 필요한 이유
    - 신경망은 문자열을 못 먹는다. 숫자여야 한다.
    - 이 정수는 임베딩 행렬의 행 번호로 쓰인다. id = 903이면 embedding_matrix[903]이 그 토큰의 벡터다. 룩업 테이블의 열쇠인 셈.

ID 자체에는 의미가 없다. 5번 토큰이 6번 토큰보다 "작거나" "가깝지" 않다. 번호는 그냥 자리표일 뿐이고, 의미는 전적으로 임베딩 벡터가 담는다. ([PAD]가 관습적으로 0번인 정도만 의미가 있다.)

b. 인코딩

    원문:     "토큰화는 재밌다"

    토큰화:   ["▁토큰", "화", "는", "▁재밌", "다"]          ← subword 5개

    ID 변환:  [1243, 55, 12, 8890, 9]                       ← vocab 조회

    배치화:   input_ids      = [1243, 55, 12, 8890, 9, 0, 0]   ← PAD 채움
            attention_mask = [   1,  1,  1,    1, 1, 0, 0]

    임베딩:   각 ID → d차원 벡터  →  (seq_len × d) 행렬        ← 모델 본체 입력

c. 디코딩

    [1243, 55, 12, 8890, 9]
    → ["▁토큰", "화", "는", "▁재밌", "다"]
    → "토큰화는 재밌다"        (▁ 를 공백으로 복원)

보통 decode(encode(x)) == x가 성립하도록 설계하지만(특히 byte-level BPE, SentencePiece), 정규화가 개입하면 완벽히 같지 않을 수 있다(예: 유니코드 정규화, 소문자화).

ㅁ) 실무 포인트
    - 과금·컨텍스트 한도가 토큰 단위다. 문자 수나 단어 수가 아니다. 프롬프트 길이를 가늠하려면 토크나이저를 돌려봐야 한다.
    - 한국어는 토큰을 많이 먹는다. 영어 대비 1.5~2배가 흔하다. 비용·지연·컨텍스트 측면에서 불리하니 모델 선택 시 토크나이저도 본다.
    - 토큰 경계가 만드는 약점: "strawberry에 r이 몇 개"를 모델이 자주 틀리는 건 strawberry가 몇 개의 서브워드 덩어리로 들어가서 글자 단위 정보가 흐려지기 때문이다. 숫자 연산이 불안정한 것도 비슷한 이유(숫자가 일관되지 않게 쪼개짐).
    - 드물게 학습된 토큰의 이상 동작: 코퍼스에 거의 안 나온 토큰은 임베딩이 제대로 학습되지 않아 엉뚱한 출력을 유발할 수 있다(GPT-2의 SolidGoldMagikarp 사례).


4. 토크나이저(Tokenizer)
텍스트 ↔ 정수 ID 시퀀스를 왕복 변환하는 컴포넌트. 모델에 딸려 있는 별도의 작은 프로그램이라고 보면 된다.

    tokenizer.encode("안녕하세요")  →  [104, 8971, 2]      (인코딩)
    tokenizer.decode([104, 8971, 2]) →  "안녕하세요"        (디코딩)

모델 체크포인트와 항상 짝으로 배포된다. 토크나이저가 다르면 같은 ID가 다른 토큰을 가리켜서 모델이 완전히 망가진다.

ㄱ) 학습/사용

| 국면 | 언제 | 하는 일 | 결과물 |
|---|---|---|---|
| 학습(training) | 모델 만들기 전에 딱 한 번 | 코퍼스를 보고 vocab·병합규칙을 만듦 | vocab.json, merges.txt |
| 사용(encode/decode) | 학습·추론 때마다 | 정해진 규칙으로 텍스트를 쪼개고 ID로 바꿈 | input_ids 등 |

대부분의 실무는 이미 학습된 토크나이저를 사용하는 쪽이다.

ㄴ) 인코딩 파이프라인 (5단계)
HuggingFace tokenizers 기준. 텍스트가 ID가 되기까지 이 순서로 통과한다.

    원문
    → 1. Normalization    (정규화)
    → 2. Pre-tokenization (1차 분할)
    → 3. Model            (서브워드 알고리즘)
    → 4. Post-processing  (특수 토큰 부착)
    → 5. → input_ids

a. Normalization (정규화)
문자 수준 정리. 토크나이저마다 다르게 설정된다.
    - 유니코드 정규화(NFC/NFKC 등) — 겉보기 같은 문자를 한 형태로 통일
    - 소문자화 (BERT uncased), 악센트 제거 (café → cafe)
    - 중복 공백 정리, 제어문자 제거
정규화가 세면 decode(encode(x))가 원문과 정확히 일치하지 않을 수 있다.

b. Pre-tokenization (1차 분할)
본격적인 서브워드 분할 전에 텍스트를 "단어 비슷한 덩어리"로 먼저 쪼갠다. 이 경계를 서브워드 토큰이 넘지 못한다.
    - 공백·구두점 기준 분할이 기본
    - ByteLevel (GPT-2 계열): 공백을 Ġ 기호로 바꾸고 텍스트를 UTF-8 바이트로 변환. 어떤 문자든 256개 바이트의 조합으로 표현되므로 진짜 OOV가 없어진다.
    - Metaspace (SentencePiece): 공백을 ▁로 치환. 공백도 문자처럼 다뤄서 디코딩이 정확히 복원됨.
    - 숫자 자릿수 분리 (Llama 등): 1234 → 1 2 3 4 — 수 계산 안정성 목적

c. Model (서브워드 알고리즘)
pre-token 덩어리를 실제 vocab에 있는 토큰으로 쪼갠다.

| 알고리즘 | 인코딩 방식 |
|---|---|
| BPE | 학습된 병합 규칙을 순서대로 최대한 적용 |
| WordPiece | 앞에서부터 vocab에 있는 가장 긴 조각을 탐욕적으로 매칭, 이어지는 조각에 ## |
| Unigram | Viterbi로 "확률이 가장 높은 분할"을 탐색 |

d. Post-processing (특수 토큰 부착)
모델이 요구하는 형식으로 포장한다.

    BERT 단일 문장:   [CLS] 토큰들 [SEP]
    BERT 문장쌍:      [CLS] A토큰들 [SEP] B토큰들 [SEP]  + token_type_ids
    Llama:           <s> 토큰들

add_special_tokens=False로 끌 수 있다 (직접 프롬프트를 조립할 때 중복 방지).

e. ID 변환
각 토큰을 vocab에서 조회해 정수로.

1. Preference Alignment (선호도 정렬)
사전학습(pretraining)은 모델에게 언어 능력과 지식을 주고, 지도 미세조정(SFT, supervised fine-tuning)은 "질문에 답변 형식으로 응답한다"는 행동을 가르친다. 하지만 SFT 데이터는 사람이 직접 작성한 정답 예시라서, "이 두 응답 중 어느 게 더 낫다"는 상대적인 판단을 직접 가르치지는 못한다. 실제로 좋은 응답이란 정답이 하나로 정해지지 않고(같은 질문에도 여러 괜찮은 답이 존재), 정확성뿐 아니라 유용함·안전함·톤처럼 사람이 "선호"로만 표현할 수 있는 기준이 섞여 있다. Preference alignment는 이 선호를 모델 행동에 직접 반영하는 후속 학습 단계다.

같은 프롬프트에 대해 모델이 낸 응답 두 개(또는 여러 개)를 사람(또는 다른 LLM)에게 "어느 쪽이 더 낫냐"고 비교시켜 선호 데이터를 모은다. 정답을 직접 쓰게 하는 것보다 "A가 B보다 낫다"는 상대 비교가 훨씬 쉽고 일관되기 때문이다. 이 비교 데이터를 이용해 모델이 사람이 선호하는 응답 쪽으로 확률을 더 주도록 학습시킨다.

ㄱ) 전체 흐름

    사전학습 → SFT → Preference Alignment
    (언어/지식 습득) → (지시 따르기 형태 학습) → (사람이 선호하는 쪽으로 행동 다듬기)

ㄴ) RLHF와 DPO

a. RLHF (Reinforcement Learning from Human Feedback): 먼저 선호 데이터로 "이 응답이 얼마나 좋은가"를 점수로 매기는 별도의 보상 모델(reward model)을 학습시킨다. 그다음 PPO 같은 강화학습 알고리즘으로 원래 모델(정책)을 이 보상 모델이 높은 점수를 주는 방향으로 반복 업데이트한다. 두 단계(보상 모델 학습 → 강화학습)를 거치는 만큼 파이프라인이 복잡하고 학습이 불안정해지기 쉽다.

b. DPO (Direct Preference Optimization): 보상 모델과 강화학습 루프를 따로 두지 않고, 선호 데이터(A가 B보다 낫다)로 정책 모델을 곧바로 최적화하는 손실 함수 하나로 대체한 방법이다. RLHF와 비슷한 효과를 훨씬 단순한 학습 절차로 얻을 수 있어서 최근 오픈소스 모델들에서 널리 쓰인다.

이 외에 사람 대신 다른 LLM이 선호 판단을 대신하는 RLAIF(AI 피드백 기반)도 있는데, 사람 라벨링 비용을 줄이는 변형이다.

AI 엔지니어 입장에서는 이미 정렬이 끝난 모델(Claude, GPT 등)을 가져다 쓰는 경우가 대부분이라 직접 RLHF나 DPO를 돌릴 일은 적지만, 모델이 왜 "그럴듯하지만 회피하는 답" 같은 특유의 습관을 갖는지(정렬 과정에서 생긴 것)와 오픈소스 모델에 커스텀 정렬(LoRA 위에 DPO)을 얹는 선택지가 있다는 것 정도는 개념으로 잡아두면 모델 선택이나 튜닝 방향을 판단할 때 도움이 된다.

ㄷ) RLHF vs PPO vs DPO
용어의 층위가 다르다. RLHF는 전체 파이프라인/프레임워크이고, PPO는 그 안의 최적화 단계에서 쓰는 강화학습 알고리즘이다. DPO는 RLHF 전체(보상 모델 + PPO 루프)를 통째로 대체하는 다른 방법이다.

    RLHF (전체 파이프라인/프레임워크)
    └─ 그 안의 최적화 단계에서 PPO(강화학습 알고리즘)를 씀

    DPO = RLHF 전체(보상 모델 + PPO 루프)를 통째로 대체하는 다른 방법

즉, RLHF와 DPO는 같은 목표를 이루는 두 가지 방법이고, PPO는 RLHF 안에서 쓰이는 부품 중 하나다.

a. RLHF의 핵심 구성요소
SFT 모델, 참조 모델, 보상 모델, 정책 모델, KL 페널티

b. PPO의 역할
PPO(Proximal Policy Optimization)는 위 구성요소들이 다 갖춰진 뒤, "보상 모델 점수(에서 KL 페널티를 뺀 값)를 최대화하도록 정책 파라미터를 어떻게 업데이트할까"를 담당하는 강화학습 알고리즘이다.

    - 프롬프트를 정책에 넣어 응답 생성 → 보상 모델이 점수 매김 → KL 페널티 적용 → PPO로 정책 파라미터 업데이트 → 반복

이 루프 안에 모델이 4개(정책, 참조, 보상, 그리고 종종 가치 함수까지) 동시에 관여해서 메모리와 구현 복잡도가 꽤 크다.

c. DPO의 핵심 구성요소
선호 데이터, 참조 모델, 손실 함수(classification 형태의 손실)

d. 요약

| | RLHF (+PPO) | DPO |
|---|---|---|
| 보상 모델 | 별도로 학습 필요 | 불필요 |
| 강화학습 루프 | 필요 (PPO로 정책 반복 업데이트) | 불필요 (지도학습 방식 1회 최적화) |
| 학습 중 관여 모델 수 | 4개 안팎 (정책·참조·보상·가치함수) | 2개 (정책·참조) |
| 구현/튜닝 난이도 | 높음, 불안정해지기 쉬움 | 상대적으로 낮고 안정적 |
| 유연성 | 보상 모델을 실시간으로 다시 돌며 온라인으로 탐색 가능 | 주어진 선호 데이터셋에 대해 오프라인으로 최적화 |

2. System & Developer Prompt
Anthropic 계열은 system 메시지 하나로 통일돼 있지만, 최근 일부 벤더(OpenAI 등)는 이를 두 층으로 나눈다. system은 플랫폼(모델 제공자)이 까는 최상위 불변 규칙이고, developer는 그 아래에서 앱 개발자가 얹는 지시다. 우선순위는 system > developer > user > tool 순으로, developer 메시지도 user 입력보다는 항상 이긴다고 학습되어 있다.

어느 쪽이든 개념은 같다 — "앱이 미리 깔아두는, 사용자가 못 보고 못 바꾸는 안정적 규칙층"이라는 역할이고, 이 규칙층을 설계하는 게 곧 응답정책 설계다.

3. 응답정책

ㄱ) 구성요소
    - 범위(scope): 이 모델/에이전트가 다루는 것과 다루지 않는 것을 명시. "~에 대해서만 답하라", 범위 밖 요청이 오면 어떻게 반응할지(정중히 거절 / 다른 채널 안내 등)까지 정해야 실전에서 안 흔들림
    - 출력 형식: 스키마, 길이 제한, 형식(JSON/마크다운/plain text), 언어. 형식은 애매하게 두면 준수율이 떨어지므로 가장 구체적으로 써야 하는 부분
    - 톤·스타일: 격식 수준, 이모지 여부, 장황함 정도
    - 행동 규칙(가드레일): 하지 말아야 할 것(민감정보 요청, 특정 주장 등)과 반드시 해야 할 것(출처 표시, 불확실성 명시 등)
    - 모호성·예외 처리: 정보가 부족하거나 요청이 애매할 때 "되물어라" 할지 "합리적으로 가정하고 진행하라" 할지를 미리 정해둠. 이걸 안 정하면 모델마다, 상황마다 제각각으로 행동함
    - 도구 사용 정책(에이전트라면): 어떤 상황에 어떤 도구를 쓰는지, 되돌리기 어려운 행동 전에는 확인을 받는지 등

ㄴ) 작성 원칙
    - 금지보다 대안: "~하지 마라"만 있으면 모델이 회피 경로를 못 찾아 오히려 이상하게 반응하는 경우가 있음. "이런 경우엔 이렇게 하라"처럼 대체 행동을 같이 주면 더 안정적으로 지켜짐
    - 측정 가능한 규칙: "친절하게 답하라" 같은 추상적 지시보다 "3문장 이내로", "불확실하면 확률 대신 확실하지 않음이라고 명시"처럼 판별 가능한 조건으로 씀
    - 우선순위를 명시적으로 정하기: 안전 규칙, 형식 규칙, 스타일 규칙이 서로 충돌할 수 있음(예: "짧게 답하라"와 "출처를 항상 표기하라"). 어느 게 이기는지 정책 안에 순서로 못박아 두지 않으면 모델이 매번 다르게 타협함
    - 예시로 규칙을 보강: 텍스트 설명만으로 애매한 경계는 few-shot 예시(user/assistant 교대 메시지)로 채워주는 게 설명을 더 늘리는 것보다 효과적인 경우가 많음

ㄷ) 검증
정책을 바꾸면 가드레일 지표(형식 준수율·회귀 스위트)로 실제 효과를 확인한다. "간결하게 답하라"를 추가했더니 전체 정확도는 오르는데 특정 유형에서 회귀가 생기는 식의 트레이드오프가 흔하기 때문에, 규칙 하나를 추가할 때마다 고정된 골든셋으로 전후 비교하는 루틴이 필요하다.

4. Baseline Prompt와 Few-shot Prompt
평가 설계 안에서 맡는 역할이 다르다.

ㄱ) Baseline Prompt(기준선 프롬프트)의 역할
Baseline은 "다른 기법(few-shot, RAG, PEFT, full fine-tuning)이 정말 효과가 있는가"를 판단하기 위한 비교 원점이다. 여기서 핵심은 baseline 자체의 성능이 아니라 공정성이다. Baseline을 대충 짜두면(지시가 모호하고, 라벨 정의가 없고, 출력 형식이 안 고정된 상태) 이후에 어떤 기법을 얹어도 "당연히" 좋아진 것처럼 보이는 착시가 생긴다. baseline에도 실제 프롬프트 엔지니어링 노력(명확한 지시, 용어 정의, 경계 규칙, 출력 형식 고정)을 충분히 들여야 하고, 그래야 이후 LoRA나 RAG가 "프롬프트로는 안 되는 부분"을 메우는지 아니면 "프롬프트를 게을리해서 생긴 격차"를 메우는지 구분된다.

baseline 프롬프트는 결국 "여기서부터 얼마나 개선됐는가"를 재는 눈금의 0점을 정하는 것이다.

ㄴ) Few-shot Prompt의 역할
Few-shot은 프롬프트 안에 입력→출력 예시를 몇 개 넣어 모델이 패턴을 그대로 모방하게 하는 in-context learning 기법이다.
    - 지시문이 못 담는 것을 예시로 메움: "모호하면 neutral로 분류하라" 같은 규칙은 글로 설명하는 것보다 실제 애매한 사례-정답 쌍 몇 개를 보여주는 쪽이 경계를 훨씬 명확하게 전달함
    - 학습 없이 성능을 끌어올려 더 강한 비교 상대를 만듦: 평가 설계 관점에서는 few-shot을 적용한 프롬프트가 "학습 기법(LoRA 등)이 진짜 이겨야 할 상대"가 됨. zero-shot 기준선(0.81)보다 few-shot 32개(0.86)가 이미 상당히 강하고, LoRA(0.87)는 그 few-shot 기준선과 겨우 비등한 수준 — 이 비교가 없었다면 LoRA가 훨씬 대단해 보였을 것

few-shot 프롬프트의 역할은 단순히 "정확도를 올리는 기법"에 그치지 않고, fine-tuning이 정말 필요한지를 판단하는 상한선 역할의 baseline이 되어준다는 데 있다. 이 비용을 감당할 수 없다면 LoRA로 같은 격차를 흡수하는 쪽이 낫다는 판단이 나온다.

ㄷ) Zero-shot Prompt
예시(데모) 없이 지시문·출력 스키마·입력만으로 구성된 프롬프트다. 채팅 역할 매핑에서 few-shot 데모에 해당하는 user/assistant 교대 메시지 줄을 통째로 빼고, system(Role+Task+Output Schema) 다음에 바로 입력이 담긴 마지막 user 메시지만 오는 형태다.
    - 모델이 이미 가진 능력을 순수하게 재는 진단 도구
    - 가장 저렴하고 빠른 실행 형태
    - 진짜 일반화 능력의 테스트

ㄹ) 정리

| | 역할 |
|---|---|
| Zero-shot | 모델의 순수 능력 진단 + 가장 싸고 빠른 실행 형태 + 최종 배포가 지향하는 지점 |
| Few-shot | 지시문이 못 담는 경계를 예시로 메움 + fine-tuning이 이겨야 할 상한선 baseline |
| Baseline | 이후 모든 기법(few-shot 포함)의 개선폭을 재는 눈금의 원점 |

평가를 설계할 때는 보통 baseline을 한 겹이 아니라 여러 단계로 둔다: zero-shot 기준선(가장 기본) → few-shot 기준선(프롬프트로 낼 수 있는 최선) → 그 위에 RAG/PEFT/FT. 각 단계 사이의 차이가 "그 기법이 추가로 벌어준 몫"이고, few-shot 기준선을 건너뛰고 zero-shot과 LoRA만 비교하면 LoRA의 기여를 과대평가하게 된다.

5. 루브릭 (정확성/형식 준수/일관성/불확실성)
가드레일 지표(형식 준수율·지연·비용·회귀)가 운영 관점의 건강 지표였다면, 루브릭은 응답 하나하나의 품질을 채점할 때 쓰는 다차원 기준표다. 개방형 과제(요약, 설명, 대화)는 정답이 하나로 안 정해져서 맞다/틀리다 이분법으로는 평가가 안 되고, 그렇다고 점수 하나로 뭉개면 어디가 문제인지가 안 보인다. 그래서 축을 나눠 각각 채점한다.

ㄱ) 네 가지 차원
    - 정확성(accuracy): 내용이 사실적·논리적으로 맞는가. 참조 정답이 있으면 대조하고, 없으면 검증 가능한 근거와 맞춰봄. 앞서 다룬 "주 지표"가 보통 이 축을 요약한 수치
    - 형식 준수(format compliance): 요구된 스키마·구조를 따르는가. 가드레일 지표에서 다룬 형식 준수율과 같은 개념이지만, 여기서는 응답 개별 단위로 채점함 — 내용이 맞아도 형식이 깨지면 이 축에서 감점
    - 일관성(consistency): 두 갈래로 본다. (1) 응답 하나 안에서 앞뒤가 모순되지 않는가(다단계 추론이나 긴 답변에서 중요), (2) 같은 질문을 여러 번 물었을 때 답이 안정적인가(run-to-run 변동). 후자는 디코딩의 다양성-일관성 상충과 직결되는데, temperature를 낮게 잡을수록 일관성은 오르고 다양성은 떨어지는 그 트레이드오프가 여기서 채점 대상이 됨
    - 불확실성(uncertainty, calibration): 모델이 자신 없는 부분을 과신하지 않고 적절히 신호를 주는가. 모르면 "확실하지 않다"고 말하는지, 근거 없는 추측을 확신에 찬 어조로 내놓는지(hallucination과 직결)를 봄. 정답을 맞히는 것 못지않게, 틀릴 수 있는 지점을 솔직하게 드러내는지가 별도로 채점할 가치가 있는 축

ㄴ) 적용
각 차원마다 척도(1~5점 또는 pass/fail)와 판단 기준을 구체적으로 정의하고, 경계가 애매한 점수는 예시(anchor example)로 고정해둔다. LLM 심판을 쓸 때는 이 루브릭을 심판 모델의 system 프롬프트에 그대로 넣어 차원별로 개별 점수를 뽑게 하는 게 흔한 패턴인데, 이는 응답정책 설계에서 나온 "측정 가능한 규칙으로 쓰기" 원칙이 평가자 쪽에도 그대로 적용되는 지점이다.

6. Self-Consistency와 Reasoning 모델 프롬프팅
사고 사슬(chain-of-thought)을 실제로 강화하는 기법과, 최근 나온 추론 특화 모델을 프롬프팅할 때 접근이 어떻게 달라지는지를 다룬다.

ㄱ) Self-Consistency
일반 CoT 프롬프팅("단계별로 생각하라")은 보통 탐욕적(또는 temperature 0)으로 추론 경로 하나만 뽑아 답을 낸다. 문제는 추론 경로 하나가 중간에 틀리면 최종 답도 같이 틀린다는 점이다.

Self-consistency는 여기에 샘플링을 끼얹는다. 같은 질문에 대해 temperature를 0보다 크게 줘서(보통 0.5~0.8) 서로 다른 추론 경로를 N개(예: 10~40개) 독립적으로 생성하고, 각 경로가 도달한 최종 답만 뽑아 다수결(majority vote)로 최종 답을 정한다.

핵심 직관은 "정답으로 가는 길은 여러 갈래일 수 있지만, 오답은 각자 다른 방식으로 틀린다"는 것이다. 추론 경로 A는 계산 실수로 틀리고 경로 B는 다른 지점에서 틀리면 오답들은 서로 흩어지는 반면, 맞는 경로들은 다른 논리를 거쳐도 같은 답에 수렴하는 경우가 많다. 그래서 여러 경로를 모아 가장 많이 나온 답을 고르면 단일 경로보다 정확도가 오른다.

트레이드오프는 명확하다 — N배 샘플링이니 비용과 지연이 N배로 뛴다. 사고 사슬 하나만 붙여도 출력 토큰이 늘어 비용이 2.5배가 된다는 앞선 예시에, self-consistency는 그 비용을 다시 N배 곱하는 셈이라 실전에서는 정확도가 정말 중요하고 호출량이 감당되는 경우(수학·코드처럼 검증 가능한 정답이 있는 과제)에 주로 쓴다.

ㄴ) Reasoning 모델 프롬프팅
여기서 말하는 reasoning 모델(OpenAI o1 계열, DeepSeek-R1, Claude의 extended thinking 등)은 일반 instruct 모델에 CoT를 프롬프트로 시키는 것과 다르다. 이 모델들은 답을 내기 전에 길게 내부적으로 추론하는 행동 자체를 학습 단계(주로 RL)에서 내재화한 모델이다. 즉 "단계별로 생각하라"는 지시가 없어도 모델이 스스로 긴 추론(종종 별도의 thinking/reasoning 채널)을 거친 뒤 최종 답을 낸다. 이 때문에 프롬프팅 접근이 달라진다.

    - "단계별로 생각하라" 지시가 불필요하거나 역효과: 이미 학습으로 그렇게 행동하도록 되어 있어서, 명시적 CoT 지시나 few-shot 추론 예시를 억지로 넣으면 오히려 모델이 원래 하던 내부 추론 패턴과 충돌하거나 불필요한 토큰만 늘리는 경우가 보고됨. 지시는 "무엇을 풀어야 하는지"에 집중하고, "어떻게 생각해야 하는지"는 모델에 맡기는 쪽이 나음
    - 추론과 최종 답이 채널로 분리됨: 내부 추론(thinking)과 사용자에게 보일 최종 답이 구조적으로 나뉘어 있는 경우가 많음. 출력 스키마를 지정할 때는 이 최종 답 채널에만 형식을 강제해야 하고, 추론 채널 자체의 형식을 통제하려 하면 잘 안 먹히거나 무의미함
    - 추론 강도(effort/budget)를 조절하는 파라미터: 얼마나 길게·깊게 추론할지를 프롬프트 지시가 아니라 별도 설정값(reasoning effort, thinking budget 같은)으로 조절함. 일관성 쪽 vs 다양성 쪽 스위트스팟처럼 과제 난이도에 맞춰 튜닝하는 새로운 손잡이 — 쉬운 과제에 추론을 과하게 시키면 비용만 늘고, 어려운 과제에 짧게 시키면 정확도가 떨어짐

ㄷ) 둘의 관계
Self-consistency는 원래 일반 instruct 모델에 CoT를 걸어 여러 번 샘플링하는 기법으로 제안됐지만, reasoning 모델에도 그대로 적용할 수 있다(같은 질문을 여러 번 돌려 다수결). 다만 reasoning 모델은 한 번의 추론 자체가 이미 깊고 자기 검증적이라 일반 모델만큼 self-consistency의 효과 폭이 크지 않은 경우가 많고, 애초에 1회 추론 비용이 훨씬 크기 때문에 N배 샘플링의 비용 부담도 더 커진다. 그래서 실전에서는 reasoning 모델 하나를 깊게 돌릴지, 일반 모델을 여러 번 샘플링해 다수결로 모을지를 비용 대비 효과로 저울질하게 된다.

7. Tool Calling과 파이프라인

ㄱ) Tool Calling
모델은 코드를 직접 실행하지 못한다. Tool calling은 모델이 "이 도구를, 이 인자로 불러달라"는 구조화된 요청(보통 JSON: 도구 이름 + 파라미터)을 텍스트 대신 출력하는 능력이고, 실제 실행은 모델 바깥의 애플리케이션(하네스)이 담당한다. 이 호출도 결국 assistant 메시지의 특수한 형태일 뿐이라 모델 입장에선 "다음 토큰을 예측한다"는 동작 자체는 똑같다.

ㄴ) 도구가 모델에 전달되는 방식
도구는 이름·설명문·파라미터 스키마(보통 JSON Schema)로 정의돼 시스템 프롬프트에 준하는 자리에 함께 들어간다. 이 도구 정의를 어떤 형식으로 직렬화하는지, tool 결과 메시지를 어떻게 표현하는지는 채팅 템플릿과 마찬가지로 모델마다 다르고, API를 쓰면 이 직렬화를 대신 처리해준다. 모델은 학습(SFT/정렬) 단계에서 바로 이 직렬화 형식으로 "언제 도구를 불러야 하는가"를 배웠기 때문에, 형식이 학습 때와 다르면 호출 정확도가 떨어진다.

ㄷ) 파이프라인 (에이전트 루프)
    - 사용자 입력 + 시스템 프롬프트(도구 정의 포함) → 모델 호출
    - 모델 출력 판별
        - 텍스트 응답 → 루프 종료, 사용자에게 반환
        - 도구 호출 요청 → 다음 단계로
    - 하네스가 요청 파싱 → 실제 함수 실행 → 결과를 tool 역할 메시지로 대화에 추가
    - 갱신된 전체 대화(도구 결과 포함)를 다시 모델에 넣고 처음 단계부터 반복

도구 결과도 결국 대화 히스토리에 쌓여 매 호출마다 통째로 다시 들어간다. 그래서 도구 결과가 길면(파일 전체, API 응답 원본 등) 컨텍스트를 빠르게 잡아먹고, 요약·잘라내기 같은 컨텍스트 관리가 같이 필요해진다.

ㄹ) 설계 시 신경 쓰는 지점
    - 도구 설계: 이름·설명문·스키마 품질이 호출 정확도를 좌우하고, 도구가 많으면 헷갈리므로 묶거나 지연 로딩함
    - 호출 형식 강제: 도구 인자가 스키마를 정확히 따라야 파싱이 되므로, 문법 제약 디코딩(grammar-constrained decoding)으로 애초에 스키마 밖 토큰을 못 뽑게 막는 경우가 많음. 이게 깨지면 형식 준수율 지표가 떨어지는 원인이 됨
    - 병렬 vs 순차 호출: 한 응답에서 여러 도구를 동시에 요청하게 할지, 하나씩 순차로 하게 할지는 모델·하네스 설계에 따라 다르고, 병렬이면 지연을 줄이지만 도구 간 의존성(A 결과가 B 입력이 되는 경우) 처리가 복잡해짐
    - 오류 처리: 도구 실행이 실패하면 에러 메시지를 그대로 tool 결과로 넣어 모델이 스스로 재시도·수정하게 하는 패턴이 일반적임
    - 종료 조건: 루프가 무한히 돌지 않도록 최대 반복 횟수나 타임아웃을 하네스 쪽(애플리케이션)에서 강제함

ㅁ) 정리
Tool calling 자체는 "모델이 구조화된 요청을 출력하는 능력"이고, 그 요청을 실행하고 결과를 다시 먹여 반복하는 게 파이프라인(에이전트 루프)이다. 능력은 모델(학습으로 내재화)에 있고, 루프는 하네스(애플리케이션 코드)에 있다는 분리가 핵심이다.

1. Indexing vs Query 파이프라인
RAG는 시점이 다른 두 개의 파이프라인으로 나뉜다.

| 구분 | Indexing (색인) 파이프라인 | Query (질의) 파이프라인 |
|---|---|---|
| 언제 | 미리, 오프라인으로 (문서가 바뀔 때만) | 사용자가 질문할 때마다, 실시간 |
| 흐름 | 문서 수집 → 정제(Boilerplate 제거) → 청킹 → 임베딩 → Vector Store 저장 | 질문 → 질문 임베딩 → 검색 → Context 조립 → LLM 호출 → 답변·Citation |
| 목표 | "찾을 수 있는 형태"로 만들어 두기 | "찾아서 근거 있게 답하기" |

핵심은 두 파이프라인이 같은 임베딩 모델을 써야 한다는 점이다. 색인할 때와 질의할 때 모델이 다르면 벡터 공간이 달라서 검색이 안 된다.

2. 역색인 (Inverted Index)
책 뒤에 있는 "찾아보기"와 같은 구조다.
    - 정방향: 문서1 → [사과, 바나나, 포도]
    - 역방향: 사과 → [문서1, 문서7], 바나나 → [문서1, 문서3]

단어를 키로 해서 그 단어가 들어 있는 문서 목록을 바로 꺼낼 수 있으므로, 모든 문서를 훑지 않아도 된다. 키워드 검색(BM25, Elasticsearch 등)의 기반이고, 이런 방식을 Sparse 검색이라고 한다. 단어가 정확히 일치해야 잘 찾고, 뜻이 같아도 다른 단어(동의어)는 놓친다는 약점이 있다. 5번의 Dense 검색과 대비되는 개념이다.

ㄱ) BM25 (Best Matching 25)
BM25는 질문의 키워드가 문서에 얼마나 잘 맞는지 점수를 매기는 공식
    - 단어 빈도 (TF, Term Frequency)
    - 희귀도 (IDF, Inverse Document Frequency)
    - 문서 길이 보정

RAG에서의 위치

a. 장점
    - 고유명사, 제품 코드, 에러 메시지처럼 정확히 일치해야 하는 단어에 강하고, 학습이 필요 없으며 빠르다.

b. 약점
    - 뜻만 같고 단어가 다르면 못 찾는다("자동차"로 "차량" 못 찾음).

c. 보완
    - Dense 검색과 섞어 쓰는 하이브리드 검색을 사용

ㄴ) Elasticsearch
대량의 문서를 저장하고 빠르게 검색해 주는 오픈소스 검색 엔진(서버)이다. Java 검색 라이브러리 Lucene을 바탕으로 만들었고, 앞에서 설명한 역색인과 BM25를 기본으로 쓴다.

RAG에서의 위치
    - 원래 키워드(Sparse) 검색 엔진이지만, 지금은 벡터 필드(dense_vector)와 kNN 검색도 지원한다.
    - BM25 검색과 벡터 검색을 한 곳에서 하이브리드로 돌릴 수 있다는 점이 장점
    - LangChain에서 ElasticsearchStore로 Vector Store처럼 사용할 수 있다.

3. Boilerplate
모든 페이지나 문서에 반복되는 내용과 무관한 틀 텍스트다.
예: 웹페이지의 메뉴·푸터·저작권 문구, PDF의 머리말·꼬리말·페이지 번호, "목차", 쿠키 안내.

ㄱ) 색인 전에 제거해야 하는 이유
    - 모든 청크에 같은 문구가 섞이면 청크끼리 비슷해 보여서 검색 품질이 떨어진다.
    - 쓸데없는 토큰이 Context를 차지해서 비용이 늘고 답변이 흐려진다.

4. 청킹 (Chunking)
긴 문서를 검색과 투입에 적당한 크기의 조각으로 자르는 단계다.

ㄱ) 사용하는 이유
    - 문서 전체를 하나의 벡터로 만들면 의미가 뭉개지고, 질문과 관련된 부분만 골라 LLM에 넣을 수도 없다.

ㄴ) 트레이드오프
    - 너무 작으면 문맥이 끊기고, 너무 크면 검색이 부정확해지고 토큰이 낭비된다.

ㄷ) overlap
    - 경계에서 문장이 잘리는 것을 막으려고 앞뒤 조각을 조금씩 겹치게 자른다.

ㄹ) 기준
    - 고정 글자 수 / 문단·문장 단위 / 제목 구조(Markdown 헤더) 단위 등이 있다.

    - 청크에는 출처(파일명, 페이지 등) 메타데이터를 붙여 둔다. Citation(인용·출처 표시)에 필요하다.

5. 임베딩과 Dense
임베딩은 텍스트를 의미를 담은 숫자 벡터(예: 768차원)로 바꾸는 것이다. 뜻이 비슷한 문장은 벡터 공간에서 가까이 놓인다.
Dense는 이 벡터의 모양을 가리키는 말이다.

    - Dense 벡터: 모든 차원에 값이 차 있음 → 의미 기반 검색. "자동차"로 검색해도 "차량" 문서를 찾음.
    - Sparse 벡터: 단어 사전 크기만큼 길고 대부분 0 → 역색인·키워드 검색.

질문도 같은 모델로 임베딩한 뒤, 코사인 유사도 같은 기준으로 가장 가까운 청크를 찾는다. 실무에서는 둘의 장점을 합친 하이브리드 검색(Dense + Sparse)도 자주 쓴다.

6. Vector Store
임베딩 벡터를 원문 텍스트·메타데이터와 함께 저장하고, 유사한 벡터를 빠르게 찾아 주는 저장소다. (예: Chroma, FAISS, Qdrant, pgvector)

    - 저장 단위: {벡터, 청크 원문, 메타데이터(출처·페이지)}
    - 수백만 개의 벡터를 하나하나 비교하면 느리므로, 근사 최근접 탐색(ANN) 인덱스로 "거의 정확하지만 아주 빠르게" 찾는다.
    - LangChain에서는 보통 vectorstore.as_retriever()로 바꿔서 체인 안에서 검색기로 쓴다.

ㄱ) Chroma
    - Python에서 쓰기 쉬운 오픈소스 벡터 DB
    - pip install chromadb 한 줄로 설치하고, 별도 서버 없이 내 프로그램 안에서(임베디드) 바로 쓸 수 있다. 로컬 폴더에 저장해 두고 다음에 다시 불러올 수 있고, 메타데이터 필터도 지원한다.
    - 학습, 프로토타입, 소규모 프로젝트. LangChain 튜토리얼에서 가장 많이 나온다.

ㄴ) FAISS
    - Meta가 만든 벡터 검색 라이브러리다. DB가 아니다.
    - 유사도 검색 속도가 매우 빠르고 GPU도 지원한다. 다만 DB 기능(서버, 메타데이터 필터, 개별 삭제·수정 관리)은 거의 없어서 "빠른 검색 엔진 부품"에 가깝다. LangChain이 원문·메타데이터 보관을 대신 처리해 준다.
    - 데이터가 자주 바뀌지 않고 검색 속도가 중요할 때, 로컬 실험할 때.

ㄷ) Qdrant
    - Rust로 만든 운영용 벡터 DB
    - Docker나 클라우드에 서버로 띄워서 API로 접근한다. 메타데이터(payload) 필터링이 강력하고, 하이브리드 검색(Dense + Sparse)을 지원하며, 대규모 데이터와 동시 접속에도 버틴다.
    - 실제 서비스 배포, 필터 조건이 복잡한 검색이 필요할 때.

ㄹ) pgvector
    - PostgreSQL에 벡터 타입과 벡터 검색을 추가하는 확장(extension)
    - 기존 Postgres 안에서 벡터를 일반 컬럼처럼 다룬다. SQL WHERE, JOIN, 트랜잭션을 그대로 쓸 수 있어서, 사용자·권한 같은 일반 데이터와 벡터를 한 DB에서 관리할 수 있다.
    - 이미 Postgres를 쓰는 서비스, DB를 하나 더 늘리고 싶지 않을 때.

7. ANN(Approximate Nearest Neighbor, 근사 최근접 이웃 탐색)

ㄱ) KNN의 한계
질문 벡터와 가장 가까운 벡터 k개를 정확하게 찾으려면 저장된 벡터 전부와 거리를 하나씩 계산해야 한다. 이 방식을 정확한 kNN, 또는 Brute-force(전수 탐색)라고 한다.
    - 벡터 100만 개 × 768차원 → 질문 한 번에 곱셈·덧셈이 약 7억 번
    - 데이터가 늘어나는 만큼 검색 시간도 그대로 늘어난다(선형 증가).
수천~수만 개 정도면 전수 탐색으로도 충분하지만, 수백만 개를 넘어가면 실시간 응답이 어려워진다.

ㄴ) ANN의 개념(조금 틀려도 되니 훨씬 빠르게)
ANN은 모든 벡터를 보지 않고 가까울 가능성이 높은 후보만 골라서 비교한다.
    - 진짜 1등을 가끔 놓칠 수 있다. 예를 들어 실제 top-5 중 4개만 찾는 식이다.
    - 대신 속도는 수십~수백 배 빨라진다.
RAG에서는 이 정도 손해가 거의 문제가 되지 않는다. 3등 청크 대신 6등 청크가 들어가도 내용은 대부분 비슷하기 때문이다.
    - Recall(재현율): ANN의 정확도를 재는 기준이다. "정확한 kNN의 정답 k개 중 ANN이 몇 개를 찾았는가"를 뜻하고, 보통 0.95 이상을 목표로 한다.

ㄷ) 대표방식 3가지(도서관에서 비슷한 책 찾기)

a. 그래프 기반: HNSW (Hierarchical Navigable Small World)
    - 비유: 지인을 통해 사람 찾기. "이 분야라면 저 사람이 더 잘 알아" 하고 점점 가까운 사람에게 건너가는 방식

    - 구조: 벡터마다 가까운 이웃 벡터와 연결선을 만들어 둔다. 층이 여러 개라서 위층에서는 멀리 크게 이동하고, 아래층으로 내려갈수록 촘촘하게 좁혀 간다(고속도로 → 국도 → 골목길).

    - 장점: 빠르고 Recall이 높아서 현재 가장 많이 쓰이는 방식이다. Chroma, Qdrant, pgvector 모두 기본으로 HNSW를 지원한다.

    - 단점: 연결선을 저장하므로 메모리를 많이 쓴다.

b. 클러스터 기반: IVF (Inverted File Index)
    - 비유: 도서관 서가 분류. "요리" 서가와 "역사" 서가로 나눠 두고, 질문과 관련된 서가 몇 곳만 뒤지는 방식

    - 구조: 미리 벡터들을 여러 묶음(클러스터)으로 나누고 각 묶음의 중심점을 저장한다. 검색할 때는 질문과 가까운 중심점 몇 개를 고른 뒤 그 묶음 안에서만 비교한다.

    - 이름에 “Inverted”가 붙는 이유: 역색인처럼 클러스터 → [그 안의 벡터들] 목록을 만들어 두기 때문이다.

    - 단점: 정답이 경계 근처에 있으면 옆 묶음에 들어가 있어서 놓칠 수 있다. 그래서 묶음을 몇 개 뒤질지가 핵심 조절값이다.

c. 압축 기반: PQ (Product Quantization)
    - 비유: 책 전체 대신 요약 카드만 들고 비교하는 방식

    - 벡터를 작게 압축해서 메모리를 크게 줄이고 비교 속도도 높인다. 대신 정밀도가 조금 떨어진다.

    - 주로 IVF와 함께 쓴다(IVF-PQ). FAISS에서 대용량 데이터를 다룰 때 많이 쓴다.

| 방식 | 핵심 아이디어 | 강점 | 약점 |
|---|---|---|---|
| HNSW | 이웃 연결 그래프를 따라 이동 | 빠르고 정확함, 기본 선택지 | 메모리 사용량 큼 |
| IVF | 묶음으로 나눠 일부만 탐색 | 구조가 단순하고 대용량에 유리 | 경계 근처 정답을 놓칠 수 있음 |
| PQ | 벡터를 압축 | 메모리 절약 | 정밀도 감소 |

ㄹ) 속도와 정확도를 조절하는 값
모든 ANN에는 “더 많이 뒤질수록 정확하지만 느려진다”는 조절값이 있다.

    - HNSW: ef_search. 탐색할 때 유지하는 후보 수. 크게 하면 정확도가 올라가고 속도는 떨어진다.

    - IVF: nprobe. 뒤질 묶음 수. 크게 하면 정확도가 올라가고 속도는 떨어진다.

ㅁ) RAG 관점에서 정리
    - 청크가 적은 학습용·소규모 프로젝트에서는 전수 탐색이든 ANN이든 체감 차이가 거의 없다. Chroma를 쓰면 내부에서 HNSW가 알아서 동작한다.

    - 검색 품질이 나쁠 때 원인은 대부분 ANN이 아니라 청킹이나 임베딩 모델에 있다. ANN 때문에 놓치는 경우는 생각보다 드물다.

    - 데이터가 수백만 개 이상으로 커지면 그때 HNSW, IVF, PQ 중에서 고르고 조절값을 튜닝하게 된다.

ANN은 전부 비교하지 않고 그래프나 묶음 구조로 가까운 후보만 빠르게 좁혀서, 약간의 정확도를 내주고 큰 속도를 얻는 검색 방식이다.

8. Context
검색된 청크들을 모아 LLM 프롬프트 안에 넣는 근거 자료 묶음이다.
    - 프롬프트 구조: [시스템 지시] + [Context: 검색된 청크들] + [사용자 질문]
    - 지시문에서 “Context에 있는 내용만으로 답하라”고 제한해 환각을 줄인다.
    - 청크마다 [1], [2]처럼 번호나 ID를 붙여 넣어 두면, LLM이 어느 근거를 썼는지 표시할 수 있다(→ Citation).
    - 컨텍스트 창(토큰 한도)이 있으므로 몇 개를 넣을지(top-k), 어떤 순서로 넣을지가 품질에 영향을 준다.

9. 체인: prepare → invoke_model → finish
RAG 답변 생성을 세 단계 함수로 나누고 state를 넘기며 이어 붙인 구조다.

    state(dict) → prepare → invoke_model → finish → 최종 응답

    - prepare: 질문을 받아 검색하고, Context를 조립하고, 프롬프트 메시지를 만들어 state에 넣는다. 검색 결과가 없으면 여기서 일찍 "보류" 표시를 할 수도 있다.
    - invoke_model: 만들어진 프롬프트로 LLM을 호출하고 원본 응답을 state에 넣는다. 호출 오류는 여기서 잡는다.
    - finish: 원본 응답을 파싱·검증해서 최종 JSON 형태로 정리한다.

ㄱ) state 전달
각 단계가 dict 하나를 받아 필요한 키를 추가해서 다음 단계로 넘긴다. 그래서 finish 단계에서도 prepare가 만든 청크 목록을 참고해 citation을 검증할 수 있다. 단계별로 무엇이 들어왔고 나갔는지 확인하기 쉬워 디버깅에도 좋다.

ㄴ) RunnableLambda
일반 Python 함수를 LangChain의 Runnable로 감싸는 도구다. 감싸면 | 연산자로 연결할 수 있다.

    chain = RunnableLambda(prepare) | RunnableLambda(invoke_model) | RunnableLambda(finish)

ㄷ) 응답 JSON Schema
출력 형태를 고정해 둔다.

    {
        "status": "ok | insufficient | system_error | invalid_output",
        "answer": "답변 문자열",
        "citations": ["chunk_3", "chunk_7"]
    }

형태가 고정되어 있어야 프론트엔드나 다른 코드가 안정적으로 결과를 받아 쓸 수 있다.

ㄹ) 이중 JSON 파싱
LLM 출력이 깔끔한 JSON이 아닐 때를 대비한 두 단계 방어다.

    - 먼저 응답 전체를 그대로 json.loads 해 본다.
    - 실패하면 json 코드 펜스나 앞뒤 설명문을 벗겨내고, { ... } 부분만 잘라서 다시 파싱한다.

둘 다 실패하면 invalid_output으로 처리한다. LLM은 "물론입니다! 다음은 JSON입니다:" 같은 말을 덧붙이는 일이 흔해서 이 방어가 필요하다.

10. Citation (인용·출처 표시)
답변의 각 내용이 어느 청크(문서)에서 왔는지 표시하는 것이다.

a. 목적
사용자가 근거를 직접 확인할 수 있게 하고(신뢰), 개발자가 환각을 잡아낼 수 있게 한다.

b. 방식
Context에 청크 ID를 붙여 넣고, LLM에게 사용한 ID를 citations에 적도록 지시한다.

c. 검증
LLM이 실제로 주지 않은 ID를 지어낼 수 있다. finish 단계에서 “citations의 ID가 prepare에서 넣은 청크 목록 안에 있는지” 확인하고, 없는 ID는 버리거나 오류로 처리한다.
최종적으로는 ID를 메타데이터(파일명·페이지)로 바꿔서 사용자에게 보여 준다.

11. 답변 보류 (insufficient / system_error / invalid_output)
잘못된 답을 하는 것보다 "지금은 답할 수 없다"고 명확히 알리는 것이 낫다는 설계다. status로 이유를 구분한다.

| status | 의미 | 주로 나오는 곳 | 예 |
|---|---|---|---|
| insufficient | 근거 부족. 시스템은 정상이지만 Context에 답이 없음 | prepare(검색 결과 없음) 또는 LLM 스스로 판단 | 문서에 없는 내용 질문 |
| system_error | 시스템 쪽 장애 | invoke_model | LLM 서버 다운, 타임아웃, 네트워크 오류 |
| invalid_output | LLM이 답은 했지만 형식이 틀림 | finish | 이중 파싱 실패, 필수 키 누락, 없는 citation ID |

대응 방법에 따른 분류다.
    - insufficient → 사용자에게 "자료에 없습니다" 안내, 문서 보강 필요
    - system_error → 재시도하거나 운영자에게 알림
    - invalid_output → 재요청하거나 프롬프트·스키마 개선

전체 연결 요약:
Indexing 파이프라인(Boilerplate 제거 → 청킹 → Dense 임베딩 → Vector Store)으로 미리 준비해 두고, Query 파이프라인에서 체인(prepare에서 검색·Context 조립 → invoke_model → finish에서 이중 파싱·Citation 검증)을 돌려, 결과를 status/answer/citations JSON으로 돌려주며, 문제가 있으면 세 가지 보류 상태 중 하나로 정직하게 알린다.

1. randomness 와 seed

ㄱ) randomness
딥러닝 학습은 본질적으로 확률적(stochastic)이다. 무작위성이 있어야 학습이 되는 부분도 있고, 단지 편의상 무작위인 부분도 있다. MLP 파이프라인을 순서대로 따라가면 난수가 쓰이는 지점은 대략 이렇다.

| 단계 | randomness 가 쓰이는 곳 | 영향 |
|---|---|---|
| 데이터 분할 | random_split 으로 train/val 나눌 때 | 어떤 샘플이 학습/검증에 들어가는지 |
| 파라미터 초기화 | nn.Linear 의 weight/bias 초기화 (기본 Kaiming uniform) | 학습 시작점이 매번 다름 |
| DataLoader | shuffle=True → 매 epoch 배치 구성 순서 | 미니배치 SGD 의 gradient 궤적 |
| 데이터 증강 | transforms.RandomCrop, RandomHorizontalFlip 등 | 매 스텝 입력이 조금씩 달라짐 |
| Dropout | 매 forward 마다 뉴런을 무작위로 끔 | 정규화 효과, forward 출력이 확률적 |
| 멀티프로세싱 | num_workers>0 일 때 워커별 난수 상태 | 증강 결과 재현성 |
| GPU 연산 | 일부 CUDA 커널의 비결정적 atomic 연산, cuDNN 알고리즘 선택 | 같은 시드라도 미세하게 결과가 갈릴 수 있음 |

즉 같은 코드를 두 번 돌려도 loss 곡선과 최종 정확도가 다르게 나온다. 이 변동성 자체가 문제라기보다, 실험을 비교할 때 방해가 된다.

ㄴ) seed 를 고정하는 이유
같은 코드를 다시 돌려도 같은 결과가 나오는 성질을 재현성(reproducibility)이라 하고, 여러 난수 생성기(random, numpy, torch, torch.cuda)의 시드를 같은 값으로 고정하는 것이 그 출발점이다.
    - 재현성: 논문/과제 결과를 남이 똑같이 돌려볼 수 있어야 한다.
    - 디버깅: "이번엔 왜 터졌지?" 를 추적하려면 실행이 결정적이어야 한다.
    - 공정한 비교: lr=0.01 vs lr=0.001 을 비교할 때, 초기화·배치 순서가 다르면 성능 차이가 하이퍼파라미터 때문인지 운 때문인지 알 수 없다. 시드를 같게 두면 "다른 조건은 동일" 이 성립한다.

seed 는 난수 생성기(PRNG)의 시작 상태를 지정하는 값이다. PRNG 는 결정적 알고리즘이라 시작 상태가 같으면 이후 난수 시퀀스가 완전히 똑같이 재생된다.

ㄷ) PyTorch 에서 시드 고정하기

a. 기본 시드

    import random, numpy as np, torch

    def set_seed(seed: int = 42):
        random.seed(seed)                 # 파이썬 기본 random
        np.random.seed(seed)              # numpy (전처리에서 자주 씀)
        torch.manual_seed(seed)           # CPU 텐서 연산, 초기화
        torch.cuda.manual_seed_all(seed)  # 모든 GPU

b. DataLoader 는 별도로 챙겨야 완전해진다. generator 로 셔플 난수를 고정하고, 워커가 각자 난수를 다시 시드하도록 worker_init_fn 을 넘긴다.

    g = torch.Generator()
    g.manual_seed(seed)

    def seed_worker(worker_id):
        worker_seed = torch.initial_seed() % 2**32
        np.random.seed(worker_seed)
        random.seed(worker_seed)

    loader = DataLoader(dataset, batch_size=64, shuffle=True,
                        num_workers=4, worker_init_fn=seed_worker, generator=g)

c. random_split 도 generator 를 넘겨서 분할을 고정한다.

    train_ds, val_ds = random_split(dataset, [50000, 10000],
                                    generator=torch.Generator().manual_seed(seed))

d. 결정론적 실행(determinism) — 비트 단위로 같게 (속도 손해 감수)
시드 고정만으로 얻는 재현성은 "비슷한 결과"까지고, GPU 커널의 비결정적 연산까지 없애 비트 단위로 동일한 결과를 만드는 것은 별도로 결정론적 실행이라 부른다. 아래 설정이 추가로 필요하다.

    torch.use_deterministic_algorithms(True)
    torch.backends.cudnn.deterministic = True
    torch.backends.cudnn.benchmark = False   # 입력 크기별 최적 알고리즘 자동탐색 끔
    # 환경변수: CUBLAS_WORKSPACE_CONFIG=:4096:8

ㄹ) 주의할 점
    - 시드 고정 ≠ 완벽한 재현: PyTorch/CUDA/cuDNN 버전, GPU 모델, CPU vs GPU 가 다르면 결과가 갈릴 수 있다. 재현성은 "같은 환경 + 같은 시드" 조건부이고, 시드만으로는 재현성(비슷한 결과)까지다. 비트 단위 동일(결정론)은 ㄷ) d. 설정이 추가로 필요하다.
    - 결정적 모드는 느리다: cudnn.benchmark=False, use_deterministic_algorithms(True) 는 학습 속도를 떨어뜨린다. 최종 실험이나 디버깅 때만 켜는 경우가 많다.
    - 단일 시드 결과를 과신하지 말 것: 시드 하나로 낸 정확도는 그 시드의 운을 포함한다. 모델/방법을 비교할 때는 시드 3~5개로 돌려서 평균 ± 표준편차로 보고하는 게 올바르다. 시드 고정은 "재현" 을 위한 것이고, 성능 평가는 "여러 시드의 분포" 로 해야 한다.
    - 호출 위치: set_seed() 는 스크립트 맨 앞, 모델·DataLoader 생성 전에 한 번 부른다. 중간에 다시 부르면 난수 시퀀스가 꼬여 의도와 달라진다.
    - 시드 값을 로그에 남겨라: 어떤 시드로 낸 결과인지 기록해야 나중에 재현할 수 있다.


2. logging 설계
logging 은 "학습이 잘 되고 있는지 지금 판단" + "나중에 실험을 재현·비교" 두 목적을 동시에 만족해야 한다. 이 관점에서 무엇을, 언제, 어디에, 어떤 구조로 남길지를 설계한다.

ㄱ) 무엇을 남길까 (what)

| 범주 | 항목 | 목적 |
|---|---|---|
| 설정(config) | seed, lr, batch_size, optimizer, 모델 구조, 데이터셋 버전 | 재현·비교의 기준 |
| 학습 지표 | train loss, (필요시) train accuracy | 수렴 여부, 과적합 시작점 |
| 검증 지표 | val loss, val accuracy/F1 등 | 일반화 성능, early stopping / 모델 선택 |
| 최적화 상태 | learning rate (스케줄러 사용 시), gradient norm | LR 스케줄 확인, gradient explosion/vanishing 진단 |
| 파라미터 통계 | weight/activation 의 평균·표준편차·히스토그램 (선택) | 초기화·정규화 문제 진단 |
| 자원 | epoch 소요 시간, GPU 메모리, throughput(it/s) | 병목 파악 |
| 산출물 | checkpoint 경로, best metric, 최종 결과 | 이어 학습·평가 |

핵심은 train 과 val 을 항상 쌍으로 남기는 것. 둘의 간격이 과적합 신호다.

ㄴ) 언제 남길까 (granularity)
    - step(iteration) 단위: train loss 는 스텝마다 찍으면 노이즈가 크다. 보통 N 스텝마다(예: 50) 찍거나, 구간 평균(running average)을 찍는다.
    - epoch 단위: val 지표, epoch 평균 train loss, LR, 소요 시간. 사람이 읽는 요약 로그는 여기서.
    - best 갱신 시점: val 지표가 개선될 때만 checkpoint 저장 + "new best" 로그.

두 채널을 분리한다: 콘솔에는 epoch 요약만 깔끔하게, 파일/트래커에는 step 단위 세부까지.

ㄷ) 어디에 남길까 (sinks)

| sink | 용도 |
|---|---|
| 콘솔(stdout) | 사람이 실시간으로 보는 요약. logging 모듈 사용 |
| 파일 로그 | 콘솔과 동일 내용 + 타임스탬프. train.log |
| 구조화 지표 파일 | metrics.csv 또는 metrics.jsonl (스크립트로 후처리·plot) |
| 실험 트래커 | TensorBoard(로컬, 가벼움) 또는 W&B/MLflow(팀·다수 실험 비교) |
| config 스냅샷 | config.yaml / hparams.json (실행 시점 그대로 덤프) |
| checkpoint | ckpt/best.pt, ckpt/last.pt |

학습용 소규모 프로젝트라면 logging 모듈 + CSV + TensorBoard 조합이면 충분하다.

ㄹ) run 디렉토리 규칙
실험마다 폴더 하나로 격리한다. 이름에 타임스탬프 + 핵심 하이퍼파라미터.

    runs/
      2026-08-27_lr0.01_bs64_seed42/
        config.json
        train.log
        metrics.csv
        tb/
        best.pt
        last.pt

이렇게 하면 나중에 metrics.csv 여러 개를 모아 비교 plot 을 그리기 쉽다.

ㅁ) 흔한 실수
    - train loss 만 로깅: 과적합을 못 본다. val 을 반드시 같이.
    - step 단위 raw loss 만 남김: 노이즈에 묻힌다. 이동평균 또는 주기적 로깅.
    - config 를 안 남김: 두 달 뒤 "이 결과 어떤 lr 이었지?" 를 알 수 없다. 코드 수정으로 기본값이 바뀌면 과거 로그 해석 불가 → 실행 시점에 덤프.
    - git commit hash 미기록: 코드가 바뀌면 재현 불가. subprocess 로 git rev-parse HEAD 찍어두면 좋다.
    - print 사용: 타임스탬프·레벨·파일 저장이 안 된다. logging 모듈로.
    - 매 스텝 tb.add_histogram: 느리고 로그 파일이 비대해진다. 히스토그램은 epoch 단위 또는 아예 생략.
    - 여러 프로세스(DDP)에서 전원 로깅: rank 0 에서만 파일/트래커에 쓰도록 가드.
    - checkpoint 를 매 epoch 무조건 저장: 디스크 폭발. best.pt + last.pt 두 개만 굴리는 게 보통.


3. state_dict 와 checkpoint

ㄱ) state_dict
PyTorch 에서 학습 가능한 상태를 담은 파이썬 딕셔너리다. 텐서 자체가 아니라 "이름 → 텐서" 매핑이다.

a. 모델의 state_dict: 각 레이어의 파라미터(weight, bias)와 버퍼(buffer)를 담는다.

    model = nn.Sequential(
        nn.Linear(784, 256), nn.ReLU(),
        nn.BatchNorm1d(256),
        nn.Linear(256, 10),
    )
    for k, v in model.state_dict().items():
        print(k, tuple(v.shape))

    # 0.weight              (256, 784)
    # 0.bias                (256,)
    # 2.weight              (256,)      # BatchNorm gamma
    # 2.bias                (256,)      # BatchNorm beta
    # 2.running_mean        (256,)      # buffer (학습 대상 아님, 추적값)
    # 2.running_var         (256,)      # buffer
    # 2.num_batches_tracked ()          # buffer
    # 4.weight              (10, 256)
    # 4.bias                (10,)

    - 파라미터(nn.Parameter, requires_grad=True): optimizer 가 업데이트하는 대상. model.parameters() 로 순회.
    - 버퍼(register_buffer 로 등록): gradient 는 없지만 모델 상태의 일부. BatchNorm 의 running stats 가 대표적. state_dict 에 포함되므로 저장/로드할 때 같이 따라간다. 버퍼를 안 담으면 추론 시 BN 통계가 초기화되어 성능이 망가진다.
    - 키 이름은 모듈 계층 구조를 . 으로 연결한 것.

b. optimizer 의 state_dict: 옵티마이저도 상태를 가진다.

    opt = torch.optim.Adam(model.parameters(), lr=1e-3)
    opt.state_dict()
    # {'state': {0: {'step': .., 'exp_avg': tensor, 'exp_avg_sq': tensor}, ...},
    #  'param_groups': [{'lr': 0.001, 'betas': (0.9, 0.999), ...}]}

    - Adam 의 1차/2차 모멘트(exp_avg, exp_avg_sq), SGD-momentum 의 velocity 등이 여기 있다. 학습을 중단했다가 정확히 이어서 하려면 이걸 반드시 저장해야 한다. 안 그러면 모멘텀이 0부터 다시 쌓여 loss 가 튄다.

c. state_dict 를 쓰는 이유 (모델 통째 저장 vs state_dict)

    torch.save(model, "model.pt")              # 방법 A: 모델 객체 통째 (pickle)
    torch.save(model.state_dict(), "model.pt") # 방법 B: state_dict 만  ← 권장

방법 A 는 pickle 이 클래스 정의 위치(모듈 경로)에 의존한다. 파일을 옮기거나 리팩터링하면 로드가 깨진다. 방법 B 는 순수한 텐서 딕셔너리라 이식성이 좋다. 로드할 때는 모델을 먼저 코드로 만들고 파라미터만 부어넣는다.

ㄴ) checkpoint
"학습의 특정 시점을 통째로 저장한 것". state_dict 는 재료이고, checkpoint 는 그 재료들을 모은 딕셔너리다. 학습 재개와 모델 선택에 필요한 모든 것을 담는다.

a. 무엇을 담느냐는 목적에 따라 다르다

| 목적 | 필요한 것 |
|---|---|
| 추론/배포만 | model.state_dict() (+ config) |
| 학습 정확히 이어서 | model + optimizer + scheduler + scaler + epoch/step + RNG state |
| 실험 관리 | 위 + best metric + config + git hash |

b. checkpoint 로드해서 학습 재개 → 4절 참고.

c. best 와 last 를 나눠 굴리는 이유

    ckpt/
      last.pt   # 매 epoch 덮어씀 → 학습 크래시 시 재개용
      best.pt   # val 지표 개선될 때만 저장 → 최종 평가·배포용

    - last.pt: 이어 학습이 목적. optimizer/scheduler/RNG 포함, full checkpoint.
    - best.pt: 성능이 가장 좋았던 순간의 모델. 마지막 epoch 이 항상 최고는 아니다(과적합). 보통 model.state_dict() + metric + config 만 담아 가볍게.

d. 자주 겪는 문제
    - Missing key(s) / Unexpected key(s): 모델 구조가 저장 시점과 다르다. 레이어를 추가/제거했거나 이름이 바뀜. 부분 로드는 model.load_state_dict(sd, strict=False).
    - DataParallel/DDP 접두사 module.: 래핑된 모델로 저장하면 키가 module.0.weight 가 된다. 저장 시 model.module.state_dict() 를 쓰거나, 로드 시 접두사를 벗긴다.
    - BatchNorm 성능 저하: 버퍼(running stats)를 안 담았거나, 로드 후 model.eval() 을 안 불렀다. 추론 전 eval() 필수.
    - device 불일치: 로드 시 map_location 을 지정. GPU 에서 저장한 걸 CPU 에서 열 때 특히.
    - weights_only: 최신 PyTorch 는 torch.load(..., weights_only=True) 가 기본/권장(임의 코드 실행 방지). 순수 텐서 딕셔너리면 문제없지만, config 에 커스텀 객체가 있으면 안전한 타입만 쓰거나 weights_only=False 를 명시.
    - optimizer state 누락으로 재개 후 loss 튐: 위에서 말한 모멘텀 문제. full checkpoint 를 저장하라.
    - 재현 안 됨: RNG state 를 안 담으면 재개 후 데이터 셔플 순서가 달라진다. 엄밀한 재현이 필요하면 rng_state 포함.


4. 모델 불러오기 vs 학습 재개
둘 다 torch.load 로 파일을 여는 건 같지만, 목적과 복원 범위가 다르다.

| 항목 | 모델 불러오기 (load model) | 학습 재개 (resume training) |
|---|---|---|
| 목적 | 추론/평가, 또는 새 학습의 출발점(전이학습·파인튜닝) | 중단된 그 학습을 끊김 없이 그대로 계속 |
| 복원하는 것 | model.state_dict() 만 | model + optimizer + scheduler + scaler + epoch/step + best metric + RNG state |
| 필요한 파일 | 가벼운 weight 파일 (best.pt) | full checkpoint (last.pt) |
| optimizer | 새로 생성 (모멘텀 0에서 시작) | 저장된 상태 복원 (모멘텀 유지) |
| 시작 epoch | 0 (또는 새 스케줄) | 저장된 epoch + 1 |
| LR 스케줄 | 새로 시작 | 저장된 시점부터 이어짐 |
| 데이터 순서 | 상관없음 / 새 시드 | RNG 복원 시 원래 순서 이어감 |
| 결과 | 원본과 다른 학습 궤적 (의도된 것) | 중단 없이 돌린 것과 (거의) 동일해야 함 |

ㄱ) 모델 불러오기
"이 파라미터 값" 만 있으면 되는 경우다.
    - 추론/평가
    - 전이학습 / 파인튜닝 (새 학습의 출발점)

ㄴ) 학습 재개
"중단된 지점의 학습 상태 전체" 를 복원한다. 서버가 죽었거나, 시간 제한에 걸렸거나, 이어서 더 돌리고 싶을 때.

ㄷ) optimizer 복원이 필요한 이유
Adam 을 예로 들면, 각 파라미터마다 exp_avg(1차 모멘트), exp_avg_sq(2차 모멘트), step(카운터) 을 누적하고 있다. 실효 학습률은 이 누적값에 따라 조정된다.
    - optimizer 를 새로 만들고 재개하면 → 이 누적값이 0에서 다시 시작 → 첫 스텝들의 업데이트 크기가 왜곡 → loss 가 눈에 띄게 튀었다가 회복. 짧은 학습이면 최종 성능까지 영향.
    - SGD + momentum 도 마찬가지로 velocity 가 날아간다.

그래서 "이어서 학습" 이 목적이면 optimizer state 는 필수, "새 학습" 이 목적이면 버리는 게 맞다.

ㄹ) scheduler / epoch 복원이 필요한 이유
    - scheduler: Cosine, StepLR 등은 내부에 last_epoch 카운터가 있다. 복원 안 하면 LR 이 초기값으로 돌아가 스케줄이 어긋난다. scheduler.load_state_dict 또는 생성 시 last_epoch=start_epoch-1.
    - start_epoch: 복원 안 하고 0부터 돌리면 이미 학습한 데이터를 또 학습하고, 총 epoch 수가 늘어난다.
    - global_step: 로깅 x축이 어긋나서 그래프가 겹친다.

ㅁ) 판단 기준
    - 지금 이 실험을 중단 없이 계속 하는 게 목표다 → 학습 재개 (full checkpoint, last.pt)
    - 학습된 가중치를 재료로 써서 다른 걸 한다 (추론, 평가, 파인튜닝, 다른 데이터) → 모델 불러오기 (best.pt 의 model 만)

결론은 모델 불러오기는 "값" 을 가져오는 것, 학습 재개는 "진행 상태" 를 복원하는 것.


5. 평가·추론에서 eval() + inference_mode() 를 쓰는 이유
eval() 과 inference_mode() 는 직교(orthogonal)한다. 서로를 대체하지 않으므로 추론할 때는 둘 다 필요하다.

ㄱ) 모델 상태만 복원하면 되는 이유
추론에서는 파라미터 업데이트가 일어나지 않는다. 그러니 optimizer / scheduler / epoch / RNG 같은 학습 재개용 상태는 전부 불필요하고, model.state_dict()(파라미터 + 버퍼) 만 있으면 된다. 그래서 배포·평가용 체크포인트(best.pt)는 가볍게 만든다.

ㄴ) model.eval() 을 사용하는 이유
eval() 은 모델의 모든 서브모듈에 self.training = False 를 재귀적으로 설정한다. 일부 레이어는 train/eval 에서 동작이 다르다.

a. Dropout
    - train: 뉴런을 확률 p 로 끄고 나머지를 1/(1-p) 배 스케일 (inverted dropout).
    - eval: 아무것도 끄지 않음. 전체 뉴런 사용.
    - eval() 안 하면 → 추론인데도 뉴런이 무작위로 꺼져서 같은 입력에 매번 다른 출력이 나오고 성능이 떨어진다.

b. BatchNorm
    - train: 현재 미니배치의 평균/분산으로 정규화하고, 그 통계로 running_mean/running_var 를 업데이트.
    - eval: 학습 중 누적한 running_mean/running_var(고정값)로 정규화. 통계 업데이트 안 함.
    - eval() 안 하면 → 배치의 통계를 쓰므로 배치 크기·배치 구성에 따라 출력이 달라진다. 특히 batch size = 1 이면 분산이 0이라 계산이 망가진다. 또 추론 데이터로 running stats 가 오염된다.

eval() 은 autograd 와는 무관하다. eval() 만 해도 gradient 는 여전히 계산되고 그래프도 쌓인다.

ㄷ) inference_mode() (또는 no_grad())
기본적으로 PyTorch 는 모든 연산에서 autograd 그래프를 만든다. 추론에서는 backward 를 안 하므로 낭비다.
    - 그래프를 안 만든다 → 중간 activation 을 안 붙잡음 → 메모리 크게 절약 (큰 모델·큰 배치에서 체감)
    - 연산이 빠르다 → autograd 부기(bookkeeping) 생략
    - 실수로 gradient 가 계산될 일이 없다.

    model.eval()
    with torch.inference_mode():
        logits = model(x)
        preds = logits.argmax(dim=1)

a. no_grad() 와의 차이
    - no_grad(): 그래프 추적만 끈다.
    - inference_mode(): 거기에 더해 version counter, view 추적 같은 부기까지 전부 끈다. 더 공격적으로 최적화되지만, 이 블록에서 만든 텐서는 나중에 autograd 계산에 다시 넣을 수 없다.
    - 순수 추론이면 inference_mode() 가 낫다. 추론 결과 텐서를 이후에 gradient 가 필요한 연산(예: 적대적 예제 생성, 일부 메타러닝)에 써야 하면 no_grad() 를 쓴다.


6. 학습곡선 (train/val loss)
학습 로그 숫자만 봐서는 "지금 상태" 를 판단하기 어렵다. 두 곡선을 겹쳐 그리면 다음을 한눈에 본다.
    - 일반화 상태 진단: 과적합(overfitting) / 과소적합(underfitting) / 적정 중 어디인가
    - 언제 멈출까: val loss 가 최소가 되는 지점 = 모델 선택 시점, early stopping 기준
    - 용량·정규화·LR 튜닝 방향: 곡선 모양이 "모델을 키워라 / 규제를 더 걸어라 / LR 을 낮춰라" 를 알려준다
    - 버그 탐지: loss 가 안 내려간다, NaN 으로 튄다, val 이 train 보다 한참 낮다 → 코드 문제 신호
    - 실험 비교: 여러 run 의 val 곡선을 겹치면 어느 설정이 더 낫고 더 안정적인지 보인다

ㄱ) 보는 3가지 축
    a. 두 곡선 사이의 간격 (gap): train 과 val 의 차이 = 일반화 갭. 크면 과적합.
    b. 각 곡선의 추세와 모양: 아직 내려가는 중인가, 평평해졌는가(plateau), 다시 올라가는가(U자).
    c. val 곡선의 최저점 위치: 최저점이 마지막 epoch 이면 더 학습할 여지 있음. 최저점이 중간이고 이후 상승이면 그 지점에서 멈췄어야 함 (early stopping).

ㄴ) 대표 패턴과 해석

| 패턴 | train | val | 해석 | 대응 |
|---|---|---|---|---|
| 적정 학습 | 꾸준히 감소 후 수렴 | train 을 따라 감소, 갭 작음 | 좋음 | 그대로. 살짝 더 키워볼 수도 |
| 과적합 | 계속 감소 (0에 근접) | 어느 시점부터 정체 후 상승(U자) | 모델이 train 을 암기 | early stopping, 규제↑(weight decay, dropout), 데이터 증강, 모델 축소 |
| 과소적합 | 높은 값에서 정체 | train 과 비슷하게 높게 정체 | 모델이 패턴을 못 배움 | 모델 용량↑, 학습 더 오래, LR 조정, feature 점검 |
| 아직 학습 중 | 감소 중 | 감소 중, 아직 안 꺾임 | 덜 돌렸음 | epoch 늘리기 |
| LR 너무 큼 | 요동치거나 발산, NaN | 마찬가지 | 업데이트가 너무 큼 | LR↓, gradient clipping, warmup |
| LR 너무 작음 | 매우 느리게 조금씩 감소 | 마찬가지 | 진전이 미미 | LR↑, 스케줄 조정 |
| val < train | 보통 | train 보다 꾸준히 낮음 | 대개 정상 아님(누수/설정) | 아래 ㄷ) 참고 |
| val 이 심하게 출렁 | 매끈 | 큰 진폭으로 오르내림 | val set 이 작거나 규제 영향 | val set 키우기, 여러 epoch 평균, 곡선 스무딩 |
| 계단식 하락 | 특정 epoch 에 뚝 떨어짐 | 같이 떨어짐 | LR 스케줄러가 LR 낮춘 시점 | 정상. 스케줄 타이밍 참고 |

ㄷ) "val loss < train loss" 에 대한 대응
의외로 흔하고, 원인이 여러 가지다.
    - Dropout/규제: train 은 dropout 켠 상태로 측정, val 은 끈 상태(eval()). val 이 유리해서 낮게 나올 수 있음 → 경미하면 정상.
    - 측정 시점 차이: train loss 는 그 epoch 동안 파라미터가 계속 바뀌며 누적 평균낸 값, val 은 epoch 끝의 고정 모델로 측정. train 이 불리 → 정상.
    - val set 이 train 보다 쉬움: 분할이 편향됨 → split 재확인.
    - 데이터 누수(leakage): 정규화 통계를 전체 데이터로 계산, train 샘플이 val 에 섞임, 중복 샘플 → 버그. 반드시 수정.
    - 갭이 크고 지속적이면 누수를 의심하라.

ㄹ) 팁
    - 같은 축·같은 스케일에 두 곡선을 겹쳐 그린다. 별도 그래프로 그리면 갭이 안 보인다.
    - loss 가 여러 자릿수로 변하면 y축 log scale.
    - accuracy(또는 실제 관심 지표) 곡선도 같이 본다. loss 는 개선되는데 accuracy 는 안 오르거나 그 반대인 경우가 있다 (특히 클래스 불균형).
    - train loss 가 노이즈가 심하면 이동평균으로 스무딩하되, 원본도 흐리게 같이 표시.
    - 최저 val 지점에 마커를 찍고 그 epoch 를 기록 → 그게 배포할 체크포인트.
    - 곡선 하나로 결론내지 말 것. 시드 3~5개의 val 곡선을 겹쳐 그려 평균과 밴드(±std)를 보면, 성능 차이가 진짜인지 노이즈인지 구분된다.
    - x축은 epoch 뿐 아니라 wall-clock 시간이나 step 으로도 그려보면 효율 비교에 유용.

ㅁ) 요약
    val loss 가 아직 내려가는 중          → 더 학습
    val loss 가 평평, train 도 평평(높음)  → 과소적합: 용량/학습량 늘리기
    val loss 가 바닥 치고 올라감          → 과적합: 그 지점에서 멈추고 규제 강화
    loss 가 튀거나 NaN                    → LR 낮추기, clipping
    두 곡선이 거의 붙어서 낮게 수렴        → 이상적


7. Overfitting 과 Underfitting
모델의 목표는 학습 데이터를 잘 맞추는 것이 아니라, 본 적 없는 데이터에서 잘 작동하는 것(일반화)이다. 이 관점에서 두 실패 유형이 있다.
    - Underfitting (과소적합): 모델이 데이터의 패턴 자체를 충분히 못 배움. train 도 못 맞추고 val 도 못 맞춤 → 둘 다 성능 나쁨.
    - Overfitting (과적합): 모델이 train 데이터의 신호(signal) + 잡음(noise)까지 통째로 암기. train 은 아주 잘 맞추는데 val 은 나쁨 → 갭이 큼.

| 상태 | train 성능 | val 성능 | train-val 갭 |
|---|---|---|---|
| Underfitting | 나쁨 | 나쁨 | 작음 |
| 적정 | 좋음 | 좋음 | 작음 |
| Overfitting | 매우 좋음 | 나쁨 | 큼 |

ㄱ) Bias–Variance 관점
    - Bias(편향): 모델의 표현력 부족에서 오는 구조적 오차. 높으면 underfitting. (예: 비선형 데이터를 선형 모델로)
    - Variance(분산): 학습 데이터가 조금만 바뀌어도 모델이 크게 흔들리는 정도. 높으면 overfitting. (train set 의 우연한 패턴에 과민 반응)

전통적으로는 모델 복잡도를 키우면 bias↓ variance↑ 라 그 사이 최적점을 찾는 문제로 본다. (딥러닝의 과매개변수 영역에서는 이 그림이 항상 맞진 않지만, MLP 학습 감각을 잡는 데는 유효하다.)

ㄴ) loss 곡선으로 식별

| 상태 | train loss | val loss |
|---|---|---|
| Underfitting | 높은 값에서 정체 | train 과 비슷하게 높게 정체 |
| 적정 | 낮게 수렴 | train 을 따라 낮게 수렴, 갭 작음 |
| Overfitting | 계속 감소 (0에 근접) | 어느 시점 이후 정체하다 다시 상승 (U자) |

Overfitting 의 전형적 신호는 val loss 가 최저점을 찍고 올라가는데 train loss 는 계속 내려가는 벌어짐이다.

ㄷ) Underfitting — 원인과 대응

a. 원인
    - 모델 용량 부족 (레이어/뉴런 수가 적음, 비선형성 부족)
    - 학습을 너무 짧게 함
    - 학습률이 너무 작거나 너무 커서 제대로 수렴 못 함
    - 규제가 과함 (weight decay, dropout 과도)
    - feature 가 부실하거나 정규화가 안 됨

b. 대응
    - 모델 키우기: 은닉층·뉴런 추가, 활성함수 점검
    - 더 오래 학습, 학습률/스케줄 조정
    - 규제 완화
    - 입력 정규화, feature engineering
    - 먼저 작은 데이터 배치 하나에 일부러 overfit 되는지 확인 (안 되면 모델·학습 코드 버그)

ㄹ) Overfitting — 원인과 대응

a. 원인
    - 데이터 양에 비해 모델이 너무 큼
    - 학습을 너무 오래 함
    - 데이터가 적거나 다양성이 부족
    - 규제가 없음
    - 데이터 누수로 특정 패턴을 외우기 쉬움

b. 대응 (효과 큰 순서로 대략)
    - 데이터 늘리기 / 데이터 증강 — 가장 근본적
    - Early stopping — val loss 최저 지점에서 중단
    - 규제 추가: weight decay(L2), dropout
    - 모델 축소: 레이어/뉴런 줄이기
    - Batch Normalization, label smoothing 등
    - 앙상블, 사전학습 모델 활용
    - 누수 점검 (정규화 통계는 train 으로만 계산, split 중복 제거)

ㅁ) Underfitting ↔ 적정 ↔ Overfitting
세 가지 레버가 함께 작용한다.
    - 모델 복잡도: 키우면 overfit 쪽, 줄이면 underfit 쪽
    - 학습 시간(epoch): 오래 하면 overfit 쪽. 그래서 early stopping 이 규제처럼 작동
    - 데이터 양·품질: 많아지면 같은 모델도 overfit 이 줄어듦

목표는 "train 을 완벽히 맞추는 것" 이 아니라 val 성능이 최고가 되는 지점을 찾는 것이다.

ㅂ) 팁
    - 먼저 작은 부분집합에 overfit 시켜본다 → 모델·손실·역전파가 정상인지 확인 (underfit 이면 여기서 걸림)
    - 전체 데이터로 학습하며 train/val 곡선을 겹쳐 관찰
    - 갭이 크면(overfit) → 규제·데이터·early stopping
    - 둘 다 나쁘면(underfit) → 용량·학습량·LR
    - 최종 모델은 val 최저점의 체크포인트, 성능 보고는 여러 시드의 평균 ± std, 최종 수치는 학습·튜닝에 안 쓴 test set 으로 한 번만

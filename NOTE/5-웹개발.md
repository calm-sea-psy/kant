## HTTP 기초 (요청 메시지·메서드·상태 코드)

> 출처 TIL: 260922

### 1. HTTP 요청 메시지의 네 부분

HTTP 요청은 정해진 형식을 따르는 텍스트 메시지입니다. 요청줄(request line), 헤더(headers), 빈 줄, 본문(body)의 네 부분으로 이루어집니다.

```text
POST /users?notify=true HTTP/1.1      ← ① 요청줄
Host: api.example.com                 ← ② 헤더
Content-Type: application/json
Content-Length: 26
Authorization: Bearer eyJhbGciOi...
                                      ← ③ 빈 줄
{"name": "Kim", "age": 30}            ← ④ 본문
```

| 구성 요소 | 역할 | 필수 여부 |
|---|---|---|
| 요청줄 | 무엇을(메서드), 어디에(대상), 어떤 버전으로 | 필수 |
| 헤더 | 요청에 대한 부가 정보(메타데이터) | Host는 필수, 나머지는 필요할 때 |
| 빈 줄 | 헤더가 끝나고 본문이 시작된다는 표시 | 필수 |
| 본문 | 실제로 보낼 데이터 | 선택(GET은 보통 없음) |

택배에 비유하면 요청줄은 배송 방법과 주소, 헤더는 송장에 적힌 세부 정보(보낸 사람, 내용물 종류, 무게), 본문은 상자 속 물건입니다. 응답도 뼈대가 같고, 첫 줄만 `HTTP/1.1 200 OK` 같은 상태줄(status line)로 바뀝니다.

### 2. 요청줄과 URL의 분해

요청줄은 메서드(method), 요청 대상(request target), HTTP 버전 세 부분을 공백으로 구분합니다. `POST /users?notify=true HTTP/1.1`이라면 메서드는 무엇을 할지(POST), 요청 대상은 어떤 자원에 할지(경로와 쿼리 문자열인 `/users?notify=true`), 버전은 어떤 버전의 HTTP 규칙을 따를지(HTTP/1.1)를 나타냅니다.

브라우저 주소창의 URL은 통째로 전송되지 않고 요청 안에서 나뉘어 들어갑니다. `https://api.example.com:443/users/123?fields=name#profile`을 요청하면 이렇게 나뉩니다.

| URL 부분 | 예 | HTTP 요청에서는 |
|---|---|---|
| 스킴(scheme) | `https` | 요청 메시지에는 안 들어가고, 암호화 연결(TLS)을 쓸지 정하는 데만 씀 |
| 호스트(host) | `api.example.com` | Host 헤더로 감 |
| 포트(port) | `443` | 연결할 때 씀. 기본 포트(http 80, https 443)가 아니면 Host 헤더에 함께 적힘(`Host: localhost:8000`) |
| 경로(path) | `/users/123` | 요청줄로 감 |
| 쿼리 문자열(query string) | `?fields=name` | 요청줄로 감 |
| 조각(fragment) | `#profile` | 서버로 보내지 않음. 브라우저가 페이지 안의 위치로 이동할 때만 씀 |

### 3. 경로 파라미터와 쿼리 파라미터

경로 파라미터(path parameter)는 특정 자원을 가리킬 때 씁니다(`/users/123`). 쿼리 파라미터(query parameter)는 조건이나 옵션을 줄 때 씁니다(`/users?role=admin&page=2`). 쿼리는 `?` 뒤에 `키=값` 형태로 쓰고, 여러 개면 `&`로 잇습니다.

둘을 구분하는 요령은 그 값을 뺐을 때 어떻게 되는지 보는 것입니다. 빼면 다른 자원이 되면 경로이고, 빼도 같은 자원이고 결과만 달라지면 쿼리입니다. `/users/123`에서 `123`을 빼면 사용자 목록이라는 다른 자원이 되니 경로가 맞고, `/users?role=admin`에서 조건을 빼도 여전히 사용자 목록이니 쿼리가 맞습니다.

URL에는 공백이나 한글을 그대로 넣을 수 없어서 퍼센트 기호와 16진수로 바꿔 보냅니다. 이를 URL 인코딩(percent-encoding)이라고 하며, `?q=안녕`은 `?q=%EC%95%88%EB%85%95`로 전송됩니다. 한글 한 글자는 UTF-8로 3바이트이고, 바이트 하나가 `%XX` 하나로 바뀌기 때문에 글자당 세 덩어리가 됩니다.

### 4. 요청 헤더

헤더는 `이름: 값` 형식으로 한 줄에 하나씩 쓰고, 이름은 대소문자를 가리지 않습니다(`content-type`과 `Content-Type`은 같습니다). 자주 보는 요청 헤더를 용도별로 묶으면 다음과 같습니다.

| 용도 | 헤더 | 의미 | 예 |
|---|---|---|---|
| 대상 | Host | 요청을 받을 서버의 도메인. HTTP/1.1에서 반드시 넣어야 하며, 서버 하나(IP 하나)에서 여러 사이트를 운영해도 어느 사이트로 온 요청인지 구분해 줌 | `api.example.com` |
| 본문 설명 | Content-Type | 내가 보내는 본문의 형식 | `application/json` |
| 본문 설명 | Content-Length | 본문 크기(바이트) | `26` |
| 원하는 응답 | Accept | 받고 싶은 응답 형식 | `application/json` |
| 원하는 응답 | Accept-Language | 선호하는 언어 | `ko-KR` |
| 인증 | Authorization | 인증 정보. 보통 Bearer 토큰 형태이고, 서비스에 따라 X-API-Key 같은 전용 헤더를 쓰기도 함 | `Bearer eyJhbGci...` |
| 인증 | Cookie | 서버가 전에 준 쿠키를 브라우저가 자동으로 돌려보냄(로그인 세션 등) | `session_id=abc123` |
| 보낸 쪽 정보 | User-Agent | 요청을 보낸 프로그램 | `Mozilla/5.0 ...`, `curl/8.21.0` |
| 보낸 쪽 정보 | Origin | 요청을 보낸 웹페이지의 출처. 브라우저가 자동으로 붙이고 CORS 판단에 쓰임 | `http://localhost:5173` |
| 캐시 | If-None-Match | 가지고 있는 캐시의 버전(ETag). 바뀐 게 없으면 서버가 본문 없이 304로 응답 | `"v3"` |

Content-Type과 Accept는 방향이 반대입니다. Content-Type은 "제가 보내는 건 JSON이에요"라는 뜻이고, Accept는 "답은 JSON으로 주세요"라는 뜻입니다.

Origin 헤더가 쓰이는 CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)는 한 출처의 웹페이지가 다른 출처의 서버를 호출할 때, 서버가 허용한 경우에만 브라우저가 응답을 페이지에 넘겨주는 규칙입니다. 출처는 스킴·호스트·포트의 조합이라, React 개발 서버(`localhost:5173`)에서 FastAPI(`localhost:8000`)를 호출하면 포트가 달라 다른 출처가 됩니다. 서버가 허용하지 않으면 브라우저가 응답을 막고, FastAPI에서는 CORSMiddleware로 허용할 출처를 지정합니다.

### 5. 빈 줄과 본문

빈 줄은 헤더가 끝났다는 표시입니다. 서버는 빈 줄을 만나면 그 뒤부터를 본문으로 읽습니다. 실제로는 줄바꿈 문자 `\r\n`이 두 번 연달아 온 것입니다.

본문은 서버에 보낼 실제 데이터로, 주로 생성·수정 요청(POST·PUT·PATCH)에 담고 형식은 Content-Type 헤더로 알려줍니다.

| Content-Type | 본문 모양 | 주로 쓰는 곳 |
|---|---|---|
| `application/json` | `{"name": "Kim", "age": 30}` | REST API(가장 흔함) |
| `application/x-www-form-urlencoded` | `name=Kim&age=30` | HTML 폼의 기본 전송 방식 |
| `multipart/form-data` | 여러 부분으로 나눠 글자와 파일을 함께 보냄 | 파일 업로드 |
| `text/plain` | `hello` | 일반 텍스트 |

GET 요청에는 본문을 넣지 않습니다. 표준에서 GET 본문의 의미를 정해 두지 않아서 서버나 프록시가 무시하거나 거부할 수 있기 때문입니다. 조회 조건은 쿼리 문자열로 보냅니다.

### 6. 데이터를 어디에 담을까 — 경로·쿼리·헤더·본문

요청에 데이터를 싣는 자리는 네 곳이고, 담는 데이터의 성격에 따라 자리가 정해집니다.

| 위치 | 담는 것 | 예 |
|---|---|---|
| 경로(path) | 특정 자원을 가리키는 값 | `/users/123` |
| 쿼리 문자열(query) | 조회 조건과 옵션(필터·정렬·페이지) | `?role=admin&page=2` |
| 헤더(header) | 요청에 대한 부가 정보(인증·형식·언어) | `Authorization: Bearer ...` |
| 본문(body) | 생성·수정할 실제 데이터 | `{"name": "Kim"}` |

비밀번호나 토큰 같은 민감한 값은 URL(경로·쿼리)에 넣지 않습니다. URL은 서버 로그, 브라우저 기록, 프록시 기록에 그대로 남기 때문입니다. 헤더나 본문에 담고 HTTPS로 보내야 합니다.

FastAPI는 함수 매개변수를 어떻게 선언하느냐로 이 네 위치를 구분합니다.

```python
@app.post("/users/{user_id}/orders")
def create_order(
    user_id: int,                   # 경로: 주소의 {user_id} 자리 → /users/123/orders
    order: OrderCreate,             # 본문: Pydantic 모델은 JSON 본문에서 읽음
    notify: bool = False,           # 쿼리: 주소에 없는 단순 값 → ?notify=true
    authorization: str = Header(),  # 헤더: Authorization 헤더에서 읽음
):
    ...
```

주소 문자열의 `{user_id}` 자리와 이름이 같은 매개변수는 경로에서, Pydantic 모델 타입은 JSON 본문에서, 주소에 없는 int·bool·str 같은 단순 타입은 쿼리 문자열에서, `Header()`로 표시한 매개변수는 헤더에서 읽습니다. 들어온 요청이 이 선언과 맞지 않으면 FastAPI가 자동으로 422를 돌려줍니다.

### 7. HTTP 메서드와 안전성·멱등성

| 메서드 | 의미 | 예 | 안전(safe) | 멱등(idempotent) |
|---|---|---|---|---|
| GET | 조회 | `GET /users/1` | O | O |
| POST | 생성(ID는 서버가 부여) | `POST /users` | X | X |
| PUT | 전체 교체(없으면 생성 가능) | `PUT /users/1` | X | O |
| PATCH | 부분 수정 | `PATCH /users/1` | X | X(보장 안 됨) |
| DELETE | 삭제 | `DELETE /users/1` | X | O |

안전한(safe) 메서드는 서버 상태를 바꾸지 않는 읽기 전용 메서드라서, 여러 번 호출하거나 캐시해도 부작용이 없습니다. 멱등한(idempotent) 메서드는 같은 요청을 한 번 보내든 열 번 보내든 서버 상태가 똑같습니다. `DELETE /users/1`을 두 번 보내면 첫 번째는 204, 두 번째는 404가 돌아오지만, 1번 사용자가 없는 상태라는 결과는 같으므로 멱등입니다. 멱등성은 응답이 아니라 서버 상태를 기준으로 판단합니다. 반면 `POST /users`를 두 번 보내면 사용자가 두 명 생기므로 멱등이 아닙니다.

멱등성이 중요한 이유는 재시도를 판단하는 기준이 되기 때문입니다. 네트워크가 끊겨 응답을 못 받았을 때, 멱등한 요청은 다시 보내도 안전합니다. 멱등하지 않은 POST를 무심코 다시 보내면 같은 주문이 두 번 생기는 식의 중복이 일어날 수 있습니다.

PUT과 PATCH는 둘 다 수정이지만 범위가 다릅니다. PUT은 자원 전체를 보낸 내용으로 통째로 교체하므로 보내지 않은 필드는 사라지고, PATCH는 보낸 필드만 수정합니다.

```text
현재 상태:  {"name": "Kim", "email": "kim@a.com", "age": 30}

PUT   /users/1  {"name": "Lee"}  →  {"name": "Lee"}
PATCH /users/1  {"name": "Lee"}  →  {"name": "Lee", "email": "kim@a.com", "age": 30}
```

### 8. HTTP 상태 코드의 다섯 분류

상태 코드는 세 자리 숫자이고 첫 자리가 분류입니다. 그래서 클라이언트는 처음 보는 코드를 받아도 첫 자리만 보고 처리할 수 있습니다(처음 보는 4xx는 400처럼 취급).

| 범위 | 분류 | 한 줄 의미 |
|---|---|---|
| 1xx | 정보(informational) | 받았음, 처리 계속 중 |
| 2xx | 성공(success) | 요청 성공 |
| 3xx | 리다이렉션(redirection) | 다른 곳으로 가라 / 캐시를 써라 |
| 4xx | 클라이언트 오류(client error) | 요청이 잘못됨. 보낸 쪽이 고쳐야 함 |
| 5xx | 서버 오류(server error) | 요청은 정상인데 서버가 처리에 실패 |

1xx는 API 개발에서 직접 다룰 일이 거의 없습니다. 100 Continue는 헤더는 받았으니 본문을 계속 보내라는 뜻으로 큰 파일을 올리기 전 확인에 쓰이고, 101 Switching Protocols는 HTTP에서 웹소켓(WebSocket)으로 프로토콜을 바꾸는 것을 승인하는 응답입니다.

### 9. 2xx 성공과 3xx 리다이렉션

| 코드 | 이름 | 의미 / 언제 |
|---|---|---|
| 200 | OK | 요청 성공. GET 조회 결과, PUT·PATCH 수정 후 결과 반환 |
| 201 | Created | 새 자원 생성 성공(주로 POST). Location 헤더에 새 자원 주소를 담음(`Location: /users/124`) |
| 202 | Accepted | 접수는 했지만 아직 처리 전(영상 변환, 대량 배치 같은 비동기 작업). 보통 진행 상황을 확인할 주소를 함께 줌 |
| 204 | No Content | 성공했지만 돌려줄 본문 없음(DELETE 성공 등) |
| 206 | Partial Content | 요청한 범위만 일부 응답(영상 구간 이동, 다운로드 이어받기) |

3xx는 주로 브라우저나 캐시가 자동으로 처리합니다.

| 코드 | 이름 | 의미 |
|---|---|---|
| 301 | Moved Permanently | 영구 이동. Location의 새 주소로 가고, 앞으로도 그 주소를 써라 |
| 302 | Found | 임시 이동. 이번에만 Location으로 가라 |
| 304 | Not Modified | 가진 캐시가 아직 유효하니 그대로 써라. 본문 없음(ETag 비교 같은 조건부 요청의 결과) |
| 307 | Temporary Redirect | 302와 같지만 메서드·본문 유지를 보장(POST는 POST 그대로) |
| 308 | Permanent Redirect | 301과 같지만 메서드·본문 유지를 보장 |

301·302를 받으면 브라우저가 POST를 GET으로 바꿔 다시 요청하는 경우가 있어서, 메서드를 절대 바꾸지 않는 307·308이 따로 생겼습니다.

### 10. 4xx 클라이언트 오류

| 코드 | 이름 | 의미 / 언제 |
|---|---|---|
| 400 | Bad Request | 요청 자체가 잘못됨(JSON 문법 오류, 필수 값 누락, 타입 불일치) |
| 401 | Unauthorized | 인증 안 됨("누구세요?"). 토큰 없음·만료·위조. 이름은 Unauthorized지만 실제 뜻은 미인증 |
| 403 | Forbidden | 권한 없음("누군지는 알지만 안 됩니다"). 일반 사용자가 관리자 API 호출 |
| 404 | Not Found | 자원이 없음(없는 ID, 잘못된 주소). 자원이 있다는 사실 자체를 숨기려고 403 대신 쓰기도 함 |
| 405 | Method Not Allowed | 주소는 있지만 그 메서드는 안 됨(삭제할 수 없는 자원에 DELETE). Allow 헤더로 가능한 메서드를 알려줌 |
| 409 | Conflict | 자원의 현재 상태와 충돌(이미 가입된 이메일로 가입, 동시 수정 충돌) |
| 413 | Content Too Large | 요청 본문이 너무 큼(업로드 용량 초과) |
| 415 | Unsupported Media Type | 지원하지 않는 Content-Type(JSON만 받는데 XML을 보냄) |
| 422 | Unprocessable Content | 형식은 맞는데 내용이 검증에 실패(이메일 형식이 아님, 나이가 음수). FastAPI는 Pydantic 검증에 실패하면 기본으로 422를 돌려줌 |
| 429 | Too Many Requests | 요청 한도(rate limit) 초과. Retry-After 헤더로 언제 다시 보내면 되는지 알려주기도 함 |

헷갈리기 쉬운 두 쌍이 있습니다. 400은 요청을 아예 읽을 수 없을 때(문법 오류)이고, 422는 읽을 수는 있는데 규칙을 어겼을 때(의미 오류)입니다. 둘 다 400으로 통일하는 API도 많으니 팀 안에서 일관되게만 쓰면 됩니다. 401은 (다시) 로그인하면 풀릴 수 있지만, 403은 로그인해도 권한이 없어서 안 됩니다.

### 11. 5xx 서버 오류

| 코드 | 이름 | 의미 / 언제 |
|---|---|---|
| 500 | Internal Server Error | 서버 내부 오류(처리하지 못한 예외, 버그). 가장 흔한 서버 오류 |
| 502 | Bad Gateway | 중간 서버(게이트웨이)가 뒤쪽 서버에서 잘못된 응답을 받음(뒤쪽 앱 서버가 죽어 있음) |
| 503 | Service Unavailable | 일시적으로 처리 불가(과부하, 점검 중). Retry-After로 복구 예상 시점을 알려주기도 함 |
| 504 | Gateway Timeout | 중간 서버가 뒤쪽 서버의 응답을 기다리다 시간 초과 |

502와 504는 클라이언트와 앱 서버 사이에 게이트웨이(예: Nginx)가 있을 때 나옵니다.

```text
클라이언트 → [게이트웨이 (예: Nginx)] → [앱 서버]
                  ├─ 앱 서버가 연결 거부 / 이상한 응답 → 502
                  └─ 앱 서버가 너무 오래 응답 없음     → 504
```

LLM 응답처럼 생성이 오래 걸리는 요청은 게이트웨이의 시간 제한(예: Nginx 기본 60초)에 걸려 504가 나기 쉽습니다. 생성되는 대로 조금씩 흘려보내는 스트리밍 응답을 쓰는 이유 중 하나입니다.


## REST API 설계 (원칙·URI 규칙·응답 코드)

> 출처 TIL: 260922

### 1. REST란 무엇인가

> 참고 · 요청 메시지의 구조는 [HTTP 기초 · 1. HTTP 요청 메시지의 네 부분](#1-http-요청-메시지의-네-부분)

REST(Representational State Transfer)는 2000년 로이 필딩(Roy Fielding)이 박사 논문에서 제안한 아키텍처 스타일입니다. 프로토콜이나 표준이 아니라, HTTP로 API를 설계할 때 따르는 원칙의 모음입니다. 세 가지 요소로 요약됩니다.

| 요소 | 담당 | 예 |
|---|---|---|
| 자원(resource) | URI가 "무엇을" 다룰지 식별 | `/users/123` |
| 행위(verb) | HTTP 메서드가 "어떻게" 할지 표현 | GET, POST, DELETE |
| 표현(representation) | 자원의 현재 상태를 담은 데이터 형식 | JSON |

이름 그대로 자원의 상태를 JSON 같은 표현으로 전송한다는 뜻입니다. 서버는 DB 행을 그대로 넘기지 않고, 그 상태를 JSON으로 표현해서 주고받습니다.

```text
GET /users/123 HTTP/1.1          ← 메서드 + URI
Accept: application/json

HTTP/1.1 200 OK                  ← 상태 코드
Content-Type: application/json

{"id": 123, "name": "Kim"}       ← 표현
```

### 2. REST의 6가지 제약 조건

> 참고 · 매 호출마다 전체 대화를 다시 넣는 원리는 [LLM · 9. 채팅 메시지 역할 — system, user, assistant](4-LLM.md#9-채팅-메시지-역할--system-user-assistant)

필딩이 정한, 이것을 지켜야 REST라고 부를 수 있다는 원칙입니다.

| 제약 조건 | 의미 | 얻는 이점 |
|---|---|---|
| 클라이언트-서버(client-server) | 화면(클라이언트)과 데이터·로직(서버)을 분리 | 양쪽을 따로 개발·배포할 수 있음(예: React 프론트 ↔ FastAPI 백엔드) |
| 무상태(stateless) | 서버는 요청 사이에 클라이언트 상태를 기억하지 않음. 필요한 정보(인증 토큰 등)는 매 요청에 전부 담아 보냄 | 어느 서버가 받아도 처리 가능 → 서버를 늘리기(수평 확장) 쉬움 |
| 캐시 가능(cacheable) | 응답이 캐시해도 되는지 스스로 밝힘(Cache-Control, ETag 헤더) | 중복 요청이 줄고 빨라짐 |
| 균일한 인터페이스(uniform interface) | 모든 자원을 같은 방식(URI + 메서드 + 표준 형식)으로 다룸 | API를 예측할 수 있게 됨. REST의 핵심 |
| 계층화 시스템(layered system) | 중간에 부하 분산기·프록시·게이트웨이가 있어도 클라이언트는 몰라도 됨 | 보안·캐시·부하 분산 계층을 자유롭게 추가 |
| 주문형 코드(code on demand) | 서버가 실행 코드(JS)를 내려줄 수 있음 | 6개 중 유일한 선택 조건 |

무상태의 익숙한 예가 LLM 채팅 API입니다. Ollama의 `/api/chat` 같은 채팅 API도 무상태라서, 대화를 이어 가려면 이전 메시지 전체를 요청마다 다시 보내야 합니다. 서버는 앞서 나눈 대화를 기억하지 않습니다.

균일한 인터페이스는 다시 네 가지로 나뉩니다. 자원은 URI로 식별하고(자원 식별), 자원을 직접 건드리지 않고 JSON 같은 표현을 주고받아 조작하며(표현을 통한 조작), 메시지만 보고도 해석할 수 있어야 하고(자기 서술적 메시지, self-descriptive message — Content-Type·메서드·상태 코드가 이 역할), 응답에 다음에 할 수 있는 행동의 링크를 담습니다(HATEOAS, Hypermedia As The Engine Of Application State). 다만 HATEOAS까지 지키는 실무 API는 드물고, 보통 "RESTful하다"고 하면 다음 절의 URI 규칙과 메서드·상태 코드 사용 규칙을 지키는 정도를 말합니다.

### 3. URI 설계 규칙

> 참고 · 경로와 쿼리를 나누는 기준은 [HTTP 기초 · 3. 경로 파라미터와 쿼리 파라미터](#3-경로-파라미터와-쿼리-파라미터)

가장 중요한 규칙은 URI는 명사(자원)로, 행위는 HTTP 메서드로 표현한다는 것입니다. URI에 동사를 넣지 않습니다.

| 나쁜 예 | 좋은 예 |
|---|---|
| `GET /getUsers` | `GET /users` |
| `POST /createUser` | `POST /users` |
| `POST /updateUser/1` | `PUT /users/1` 또는 `PATCH /users/1` |
| `GET /deleteUser?id=1` | `DELETE /users/1` |

그 밖의 작성 규칙은 다음과 같습니다.

| 규칙 | 예 | 설명 |
|---|---|---|
| 복수형 명사 | `/users`, `/users/123` | 컬렉션은 복수형, 개별 자원은 그 아래 ID |
| 계층 관계는 `/`로 | `/users/123/orders/456` | 123번 사용자의 456번 주문 |
| 소문자와 하이픈(-) | `/user-profiles` | URI 경로는 대소문자를 구분하므로 소문자로 통일, 밑줄(_)은 링크 밑줄에 묻혀 안 보이므로 피함 |
| 끝에 `/` 붙이지 않기 | `/users/` 대신 `/users` | |
| 확장자 넣지 않기 | `/users/1.json` 대신 `/users/1` | 형식은 `Accept: application/json` 헤더로 요청 |
| 필터·정렬·페이지 나누기(pagination)는 쿼리로 | `GET /users?role=admin&sort=created_at&page=2&size=20` | |
| 버전 표시 | `/v1/users` | 경로에 넣는 방식이 가장 흔함 |
| 동사가 꼭 필요한 행위는 하위 자원처럼 | `POST /orders/123/cancel` | 자주 쓰는 실용적 타협 |

### 4. 메서드별 대표 응답 코드

> 참고 · 각 상태 코드의 의미는 [HTTP 기초 · 8. HTTP 상태 코드의 다섯 분류](#8-http-상태-코드의-다섯-분류)부터

| 요청 | 성공 | 대표 실패 |
|---|---|---|
| `GET /users`(목록) | 200. 결과가 0건이어도 200 + `[]`(404 아님) | 400(잘못된 쿼리 파라미터) |
| `GET /users/1` | 200 | 404 |
| `POST /users` | 201 + Location 헤더(비동기 처리면 202) | 400·422(검증 실패), 409(중복) |
| `PUT /users/1` | 200(수정 결과 반환) 또는 204. 새로 만들었으면 201 | 400·422, 404 |
| `PATCH /users/1` | 200 또는 204 | 400·422, 404, 409 |
| `DELETE /users/1` | 204 | 404 |
| 모든 요청 공통 | — | 401, 403, 429, 500, 503 |

목록 조회 결과가 0건이면 자원(컬렉션)은 있고 내용만 빈 것이므로, 404가 아니라 200과 빈 배열로 응답합니다.

## 1. 클래스 불균형(Class Imbalance)

분류 문제에서 각 클래스(레이블)에 속하는 데이터 개수가 크게 차이 나는 상황을 말합니다. 예를 들어 사기 탐지 데이터에서 정상 거래가 대부분이고 사기 거래는 극소수(전체의 1% 수준)인 경우가 대표적입니다.

이런 상황에서는 모델이 무조건 다수 클래스(정상)로만 예측해도 정확도가 매우 높게 나올 수 있어, 정확도만으로는 모델 성능을 제대로 평가할 수 없습니다. 그래서 정밀도, 재현율, F1-score, AUC 같은 지표를 함께 봐야 합니다.

## 2. 혼동행렬(Confusion Matrix)의 4요소

이진 분류에서 "양성"(예: 사기, 질병 있음)을 기준으로 예측 결과를 네 가지로 나눕니다.

- **TP(True Positive)**: 실제로 양성인데 양성으로 맞게 예측한 경우 (예: 사기인데 사기로 잡음)
- **FP(False Positive)**: 실제로는 음성인데 양성으로 잘못 예측한 경우 (예: 정상인데 사기로 오탐)
- **FN(False Negative)**: 실제로 양성인데 음성으로 잘못 예측한 경우 (예: 사기인데 놓침)
- **TN(True Negative)**: 실제로 음성인데 음성으로 맞게 예측한 경우 (예: 정상을 정상으로 맞춤)

## 3. 양성률(Positive Rate)

문맥에 따라 두 가지로 쓰입니다.

- **실제 양성 비율(prevalence)**: 전체 데이터 중 실제로 양성 클래스인 데이터의 비율. 클래스 불균형이 심할수록 이 값은 매우 작아집니다.
- **예측 양성 비율**: 모델이 양성이라고 예측한 데이터의 비율.

여기서 파생되는 대표적인 지표들은 다음과 같습니다.

- **재현율(Recall)**: 실제 양성 중에서 모델이 얼마나 잘 잡아냈는지의 비율
- **정밀도(Precision)**: 양성이라고 예측한 것 중에서 실제로 양성이었던 것의 비율
- **위양성률(FPR)**: 실제 음성 중에서 모델이 잘못 양성으로 예측한 것의 비율

클래스 불균형 상황에서는 재현율·정밀도·F1을 정확도보다 우선해서 봐야, 모델이 소수 클래스(보통 더 중요한 클래스, 예: 사기·질병)를 얼마나 잘 잡아내는지 제대로 파악할 수 있습니다.

## 4. F1-score

정밀도와 재현율의 조화평균입니다. 산술평균 대신 조화평균을 쓰는 이유는, 정밀도와 재현율 중 어느 하나라도 낮으면 F1도 크게 낮아지도록 만들기 위해서입니다.

예를 들어 정밀도가 완벽한데 재현율이 0이라면(즉 양성을 하나도 못 잡아낸 쓸모없는 모델이라면), 산술평균으로는 꽤 괜찮은 점수가 나오지만 조화평균으로 계산한 F1은 0에 가깝게 나와 모델이 쓸모없다는 사실을 정확히 반영합니다. 즉 정밀도와 재현율 중 어느 한쪽만 극단적으로 잘해도 점수가 부풀려지지 않게 막아줍니다.

불균형 데이터에서는 정확도가 왜곡되기 쉽고, 정밀도와 재현율은 서로 트레이드오프 관계(하나를 올리면 다른 하나가 내려가는 경향)에 있는 경우가 많습니다. 임계값을 낮추면 양성 예측이 늘어나 재현율은 오르고 정밀도는 내려가며, 임계값을 높이면 반대 현상이 나타납니다. F1은 이 둘을 한 숫자로 균형 있게 요약해주기 때문에, 모델을 비교하거나 최적 임계값을 고를 때 자주 쓰입니다.

## 5. ROC-AUC와 AP(Average Precision)

둘 다 분류 임계값을 하나로 고정하지 않고, 임계값을 처음부터 끝까지 쭉 바꿔가면서 모델 성능을 종합적으로 평가하는 지표입니다.

**ROC-AUC**: 임계값을 바꿔가며 위양성률과 재현율(진짜 양성 비율)을 각각 좌표로 찍어 이은 곡선(ROC 곡선) 아래의 면적입니다. 완전히 무작위로 예측하는 수준부터 완벽하게 분류하는 수준까지의 사이 값을 가지며, 직관적으로는 "무작위로 양성 샘플 하나와 음성 샘플 하나를 뽑았을 때, 모델이 양성 샘플에 더 높은 점수를 줄 확률"로 해석할 수 있습니다.

위양성률의 분모는 실제 음성 샘플 전체의 개수입니다. 음성이 압도적으로 많은 불균형 데이터에서는, 오탐(FP)이 꽤 늘어나도 분모가 워낙 커서 위양성률 자체는 거의 변하지 않습니다. 그 결과 ROC-AUC가 실제보다 낙관적으로 좋게 나오는 경향이 있다는 함정이 있습니다.

**AP(Average Precision)**: 임계값을 바꿔가며 재현율과 정밀도를 좌표로 찍어 이은 곡선(PR 곡선) 아래의 면적입니다. 정밀도의 분모는 모델이 양성이라고 예측한 것들의 개수입니다. 음성이 아무리 많아도 오탐이 조금만 늘어도 이 분모 대비 비중이 크게 잡혀 정밀도가 민감하게 반응하므로, 소수 클래스(양성)를 잘 맞추는지를 훨씬 엄격하게 반영합니다.

정리하면, ROC-AUC는 분모에 다수 클래스(TN)가 포함되어 클래스 불균형 시 과대평가되기 쉬운 반면, AP는 다수 클래스가 분모에 포함되지 않아 더 현실적인 평가를 제공합니다. 그래서 클래스가 비교적 균형 잡힌 경우에는 ROC-AUC가, 사기 탐지·질병 진단처럼 불균형이 심하고 소수 클래스가 중요한 경우에는 AP가 더 적합합니다.

## 6. 임계값(Threshold)

대부분의 분류 모델은 "양성이다/음성이다"를 직접 뱉지 않고, "이 샘플이 양성일 확률(또는 점수)"을 연속적인 숫자로 출력합니다. 이 연속적인 확률값을 양성과 음성이라는 이산적인 클래스로 변환하기 위해 기준선을 긋는데, 그 기준값이 임계값입니다. 확률이 임계값 이상이면 양성으로, 미만이면 음성으로 분류합니다.

같은 모델, 같은 확률 출력이라도 임계값을 어디에 긋느냐에 따라 TP·FP·FN·TN이 전부 달라집니다. 임계값을 낮추면 더 많은 샘플이 양성으로 분류되어 놓치는 경우(FN)는 줄지만 오탐(FP)은 늘어나 재현율이 오르고 정밀도는 내려갑니다. 반대로 임계값을 높이면 확실한 것만 양성으로 분류해 오탐은 줄지만 애매한 것을 놓쳐(FN 증가) 정밀도가 오르고 재현율은 내려갑니다.

임계값을 극단에서 반대쪽 극단까지 미끄러뜨리면서, 그때마다 계산되는 위양성률·재현율 쌍 또는 재현율·정밀도 쌍을 좌표에 이어 그린 것이 각각 ROC 곡선, PR 곡선입니다. 즉 이 곡선들은 특정 임계값 하나를 정하지 않고 모든 임계값에서의 성능을 한번에 보여주므로, 임계값 선택과 무관하게 모델 자체의 판별력을 비교할 수 있게 해줍니다.

## 7. SMOTE (Synthetic Minority Over-sampling Technique)

클래스 불균형 문제를 데이터 단계에서 완화하는 대표적인 오버샘플링 기법입니다. 소수 클래스의 샘플 수를 인위적으로 늘려 다수 클래스와 비율을 맞춰줍니다.

가장 단순한 오버샘플링 방법인 단순 복제는 소수 클래스 샘플을 그냥 복사해서 늘리는 것인데, 이 경우 완전히 똑같은 데이터가 여러 번 등장해 모델이 과적합되기 쉽고 새로운 정보는 전혀 추가되지 않는다는 문제가 있습니다.

SMOTE는 단순 복제 대신, 기존 소수 클래스 샘플들 사이를 보간해 새로운 합성 샘플을 만듭니다. 소수 클래스 샘플 하나를 고르고, 그 샘플과 가까운 이웃 중 같은 소수 클래스인 샘플 하나를 무작위로 골라, 두 샘플을 잇는 선분 위의 임의의 한 점을 새로운 합성 샘플로 생성합니다. 이 과정을 원하는 비율이 될 때까지 반복합니다. 이렇게 하면 단순 복제보다 훨씬 다양성 있는 소수 클래스 데이터를 만들 수 있어 과적합을 완화하고, 모델이 소수 클래스의 결정 경계를 더 폭넓게 학습하도록 돕습니다.

다만 다음과 같은 주의사항이 있습니다.

- 소수 클래스 샘플 중 이상치이거나 다수 클래스 영역에 섞여 있는 샘플 사이를 보간하면, 오히려 다수 클래스 영역에 잘못된 소수 클래스 합성 샘플이 생길 수 있습니다.
- 고차원 데이터에서는 이웃 기반 보간이 덜 의미 있어질 수 있습니다(차원의 저주).
- 반드시 학습(train) 데이터에만 적용해야 합니다. 검증·테스트 데이터에 SMOTE를 적용하면 합성 샘플의 정보가 원본 샘플에서 새어 나가 성능이 부풀려집니다.
- 교차검증을 쓸 때도, fold를 나눈 뒤 학습 fold 안에서만 SMOTE를 적용해야 합니다.

대안으로는 다수 클래스를 줄이는 언더샘플링(정보 손실 위험이 있음)이나, 데이터를 건드리지 않고 손실함수에서 소수 클래스에 더 큰 가중치를 주는 클래스 가중치 조정(SMOTE와 함께 쓰기도 함)이 있습니다.

## 8. 봉인 테스트(Sealed Test) 원칙

머신러닝 모델 개발 시, 테스트 데이터를 마지막 최종 평가 전까지 절대 들여다보지도, 사용하지도 않고 봉인해서 따로 떼어놓는다는 원칙입니다. 데이터 유출을 막기 위한 핵심 원칙 중 하나입니다.

모델 개발 과정은 보통 전처리, 학습, 성능 확인, 하이퍼파라미터 조정, 다시 학습이라는 반복 루프를 거칩니다. 이 반복 루프에서 테스트 데이터로 성능을 확인하면서 조정을 하면, 개발자가 의식하지 못하는 사이에 모델(또는 개발자의 선택)이 테스트 데이터에 맞춰지게 됩니다. 이러면 테스트 데이터는 더 이상 "한 번도 못 본 데이터"가 아니게 되어, 실제 운영 환경(진짜 처음 보는 데이터)에서는 성능이 뚝 떨어지는 낙관적 편향이 생깁니다.

데이터는 학습 데이터(모델 파라미터를 직접 학습), 검증 데이터(하이퍼파라미터 튜닝·모델 선택·조기 종료 판단에 사용), 테스트 데이터(오직 마지막에 딱 한 번만 최종 성능 확인)로 나누어, 학습·검증 데이터는 개발 중 자유롭고 반복적으로 쓰지만 테스트 데이터는 튜닝이 전부 끝나고 모델이 확정된 뒤 정말 마지막에 딱 한 번만 열어봅니다.

실무에서 흔히 이 원칙이 깨지는 경우로는 다음이 있습니다.

- 테스트 성능을 보고 하이퍼파라미터를 다시 조정하는 경우 (사실상 테스트가 검증처럼 쓰여 봉인이 깨짐)
- 정규화, 결측치 대체, SMOTE 같은 전처리를 전체 데이터에 먼저 적용한 뒤 학습/테스트로 분할하는 경우 (테스트의 통계 정보가 학습 과정에 스며듦)
- 특성 선택을 전체 데이터로 한 뒤 분할하는 경우 (마찬가지로 정보 유출)
- 여러 모델을 테스트 데이터로 비교해서 그중 제일 좋은 것을 최종 선택하는 경우 (테스트가 모델 선택 기준으로 쓰인 것이므로 봉인 위반)
- 교차검증을 쓸 때도 fold 분할 전에 전처리·오버샘플링을 하는 경우
- 시계열 데이터를 무작위로 분할하는 경우 (미래 데이터가 학습에 섞여 들어가 미래 정보를 미리 학습하는 시간 유출)

## 9. 배포 후 새로 만날 "단위" 기준으로 분할하기

봉인 테스트 원칙의 핵심은 "테스트 데이터가 진짜 처음 보는 데이터여야 한다"는 것이지만, "처음 보는 데이터"가 정확히 무엇을 의미하는지는 문제마다 다릅니다. 이를 정하는 것이 바로 데이터를 나누는 단위를 선택하는 문제입니다. 핵심 질문은 "모델을 배포하고 나면, 실제 운영 환경에서는 어떤 새로운 것을 만나게 되는가?"입니다.

- **행(row) 단위로 무작위 분할하는 것은 흔히 저지르는 실수**입니다. 예를 들어 사용자별 거래 로그를 거래 건별로 무작위 분할하면, 같은 사용자의 데이터가 학습과 테스트 양쪽에 다 들어가게 됩니다. 그런데 배포 후 실제로 만나는 상황은 대개 "한 번도 본 적 없는 새로운 사용자"이므로, 이렇게 분할하면 신규 사용자에 대한 실제 성능보다 낙관적으로 평가됩니다.
- **올바른 단위는 사용자(그룹) 단위 분할**입니다. 일부 사용자 전체를 학습에, 나머지 사용자 전체를 테스트에 배정해, 테스트에 포함된 사용자는 학습에서 단 한 건도 등장하지 않도록 합니다.
- **배포 후 만나는 새로움이 미래 시점의 데이터라면(대부분의 실무 상황이 그렇습니다), 시간순 분할**이 맞습니다. 과거 데이터를 학습에, 미래 데이터를 테스트에 배정해야 하며, 무작위로 섞어서 분할하면 미래 데이터가 학습에 섞여 들어가 미래 정보를 미리 학습하는 문제가 생깁니다.
- 신약 효과를 새로운 환자에게 적용할 모델이라면 환자 단위로, 특정 병원에서 학습해 다른 병원에 배포할 모델이라면 병원 단위로 분할해야 합니다.

정리하면, 완전히 새로운 사용자·고객·환자·기기를 만나는 경우는 그룹 단위 분할이, 미래 시점의 데이터를 만나는 경우는 시간 단위 분할이, 새로운 지역·매장·기관을 만나는 경우는 해당 단위의 그룹 분할이, 정말로 독립적인 개별 관측치를 만나는 경우는 단순 무작위 분할도 무방합니다. "테스트 데이터를 어떤 단위로 나눌지"는 통계적 선택이 아니라 "배포 후 모델이 실제로 마주칠 새로움이 무엇인가"에 대한 답이어야 하며, 이 매칭이 틀리면 테스트 성능이 아무리 좋아도 실제 운영에서는 재현되지 않습니다.

## 10. 교차검증 분할 방식 4종 비교

모두 데이터를 여러 개의 조각(fold)으로 나눠서 번갈아가며 학습/검증으로 쓰는 k-fold 교차검증의 변형입니다.

**기본형(KFold)**: 데이터를 순서대로(또는 무작위로 섞은 뒤) 여러 등분으로 나눠, 매 라운드마다 한 조각을 검증으로, 나머지를 학습으로 사용합니다. 클래스 비율이나 그룹을 전혀 고려하지 않으므로, 불균형 데이터라면 어떤 조각에는 소수 클래스가 거의 없을 수 있고, 같은 사용자의 데이터가 학습·검증에 섞여 들어갈 수 있는 leakage 위험이 있습니다.

**클래스 비율 유지형(StratifiedKFold)**: 각 조각을 나눌 때 클래스 비율이 원본 데이터와 동일하게 유지되도록 층화해서 분할합니다. 불균형 데이터에서는 사실상 필수적인데, 그렇지 않으면 특정 조각에 소수 클래스가 거의 안 들어가 그 조각의 평가가 불안정하거나 왜곡될 수 있기 때문입니다.

**그룹 단위 분리형(GroupKFold)**: 같은 그룹(예: 같은 사용자, 같은 환자)의 데이터가 학습과 검증에 절대 동시에 들어가지 않도록 그룹 단위로 조각을 나눕니다. "배포 후 새로운 사용자를 만난다"는 상황을 재현하는 방식입니다. 클래스 비율은 신경 쓰지 않고 오직 그룹이 겹치지 않는 것만 보장하므로, 그룹별 클래스 비율이 원래 들쭉날쭉하다면 조각을 나누는 과정에서 어떤 조각은 양성 비율이 확 낮아지거나 높아질 수 있다는 한계가 있습니다.

**그룹+클래스 결합형(StratifiedGroupKFold)**: 그룹은 겹치지 않게 분리하면서 동시에 각 조각의 클래스 비율도 최대한 원본과 비슷하게 유지하려고 시도하는 방식으로, 그룹 단위 분리와 클래스 균형을 동시에 만족시키려는 절충안입니다. 완벽하게 둘 다 만족시키긴 어렵기 때문에 최대한 비슷하게 맞추는 근사적인 방법을 씁니다. 사용자 단위로 그룹핑해야 하고 동시에 클래스 비율이 매우 불균형한 경우(예: 사기 탐지)에 가장 이상적입니다.

## 11. TimeSeriesSplit

시계열 데이터는 무작위 셔플 기반의 k-fold류 분할을 쓰면 안 됩니다. 미래 데이터가 학습에 섞여 들어가 모델이 미래 정보를 미리 보고 학습하는 시간 유출이 발생하기 때문입니다. TimeSeriesSplit은 항상 과거로 학습하고 미래로 검증하도록 설계된 분할 방식입니다.

데이터를 시간 순서대로 여러 등분한 뒤, 매 라운드마다 학습 구간이 점점 확장되면서 그 바로 다음 구간을 검증으로 씁니다. 즉 학습 구간은 항상 검증 구간보다 과거 시점이고, 라운드가 진행될수록 학습 데이터 양이 누적되며 늘어나, 실제 운영에서 시간이 지나며 데이터가 쌓이는 상황과 동일한 구조를 만듭니다.

주요 설정으로는 몇 라운드로 나눌지, 학습 구간이 무한정 커지지 않도록 최대 크기를 제한할지(오래된 데이터가 최신 패턴과 안 맞을 때 유용한 방식), 각 검증 구간의 크기를 얼마로 고정할지, 그리고 학습 구간의 끝과 검증 구간의 시작 사이에 공백을 둘지가 있습니다. 이 공백은 예측 시점과 실제 라벨이 확정되는 시점 사이에 지연이 있는 경우(예: "30일 후 이탈 여부"라는 라벨은 30일이 지나야 확정됨) 정보 유출을 막기 위해 사용합니다.

학습 구간을 계속 누적해서 키우는 방식(전체 데이터를 최대한 다 활용)과, 항상 일정 크기의 최근 구간만 학습에 사용하는 방식(오래된 패턴이 최신 트렌드와 다를 때 더 현실적) 중에서 선택할 수 있습니다.

시계열 데이터에서 검증 구간을 딱 한 구간만 떼어 평가하면 그 시기(계절성, 이벤트 등)의 특성에 운 좋게 또는 나쁘게 걸릴 수 있어 평가가 불안정한데, 여러 시점에서 반복 검증함으로써 모델이 다양한 시간대에 걸쳐 일관되게 잘 작동하는지 확인할 수 있습니다.

주의할 점으로는, 최종 테스트 구간(봉인 구간)은 별도로 가장 마지막 시점을 떼어놓고 그 이전 구간 안에서만 TimeSeriesSplit을 하이퍼파라미터 튜닝용 검증으로 사용해야 한다는 것, 전처리 통계량도 각 조각의 학습 구간 안에서만 계산해야 한다는 것, 그룹(예: 여러 매장의 시계열)과 시간이 동시에 존재하는 데이터라면 기본 TimeSeriesSplit만으로는 부족해 그룹별로 따로 시간 분할을 적용하거나 커스텀 로직이 필요할 수 있다는 것이 있습니다.

## 12. 데이터 유출(Leakage)의 다섯 가지 유형

지금까지 설명한 봉인 테스트, 분할 방식, SMOTE 관련 주의사항들은 사실 모두 데이터 유출이라는 하나의 큰 개념의 서로 다른 측면입니다.

**분할 누수(Split Leakage)**: 어떤 단위로 학습·테스트를 나눠야 하는지를 잘못 정해서, 같은 정보가 양쪽에 동시에 들어가는 경우입니다. 같은 사용자의 거래가 학습·테스트에 흩어져 들어가거나, 미래 데이터가 학습에 섞여 들어가는 경우가 해당합니다. 배포 후 마주칠 새로움의 단위에 맞춰 그룹 분할이나 시간 분할을 사용해 해결합니다.

**전처리 누수(Preprocessing Leakage)**: 정규화, 결측치 대체, 특성 선택 같은 전처리의 통계량을 학습·테스트 분할 전에 전체 데이터로 계산해서, 테스트 데이터의 정보가 학습 과정에 스며드는 경우입니다. 전처리 파라미터는 학습 데이터로만 계산(fit)하고, 테스트 데이터에는 그 파라미터를 적용(transform)만 해야 합니다. 교차검증을 쓸 때도 각 조각의 학습 구간 안에서만 계산해야 합니다.

**Target·미래 누수(Target/Future Leakage)**: 예측 시점에는 아직 알 수 없어야 할 정보(미래 정보 또는 예측 대상과 인과적으로 얽힌 정보)가 입력 특성으로 들어가는 경우입니다. 가장 치명적이고 발견하기 어려운 누수 유형입니다. 예를 들어 "환자 퇴원 여부"를 예측하는데 "퇴원 후 처방된 약" 정보가 특성에 포함되어 있다면 사실상 정답이 특성에 숨어 있는 것이고, 라벨이 확정되는 시점 이전 특성에 그 이후 발생한 이벤트 정보가 섞여 들어가는 경우, 집계 특성(예: 고객의 평균 구매액)을 만들 때 미래 시점의 구매 데이터까지 포함해 계산하는 경우도 이에 해당합니다. 해결책은 "이 특성이 실제 예측 시점에 정말로 확보 가능한 정보인가"를 특성 하나하나 검증하는 것입니다.

**리샘플링 누수(Resampling Leakage)**: 오버샘플링·언더샘플링을 학습·테스트 분할 전(또는 교차검증의 조각 분할 전)에 전체 데이터에 적용하는 경우입니다. SMOTE가 테스트 샘플을 참고해 만든 합성 데이터가 학습에 들어갈 수 있고, 테스트 안에도 인위적으로 생성된 샘플이 섞여 평가 자체가 왜곡됩니다. 테스트 데이터는 실제 운영에서 만나는 원본 분포(불균형)를 그대로 반영해야 하므로 리샘플링해서는 안 되며, 리샘플링은 반드시 학습 데이터에만 적용해야 합니다.

**선택 누수(Selection Leakage)**: 모델·하이퍼파라미터·특성을 "선택"하는 과정에서 테스트 성능을 참고하는 경우입니다. 여러 모델을 학습시킨 뒤 테스트 점수를 보고 그중 제일 좋은 것을 최종 채택하면 테스트가 사실상 모델 선택 기준(검증)으로 쓰인 것이고, 특성 선택을 전체 데이터 기준으로 하고 나서 분할하는 것도 일종의 선택 누수입니다. 모델 선택·하이퍼파라미터 튜닝·특성 선택은 전부 검증 데이터(또는 교차검증)로만 하고, 테스트 데이터는 정말 마지막에 확정된 파이프라인 전체를 딱 한 번 통과시켜 성능만 확인해야 합니다.

**올바른 파이프라인 순서**를 정리하면, 전체 데이터를 배포 후 만날 단위에 맞는 방식으로 분할해 학습·테스트를 봉인한 뒤, 학습 데이터 안에서 전처리 통계량을 계산하고(테스트에는 적용만), 리샘플링도 학습에만 적용하며, 특성 선택과 하이퍼파라미터 튜닝은 교차검증·검증 데이터로만 수행하고, 마지막으로 확정된 모델을 봉인된 테스트에 딱 한 번 적용해 최종 성능을 확인합니다.

다섯 유형 모두 본질은 하나입니다. "모델이 실제 운영에서는 절대 접근할 수 없는 정보를, 개발 과정 어딘가에서 몰래 참고했는가?"라는 질문을 파이프라인의 매 단계(분할, 전처리, 특성, 리샘플링, 모델 선택)마다 던져보는 것이 누수를 막는 가장 확실한 방법입니다.

## 13. scikit-learn Pipeline과 누수 방지

앞서 정리한 다섯 가지 누수 중 상당수는 개발자가 매번 "전처리는 학습 데이터에만 적용해야지"라고 스스로 기억해야 하는 수동 규칙이었습니다. Pipeline은 이걸 사람이 기억하지 않아도 구조적으로 강제해주는 도구입니다.

**Pipeline이란**: 여러 변환 단계와 마지막 모델을 하나의 객체로 묶어서, 학습을 호출하면 내부적으로 각 단계를 순서대로 실행해주는 sklearn 도구입니다.

```python
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression

pipe = Pipeline([
    ('scaler', StandardScaler()),
    ('clf', LogisticRegression())
])

pipe.fit(X_train, y_train)      # scaler.fit_transform(X_train) → clf.fit(...)
pipe.predict(X_test)            # scaler.transform(X_test) → clf.predict(...)  ← fit 아님, transform만!
```

핵심은 학습을 호출하면 내부의 모든 변환 단계가 오직 그 호출에 넘긴 데이터에만 맞춰지고(fit), 이후 예측이나 변환을 호출할 때는 그 맞춰진 규칙을 적용만(transform) 할 뿐 다시 맞춰지지 않는다는 것입니다.

**Pipeline이 구조적으로 막아주는 누수**

- **전처리 누수**: Pipeline을 교차검증에 통째로 넣으면, 각 조각마다 전처리 단계가 그 조각의 학습 부분에만 맞춰지고 검증 부분은 적용만 됩니다. Pipeline 없이 수동으로 하면 흔히 "전체 데이터에 전처리를 먼저 맞추고 교차검증을 시작"하는 실수를 저지르기 쉬운데, Pipeline은 이를 원천적으로 막아줍니다.
- **리샘플링 누수**: imblearn 라이브러리가 제공하는 SMOTE 대응 Pipeline을 쓰면, SMOTE도 매 조각의 학습 부분에만 적용되고 검증·테스트에는 적용되지 않습니다.

```python
from imblearn.pipeline import Pipeline as ImbPipeline
from imblearn.over_sampling import SMOTE

pipe = ImbPipeline([
    ('smote', SMOTE()),
    ('scaler', StandardScaler()),
    ('clf', LogisticRegression())
])
```

- **선택 누수(부분적으로)**: 하이퍼파라미터 탐색 도구에 Pipeline을 통째로 넣으면, 탐색 중인 각 후보 조합이 내부 교차검증의 학습 조각으로만 학습되고 검증 조각으로 평가됩니다. 최종적으로 봉인된 테스트 데이터에는 손도 안 대게 코드를 짤 수 있어, 튜닝 중에 실수로 테스트를 참고하는 실수를 줄여줍니다.

**Pipeline이 자동으로 못 잡는 누수**: Pipeline은 "학습이 학습 데이터에만 적용되는가"라는 기계적인 순서 문제만 해결해줄 뿐, 그 이상의 논리적·의미적 문제는 전혀 못 잡습니다.

- **Target·미래 누수**: 특성 자체에 이미 미래 정보나 정답 정보가 숨어 들어가 있으면, Pipeline이 아무리 정직하게 fit·transform을 나눠도 소용이 없습니다. 이는 도메인 지식으로 특성 하나하나를 검토해야만 발견할 수 있습니다.
- **분할 누수(단위 선택 오류)**: Pipeline은 교차검증의 각 조각이 어떻게 나뉘는지는 관여하지 않고, 분할 방식이 넘겨준 조각을 그대로 신뢰합니다. 잘못된 분할 방식을 골라 같은 사용자가 학습·검증에 섞여도 Pipeline 입장에서는 정상적인 두 개의 다른 데이터셋으로만 보입니다. 분할 방식 선택은 사람이 "배포 후 무엇을 새로 만나는가"를 판단해서 골라야 하는 영역입니다.
- **외부에서 만든 특성의 누수**: 별도의 데이터베이스 조인이나 배치 작업 등 Pipeline 바깥에서 미리 만들어진 특성 테이블에 이미 누수가 있다면, Pipeline이 그 데이터를 받은 시점엔 이미 늦습니다.
- **라벨 자체의 정의 오류**: 예측 대상(y)을 정의하는 로직 자체가 미래 시점 정보를 써서 만들어졌다면, 이는 Pipeline이 다루는 입력 변환과는 완전히 별개의 문제라 감지할 수 없습니다.

정리하면, Pipeline은 전처리 누수·리샘플링 누수·부분적인 선택 누수는 구조적으로 막아주지만, 분할 누수·target/미래 누수·외부 특성 테이블의 누수는 여전히 사람이 직접 판단하고 검증해야 합니다. Pipeline은 "fit은 학습 데이터에만, transform은 항상"이라는 기계적 규율을 강제해서 절차적 누수를 없애주지만, "이 특성이나 라벨이 애초에 의미상 미래 정보를 담고 있는가"라는 질문에는 답해주지 않습니다.
